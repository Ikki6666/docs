### 快速修复：提交 bug 修复

对于简单的 bug 修复，你可以立刻开始：

<Steps>
    <Step title="复现问题">
        甚至在克隆仓库之前，也请先确保你能够稳定复现该 bug。这有助于确认问题存在，并为修复提供起点。维护者和其他贡献者应当能够仅根据你的描述复现问题，而不需要额外的环境设置或修改。
    </Step>

    <Step title="Fork 仓库">

        将 [LangChain](https://github.com/langchain-ai/langchainjs)、[LangGraph](https://github.com/langchain-ai/langgraphjs) 或 [Deep Agents](https://github.com/langchain-ai/deepagentsjs) 仓库 fork 到你的 <Tooltip tip="如果你 fork 到组织账号，维护者将无法直接编辑，这可能会显著延迟接收流程">个人 GitHub 账号</Tooltip>

    </Step>

    <Step title="克隆并设置环境">

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 例如，以 LangChain 为例：
        git clone https://github.com/parrot123/langchainjs.git

        # 对于 LangGraph：
        git clone https://github.com/parrot123/langgraphjs.git
        ```

        ```bash
        # 在仓库内安装依赖
        pnpm install
        # 为所有包创建构建，以解析 workspace 依赖
        pnpm build
        ```

    </Step>

    <Step title="创建分支">
        为你的修复创建一个新分支。这有助于让改动保持有序，也能让之后提交 pull request 更方便。

        ```bash
        git checkout -b your-username/short-bugfix-name
        ```
    </Step>

    <Step title="编写失败测试">
        添加在没有修复时会失败的[单元测试](#test-writing-guidelines)。这样可以验证 bug 确实被修复，并防止回归
    </Step>

    <Step title="进行修改">
        在遵循我们的[代码质量标准](#code-quality-standards)的前提下修复这个 bug。只做解决问题所需的**最小改动**。我们强烈建议你在开始编码前先在 issue 中评论。例如：

        > *"I'd like to work on this. My intended approach would be to [...brief description...]. Does this align with maintainer expectations?"*

        一条 30 秒写完的评论，往往可以避免因为初始思路错误而浪费时间。
    </Step>

    <Step title="运行构建">
        运行构建命令，确保该包仍然可以正常构建
        ```bash
        pnpm build
        # 或构建某个特定的 workspace 包
        pnpm --filter @langchain/core build
        ```
    </Step>


    <Step title="验证修复">
        确保测试通过，且没有引入回归。在提交 PR 之前，请确认所有测试都能在本地通过


        ```bash
        pnpm lint
        pnpm test

        # 对于涉及集成的 bug 修复，还请运行：
        pnpm test:int

        # 或在某个特定的 workspace 包中运行测试
        cd libs/langchain-core
        pnpm test
        pnpm lint

        # 或在仓库根目录针对特定包运行测试
        pnpm --filter @langchain/core test
        pnpm --filter @langchain/core lint
        ```

    </Step>

    <Step title="记录变更">
        如果行为发生变化，请更新 docstring 和/或行内注释
    </Step>

    <Step title="提交 pull request">
        按照提供的 PR 模板填写。如果适用，请使用一个[closing keyword](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)（例如 `Fixes #ISSUE_NUMBER`）来引用你修复的 issue，这样在 PR 合并后 issue 会自动关闭。
    </Step>
</Steps>

## 贡献指南

在你开始为 LangChain 项目做贡献之前，先花一点时间想清楚你为什么要这样做。如果你唯一的目标只是想在简历上加一条 "first contribution"（或者只是想快速完成一次贡献），那你可能更适合去参加 boot camp 或在线教程。

为开源项目做贡献需要投入时间和精力，但它也能帮助你成为更好的开发者，并学到新技能。不过，你也需要知道，这往往会比跟着培训课程学习更难、更慢。尽管如此，如果你愿意花时间把事情做好，那么参与开源是很值得的。

### 向后兼容

<Warning>
    除了关键安全修复之外，不允许对公开 API 引入破坏性变更。

    详情请参阅我们的[版本策略](/oss/javascript/versioning)。
</Warning>

请通过以下方式保持兼容性：

<AccordionGroup>
    <Accordion title="稳定接口">
        **始终保留**：

        - 函数签名和参数名
        - 类接口和方法名
        - 返回值结构和类型
        - 公开 API 的导入路径
    </Accordion>

    <Accordion title="安全变更">
        **可接受的修改**：


        - 添加新的可选参数或类型参数

        - 向类中添加新方法
        - 在不改变行为的前提下提升性能
        - 添加新的模块或函数
    </Accordion>

    <Accordion title="修改前请确认">
        - **这会破坏现有用户代码吗？**
        - 检查你的目标是否是公开接口

        - 测试中是否已有既有用法模式？
    </Accordion>
</AccordionGroup>

### 新功能

我们希望对新功能保持较高门槛。一般来说，如果没有现有 issue 证明确实存在迫切需求，我们不会接受外部贡献者新增核心抽象。这同样适用于基础设施和依赖项的变更。

通常，新功能贡献需要满足以下要求：

<Steps>
    <Step title="设计讨论">
        创建一个 issue，并说明：

        - 你要解决的问题
        - 拟议的 API 设计
        - 预期的使用模式
    </Step>

    <Step title="实现">
        - 遵循现有代码模式
        - 包含完整的测试和文档
        - 考虑安全影响
    </Step>

    <Step title="集成层面的考虑">
        - 它会如何与现有功能交互？
        - 是否会带来性能影响？
        - 是否会引入新的依赖？

        我们会拒绝那些可能导致安全漏洞或相关报告的功能。
    </Step>
</Steps>

### 安全指南

<Warning>
    安全至关重要。绝不要引入漏洞或不安全的模式。
</Warning>

安全检查清单：

<AccordionGroup>
    <Accordion title="输入校验">
        - 对所有用户输入进行校验和清洗
        - 在模板和查询中正确转义数据

        - 绝不要使用 `eval()`，这会导致任意代码执行漏洞

    </Accordion>

    <Accordion title="错误处理">
        - 使用具体的异常类型
        - 不要在错误消息中暴露敏感信息
        - 实现正确的资源清理
    </Accordion>

    <Accordion title="依赖">
        - 避免添加硬依赖
        - 尽量减少可选依赖
        - 审查第三方包的安全问题
    </Accordion>
</AccordionGroup>

### 运行测试

<Info>
    目录路径相对于你正在处理的包。
</Info>

在可能的情况下，我们更倾向于单元测试而不是集成测试。单元测试会在每个 pull request 上运行，因此它们应当快速且可靠。集成测试按计划运行，且需要更多设置，因此应仅用于确认与外部服务的接口点。

#### 单元测试


**位置**：`src/tests/FILENAME_BEING_TESTED.test.ts`


单元测试覆盖不需要调用外部 API 的模块化逻辑。如果你添加了新逻辑，就应当添加单元测试。在单元测试中，请检查前处理/后处理，并 mock 外部依赖。

**要求**：
- 不允许发起网络调用
- 测试所有代码路径，包括边界情况
- 对外部依赖使用 mock

运行单元测试：


```bash
# Run the entire test suite
pnpm test

# Or run a specific test file
pnpm test src/tests/FILENAME_BEING_TESTED.test.ts

# Or run a specific test function
pnpm test -t "the test that should be run"
```


#### 集成测试


**位置**：`src/tests/FILENAME_BEING_TESTED.int.test.ts`


集成测试覆盖需要调用外部 API 的逻辑（通常是与其他服务的集成）。

集成测试需要访问外部服务/provider API（可能会产生费用），因此默认不会运行。

并非每次代码变更都需要集成测试，但请记住，我们会在审查过程中单独要求/运行集成测试。

**要求**：
- 测试与外部服务的真实集成
- 使用环境变量存放 API key
- 在凭证不可用时优雅跳过

运行集成测试：

```bash
pnpm test:int
```


### 代码质量标准

贡献必须满足以下质量要求：

<Tabs>
    <Tab title="类型标注">

        **要求**：为所有函数提供完整的类型

        ```typescript
        function processDocuments(
            docs: Document[],
            processor: DocumentProcessor,
            batchSize: number = 100
        ): ProcessingResult {
            // ...
        }
        ```

    </Tab>

    <Tab title="文档">

        **要求**：所有导出的函数和接口都要有 [JSDoc](https://jsdoc.app/about-getting-started)

        ```typescript
        /**
         * Document processing instance.
         */
        interface FooDocumentProcessor {
            /**
             * Process documents in batches.
             *
             * @param docs - List of documents to process.
             * @returns Processing results with success/failure counts.
             */
            process(docs: Document[]): ProcessingResult;
        }

        /**
         * Process documents in batches.
         *
         * @param docs - List of documents to process.
         * @param processor - Document processing instance.
         * @param batchSize - Number of documents per batch.
         * @returns Processing results with success/failure counts.
         */
        export function processDocuments(
            docs: Document[],
            processor: DocumentProcessor,
            batchSize: number = 100
        ): ProcessingResult {
            // ...
        }
        ```

    </Tab>

    <Tab title="代码风格">

        **自动化**：格式化和 lint：

        ```bash
        pnpm lint    # Check style and types
        pnpm format  # Apply formatting
        ```


        **标准**：
        - 使用描述性的变量名
        - 拆分复杂函数（以少于 20 行为目标）
        - 遵循代码库中的现有模式
    </Tab>
</Tabs>

### 测试编写指南

为了编写有效的测试，有一些值得遵循的良好实践：


- 将测试封装在一个描述所测组件的 `describe` 块中
- 用自然语言描述测试名称
- 断言要详尽
- 仅对大小合理的数据对象使用 snapshot


<Tabs>
    <Tab title="单元测试">

        ```typescript
        describe("DocumentProcessor", () => {
            it("Should handle empty document list", () => {
                const processor = new DocumentProcessor();
                const result = processor.process([]);

                expect(result.success).toBe(true);
                expect(result.processedCount).toBe(0);
                expect(result.errors).toHaveLength(0);
            });
        });
        ```

    </Tab>

    <Tab title="集成测试">

        ```typescript
        describe("ChatOpenAI", () => {
            it("Should test with real API", () => {
                const chat = new ChatOpenAI();
                const response = chat.invoke("Hello");
            });
        });
        ```

    </Tab>

    <Tab title="使用 mock">

        ```typescript
        describe("APIService", () => {
            it("Should call with retry", () => {
                const mockClient = new MockClient();
                const service = new APIService(client: mockClient);
                const result = service.callWithRetry();
            });
        });
        ```

    </Tab>
</Tabs>

### 提交你的 PR

当你的测试通过且代码符合质量标准后：

1. 推送你的分支并创建 pull request
2. 遵循提供的 PR 模板
3. 使用 [closing keyword](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)（例如 `Fixes #123`）引用相关 issue
4. 等待 CI 检查完成

<Note>
    如果你的 PR 包含 AI 生成内容，必须遵守我们的 [LLM 可接受用途](/oss/javascript/contributing/overview#acceptable-uses-of-llms)政策。看起来像低质量、AI 生成垃圾内容的 PR 将被直接关闭，且不予说明。
</Note>

<Warning>
    请及时处理 CI 失败。如果 PR 未在合理时间内通过 CI，维护者可能会关闭它。
</Warning>
