title: 集成测试
description: 通过组织测试、管理密钥、处理不稳定性和控制成本，使用真实 LLM API 测试智能体。
---

集成测试会验证你的智能体是否能和模型 API 以及外部服务正确协作。不同于使用 fake 和 mock 的 [unit tests](/oss/javascript/langchain/test/unit-testing)，集成测试会发起真实网络调用，以确认各组件能协同工作、凭据有效，并且延迟可接受。

由于 LLM 响应并非确定性的，集成测试需要和传统软件测试不同的策略。本指南介绍如何组织、编写和运行智能体的集成测试。关于贡献 LangChain 本身时的一般测试基础设施，请参见 [Contributing to code](/oss/javascript/contributing/code#running-tests)。

## 分离单元测试和集成测试

集成测试更慢，而且需要 API 凭据，所以要把它们和单元测试分开。这样你就能在每次改动时运行快速的单元测试，而把集成测试留给 CI 或预发布检查。



使用文件命名约定把集成测试分开。把集成测试文件命名为 `*.int.test.ts`，并配置 vitest 在默认运行中排除它们：

```ts vitest.config.ts
import { configDefaults, defineConfig } from "vitest/config";

export default defineConfig((env) => {
  if (env.mode === "int") {
    return {
      test: {
        testTimeout: 100_000,
        include: ["**/*.int.test.ts"],
        setupFiles: ["dotenv/config"],
      },
    };
  }

  return {
    test: {
      testTimeout: 30_000,
      exclude: ["**/*.int.test.ts", ...configDefaults.exclude],
    },
  };
});
```

在 `package.json` 中添加脚本：

```json
{
  "scripts": {
    "test": "vitest",
    "test:integration": "vitest --mode int"
  }
}
```

显式运行集成测试：

```bash
npm run test:integration
```


## 管理 API 密钥

集成测试需要真实的 API 凭据。请从环境变量加载它们，避免把密钥放进源码控制。



把 `dotenv/config` 加到 vitest setup file，这样环境变量会自动从 `.env` 加载：

```ts vitest.config.ts
export default defineConfig({
  test: {
    setupFiles: ["dotenv/config"],
  },
});
```

```bash .env
OPENAI_API_KEY=sk-...
```

在缺少密钥时跳过测试：

```ts
import { test } from "vitest";

test.skipIf(!process.env.OPENAI_API_KEY)(
  "agent responds with tool call",
  async () => {
    // ...
  }
);
```


<Warning>
    把 `.env` 加进 `.gitignore`，避免提交凭据。在 CI 中，请通过你所用平台的密钥管理功能注入 secrets（例如 GitHub Actions secrets）。
</Warning>

## 断言结构，而不是内容

LLM 响应每次运行都可能不同。与其断言精确输出字符串，不如验证响应的结构属性：消息类型、工具调用名称、参数形状和消息数量。



```ts
test("agent calls weather tool", async () => {
  const agent = createAgent({ model: "claude-sonnet-4-6", tools: [getWeather] });
  const result = await agent.invoke({
    messages: [new HumanMessage("What's the weather in SF?")]
  });

  const aiMsg = result.messages.find(
    (m) => AIMessage.isInstance(m) && m.tool_calls?.length
  );
  expect(aiMsg).toContainToolCall({ name: "get_weather" });
  expect(result.messages.at(-1)).toBeAIMessage();
});
```

这个示例使用了 [custom test matchers](#use-custom-test-matchers)。关于设置和完整 matcher 参考，请看下面的章节。


<Tip>
    如果你需要更严格的轨迹断言，请使用 [AgentEvals](/oss/javascript/langchain/test/evals) evaluators，它们支持像 `unordered` 和 `superset` 这样的模糊匹配模式。
</Tip>

## 使用自定义测试 matcher
`langchain` 提供了 [custom vitest matchers](https://vitest.dev/guide/extending-matchers.html)，让结构化断言更易读，并在失败时给出清晰的错误信息。只需要在一个 setup 文件里注册一次，它们就会在每次 `expect()` 调用中可用。

### 设置

添加一个 vitest setup 文件，用 LangChain matchers 扩展 `expect`：

```ts vitest.setup.ts
import { langchainMatchers } from "@langchain/core/testing";

expect.extend(langchainMatchers);
```

在 vitest 配置里引用它：

```ts vitest.config.ts
export default defineConfig({
  test: {
    setupFiles: ["vitest.setup.ts"],
  },
});
```

TypeScript 类型会自动包含，因此不需要额外配置自动补全。

### 检查消息类型

每个消息类都有对应的 matcher：`toBeHumanMessage()`、`toBeAIMessage()`、`toBeSystemMessage()` 和 `toBeToolMessage()`。不传参数时只检查类型；传入字符串时也可以匹配内容：

```ts
const response = await agent.invoke({
  messages: [new HumanMessage("What's the weather?")]
});
const lastMessage = response.messages.at(-1);

expect(lastMessage).toBeAIMessage();
expect(lastMessage).toBeAIMessage("It's 72°F and sunny.");
```

传入对象可以匹配特定字段：

```ts
expect(lastMessage).toBeAIMessage({ name: "weather-bot" });
expect(toolMsg).toBeToolMessage({ tool_call_id: "call_1" });
```

### 断言工具调用

三个 matcher 用于对 [`AIMessage`](https://reference.langchain.com/javascript/langchain-core/messages/AIMessage) 的工具调用做断言：

js
```ts
const response = await agent.invoke({
  messages: [new HumanMessage("Weather in SF and NYC?")]
});
const aiMsg = response.messages.find(
  (m) => AIMessage.isInstance(m) && m.tool_calls?.length
);

// 检查是否包含特定工具调用（不要求顺序）
expect(aiMsg).toHaveToolCalls([
  { name: "get_weather", args: { city: "San Francisco" } },
  { name: "get_weather", args: { city: "New York" } },
]);

// 只检查数量
expect(aiMsg).toHaveToolCallCount(2);

// 检查是否至少包含一个匹配的 tool call（支持 .not）
expect(aiMsg).toContainToolCall({ name: "get_weather" });
expect(aiMsg).not.toContainToolCall({ name: "send_email" });
```

### 断言工具消息

`toHaveToolMessages()` 会接收完整的消息数组，并按顺序检查其中的 [`ToolMessage`](https://reference.langchain.com/javascript/langchain-core/messages/ToolMessage) 实例：

```ts
expect(response.messages).toHaveToolMessages([
  { content: "San Francisco 的天气是 72°F 且晴朗" },
  { content: "New York 的天气是 68°F 且多云" },
]);
```

### 断言中断和结构化响应

`toHaveBeenInterrupted()` 会检查 [LangGraph interrupt](/oss/javascript/langchain/human-in-the-loop) 结果中是否存在 `__interrupt__` 字段。你可以传入一个值来匹配中断 payload：

```ts
const result = await graph.invoke(input);

expect(result).toHaveBeenInterrupted();
expect(result).toHaveBeenInterrupted("confirm_action");
```

`toHaveStructuredResponse()` 会检查结果中是否存在 `structuredResponse` 字段。你可以传入对象来匹配特定字段：

```ts
expect(result).toHaveStructuredResponse();
expect(result).toHaveStructuredResponse({ name: "Alice", age: 30 });
```

### Matcher 参考

| Matcher | 说明 |
| --- | --- |
| `toBeHumanMessage(expected?)` | 检查值是否为 `HumanMessage`。可选地匹配内容（字符串）或字段（对象）。 |
| `toBeAIMessage(expected?)` | 检查值是否为 `AIMessage`。可选地匹配内容或字段。 |
| `toBeSystemMessage(expected?)` | 检查值是否为 `SystemMessage`。可选地匹配内容或字段。 |
| `toBeToolMessage(expected?)` | 检查值是否为 `ToolMessage`。可选地匹配内容或诸如 `tool_call_id` 之类的字段。 |
| `toHaveToolCalls(expected)` | 检查 `AIMessage` 是否恰好包含给定的 tool call（不要求顺序）。 |
| `toHaveToolCallCount(n)` | 检查 `AIMessage` 是否恰好包含 `n` 个 tool call。 |
| `toContainToolCall(expected)` | 检查 `AIMessage` 是否至少包含一个匹配的 tool call。支持 `.not`。 |
| `toHaveToolMessages(expected)` | 检查消息数组是否按顺序包含给定的 `ToolMessage`。 |
| `toHaveBeenInterrupted(value?)` | 检查结果是否具有 `__interrupt__`。可选地匹配中断值。 |
| `toHaveStructuredResponse(expected?)` | 检查结果是否具有 `structuredResponse`。可选地匹配特定字段。 |

:::

## 降低成本和延迟

调用 LLM API 的集成测试会产生真实成本。下面这些做法可以帮助你让测试套件更快、更省钱：

- **使用更小的模型**：比如 `gemini-3.1-flash-lite`，或其他只需要验证工具调用和响应结构的等价模型。
- **设置 `maxTokens`**：限制输出长度，避免生成又长又贵的完成结果。
- **缩小测试范围**：每个测试只验证一个行为。只要单轮测试就能说明问题，就不要写要串很多 LLM 调用的端到端场景。
- **选择性运行**：使用上面的测试分离方式，让集成测试只在 CI 或发布前运行，而不是每次保存文件都跑。



```ts
const agent = createAgent({
  model: "gemini-3.1-flash-lite",
  tools: [getWeather],
  modelArgs: { maxTokens: 256 },
});
```
