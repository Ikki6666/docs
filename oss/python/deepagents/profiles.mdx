**Harness 配置档案** 允许你为特定模型或 provider 自定义 Deep Agents harness。你可以调整 system prompt 和工具描述、排除工具或 middleware、添加 middleware，以及配置通用子 agent。每当你选择匹配的模型时，Deep Agents 都会应用这些设置，无需更改你的 agent 创建代码。

**Provider 配置档案** 为创建模型定义默认设置，例如 temperature 和 timeout。这些设置不影响 harness。大多数调用方都不需要 provider 配置档案。在封装需要共享默认值、凭据检查或运行时计算设置的集成时，它们很有用。




## Harness 配置档案

Deep Agents 提供了 **内置 harness 配置档案**，包含针对特定 provider 和模型的默认设置。

使用 `HarnessProfile` 定义 `create_deep_agent` 在构建 chat model 之后会应用的设置：

<ProfilesHarnessRegisterPy />




<ResponseField name="base_system_prompt" type="string">
    设置该配置档案的基础指令。对于主 agent，这些指令会跟在调用方的 system 指令之后；默认不添加基础指令。对于声明式子 agent，这会替换它们自己编写的 system prompt。
</ResponseField>

<ResponseField name="system_prompt_suffix" type="string">
    在调用方指令和配置档案的基础指令之后追加文本。该设置会同时应用于主 agent、声明式子 agent 和自动添加的通用子 agent。
</ResponseField>

<ResponseField name="tool_description_overrides" type="Mapping[str, str]">
    按工具名覆盖单个工具描述。
</ResponseField>

<ResponseField name="excluded_tools" type="frozenset[str]">
    从工具集中移除特定的 harness 级工具。按工具名（字符串）匹配，作为注入后的过滤器，因此可以移除用户提供的工具，也可以移除 harness middleware 添加的工具。有关完整示例，请参见[不使用默认文件系统工具运行](/oss/python/deepagents/overview#virtual-filesystem-access)。
</ResponseField>

<ResponseField name="excluded_middleware" type="frozenset[type[AgentMiddleware] | str]">
    从 [Deep Agents 栈](/oss/python/deepagents/customization#deep-agents-stack) 中剔除特定 middleware 类。可接受 middleware 类本身或字符串名称。
</ResponseField>

<ResponseField name="extra_middleware" type="Sequence[AgentMiddleware] | Callable[[], Sequence[AgentMiddleware]]">
    把 middleware 追加到该配置档案适用的每个堆栈中。有关内置顺序，请参见 [Deep Agents 栈](/oss/python/deepagents/customization#full-stack)。
</ResponseField>

<ResponseField name="general_purpose_subagent" type="GeneralPurposeSubagentProfile">
    禁用、重命名，或重新提示通用子 agent。当这个字段与 `base_system_prompt` 一起设置时，通用子 agent 专属的 prompt 会优先生效，见 [通用子 agent prompt](/oss/python/deepagents/customization#general-purpose-subagent-prompt)。
</ResponseField>




<Note>
    调用方提供的 `system_prompt=` 永远位于组装后 prompt 的最前面，而 `system_prompt_suffix` 永远位于最后面，不受所选模型影响。同样的覆盖规则也适用于子 agent：每个子 agent 都会基于自己的模型重新执行 profile 解析。有关自定义指令和子 agent prompt 行为，请参见 [System prompt](/oss/python/deepagents/customization#system-prompt)。
</Note>




<Warning>
    若要在没有 `task` 工具的情况下运行 agent，请参见[不使用 subagent 运行](/oss/python/deepagents/subagents#running-without-subagents)：把 `general_purpose_subagent=GeneralPurposeSubagentProfile(enabled=False)`，并且不要通过 `subagents=` 传入同步 subagent。只有当至少存在一个同步 subagent 时，`SubAgentMiddleware`（以及 `task` 工具）才会被挂载，因此这种配置会干净地将它移除。异步 subagent 不受影响。

    如果在 `excluded_middleware` 中列出 `FilesystemMiddleware`、`SubAgentMiddleware`，或内部权限 middleware，会抛出 `ValueError`，因为它们是 [Deep Agents 栈](/oss/python/deepagents/customization#deep-agents-stack) 中必需的脚手架。若只是想让模型看不到这些工具而不是移除 middleware，请改用 `excluded_tools`，见[不使用默认文件系统工具运行](/oss/python/deepagents/overview#virtual-filesystem-access)。
</Warning>

`excluded_middleware` 中的条目支持两种形式：

- middleware *class*（按精确类型匹配），或匹配 `AgentMiddleware.name` 的纯字符串。内置项和诸如 `"SummarizationMiddleware"` 的公开别名都可以使用字符串。
- `module:Class` 导入引用（例如 `"my_pkg.middleware:TelemetryMiddleware"`），用于在配置文件中精确定位某个 middleware 类。导入引用会延迟解析，所以只应在可信的本地配置中使用，因为加载时会导入 Python 代码。




在创建 agent 之前注册配置档案。传入模型字符串或你自己构建的模型对象；示例参见 [配置模型参数](/oss/python/deepagents/models#configure-model-parameters)。harness 配置档案在两种情况下都会生效。

只有当你传入字符串时，provider 配置档案才会提供构造设置。


<Accordion
    title="预配置模型实例的查找顺序"
>
    当你传入模型对象时，harness 会使用该对象报告的 provider 和 identifier 来查找它的配置档案。

    1. 精确匹配 `provider:identifier`
    2. 仅匹配 identifier（仅在 identifier 本身已经包含 `:` 时）
    3. 所报告 provider 的默认值；如果 provider 未知，则使用 identifier 前缀的默认值

    两个精确候选都优先于 provider 默认值。



</Accordion>


## 注册键

配置档案注册使用以下键：

- **provider 级**：仅 provider 名称，例如 `"openai"`，会应用到该 provider 的所有模型。
- **model 级**：完整的 `provider:model` 键，例如 `"openai:gpt-6-astra"`，只应用到该特定模型。

当 provider 级和 model 级 profile 同时存在时，它们会在解析时合并。未设置的 model 级字段会继承 provider 级 profile；显式设置的 model 级值会覆盖 provider 级值。

只有第一个冒号用于分隔 provider 和模型 identifier。对于假设的键 `my_provider:my-model:tag`，provider 是 `my_provider`，完整的模型 identifier 是 `my-model:tag`。其余冒号都属于模型 identifier 的一部分。




例如，为某个假设 provider 的模型排除一个工具，然后为一个模型自定义 prompt 后缀：

<ProfilesRegistrationPy />




使用 model 级注册的 agent 会排除 `execute`，并收到 100 词的后缀。`my_provider` 的其他模型会排除 `execute`，并收到 500 词的后缀。

在已有键上重新注册时，新 profile 会叠加到之前的 profile 上，而不是替换它。这也让你可以通过在内置 profile 的键下注册来自定义它。有关逐字段规则，请参见[合并语义](#merge-semantics)。

<Note>
    没有能匹配所有 provider 的通配键。若要在所有地方都应用同样的覆盖，例如无论选择哪个模型都移除 `TodoListMiddleware`，请在你使用的每个 provider 键下都注册该 profile。profile 的设计目标是对所选模型相关的调整。应在 `create_deep_agent` 调用位置完成那些与模型无关、应该无条件生效的全局调整。
</Note>




## 合并语义

| 字段 | 合并行为 |
| --- | --- |
| `base_system_prompt`, `system_prompt_suffix` | 若设置了新值，则新值生效；否则继承 |
| `tool_description_overrides` | 映射按键合并；共享键上新值生效 |
| `excluded_tools`, `excluded_middleware` | 集合并集 |
| `extra_middleware` | 按具体类型合并：新实例替换其位置上的旧实例，新类型追加到末尾 |
| `general_purpose_subagent` | 按字段合并（未设置字段继承） |
| `init_kwargs`（provider） | 按键合并字典；共享键上新值生效 |
| `pre_init`（provider） | 可调用对象串联：先运行已有的，再运行新的 |
| `init_kwargs_factory`（provider） | 工厂函数串联，其输出会在每次模型构建时合并 |

## 从配置文件加载 profile

对于基于 YAML/JSON 的工作流，请使用 `HarnessProfileConfig`。它映射的是 `HarnessProfile` 的可声明子集（prompt 文本、工具描述覆盖、排除工具和 middleware、通用子 agent 调整），并负责 `to_dict` / `from_dict`。运行时状态——middleware 实例、工厂函数，以及 class 形式的 `excluded_middleware` 条目——仍然保留在 `HarnessProfile` 中。

`register_harness_profile` 接受这两种类型，所以使用配置文件的调用方不需要手动转换：




<ProfilesConfigOpenaiYaml />




<ProfilesLoadConfigPy />

若要反向导出到另一种格式，可以在只使用可序列化功能时，用 `HarnessProfileConfig.from_harness_profile(...)` 把运行时 profile 导出回声明式形状：

- class 形式的 `excluded_middleware` 条目会序列化为公开别名（如果该类通过 `serialized_name: ClassVar[str]` 暴露了别名），或者序列化为 `module:Class` 导入引用。
- 非空的 `extra_middleware`，以及在 `__main__` 中或函数作用域内声明的 middleware 类，都无法被序列化——导出时会抛出 `ValueError`。
