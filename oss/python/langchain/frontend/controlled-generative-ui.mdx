## 概览

受控 generative UI 位于 [generative UI 范围](/oss/python/langchain/frontend/generative-ui-overview) 中由作者控制的一端。你编写组件，由智能体决定渲染哪一个以及向其中传入什么数据。智能体从不生成标记：它从你构建并测试过的一组固定界面中选择。

这种模式提供了所有 generative UI 方式中最高的可预测性。因为每个组件都来自你的代码库，你可以精确控制品牌、布局、无障碍性和行为，并且可以保证智能体呈现的任何内容都通过了你的审核。代价是工程成本：每项新能力都需要一个你预先编写的组件。你的组件库就是边界：智能体只能渲染你发布的内容。

## 何时使用这种方式

在高流量、品牌关键的界面上使用受控 generative UI，这些界面的输出集合是预先已知的，正确性比新颖性更重要：表单、确认流程，以及任何有严格品牌或无障碍性要求的界面。当你需要智能体组合出你没有预料到的布局，覆盖长尾的次要交互时，沿着这个范围向前一步，使用[声明式 generative UI](/oss/python/langchain/frontend/declarative-generative-ui)。

受控 generative UI 涵盖四种技术，从智能体选择整个界面开始，到前端响应智能体内部状态结束。

## 组件作为工具

你可以像暴露工具那样向智能体暴露 UI 组件。每个组件都有一个名称、一个描述和一组类型化的属性，智能体在响应中选择一个组件并提供其数据。前端将智能体的选择映射到你的真实实现。这让智能体的任务保持简单，即判断哪个预先批准的界面适合当前时刻，而你的代码掌管外观和行为的所有细节。

CopilotKit 将这种模式记录为 [components as tools](https://docs.copilotkit.ai/generative-ui/tool-based)。

## 工具调用渲染

当智能体调用工具时，调用会经历一个生命周期：待处理，然后完成或失败。工具调用渲染把每个阶段变成专门构建的 UI，例如搜索运行时的加载卡片、返回时的结果卡片，以及失败时的错误状态，而不是显示原始 JSON。这让智能体的动作清晰可读，让用户对正在发生的事情有信心。

参见 [Tool calling](/oss/python/langchain/frontend/tool-calling) 模式。

## 状态渲染

智能体在消息列表之外暴露持久的、类型化的状态：待办事项、流水线输出、引用、沙盒文件、指标和自定义业务对象。状态渲染把你的组件绑定到这些状态上，让 UI 成为智能体工作的实时视图，而不是一份记录。当智能体更新状态时，界面随之更新。

参见前端概览中的 [typed agent state](/oss/python/langchain/frontend/overview)。关于把单个类型化响应 payload 映射到自定义 UI，参见 [Structured output](/oss/python/langchain/frontend/structured-output)。

## 推理

具有扩展思考能力的模型会生成与其最终答案分开的推理内容。渲染推理内容可以向用户展示智能体如何得出结果，这有助于建立信任、辅助调试并支持审计。你可以控制推理内容出现的方式和时机，例如在与响应不同的可折叠块中。

参见 [Reasoning tokens](/oss/python/langchain/frontend/reasoning-tokens) 模式。
