人类在回路中（HITL）[中间件](/oss/python/langchain/middleware/built-in#human-in-the-loop) 让你可以为智能体工具调用加入人工审核。
当模型提出一个可能需要复核的动作时，例如写文件或执行 SQL，中间件可以暂停执行并等待决策。

它的做法是把每个工具调用拿去和可配置策略做比对。如果需要人工介入，中间件就会发出一个 [interrupt](https://reference.langchain.com/python/langgraph/types/interrupt)，从而中止执行。图状态会通过 LangGraph 的 [持久化层](/oss/python/langgraph/persistence) 保存，因此执行可以安全暂停，并在之后恢复。

人工决策随后决定下一步怎么做：动作可以原样批准（`approve`）、执行前修改（`edit`）、带反馈拒绝（`reject`），或者在 "ask user" 这类工具里直接回复（`respond`）。

## 中断决策类型

[中间件](/oss/python/langchain/middleware/built-in#human-in-the-loop) 定义了四种人类对中断的内置响应方式：

<HitlDecisionTypesTable />

每个工具可用的决策类型取决于你在 `interrupt_on` 中配置的策略。




当多个工具调用同时暂停时，每个动作都需要单独决策。

在默认的批量模式下，请按照动作在中断请求中出现的顺序提供决策。在[逐调用模式](#pause-once-per-tool-call)下，每个工具调用都有自己的中断，只需要一个决策。

当人类是在拒绝请求的动作时，请使用 `reject`。只有在人工是在充当工具本身时才使用 `respond`，例如回答一个 `ask_user` 提示。不要用 `respond` 去拒绝会产生副作用的工具，因为它的消息会被当作成功的工具结果。


<Tip>
在**编辑**工具参数时，请尽量保守地修改。对原始参数做大幅更改，可能会让模型重新评估方案，并且可能多次执行工具，或者采取意料之外的动作。
</Tip>

## 配置中断

要使用 HITL，请在创建智能体时，把 [中间件](/oss/python/langchain/middleware/built-in#human-in-the-loop) 添加到智能体的 `middleware` 列表中。

你需要用一个工具动作到决策类型的映射来配置它。只要某个工具调用匹配到映射中的动作，中间件就会中断执行。

这个示例使用默认的批量模式。若要每个工具调用暂停一次，请参见[设置中断模式](#set-the-interrupt-mode)。

```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware # [!code highlight]
from langgraph.checkpoint.memory import InMemorySaver # [!code highlight]


agent = create_agent(
    model="gpt-5.5",
    tools=[write_file, execute_sql, read_data],
    middleware=[
        HumanInTheLoopMiddleware( # [!code highlight]
            interrupt_on={
                "write_file": True,  # 允许所有决策（approve、edit、reject、respond）
                "execute_sql": {"allowed_decisions": ["approve", "reject"]},  # 不允许编辑
                "read_data": False, # 安全操作，不需要批准
            },
            # 中断消息前缀 - 会和工具名及参数一起拼成完整消息
            # 例如："Tool execution pending approval: execute_sql with query='DELETE FROM...'"
            # 单个工具可以通过在其中断配置里指定 "description" 来覆盖它
            description_prefix="Tool execution pending approval",
        ),
    ],
    # Human-in-the-loop 需要 checkpointing 来处理中断。
    # 在生产环境中，请使用持久化 checkpointer，例如 AsyncPostgresSaver 或 MongoDBSaver。
    checkpointer=InMemorySaver(),  # [!code highlight]
)
```





<Info>
    你必须配置一个 checkpointer，才能在中断之间持久化图状态。
    在生产环境中，请使用持久化 checkpointer，例如 [`AsyncPostgresSaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.postgres.aio.AsyncPostgresSaver) 或 [`MongoDBSaver`](https://pypi.org/project/langgraph-checkpoint-mongodb/)。测试或原型阶段可以使用 [`InMemorySaver`](https://reference.langchain.com/python/langgraph/checkpoints/#langgraph.checkpoint.memory.InMemorySaver)。



    调用智能体时，请传入包含 **thread ID** 的 `config`，用于把执行关联到某个会话线程。
    详情请参见 [LangGraph interrupts 文档](/oss/python/langgraph/interrupts)。
</Info>

<Accordion title="配置选项">

<ParamField body="interrupt_on" type="dict" required>
    工具名到批准配置的映射。值可以是 `True`（使用默认配置中断）、`False`（自动批准），或者一个 `InterruptOnConfig` 对象。
</ParamField>

<ParamField body="description_prefix" type="string" default="Tool execution requires approval">
    动作请求描述的前缀
</ParamField>

<ParamField body="interrupt_mode" type="string" default="batched">
    智能体暂停等待审查的方式。`"batched"` 在每个模型轮次发出一个中断，用一个有序列表应答。`"per_call"` 为每个受拦截的调用发出一个中断，以中断 ID 应答。`"per_call"` 需要 `langchain>=1.4.6`。请参见[设置中断模式](#set-the-interrupt-mode)。
</ParamField>

<ParamField body="edit_notice" type="string | None">
    添加在审查者用 `edit` 决策替换的调用的结果之前的文本，让模型知道该调用已发生更改。默认为一条说明，指出人工审查者替换了该调用。传入 `None` 则不添加任何内容。
</ParamField>

**`InterruptOnConfig` 选项：**

<ParamField body="allowed_decisions" type="list[string]">
    允许的决策列表：`'approve'`、`'edit'`、`'reject'` 或 `'respond'`
</ParamField>

<ParamField body="description" type="string | callable">
    用于自定义描述的静态字符串或可调用函数
</ParamField>

<ParamField body="when" type="callable">
    可选谓词，接收一个 [ToolCallRequest](https://reference.langchain.com/python/langgraph.prebuilt/tool_node/ToolCallRequest)，并返回 `True` 表示中断，返回 `False` 表示自动批准。可用它按调用参数来控制中断。需要 `langchain>=1.3.3`。
</ParamField>

## 条件中断

默认情况下，`interrupt_on` 中列出的每个工具调用都会暂停等待审查。若只想暂停部分调用，可以给某个工具的 `InterruptOnConfig` 加上 `when` 谓词。这个谓词会接收一个 `ToolCallRequest`，并返回 `True` 表示中断，`False` 表示自动批准，这样你就能按工具参数来控制。




<Note>
条件中断需要 `langchain>=1.3.3`。
</Note>

```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware, ToolCallRequest
from langgraph.checkpoint.memory import InMemorySaver


def writes_outside_workspace(request: ToolCallRequest) -> bool:
    """暂停写入工作区目录之外的路径。"""
    path = request.tool_call["args"].get("path", "")
    return not path.startswith("/workspace/")


def is_write_query(request: ToolCallRequest) -> bool:
    """暂停不是只读 SELECT 的 SQL。"""
    query = request.tool_call["args"].get("query", "")
    return not query.lstrip().upper().startswith("SELECT")


agent = create_agent(
    model="gpt-5.5",
    tools=[write_file, execute_sql, read_data],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "write_file": {
                    "allowed_decisions": ["approve", "edit", "reject"],
                    "when": writes_outside_workspace,
                },
                "execute_sql": {
                    "allowed_decisions": ["approve", "reject"],
                    "when": is_write_query,
                },
            },
        ),
    ],
    checkpointer=InMemorySaver(),
)
```

当 `when` 谓词返回 `False` 时，调用会直接运行而不中断。当它返回 `True`，或者你省略 `when` 时，调用就会像平常一样暂停。评估为 `False` 的调用永远不会暂停，因此审查者只会看到需要决策的动作。

智能体恢复时，谓词会再次运行，因此它必须对同一个调用返回相同的结果。如果它在恢复时返回 `False`，工具会直接运行，审查者的答案会被忽略，即使是 `reject` 也是如此。在批量模式下，如果结果只对部分调用发生了变化，中间件会抛出 `ValueError`。




## 设置中断模式

中间件以两种模式之一暂停，由 `interrupt_mode` 设置：

- **`"per_call"`**：每个需要审查的工具调用在开始时都会发出自己的中断。每个中断携带一个 [`response_schema`](/oss/python/langgraph/interrupts#define-an-interrupt-response-schema)，描述它接受的答案。你用一个决策来应答，并以中断 ID 作为键。
- **`"batched"`**（默认）：每个模型轮次发出一个中断，列出所有需要审查的调用。你按相同的顺序用一个决策列表来应答。

新智能体请使用逐调用模式。LangChain 计划在下一个主要版本中将其设为默认值。有关两种模式的并排对比以及逐调用模式解决的问题，请参见[人类在回路中概述](/oss/python/concepts/human-in-the-loop)。

### 按 ID 恢复每个调用

用一条决策应答每个中断，以中断 ID 作为键：

<HitlPerCallResumePy />

你也可以逐个应答中断。未应答的中断会保持待处理状态，一旦收到答案，其对应的工具就会运行。

<Warning>
如果一起发送的多个答案中有一个无效，其他答案对应的工具可能已经运行，而它们的中断仍显示为待处理。再次应答它们会让这些工具运行两次。一起发送前请先对照 `response_schema` 检查答案，或者逐个发送。
</Warning>

### 纠正无效答案

LangGraph 在保存答案前会对照中断的 `response_schema` 检查每个答案。无效答案会抛出 `ValidationError`，并且不会保存任何内容，因此你可以向同一个中断 ID 发送纠正后的答案。这里，编辑操作遗漏了 `content`：

<HitlPerCallInvalidPy />

每个错误都会指出未通过检查的字段，因此你可以把它展示给审查者。对于参数是原始 JSON Schema 而非 Pydantic 模型的工具，`response_schema` 会展示这些参数，但 LangGraph 不会对照它们检查编辑操作。

### 为逐调用审查排列中间件顺序

在逐调用模式下，审查发生在工具调用开始时，位于工具调用中间件链内：

- 把 `HumanInTheLoopMiddleware` 列在工具重试或错误处理中间件之前，例如 [ToolRetryMiddleware](https://reference.langchain.com/python/langchain/agents/middleware/tool_retry/ToolRetryMiddleware) 和 [ToolErrorMiddleware](https://reference.langchain.com/python/langchain/agents/middleware/tool_error/ToolErrorMiddleware)，以便它包裹它们。否则，重试的调用会再次询问审查者，无效答案会被重试，或者作为工具错误返回给模型。
- 当智能体恢复时，列在 `HumanInTheLoopMiddleware` 之前的中间件会重新运行到暂停点为止，因此它在调用自己的处理器之前不能有副作用。工具只会在收到答案后才运行。
- [`when` 谓词](#conditional-interrupts)在每次调用开始时运行，因此它收到的 [ToolCallRequest](https://reference.langchain.com/python/langgraph.prebuilt/tool_node/ToolCallRequest) 包含该工具。





## 响应中断

当你调用智能体时，它会一直运行到完成或者触发一个中断。只要某个工具调用匹配到你在 `interrupt_on` 中配置的策略，就会触发中断。使用 `version="v2"` 时，返回结果是一个带有 `interrupts` 属性的 `GraphOutput`，其中包含需要审查的动作。然后你可以把这些动作展示给审查者，并在获得决策后恢复执行。




本节中的示例以及下面的决策类型都使用默认的批量模式。有关逐调用模式，请参见[每个工具调用暂停一次](#pause-once-per-tool-call)。


```python
from langgraph.types import Command

# Human-in-the-loop 依赖 LangGraph 的持久化层。
# 你必须提供 thread ID，把执行关联到某个会话线程，
# 这样会话才能被暂停和恢复（这也是人工审查所需要的）。
config = {"configurable": {"thread_id": "some_id"}} # [!code highlight]
# 运行图，直到触发中断。
result = agent.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "Delete old records from the database",
            }
        ]
    },
    config=config, # [!code highlight]
    version="v2", # [!code highlight]
)

# result 是一个带 .value 和 .interrupts 的 GraphOutput
print(result.interrupts)  # [!code highlight]
# > (
# >    Interrupt(
# >       value={
# >          'action_requests': [
# >             {
# >                'name': 'execute_sql',
# >                'args': {'query': 'DELETE FROM records WHERE created_at < NOW() - INTERVAL \'30 days\';'},
# >                'description': 'Tool execution pending approval\n\nTool: execute_sql\nArgs: {...}'
# >             }
# >          ],
# >          'review_configs': [
# >             {
# >                'action_name': 'execute_sql',
# >                'allowed_decisions': ['approve', 'reject']
# >             }
# >          ]
# >       }
# >    ),
# > )

# 用批准决策恢复
agent.invoke(
    Command( # [!code highlight]
        resume={"decisions": [{"type": "approve"}]}  # 或 "reject" [!code highlight]
    ), # [!code highlight]
    config=config, # 相同 thread ID，用于恢复已暂停的会话
    version="v2",
)
```

    ```python
                        "type": "reject",
                        # 可选：解释为什么拒绝该动作，
                        # 以及智能体是否应该尝试不同的方法。
                        "message": "User rejected this action. Do not retry this tool call.",
                    }
                ]
            }
        ),
        config=config,  # 相同 thread ID，用于恢复已暂停的会话
        version="v2",
    )
    ```




拒绝消息会被加入对话，作为反馈帮助智能体理解为什么该动作被拒绝，以及下一步应该怎么做。如果你省略 `message`，中间件会使用默认的拒绝消息，告诉模型这个工具没有执行，并且除非用户要求，否则不要重复同一个工具调用。对于有副作用的工具，请提供更具体的领域消息，明确说明智能体应该放弃该动作、提出后续问题，还是尝试更安全的替代方案。

</Tab>

<Tab title="respond">
    当工具本质上是"ask user"这类场景时，请使用 `respond`，此时工具的真实实现就是人类的回复。`message` 内容会直接作为工具结果返回；工具本身不会执行。

    ```python
    agent.invoke(
        Command(
            # 决策以列表形式提供，每个待审动作对应一个。
            # 决策顺序必须和中断请求中动作的顺序一致。
            resume={
                "decisions": [
                    {
                        "type": "respond",
                        # 人类的回复，会直接作为工具结果返回
                        "message": "Blue.",
                    }
                ]
            }
        ),
        config=config,  # 相同 thread ID，用于恢复已暂停的会话
        version="v2",
    )
    ```




`message` 会作为一个成功的 `ToolMessage` 返回给智能体。当工具刻意作为人工输入的占位符时，请使用 `respond`，例如提示澄清的 `ask_user` 工具。不要用 `respond` 拒绝提议的动作，因为它会告诉模型该工具已成功完成。

</Tab>

</Tabs>

## 使用人类在回路中进行流式处理

你可以在智能体运行并处理中断时，使用 `stream_events()` 实时流式获取更新。使用 `stream.messages` 流式获取 LLM token，使用 `stream.values` 检查智能体状态快照里的中断。

```python
from langgraph.types import Command

config = {"configurable": {"thread_id": "some_id"}}

# 流式输出智能体进度和 LLM token，直到中断
stream = agent.stream_events(
    {"messages": [{"role": "user", "content": "Delete old records from the database"}]},
    config=config,
    version="v3",  # [!code highlight]
)
for message in stream.messages:  # [!code highlight]
    for token in message.text:  # [!code highlight]
        print(token, end="", flush=True)

# 检查运行是否因人工输入而暂停
if stream.interrupted:  # [!code highlight]
    print(f"\n\nInterrupt: {stream.interrupts}")  # [!code highlight]

# 在人工决策后，继续流式恢复
stream = agent.stream_events(
    Command(resume={"decisions": [{"type": "approve"}]}),
    config=config,
    version="v3",  # [!code highlight]
)
for message in stream.messages:  # [!code highlight]
    for token in message.text:
        print(token, end="", flush=True)
```

在[逐调用模式](#pause-once-per-tool-call)下，`stream.interrupts` 会为每个受拦截的工具调用保存一个中断。恢复时使用以中断 ID 为键的字典：

## 执行生命周期

中间件定义了一个 `after_model` 钩子，它会在模型生成回复之后、任何工具调用执行之前运行：

1. 智能体调用模型生成回复。
2. 中间件检查回复中是否有工具调用。
3. 如果任何调用需要人工输入，中间件会构建一个带有 `action_requests` 和 `review_configs` 的 [HITLRequest](https://reference.langchain.com/python/langchain/agents/middleware/human_in_the_loop/HITLRequest)，并调用 [interrupt](https://reference.langchain.com/python/langgraph/types/interrupt)。
4. 智能体等待人工决策。
5. 根据 `HITLResponse` 中的决策，中间件会执行已批准或已编辑的调用，为被拒绝的调用合成 [ToolMessage](https://reference.langchain.com/python/langchain-core/messages/tool/ToolMessage)，对于 `respond` 决策则直接把人类回复作为 [ToolMessage](https://reference.langchain.com/python/langchain-core/messages/tool/ToolMessage) 返回，然后继续执行。




在[逐调用模式](#pause-once-per-tool-call)下，`after_model` 钩子不做任何事情。中间件改为在每个受拦截的调用运行时暂停它，每个调用对应一个 [interrupt](https://reference.langchain.com/python/langgraph/types/interrupt)，并在该调用的决策到达后运行工具。
