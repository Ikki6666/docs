LangChain 拥有庞大的集成生态，能够接入本地或远程文件系统、API、数据库等多种外部资源。这些集成让开发者可以构建灵活的应用，把 LLM 的能力与访问、交互和操作外部资源的能力结合起来。

## 最佳实践

在构建这类应用时，开发者应当牢记以下良好安全实践：

* [**限制权限**](https://en.wikipedia.org/wiki/Principle_of_least_privilege)：将权限范围精确限制在应用所需的程度。授予宽泛或过度的权限可能引入严重的安全漏洞。为避免这类问题，请根据应用场景考虑使用只读凭证、禁止访问敏感资源、采用沙箱技术（例如在容器中运行）、指定代理配置以控制外部请求等措施。
* **预判潜在误用**：人会犯错，大语言模型（LLM）也一样。请始终假设，任何系统访问能力或凭证都可能以其权限所允许的任意方式被使用。举例来说，如果一组数据库凭证允许删除数据，那么最安全的假设就是，任何能使用这些凭证的 LLM 都确实可能删除数据。
* [**纵深防御**](https://en.wikipedia.org/wiki/Defense_in_depth_(computing))：没有任何单一安全技术是完美的。微调和良好的 chain 设计可以降低大语言模型（LLM）出错的概率，但无法彻底消除。最佳做法是组合多层安全策略，而不是依赖单层防护来保障安全。比如，同时使用只读权限和沙箱，以确保 LLM 只能访问明确授权给它使用的数据。

如果不这样做，可能带来的风险包括但不限于：

* 数据损坏或丢失。
* 未经授权访问机密信息。
* 关键资源的性能或可用性受损。

下面是一些典型场景及其缓解策略：

* 用户可能会要求一个具有文件系统访问权限的智能体删除不应删除的文件，或读取包含敏感信息的文件内容。为降低风险，请把智能体限制在特定目录中，并且只允许它读取或写入那些可以安全读写的文件。还可以进一步把智能体放进容器中运行，以增强沙箱隔离。
* 用户可能会要求一个具有外部 API 写权限的智能体向 API 写入恶意数据，或删除该 API 中的数据。为降低风险，请为智能体提供只读 API key，或将其限制为只使用那些本身就具备抗误用能力的端点。
* 用户可能会要求一个具有数据库访问权限的智能体删除表或修改 schema。为降低风险，请将凭证范围限制到智能体真正需要访问的表，并考虑发放只读凭证。

如果你正在构建会访问文件系统、API 或数据库等外部资源的应用，请考虑与公司安全团队沟通，以确定最适合的应用设计与安全方案。
