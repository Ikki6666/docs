最强大的 LLM 应用之一，是复杂的问答（Q&A）chatbots。它们通过在推理时向 LLM 提供一组数据访问能力来增强模型。
这些数据可以是私有数据、最新数据，或者并不属于 LLM 训练数据的数据。
这类应用使用一种称为 Retrieval Augmented Generation，或 [RAG](/oss/langchain/retrieval/) 的技术。

[Deep Agents](/oss/deepagents/overview) 为 RAG 提供了 primitives：自定义检索工具、[filesystem backend](/oss/deepagents/backends)、[subagents](/oss/deepagents/subagents)、[skills](/oss/deepagents/skills) 和 [grading rubrics](/oss/deepagents/rubric)。你可以根据语料规模、延迟要求，以及答案必须多严格地基于源数据来组合这些能力。

本指南介绍几种 RAG 模式，并演示一个端到端示例：一个文档问答 agent，它会索引 [docs.langchain.com](https://docs.langchain.com) 的一部分，在查询时检索相关 chunks，把它们卸载到文件系统，并将分析委派给 subagents，让 orchestrator context 保持干净。

## RAG 模式

Deep Agents 允许你用几种方式编排检索、分析和综合：

- **Skills 引导的检索**：用户提出问题。Agent 加载一个相关 skill，该 skill 描述如何搜索你的语料库（使用哪个 index、如何构造 query、citation 格式）。Agent 按照该 guidance 调用检索工具，然后综合答案。
- **Rubric 检查的 grounding**：用户提出问题。Agent 检索证据并起草答案。配置了 `RubricMiddleware` 的 grader sub-agent 会评估回答是否基于检索到的源材料。Agent 会不断修订，直到 rubric 通过或达到迭代上限。
- **Todo 驱动的调查**：用户提出问题。Agent 使用[规划工具](/oss/deepagents/overview#task-planning)创建要调查的文档页面或搜索 query todo list。它会检索每个 item 的结果，然后从收集到的证据综合回答。
- **Retrieve、offload 和 delegate**：用户提出问题。Agent 检索匹配 chunks，并把它们写入 filesystem backend，而不是把完整文本保留在 orchestrator context 中。Subagents 并行读取、搜索和总结单个文件。对于大型文档，agent 可以用内置搜索工具分页浏览文件，或运行 [code interpreter](/oss/deepagents/code/overview) 从源数据生成表格、时间线或视觉内容。

:::

本教程实现 **retrieve、offload 和 delegate** 模式。其他模式也使用相同 primitives：skills 通常封装检索工作流，rubrics 可以为这些流程评分，todo planning 则帮助把复杂问题拆成聚焦的搜索。

## 为什么检索很重要

语言模型本身无法访问你的文档。向它询问最近变更过的具体 API 时，它会根据训练数据回答：通常看似合理，有时错误，而且绝不会基于你的真实 source of truth。

即使文档可用，通常也不能把全部文档都塞进 context window。因此你必须只选择与给定问题相关的 passages，而这本身就是一项并不简单的任务。

### 你将构建什么

1. **Index**：将 LangChain 文档加载到 vector store 中。
2. **Search**：构建一个自定义工具，运行 vector similarity search，并把每个检索到的 chunk 写入 agent filesystem。
3. **Analyze**：把文件分析委派给 subagent，由它读取文件并返回聚焦摘要。
4. **Synthesize**：使用 main agent 根据 subagent reports 生成最终答案。

## 索引 LangChain 文档

在 indexing 步骤中，你会获取源内容，并把它的 _chunks_ 转换为数值表示。这个数值表示会捕捉 chunk 的语义。将这些数值表示与 document chunks 的映射存入 `VectorStore` 后，当用户发送 query 时，就可以基于 query 自身的数值表示高效检索相关内容。

Indexing 通常分为四步：

1. **[Load](#load-documents)**：将数据源加载为 @[`Document`] objects。
2. **[Split](#split-documents)**：使用 [text splitters](/oss/integrations/splitters) 将大型 `Document`s 拆成更小的 chunks。这对于 indexing 数据和传给模型都很有用，因为大 chunks 更难搜索，而且要么装不进模型有限的 context window，要么会消耗不必要的 token。
3. **[Embed](#select-an-embeddings-model)**：[Embeddings](/oss/integrations/embeddings) models 将每个 chunk 转为捕捉其含义的数值 vector，从而支持内容相似度搜索。
4. **[Store](#store-chunks-and-embeddings-in-vectorstore)**：使用 [VectorStore](/oss/integrations/vectorstores) 为 chunks 和 embeddings 建索引以便检索。

![index_diagram](/images/rag_indexing.png)

在 indexing 步骤中，获取文档页面，将其拆成 chunks，embed chunks，并存入 `VectorStore`。Agent 会在运行时搜索这个 index；它不会在每个问题上重新抓取整个站点。

### 切分文档

加载后的文档很长，总计超过 100k tokens，对许多模型来说太大，无法放进 context window。
即使某些模型的 context window 可以容纳完整语料，模型也可能难以在超长输入中找到信息。将 context window 用于大量内容也不够 token 高效。

为了方便使用，把 @[`Document`] objects 切成 chunks。这些 chunks 会在下一步中用于 embedding 和 vector storage。

使用 `RecursiveCharacterTextSplitter` 按换行等常见分隔符递归拆分文档，直到每个 chunk 达到合适大小。
`RecursiveCharacterTextSplitter` 是通用文本场景推荐的 `TextSplitter`。

## 安全注意事项

<Warning>
RAG 应用容易受到**间接 prompt injection** 影响。检索到的文档可能包含看起来像指令的文本。由于检索到的 chunks 与 system prompt 共享 context window，模型可能会遵循嵌入在文档中的指令，而不是你的预期 prompt。
</Warning>

没有任何 prompt 或 delimiter 策略可以完全防止间接 prompt injection。本教程中的 orchestrator 和 subagent prompts 会要求模型只把检索到的内容视为数据，search tool 也会给 chunks 加上 `# Source:` header，让 analysts 能区分 metadata 和正文。这些模式在某些情况下有帮助，但无法提供可靠保护。

在向用户展示 agent 输出之前，请验证它们。检查答案是否引用预期文档路径，以及 claims 是否与检索到的源材料一致。

有关此主题的更多信息，请参见关于 [prompt injection](https://simonwillison.net/series/prompt-injection/) 的研究。
