围绕你的目标来构建 harness。`create_deep_agent` 给你一个生产就绪的基础：把它连接到数据，塑造它的行为，并添加你的使用场景所需的能力。

:::python

```python
from deepagents import create_deep_agent

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    system_prompt="You are a helpful assistant.",
    tools=[search, fetch_url],
    memory=["./AGENTS.md"],
    skills=["./skills/"],
)
```

|---|---|

```python
import asyncio
from langchain_mcp_adapters.client import MultiServerMCPClient
from deepagents import create_deep_agent

async def main():
    async with MultiServerMCPClient(
        {
            "my_server": {
                "transport": "http",
                "url": "http://localhost:8000/mcp",
            }
        }
    ) as client:
        tools = await client.get_tools()

        agent = create_deep_agent(
            model="openai:gpt-5.5",
            tools=tools,
        )

        result = await agent.ainvoke(
            {"messages": [{"role": "user", "content": "Use the MCP server to help me."}]},
            config={"configurable": {"thread_id": "1"}},
        )

asyncio.run(main())
```

## System prompt

Deep Agents 自带内置 system prompt。deep agent 的价值来自 SDK 在模型之上提供的 orchestration 层，也就是规划、虚拟文件系统工具和子 agent，而模型需要知道这些能力存在，以及什么时候该使用它们。内置 prompt 会教 agent 如何使用这些脚手架，这样你就不必在每个项目里重新推导一遍；你可以通过 [profile](/oss/deepagents/profiles#harness-profiles) 或自己的 `system_prompt=` 调整它，而不是逐字复制。

当 middleware 添加特殊工具时，例如文件系统工具，它会把这些工具追加到 system prompt 中。

### Prompt 组装

Deep Agents 会把 system prompt 组装成最多四个命名部分，让调用方提供的指令、SDK 内置的 agent 引导，以及任何按模型定制的 [profile](/oss/deepagents/profiles) 覆盖可以按照可预测的优先级共存。没有这种分层，面向 Claude 调整的 profile suffix 之类内容可能会被你的 `system_prompt=` 参数覆盖，或者反过来覆盖你的参数，具体取决于调用顺序；命名槽位让顺序变得显式且稳定。

实际上，大多数调用方只会遇到两个槽位：`USER`（你的 `system_prompt=`）和 `BASE`（SDK 默认值）。如果选择了带内置 profile 的模型，例如今天的 Anthropic 或 OpenAI，就会增加一个 `SUFFIX`。完整的四段组装主要在你编写自定义 `HarnessProfile`，或者调试为什么 profile 文本出现在它所在的位置时才特别相关。

四个命名部分（每个都可以缺省）：

| 名称 | 来源 | 说明 |
| -------- | ------------------------------------------------- | ------------------------------------------------- |
| `USER` | `create_deep_agent` 的 `system_prompt=` 参数 | `str` 或 `SystemMessage`；未设置时省略。 |
| `BASE` | SDK 默认值（`BASE_AGENT_PROMPT`） | 默认始终存在，除非被 profile 的 `CUSTOM` 替换。 |
| `CUSTOM` | [`HarnessProfile.base_system_prompt`](/oss/deepagents/profiles#harness-profiles) | 当匹配的 profile 设置它时，会直接替换 `BASE`。 |
| `SUFFIX` | [`HarnessProfile.system_prompt_suffix`](/oss/deepagents/profiles#harness-profiles) | 当匹配的 profile 设置它时，会最后追加。 |

顺序永远是 **`USER` -> (`BASE` 或 `CUSTOM`) -> `SUFFIX`**，并用空行（`\n\n`）连接。由此得到两个不变量：

1. **`USER` 永远在最前面。** 调用方文本先于任何 SDK 或 profile 内容，因此 persona / 指令无论选择哪个模型都优先。
2. **`SUFFIX` 永远在最后。** profile suffix 紧贴对话历史，模型调优指令在这里最可靠。

组装后的形状（✓ = 字段已设置，- = 字段未设置）：

| `system_prompt=` | profile `base_system_prompt` (`CUSTOM`) | profile `system_prompt_suffix` (`SUFFIX`) | 最终组装出的 system prompt |
| ---------------- | :-------------------------------------: | :---------------------------------------: | ----------------------------- |
| `None`           |                    -                    |                     -                     | `BASE`                        |
| `None`           |                    -                    |                     ✓                     | `BASE` + `SUFFIX`             |
| `None`           |                    ✓                    |                     -                     | `CUSTOM`                      |
| `None`           |                    ✓                    |                     ✓                     | `CUSTOM` + `SUFFIX`           |
| `str`            |                    -                    |                     -                     | `USER` + `BASE`               |
| `str`            |                    -                    |                     ✓                     | `USER` + `BASE` + `SUFFIX`    |
| `str`            |                    ✓                    |                     -                     | `USER` + `CUSTOM`             |
| `str`            |                    ✓                    |                     ✓                     | `USER` + `CUSTOM` + `SUFFIX`  |

示例——内置 profile（Anthropic、OpenAI）只带 `system_prompt_suffix`，所以典型调用会落在 `str` + `-` + `✓` 这一行：

```python
agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    system_prompt="You are a customer-support agent for ACME Corp.",
)
# Final = USER + BASE + SUFFIX
#       = "You are a customer-support agent for ACME Corp."
#         + "\n\n"
#         + BASE_AGENT_PROMPT
#         + "\n\n"
#         + <Claude-specific guidance>
```

<Note>
    传入 `SystemMessage`（而不是字符串）时，会走不同的拼接路径：右侧的组装结果（`BASE` 或 `CUSTOM` 再加上任何 `SUFFIX`）会作为额外的 text content block 追加到该消息现有的 `content_blocks` 上。逻辑顺序仍然相同（调用方 block 在前），而且会保留调用方 block 上的任何 `cache_control` 标记，这对放置显式的 Anthropic prompt-cache 分界点很有用。
</Note>

<AccordionGroup>
    <Accordion title="子 agent prompts">
        [prompt 组装](#prompt-assembly) 的覆盖规则同样适用于声明式 [subagents](/oss/deepagents/subagents)：每个子 agent 都会基于**自己的模型**重新执行 profile 解析，然后把解析得到的 `base_system_prompt` / `system_prompt_suffix` 应用到它自己编写的 `system_prompt` 上。子 agent 的 `system_prompt` 扮演 `BASE` 角色；`CUSTOM` 和 `SUFFIX` 来自匹配该子 agent 模型的 profile（这可能不同于主 agent 的 profile）。

        | `spec["system_prompt"]` | profile `base_system_prompt` (`CUSTOM`) | profile `system_prompt_suffix` (`SUFFIX`) | 最终子 agent system prompt |
        | ----------------------- | :-------------------------------------: | :---------------------------------------: | ---------------------------- |
        | authored                |                    -                    |                     -                     | authored                     |
        | authored                |                    -                    |                     ✓                     | authored + `SUFFIX`          |
        | authored                |                    ✓                    |                     -                     | `CUSTOM`                     |
        | authored                |                    ✓                    |                     ✓                     | `CUSTOM` + `SUFFIX`          |

        子 agent 没有 `USER` 段。spec 中作者编写的 `system_prompt` 是最接近的对应项，位于 `BASE` 槽位。只带 `system_prompt_suffix` 的 profile（内置 Anthropic / OpenAI profile 的常见情况）只是追加到子 agent 作者原本写的内容后面。设置了 `base_system_prompt` 的 profile 会直接替换作者写的 prompt。
    </Accordion>
    <Accordion title="通用子 agent prompt">
        自动添加的[通用子 agent](/oss/deepagents/subagents#the-general-purpose-subagent) 会遵循 [prompt 组装](#prompt-assembly) 的覆盖规则，不过会多一层：GP base prompt 的解析顺序是 **`general_purpose_subagent.system_prompt`（如果设置了）-> `HarnessProfile.base_system_prompt`（如果设置了）-> SDK 通用默认值**。无论哪种方式，profile suffix 都会叠加在上面。

        这两个覆盖字段都可以携带 base prompt 替换，但它们并不等价。`general_purpose_subagent.system_prompt` 是通用子 agent 专属配置；`base_system_prompt` 是一个全局覆盖，主要面向主 agent。当两者都设置时，**通用子 agent 的专属意图在通用子 agent 上生效**，这样同时调这两个字段的用户不会发现自己的 GP 覆盖被悄悄丢掉：

        ```python
        register_harness_profile(
            "anthropic",
            HarnessProfile(
                base_system_prompt="You are ACME's support orchestrator.",  # main agent
                general_purpose_subagent=GeneralPurposeSubagentProfile(
                    system_prompt="You are a research subagent. Cite sources.",  # GP subagent
                ),
                system_prompt_suffix="Always think step by step.",
            ),
        )
        ```

        | Stack | 最终 system prompt |
        | ----- | ------------------- |
        | Main agent | `"You are ACME's support orchestrator." + SUFFIX` |
        | GP subagent | `"You are a research subagent. Cite sources." + SUFFIX` |

        如果 `general_purpose_subagent.system_prompt` 未设置，GP 子 agent 会回退到 `base_system_prompt`（如果设置了），然后再回退到 SDK 通用默认值。
    </Accordion>
</AccordionGroup>

## Middleware

Deep Agents 支持任意 [middleware](/oss/langchain/middleware/overview)，包括下方列出的内置 middleware、LangChain 的 prebuilt middleware、provider-specific middleware，以及你自己编写的自定义 middleware。

:::python
把 middleware 传给 `create_deep_agent` 的 `middleware` 参数。自定义 middleware 会追加在 @[PatchToolCallsMiddleware] 之后、[默认堆栈](#default-stack-main-agent) 中的尾部堆栈之前。
:::

:::js
把 middleware 传给 `createDeepAgent` 的 `middleware` 参数。自定义 middleware 会追加在 @[PatchToolCallsMiddleware] 之后、[默认堆栈](#default-stack-main-agent) 中的尾部堆栈之前。
:::

默认情况下，Deep Agents 可以使用以下 middleware：

### 默认堆栈（主 agent）

从前到后：

:::python

1. @[TodoListMiddleware]：跟踪并管理 todo 列表，用于组织 agent 任务和工作。
2. @[SkillsMiddleware]：仅在你传入 `skills` 时启用。它会**紧跟**在 todo middleware 之后、**文件系统 middleware 之前**注入，这样在文件工具运行前就能使用 skill 元数据。
3. @[FilesystemMiddleware]：处理读写和目录导航等文件系统操作。当你传入 `permissions` 时，文件系统权限 enforcement 也会包含在这里，这样它就能评估 agent 可能调用的每个工具。
4. @[SubAgentMiddleware]：派生并协调子 agent，用于把任务委派给专门 agent。
5. @[SummarizationMiddleware]：当对话变长时压缩消息历史，以保持在上下文限制内（通过 @[create_summarization_middleware]）。
6. @[PatchToolCallsMiddleware]：当运行在中断后恢复，或者收到格式不正确的 tool-call 参数时，修复消息历史中悬空的工具调用。它会在 Anthropic prompt caching 和下面的尾部堆栈之前运行。
7. @[AsyncSubAgentMiddleware]：仅在你配置 async subagent 时启用。
8. **你的 middleware 参数**：你通过 `middleware` 参数传入的可选 middleware 会追加在这里（在 Patch 之后、尾部堆栈之前）。
9. **Harness profile 额外项**：来自解析后模型 profile 的 provider-specific middleware（如果有）。
10. **排除工具过滤**：当 harness profile 列出 excluded tools 时，middleware 会把这些工具从 agent 中移除。
11. **Prompt caching**（@[AnthropicPromptCachingMiddleware] 和 @[BedrockPromptCachingMiddleware]）：两者都会始终注册，并在 Patch 和你的 middleware 之后运行，这样缓存前缀就与实际发送给模型的内容一致。它们会在不支持的模型上 no-op（`unsupported_model_behavior="ignore"`），因此 Anthropic middleware 作用于 Anthropic 模型，Bedrock middleware 作用于支持缓存的 AWS Bedrock 模型。
12. @[MemoryMiddleware]：仅在你传入 `memory` 时启用。

    <Note>
    `MemoryMiddleware` 被放在 profile 额外项和 prompt caching middleware 之后，这样注入的 memory 更新就更不容易让缓存前缀失效。`create_deep_agent` 的实现注释里也说明了同样的顺序考量。
    </Note>

13. `HumanInTheLoopMiddleware`：仅在你传入 `interrupt_on` 时启用。在配置好的工具调用处暂停，等待人工批准或输入。

:::

:::js

1. @[TodoListMiddleware]：跟踪并管理 todo 列表，用于组织 agent 任务和工作。
2. @[SkillsMiddleware]：仅在你传入 `skills` 时启用。它会**紧跟**在 todo middleware 之后、**文件系统 middleware 之前**注入，这样在文件工具运行前就能使用 skill 元数据。
3. @[FilesystemMiddleware]：处理读写和目录导航等文件系统操作。当你传入 `permissions` 时，文件系统权限 enforcement 也会包含在这里，这样它就能评估 agent 可能调用的每个工具。
4. @[SubAgentMiddleware]：派生并协调子 agent，用于把任务委派给专门 agent。
5. @[SummarizationMiddleware]：当对话变长时压缩消息历史，以保持在上下文限制内（通过 @[createSummarizationMiddleware]）。
6. @[PatchToolCallsMiddleware]：当运行在中断后恢复，或者收到格式不正确的 tool-call 参数时，修复消息历史中悬空的工具调用。它会在 Anthropic prompt caching 和下面的尾部堆栈之前运行。
7. @[AsyncSubAgentMiddleware]：仅在你配置 async subagent 时启用。
8. **你的 middleware 参数**：你通过 `middleware` 参数传入的可选 middleware 会追加在这里（在 Patch 之后、尾部堆栈之前）。
9. **Harness profile 额外项**：来自解析后模型 profile 的 provider-specific middleware（如果有）。
10. **排除工具过滤**：当 harness profile 列出 excluded tools 时，middleware 会把这些工具从 agent 中移除。
11. **Prompt caching**（@[AnthropicPromptCachingMiddleware] 和 @[BedrockPromptCachingMiddleware]）：会自动为 Anthropic 模型和 Amazon Bedrock Converse 模型添加。两者都在 Patch 和你的 middleware 之后运行，这样缓存前缀就与实际发送给模型的内容一致。
12. @[MemoryMiddleware]：仅在你传入 `memory` 时启用。

    <Note>
    `MemoryMiddleware` 被放在 profile 额外项和 prompt caching middleware 之后，这样注入的 memory 更新就更不容易让缓存前缀失效。`createDeepAgent` 的实现注释里也说明了同样的顺序考量。
    </Note>

13. `HumanInTheLoopMiddleware`：仅在你传入 `interruptOn` 时启用。在配置好的工具调用处暂停，等待人工批准或输入。

:::

### 默认堆栈（同步 subagent）

:::python

## Profiles

[harness profile](/oss/deepagents/profiles#harness-profiles) 是一个可复用的、按模型划分的配置包，`create_deep_agent` 会在匹配的模型被选中时自动应用它。profile 适合那些你希望跟随模型而不是跟随调用位置的行为，例如针对 Claude 指令风格调优的 system prompt suffix、为 GPT 重写的工具描述，或者只在特定 provider 上有意义的额外 middleware。

一个 profile 可以包含：自定义 base system prompt（`base_system_prompt`）、追加的 suffix（`system_prompt_suffix`）、工具描述覆盖、要排除的工具或 middleware、要注入的额外 middleware，以及对自动添加的通用子 agent 的编辑。
