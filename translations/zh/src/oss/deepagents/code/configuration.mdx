Deep Agents Code 把配置存放在 `~/.deepagents/` 目录下。主要配置文件如下：

| 文件 | 格式 | 用途 |
|------|--------|---------|
| `config.toml` | TOML | 模型默认值、provider 设置、构造参数、profile 覆盖、主题、更新设置 |
| `.env` | Dotenv | 全局 API keys、secret 和其他环境变量 |
| `hooks.json` | JSON | 外部工具订阅 Deep Agents Code 生命周期事件 |
| `.mcp.json` | JSON | 全局 MCP server 定义 |

<Note>
    `~/.deepagents/.state/` 下的文件保存每台机器的 Deep Agents Code 状态，并由系统自动管理。
</Note>

---

## 查看配置

`dcode config` 命令组会在不启动会话的情况下，报告当前生效的配置，以及每个值来自哪里。它适合确认某个环境变量或 `config.toml` 设置是否被读取，也适合在 bug 报告中共享一份已脱敏的快照。

| 命令 | 说明 |
|---------|-------------|
| `dcode config show` | 根据当前环境和 `config.toml` 解析每个选项，打印最终生效的值以及来源 |
| `dcode config list`（别名 `ls`） | 列出所有可用选项及其类型、默认值和可设置位置，但不解析具体值 |
| `dcode config get <key>` | 显示单个选项的最终值和来源，例如 `dcode config get interpreter.memory_limit_mb` |
| `dcode config path` | 显示磁盘上的配置文件位置（`config.toml`、project/global `.env`、`hooks.json` 和 managed state 文件）以及它们是否存在 |

每个选项都会按第一个已设置的来源进行解析，顺序如下：带 `DEEPAGENTS_CODE_` 前缀的 env var、标准 env var、`config.toml`，然后是内置默认值。

这四个命令都支持 `--json`，便于机器读取输出。

<Warning>
    Provider 凭据和其他 secret 只会以“已配置 / 未配置”的方式报告，不会显示实际值，因此 `config show` 和 `config get` 的输出可以安全地粘贴到 bug 报告中。
</Warning>

## Provider 凭据

Deep Agents Code 需要为你使用的每个模型 provider 提供 API key。推荐通过 [`/auth`](#use-%2Fauth-recommended) 凭据管理器添加 key。对于非交互式运行，也可以通过 shell 使用 [`dcode auth`](#manage-credentials-from-the-shell-dcode-auth) 管理同一批已存储的 key，或者改用 [环境变量](#environment-variables-ci-and-headless)。

如果同一个 key 在多个地方都设置了，请参见 [Key resolution order](#key-resolution-order) 了解哪个会生效。

### 使用 `/auth`（推荐）

在任意会话中打开凭据管理器：

```txt
/auth
```

管理器会列出你安装中可用的 LLM providers，以及 Tavily web search 之类的非模型服务，并标记哪些已经设置了 key。你可以选择某个 provider 来添加或替换 key，也可以移除已经存储的 key。你在这里保存的 key 会跨会话保留。

<Accordion title="Provider 行标签" icon="list-check">
    每一行都会显示 provider 名称，以及它的 key 来自哪里：

    | 标签 | 含义 |
    |-------|---------|
    | `[stored]` | 通过 `/auth` 在这个管理器里保存的 key |
    | `[env: VARNAME]` | key 来自环境变量 `VARNAME`（解析后的名字，例如 `DEEPAGENTS_CODE_OPENAI_API_KEY` 或 `OPENAI_API_KEY`） |
    | `[missing]` | 没有存储 key，且 env var 未设置；选择这一行即可粘贴一个 |
</Accordion>

`/auth` 提示里还有一个可选的 **base URL** 字段。留空则使用 provider 的默认 endpoint；也可以设置一个自定义值与这个 key 配合使用。base URL 会和 key 一起保存。关于 endpoint 如何解析，包括 gateway 的情况，请参见 [Endpoints, keys, and gateways](#endpoints-keys-and-gateways)。

<Warning>
    已存储的 base URL 不是 secret，可能会被记录；与它配对的 key 永远不会被记录。
</Warning>

<Note>
    Key 只会绑定到这台机器上的你的用户账号 - Deep Agents Code 不会把它们传到别处，除非传给所配置 provider 的 API。
</Note>

#### 使用 ChatGPT 登录

在 `/auth` 中选择 `openai_codex` provider 会启动浏览器登录，而不是提示输入 API key，这样你就可以使用 ChatGPT 订阅访问 OpenAI 模型。要重新认证或登出，再次选择 `openai_codex` 即可。完整流程见 [Sign in with ChatGPT (Codex models)](/oss/deepagents/code/providers)。

`/auth` 管理 **LLM provider** 凭据和 **Tavily web-search key**。在这里输入的 Tavily key 会和 provider keys 一起存储，并在下次启动时启用 web search - 见 [启用 Tavily web search](#enable-web-search-with-tavily)。其他工具凭据，例如 `LANGSMITH_API_KEY`（tracing），则从环境中读取 - [请把它们设置到 `~/.deepagents/.env` 或 shell 中](#environment-variables)。

### 从 shell 管理凭据（`dcode auth`）

`dcode auth` 命令组是 `/auth` 管理器的可脚本化版本：它管理同一批已存储凭据，而不启动 TUI，因此适合 dotfile 引导、CI/CD，以及通过 SSH 在远程机器上设置 key。子命令和界面中的操作保持一致：

| 命令 | 说明 |
|---------|-------------|
| `dcode auth list`（别名 `ls`） | 列出所有已知 provider 以及它们的 key 从哪里解析 |
| `dcode auth status <provider>` | 打印某个 provider 的解析来源 |
| `dcode auth set <provider>` | 存储一个 API key，默认从 stdin 读取 |
| `dcode auth remove <provider>`（别名 `rm`、`delete`） | 删除已存储的凭据 |
| `dcode auth path` | 打印凭据存储（`auth.json`）的实际路径 |

`set` 默认从 **stdin** 读取 key，因此它不会出现在 shell history 或 `argv` 中。你可以把 key 通过管道传入，或者使用 `--from-env VAR` 从某个进程环境变量复制：

```bash
# 通过管道传入 key（stdin）
echo "$ANTHROPIC_API_KEY" | dcode auth set anthropic

# 从已有环境变量复制
dcode auth set openai --from-env OPENAI_API_KEY
```

<Note>
    `set` 在交互式终端中会拒绝运行，这样就不会因为误调用而一直等待输入 - 请通过 stdin 管道传入 key，或使用 `--from-env VAR`。已存储的 key 走的是和 `/auth` 相同的存储，因此相关警告（例如关于 `auth.json` 文件权限的警告）会打印到 stderr。
</Note>

要删除已存储的 key，或者打印存储位置：

```bash
dcode auth remove anthropic
dcode auth path
```

<Note>
    `dcode auth set` 只管理 API keys。`openai_codex` provider 使用的是 ChatGPT 浏览器登录，而不是 API key，所以请运行 [`/auth` 并选择 `openai_codex`](#sign-in-with-chatgpt) 来登录。`dcode auth remove openai_codex` 会让你登出。
</Note>

### 环境变量（CI 和无头环境）

对于非交互式运行、CI/CD 流水线，或者无法使用 TUI 的场景，请在 shell 中导出 provider 的 env var：

```bash
export ANTHROPIC_API_KEY="sk-ant-..."
export OPENAI_API_KEY="sk-..."

# 使用 DEEPAGENTS_CODE_ 前缀，把 key 仅作用于 Deep Agents Code，
# 不影响其他 CI 步骤使用的共享 key
export DEEPAGENTS_CODE_OPENAI_API_KEY="sk-..."
```

如果你想把 key 保存在文件里，可以把它们定义在 [`.env` 文件](#environment-variables) 中。

### Key 解析顺序

当某个 provider 的 key 在多个地方都设置了时，Deep Agents Code 会按以下顺序使用第一个已设置的值：

1. **`DEEPAGENTS_CODE_` 前缀的 env var** - 例如 `DEEPAGENTS_CODE_OPENAI_API_KEY` 作为一条内联 shell export。[`DEEPAGENTS_CODE_` 前缀](#deepagents_code_-prefix) 是明确的“在 Deep Agents Code 中使用这个 key”覆盖开关。
2. **应用内存储的 key** - 在 `/auth` 凭据管理器中输入的 key。
3. **普通 provider env var** - 例如 `OPENAI_API_KEY`，来自你的 shell 或 `.env` 文件。

对于同一个 provider，应用内存储的 key 会覆盖普通 env var，但 `DEEPAGENTS_CODE_` 前缀的 key 会覆盖应用内存储的 key。这个前缀是用于在不清除已存储 key 的情况下，为单次运行覆盖它的方式：

```bash
# 如果通过 /auth 已经存了 key，普通 env var 不会覆盖它。
# 这次运行仍然会使用应用内存储的 key：
OPENAI_API_KEY=sk-xxxx dcode -n "..."

# DEEPAGENTS_CODE_ 前缀会覆盖它，但只对这次运行生效：
DEEPAGENTS_CODE_OPENAI_API_KEY=sk-xxxx dcode -n "..."
```

这种分层设计适用于一种常见场景：你的机器已经为其他用途导出了普通 provider 变量 - 比如其他工具、脚本或 CI 共用的 `OPENAI_API_KEY` - 但你不希望 Deep Agents Code 复用它。应用内存储的 key 或 `DEEPAGENTS_CODE_` 前缀变量可以给 Deep Agents Code 提供自己的值，同时不影响未加前缀的变量供其他地方使用，因此两者不会混在一起。

每个 provider 的 API key 和它的 endpoint（`base_url`）会作为一对从同一来源解析。参见 [Endpoints, keys, and gateways](#endpoints-keys-and-gateways)。

### 使用 Tavily 启用 web search

内置的 `web_search` 工具使用 [Tavily](https://tavily.com)。在你提供 key 之前，Deep Agents Code 启动时会显示 “Web search disabled” 通知。你可以把 key 存到 [`/auth`](#use-%2Fauth-recommended) 凭据管理器里，Tavily 会作为非模型服务出现，或者直接设置 `TAVILY_API_KEY` 环境变量。


<Tabs>
    <Tab title="使用 /auth（推荐）">
        从 [tavily.com](https://tavily.com) 获取一个 key（它以 `tvly-` 开头；免费层对大多数 Deep Agents Code 用途已经足够），然后把它存到凭据管理器中：

        ```txt
        /auth
        ```

        从列表中选择 **Tavily** 并粘贴 key。你也可以直接从 “Web search disabled” 通知里，通过选择 **Enter API key** 打开这个提示。
    </Tab>

    <Tab title="设置环境变量">
        <Steps>
            <Step title="获取 key">
                在 [tavily.com](https://tavily.com) 注册并复制 key（它以 `tvly-` 开头）。免费层对大多数 Deep Agents Code 用途已经足够。
            </Step>

            <Step title="添加到环境中">
                把 key 添加到 `~/.deepagents/.env`，这样每个会话都会读取它：

                ```bash title="~/.deepagents/.env"
                TAVILY_API_KEY=tvly-...
                ```

                Shell exports 的优先级高于 `.env` 值（见 [加载顺序和优先级](#loading-order-and-precedence)）。如果你想把 key 仅作用于 Deep Agents Code，而不影响其他读取 `TAVILY_API_KEY` 的工具，请使用 [`DEEPAGENTS_CODE_` 前缀](#deepagents_code_-prefix)：`DEEPAGENTS_CODE_TAVILY_API_KEY=tvly-...`。
            </Step>

            <Step title="重新加载或重启">
                在已有会话中，运行 `/reload` 重新读取 `.env` 文件。下次启动时，“Web search disabled” 通知会消失，agent 就可以调用 `web_search`。
            </Step>
        </Steps>
    </Tab>
</Tabs>

## 环境变量

除了 shell exports 之外，Deep Agents Code 还会从 dotenv 文件中读取环境变量，因此你可以把 API keys 从 shell profile 里移走，也无需在项目之间复制 `.env` 文件。

```bash title="~/.deepagents/.env"
ANTHROPIC_API_KEY=sk-ant-...
OPENAI_API_KEY=sk-...
```

### 加载顺序和优先级

启动时，Deep Agents Code 会先读取离你启动目录最近的项目 `.env`（从当前目录向上查找，找到的第一个 `.env` 生效），然后再读取 `~/.deepagents/.env` 作为所有项目的全局回退。项目 `.env` 的优先级高于全局 `.env`，但两者都不会覆盖你 shell 中已设置的值。运行 `/reload` 会重新读取这两个 `.env` 文件，因此你无需重启就能修改 key，不过 shell 值仍然优先。这适用于 Deep Agents Code 读取的所有变量（例如 `TAVILY_API_KEY` 或 `DEEPAGENTS_CODE_*` 设置）。Provider API keys 还有额外的解析规则；参见 [Provider 凭据](#provider-credentials)。

<Warning>
    在不受信任的项目目录中运行 `dcode` 会让你暴露在项目控制的文件之下。该目录中的恶意 `.env`、`Makefile` 或构建脚本可能会影响 agent 的进程环境和它运行的内容。把任何你不会在其中运行任意脚本的目录都视为不受信任，并在 [remote sandbox](/oss/deepagents/code/remote-sandboxes) 中处理不受信任的仓库。
</Warning>

### `DEEPAGENTS_CODE_` 前缀

所有 Deep Agents Code 专用环境变量都使用 `DEEPAGENTS_CODE_` 前缀（例如 `DEEPAGENTS_CODE_AUTO_UPDATE`、`DEEPAGENTS_CODE_DEBUG`）。完整列表请参见 [environment variable reference](#environment-variable-reference)。

这个前缀也可以作为 Deep Agents Code 读取的任意环境变量的覆盖机制，包括第三方凭据。Deep Agents Code 会先检查 `DEEPAGENTS_CODE_{NAME}`，然后回退到 `{NAME}`：

```bash title="~/.deepagents/.env"
# 给 Deep Agents Code 单独一份值，而不影响其他工具
DEEPAGENTS_CODE_OPENAI_API_KEY=sk-cli-only

# 或者把它设为空，这样 Deep Agents Code 就会忽略你 shell 里导出的 key
DEEPAGENTS_CODE_ANTHROPIC_API_KEY=
```

## 配置文件

`~/.deepagents/config.toml` 允许你自定义模型 provider、设置默认值，以及向 model constructors 传递额外参数。本节包括：

- **Defaults**：固定一个 [default model](#default-and-recent-model) 或 [agent](#default-and-recent-agent)。
- **Provider setup**：[`[models.providers.<name>]` 表](#provider-configuration)、[constructor params](#model-constructor-params)、[retries](#retries)、[profile overrides](#profile-overrides-advanced)，以及 [把模型加入 `/model` 切换器](#adding-models-to-the-interactive-switcher)。
- **Custom endpoints and providers**：[custom base URLs](#custom-base-url)、[OpenAI- or Anthropic-compatible APIs](#compatible-apis) 和 [arbitrary providers](#arbitrary-providers)。
- **Endpoints and gateways**：[API keys 和 base URLs 如何一起解析](#endpoints-keys-and-gateways)，包括通过 managed gateway 的情况。

### 默认和最近使用的模型

```toml
[models]
default = "ollama:qwen3:4b"             # 你有意设定的长期偏好
recent = "google_genai:gemini-3.5-flash"   # 上一次 /model 切换（自动写入）
```

`[models].default` 永远优先于 `[models].recent`。`/model` 命令只会写入 `[models].recent`，所以你配置的 default 不会被会话中途切换覆盖。要移除 default，可以使用 `/model --default --clear`，或者直接从配置文件里删除 `default` 键。

### 默认和最近使用的 agent

```toml
[agents]
default = "backend-dev"  # 你有意设定的长期偏好（在 /agents 选择器中按 Ctrl+S）
recent = "frontend-dev"  # 上一次 /agents 切换（自动写入）
```

`[agents].default` 永远优先于 `[agents].recent`。在 `/agents` 选择器中按 `Enter` 选中 agent 会把它写入 `recent`；在高亮行上按 `Ctrl+S` 会把它固定为 `default`。再次在同一行按 `Ctrl+S` 会清除 default。

显式的 `-a` / `--agent` 永远会覆盖这两个值，而 `-r` / `--resume` 会绕过它们，从而恢复该 thread 原始的 agent。相关 flag 见 [Command reference](/oss/deepagents/code/overview#command-reference)。

### Provider configuration

每个 provider 都是 `[models.providers]` 下的一个 TOML table：

```toml
[models.providers.<name>]
display_name = "My Provider"
api_key_url = "https://provider.example/keys"
models = ["gpt-4o"]
api_key_env = "OPENAI_API_KEY"
base_url = "https://api.openai.com/v1"
class_path = "my_package.models:MyChatModel"
enabled = true

[models.providers.<name>.params]
temperature = 0
max_tokens = 4096

[models.providers.<name>.params."gpt-4o"]
temperature = 0.7
```

provider 支持以下配置项：

<ResponseField name="models" type="string[]" post={["optional"]}>
    要在该 provider 对应的交互式 `/model` 切换器中显示的 model 名称列表。对于已经自带 model profile 的 providers，你在这里添加的名称会附加到包内自带的名称之后（对刚发布、但尚未加入包中的模型很有用）。对于 [arbitrary providers](#arbitrary-providers)，这个列表是切换器中模型的唯一来源。

    这里列出的模型会 **绕过** 应用的基于 profile 的 [过滤条件](/oss/deepagents/code/providers#which-models-appear-in-the-switcher)，始终显示在切换器里。这使它成为暴露那些因为缺少 `tool_calling` 支持，或者 profile 尚不存在而被排除的模型的推荐方式。

    这个 key 是可选的。无论某个模型是否出现在切换器里，你都可以随时在 `/model` 或 `--model` 中直接输入它的完整名称。
</ResponseField>

<ResponseField name="api_key_env" type="string" post={["optional"]}>
    保存 API key 的环境变量 **名称**（例如 `"OPENAI_API_KEY"`）。Deep Agents Code 会在启动时从这个 env var 读取凭据，以便在创建模型前验证访问权限。

    大多数 chat model packages 会自动从默认 env var 读取。请参见 [Provider reference](/oss/deepagents/code/providers#provider-reference) 表，了解每个内置 provider 会检查哪个变量名。如果 provider 不在那张表里，请把 `api_key_env` 设置为它对应的变量名（见 [Arbitrary providers](#arbitrary-providers)）。
</ResponseField>

<ResponseField name="display_name" type="string" post={["optional"]}>
    在 auth UI 中显示的人类可读 provider 名称。对于配置 key 更适合机器使用（例如 `my_gateway`），但 UI 标签需要包含空格或品牌大小写的 arbitrary providers，可以用它。
</ResponseField>

<ResponseField name="api_key_url" type="string" post={["optional"]}>
    用户创建或管理 API keys 的 provider 页面 URL。`/auth` modal 会在 API-key 输入框之前链接到这个页面。这个值是 URL，不是凭据。
</ResponseField>

<ResponseField name="base_url" type="string" post={["optional"]}>
    如支持，可覆盖 provider 使用的 base URL。更多信息请参考你 provider packages 的 [reference docs](https://reference.langchain.com/python/integrations/)。

    如果想把内置 provider 指向一个 wire-compatible endpoint，请参见 [Compatible APIs](#compatible-apis)；如果是通过 `class_path` 配置的 provider，请参见 [Arbitrary providers](#arbitrary-providers)。
</ResponseField>

<ResponseField name="base_url_env" type="string" post={["optional"]}>
    保存该 provider base URL 的环境变量名称，作用与 `api_key_env` 类似。若 endpoint 来自环境而不是固定值，请优先使用它，而不是 `base_url` - 例如某个因机器或 CI job 而不同的 gateway URL - 这样它就可以在不编辑 `config.toml` 的情况下变化，并参与 endpoint 解析与 key/endpoint 配对（见 [Endpoints, keys, and gateways](#endpoints-keys-and-gateways)）。它也会把这些能力扩展到 [built-in set](/oss/deepagents/code/providers#provider-reference) 之外的 providers；见 [Arbitrary providers](#arbitrary-providers)。

    如果两者都设置了，静态 `base_url` 会获胜：

    ```toml
    [models.providers.example]
    base_url = "https://fixed.example/v1"   # used
    base_url_env = "EXAMPLE_BASE_URL"        # base_url 存在时会被忽略
    ```
</ResponseField>

<ResponseField name="params" type="object" post={["optional"]}>
    传给 model constructor 的额外关键字参数。平铺的 key（例如 `temperature = 0`）会应用到这个 provider 的每个 model。按 model 命名的子表（例如 `[params."gpt-4o"]`）只会覆盖那个 model 的个别值；合并是浅层的（冲突时以 model 为准）。

    不要把凭据（例如 `api_key`）放进 `params`。请使用 [`api_key_env`](#provider-configuration) 指向某个环境变量。
</ResponseField>

<ResponseField name="profile" type="object" post={["optional"]}>
    （高级）覆盖 model 运行时 [profile](/oss/langchain/models#model-profiles) 中的字段（例如 `max_input_tokens`）。平铺的 key 会应用到这个 provider 的每个 model。按 model 命名的子表（例如 `[profile."claude-sonnet-4-5"]`）只会覆盖那个 model 的个别值；合并是浅层的（冲突时以 model 为准）。这些覆盖会在 model 创建后应用，因此会影响上下文长度显示、自动总结以及其他读取 profile 的功能。有关示例和 `--profile-override` flag，请参见 [Profile overrides](#profile-overrides-advanced)。
</ResponseField>

<ResponseField name="class_path" type="string" post={["optional"]}>
    用于 [arbitrary model](#arbitrary-providers) providers。格式为 `module.path:ClassName` 的完整 Python class。设置后，Deep Agents Code 会直接导入并实例化这个 class 作为 provider `<name>`。这个 class 必须是 `BaseChatModel` 的子类。
</ResponseField>

<ResponseField name="enabled" type="boolean" default="true" post={["optional"]}>
    该 provider 是否出现在 `/model` 选择器中。设为 `false` 可以隐藏某个自动发现自已安装包的 provider（例如你不想让某个传递依赖挤占模型切换器）。你仍然可以通过 `/model provider:model` 或 `--model` 直接使用它。
</ResponseField>

### Model constructor params

[`params` 字段](#provider-configuration) 会把额外参数传给 model constructor。若要让某个 model 拥有不同的值，可以加一个按 model 命名的子表，这样就不必复制整份 provider 配置：

```toml
[models.providers.ollama]
models = ["qwen3:4b", "llama3"]

[models.providers.ollama.params]
temperature = 0
num_ctx = 8192

[models.providers.ollama.params."qwen3:4b"]
temperature = 0.5
num_ctx = 4000
```

在这个配置下：

* `ollama:qwen3:4b` 得到 `{temperature: 0.5, num_ctx: 4000}` - model override 会生效。
* `ollama:llama3` 得到 `{temperature: 0, num_ctx: 8192}` - 没有 override，只用 provider 级参数。

合并是浅层的：model 子表中存在的任何 key 都会替换 provider 级 params 中相同的 key，而只存在于 provider 级的 key 会被保留。

<Tip>
    若想在不编辑 `config.toml` 的情况下做一次性调整，可以在启动时或会话中通过 `/model` 传入一个 JSON object，使用 `--model-params`。CLI flags 的优先级高于配置文件。语法和 provider 专属示例请参见 providers 页面的 [Model parameters](/oss/deepagents/code/providers#model-parameters)。
</Tip>

### Retries

使用顶层 `[retries]` section 为临时性的 model provider 错误配置重试次数。Deep Agents Code 会把这些值透传给支持 retry-count constructor kwargs 的 provider integrations。如果省略该 section，则使用 provider SDK 默认值。

```toml
[retries]
max_retries = 2

[retries.fireworks]
max_retries = 3

[retries.anthropic]
max_retries = 0
```

全局 `[retries].max_retries` 会作用于所有受支持的 providers。像 `[retries.fireworks]` 这样的 provider 专属表会覆盖该 provider 的全局值。值必须是大于或等于 `0` 的整数。

大多数受支持的 providers 会把重试次数作为 `max_retries` 传入。某些 integrations 使用不同的 constructor kwarg。对于 arbitrary provider，或者要覆盖已注册 provider 的 kwarg，请在 provider 专属 retries 表里设置 `param`：

```toml
[retries]
max_retries = 2

[retries.my_custom]
param = "retries"
max_retries = 4
```

`param` 必须是合法的 Python identifier 字符串，例如 `"max_retries"` 或 `"retries"`。Deep Agents Code 会忽略那些未设置 `param` 的未知 providers，因为传错 retry kwarg 可能会破坏 model 创建。

`[retries]` 的优先级低于 constructor 参数。完整优先级顺序如下：

1. `--max-retries N`，应用在 provider 解析后的 retry kwarg 上
2. `--model-params` 中包含 provider 的 retry kwarg，例如 `'{"max_retries": N}'` 或 `'{"retries": N}'`
3. `[models.providers.<provider>.params]` 中包含 provider 的 retry kwarg
4. `[retries.<provider>].max_retries`
5. `[retries].max_retries`
6. Provider SDK 默认值

### Profile overrides（高级）

覆盖 model 的运行时 profile 中的字段，以改变 Deep Agents Code 对 model 能力的理解。完整可覆盖字段见 @[ModelProfile]。最常见的用途是降低 `max_input_tokens`，让自动总结更早触发 - 这在测试或约束上下文使用时很有用：

```toml
# 应用于这个 provider 的所有 model
[models.providers.anthropic.profile]
max_input_tokens = 4096
```

按 model 命名的子表与 `params` 的行为相同 - model 级别的值在冲突时会获胜：

```toml
[models.providers.anthropic.profile]
max_input_tokens = 4096

# 这个 model 会得到更高的限制
[models.providers.anthropic.profile."claude-sonnet-4-5"]
max_input_tokens = 8192
```

profile overrides 会在 model 创建后并入 model 的 profile。任何读取 profile 的功能 - 状态栏中的上下文长度显示、自动总结阈值、能力检查 - 都会看到覆盖后的值。

<Accordion title="使用 --profile-override 在 CLI 中覆盖 profile" icon="terminal">
    若要在不编辑配置文件的情况下在运行时覆盖 model profile 字段，请通过 `--profile-override` 传入一个 JSON object：

    ```bash
    dcode --profile-override '{"max_input_tokens": 4096}'

    # 和 --model 组合使用
    dcode --model google_genai:gemini-3.5-flash --profile-override '{"max_input_tokens": 4096}'

    # 非交互模式
    dcode -n "Summarize this repo" --profile-override '{"max_input_tokens": 4096}'
    ```

    这些值会叠加在配置文件的 profile overrides 之上（CLI 胜出）。优先级链如下：model default < config.toml profile < CLI `--profile-override`。

    `--profile-override` 的值会在会话中途 `/model` 热切换后继续生效 - 切换 model 时会把这个 override 重新应用到新 model 上。
</Accordion>

### 把模型加入交互式切换器

有些 providers（例如 `langchain-ollama`）没有捆绑 model profile 数据（完整列表见 [Provider reference](/oss/deepagents/code/providers#provider-reference)）。在这种情况下，交互式 `/model` 切换器不会列出该 provider 的模型。你可以在配置文件里为这个 provider 定义一个 `models` 列表来补上：

```toml
[models.providers.ollama]
models = ["gemma4", "qwen3.6", "granite4.1:3b"]
```

现在 `/model` 切换器会多出一个 Ollama 分组，并列出这些模型。

这完全是可选的。你始终可以通过直接指定完整名称来切换到任意模型：

```txt
/model ollama:qwen3.6:27b
```

<Note>
    当安装了 `langchain-ollama` 且 daemon 可达时，Deep Agents Code 会自动发现本地拉取的模型并把它们合并到切换器里 - 不需要 `models` 列表。拉取新模型后运行 `/reload` 以刷新；或者设置 `DEEPAGENTS_CODE_OLLAMA_DISCOVERY=0` 来退出自动发现。
</Note>

### 自定义 base URL

某些 provider packages 支持用 `base_url` 覆盖默认 endpoint。比如 `langchain-ollama` 会通过底层 `ollama` client 默认使用 `http://localhost:11434`。若要指向别处，可以在配置里设置 `base_url`：

```toml
[models.providers.ollama]
base_url = "http://your-host-here:port"
```

关于兼容性和额外注意事项，请参考 provider 的 reference 文档。

### Compatible APIs

对于暴露 OpenAI 或 Anthropic wire-compatible APIs 的 providers，你可以通过把 `base_url` 指向 provider 的 endpoint，继续使用现有的 `langchain-openai` 或 `langchain-anthropic` packages：

```toml
[models.providers.openai]
base_url = "https://api.example.com/v1"
api_key_env = "EXAMPLE_API_KEY"
models = ["my-model"]
```

```toml
[models.providers.anthropic]
base_url = "https://api.example.com"
api_key_env = "EXAMPLE_API_KEY"
models = ["my-model"]
```

<Note>
    provider 在官方 spec 之上加的任何特性都不会被捕获。如果 provider 提供了专用的 LangChain integration package，优先使用那个。
</Note>

<Warning>
    OpenAI provider 默认使用 [Responses API](https://platform.openai.com/docs/api-reference/responses)，而大多数 OpenAI-compatible gateways 并不实现它。如果你的 provider 只支持 Chat Completions API，调用很可能会失败。请显式关闭 Responses API：

    ```toml
    [models.providers.openai.params]
    use_responses_api = false
    ```
</Warning>

### Arbitrary providers

Deep Agents Code 支持任何可进行 tool calling 的 LLM，只要它是一个 [LangChain `BaseChatModel`](https://reference.langchain.com/python/langchain_core/language_models/#langchain_core.language_models.BaseChatModel)。[内置 providers](/oss/deepagents/code/providers#provider-reference) 开箱即用；较少见或内部模型则需要多做一点配置。把 `class_path` 指向它的 `BaseChatModel` 子类，Deep Agents Code 就会直接导入并实例化这个 class。

```toml
[models.providers.my_custom]
display_name = "My Custom Provider"
api_key_url = "https://my-provider.example.com/keys"
class_path = "my_package.models:MyChatModel"
api_key_env = "MY_API_KEY"
base_url = "https://my-endpoint.example.com"

[models.providers.my_custom.params]
temperature = 0
max_tokens = 4096
```

`api_key_env` 和 `base_url` 都是可选的。`display_name` 和 `api_key_url` 会自定义 `/auth` 中显示的 provider 名称和获取 key 的链接；如果省略，它们会回退到 provider 配置 key 和 provider setup 文档。若想从环境变量中读取 endpoint，而不是把 `base_url` 写死，请使用 [`base_url_env`](#provider-configuration)；它会像内置 provider 一样解析并和 key 配对（见 [Endpoints, keys, and gateways](#endpoints-keys-and-gateways)）。

`class_path` providers 需要自己在内部处理认证 - 当你的 model 使用的是自定义认证（JWT token、专有 headers、mTLS 等），而不是标准 API key 时，这会很有用：

```toml
[models.providers.xyz]
class_path = "abc.integrations.deepagents:DeepAgentsXYZChat"
models = ["abc-xyz-1"]

[models.providers.xyz.params]
bypass_auth = true
temperature = 0
```

使用这份配置后，可以通过 `/model xyz:abc-xyz-1` 或 `--model xyz:abc-xyz-1` 切换到该 model。

<Note>
    Deep Agents Code 需要 **tool calling** 支持。如果你的自定义 model 支持 tool calling，但 Deep Agents Code 还不知道，可以在 provider profile 里声明它：

    ```toml
    [models.providers.xyz.profile]
    tool_calling = true
    max_input_tokens = 128000
    ```

    虽然可选，但强烈建议把 `max_input_tokens` 设置为 model 的 context window。否则 Deep Agents Code 无法显示上下文占用情况，而且自动总结会退回到固定触发值（大约 170,000 tokens），而不是你 model 窗口的某个比例。对于窗口更小的 model，可能在达到 model 硬限制前总结都还没触发，导致对话变长后请求开始失败。
</Note>

因为 Deep Agents Code 会在启动时导入 `class_path` class，所以定义它的 package 必须能在运行 `dcode` 的同一环境中被导入。内置 providers 作为 [install extras](/oss/deepagents/code/providers#quickstart) 提供，但自定义或内部 package 不是。请使用 `--package` flag 把它安装进 `dcode` 环境：

```bash
dcode --install my_package --package
```

在会话中，可以运行 `/install my_package --package --force`。两者都会把 package 安装到 `dcode` 旁边。如果 package 缺失或无法导入，Deep Agents Code 会跳过该 provider，它的模型也不会出现在 `/model` 中。

当你通过 `/model` 或 `--model` 切换到 `my_custom:my-model-v1` 时，模型名称（`my-model-v1`）会作为 `model` kwarg 传入：

```python
MyChatModel(model="my-model-v1", base_url="...", api_key="...", temperature=0, max_tokens=4096)
```

<Warning>
    `class_path` 会执行来自配置文件的任意 Python 代码。这和 `pyproject.toml` 的 build scripts 采用的是同一种信任模型 - 你对自己的机器负责。
</Warning>

你的 provider package 也可以选择在 `<package>.data._profiles` 中提供一个 `_PROFILES` dict，而不是在 `models` key 下定义它们。更多信息见 LangChain [model profiles](https://github.com/langchain-ai/langchain/tree/master/libs/model-profiles)。

### Endpoints, keys, and gateways

API key 和它被发送到的 endpoint 必须匹配：endpoint 必须接受这个 key，否则请求很可能失败。Deep Agents Code 会把 key 和 endpoint 一起解析，因此覆盖其中一个时，另一个也会跟着更新以保持一致。例如，如果你把 gateway 预置的 key 换成你自己的，Deep Agents Code 也会丢弃 gateway endpoint，这样你的 key 会直接发送给 provider，而不是发给会拒绝它的 gateway。

#### `base_url` 如何解析

Deep Agents Code 按以下顺序解析 provider 的 endpoint（先匹配的优先）：

1. `config.toml` 中该 provider 的 `base_url`。
2. 带 `DEEPAGENTS_CODE_` 前缀的 endpoint 变量。
3. 环境中的普通 endpoint 变量（例如 `OPENAI_BASE_URL`）。
4. `/auth` 凭据里保存的 endpoint。这个步骤会把保存的 endpoint 应用到没有 endpoint 变量的 provider - 例如你添加了 provider，但没有声明 [`base_url_env`](#provider-configuration)。对于步骤 2-3 来说，这类 provider 没有变量可读，所以这里会直接使用已保存的 endpoint。对于已经有 endpoint 变量的 provider，已保存的 endpoint 早在步骤 2 或 3 就生效了（它会写回那个变量），因此这一步不会改变任何东西。无论哪种情况，`/auth` 中输入的 endpoint 都会生效。
5. 如果以上都没有设置，则使用 provider SDK 自己的默认 endpoint。

<Note>
    已解析的 endpoint 会作为 `base_url` constructor argument 传给 model。
</Note>

和 API keys 一样，[`DEEPAGENTS_CODE_` 前缀](#deepagents_code_-prefix) 也可以把 endpoint 限定给 Deep Agents Code，而不影响其他工具。对于其他 provider，只要用 [`base_url_env`](#provider-configuration) 声明它的名字，endpoint 就会以同样方式解析并和 key 配对：

```toml
[models.providers.myprovider]
api_key_env = "MYPROVIDER_API_KEY"
base_url_env = "MYPROVIDER_BASE_URL"
models = ["my-model"]
```

字面量 `base_url` 的优先级高于 `base_url_env`，所以只设置你需要的那个：

```toml
[models.providers.myprovider]
base_url = "https://fixed.example/v1"   # used
base_url_env = "MYPROVIDER_BASE_URL"    # 在 base_url 存在时会被忽略
```

#### 覆盖会把配对保持在一起

当你通过 `/auth` 存储 key 时，连同输入的 endpoint（或者如果留空，则该 provider 的默认 endpoint）会一起生效。以空 base URL 存储一个 key，也会清除你环境里已经设置的 endpoint（例如 shell 导出的 gateway `OPENAI_BASE_URL`），这样你的 key 就会发往 provider 的默认 endpoint，而不是那个 gateway。

```bash title="把 key 和 endpoint 都限定给 Deep Agents Code"
DEEPAGENTS_CODE_OPENAI_API_KEY=sk-cli-only
DEEPAGENTS_CODE_OPENAI_BASE_URL=https://api.openai.com/v1
```

#### Managed gateways

在预置了 model gateway 的机器上（例如 LangSmith gateway），gateway 通常会一起导出 gateway key 和匹配的 endpoint 变量（`OPENAI_BASE_URL`、`ANTHROPIC_BASE_URL` 或 `GOOGLE_GEMINI_BASE_URL`）。Deep Agents Code 默认会使用这对值，因此不需要额外配置。

如果想改用你自己的 key，可以通过 `/auth` 存储它（base URL 留空则使用 provider 默认值，也可以显式设置），或者设置带 `DEEPAGENTS_CODE_` 前缀的 key 和 endpoint。这两种方式都会覆盖 gateway 的那一对值，而且不会留下不匹配的 endpoint。

## Skills 目录 allowlist

默认情况下，Deep Agents Code 加载 skills 时会校验解析后的 skill 文件路径是否仍在标准 [skill directories](/oss/deepagents/code/data-locations#skills) 之一中。这可以防止 skill 目录里的符号链接读取这些根目录之外的任意文件。

如果你把共享 skill 资源存放在非标准位置，并通过标准 skill 目录中的符号链接引用它们，就可以把那个位置加入 containment allowlist。这 **不会** 增加新的 skill discovery location：skills 仍然只会从标准目录中发现。

<ResponseField name="extra_allowed_dirs" type="string[]" post={["optional"]}>
    加入 skill containment allowlist 的路径。支持 `~` 展开。

    ```toml
    [skills]
    extra_allowed_dirs = [
        "~/shared-skills",
        "/opt/team-skills",
    ]
    ```
</ResponseField>

或者把 `DEEPAGENTS_CODE_EXTRA_SKILLS_DIRS` 环境变量设置为以冒号分隔的列表：

```bash
export DEEPAGENTS_CODE_EXTRA_SKILLS_DIRS="~/shared-skills:/opt/team-skills"
```

当环境变量被设置时，它的优先级高于配置文件值。修改会在 `/reload` 后生效。

## 主题

使用 `/theme` 打开交互式主题选择器。你可以在列表中实时预览主题，按 `Enter` 把选择保存到 `config.toml`。

Deep Agents Code 自带许多内置主题。默认主题是 `langchain`，一种带有 LangChain 品牌配色的深色主题。选中的主题会保存在 `[ui]` 下：

```toml
[ui]
theme = "langchain-dark"
```

### 用户自定义主题

在 `config.toml` 的 `[themes.<name>]` sections 中定义自定义主题。每个 section 都需要 `label`（str）。`dark`（bool）如果省略，默认为 `false` - 对于深色主题请设为 `true`。所有颜色字段都是可选的 - 省略的字段会根据 `dark` flag 回退到内置的深色或浅色调色板。

```toml
[themes.my-solarized]
label = "My Solarized"
dark = true
primary = "#268BD2"
warning = "#B58900"

# 带空格的主题名需要 TOML 引号
[themes."ocean breeze"]
label = "Ocean Breeze"
primary = "#0077B6"
background = "#CAF0F8"
```

用户自定义主题会与内置主题一起显示在 `/theme` 选择器里。

### 覆盖内置主题颜色

如果你只想微调某个内置主题的颜色，而不想新建主题，可以使用 `[themes.<builtin-name>]` section。这里只会读取颜色字段 - `label` 和 `dark` 会继承自内置主题：

```toml
[themes.langchain]
primary = "#FF5500"
```

省略的颜色字段会保留现有的内置值。

对 `[themes.*]` sections 的修改会在 `/reload` 后生效。

### 将主题映射到终端

如果你会在不同配色方案的终端之间切换（例如一个深色的 iTerm 和一个浅色的 Apple Terminal），可以在 `[ui.terminal_themes]` 下为每个终端映射一个主题。Deep Agents Code 会匹配 shell 的 `TERM_PROGRAM`，并自动应用映射的主题：

```toml
[ui.terminal_themes]
"Apple_Terminal" = "langchain-light"
"iTerm.app" = "langchain"
```

在 `/theme` 选择器里按 `T` 可以把当前高亮主题保存给当前终端；或者运行 `echo $TERM_PROGRAM` 找到你终端的标识符，再手动添加。

<Accordion title="高级：选择器快捷键、解析顺序、终端标识符">
    #### 选择器快捷键

    在 `/theme` 选择器中：

    - `N` 可以在显示标签和规范 registry key 之间切换 - 这些 key 就是 `[ui] theme` 和 `[ui.terminal_themes]` 接受的值。
    - `T` 会把当前高亮主题保存到当前 `TERM_PROGRAM` 对应的 `[ui.terminal_themes]` 中。映射后的主题在选择器里会带上 `(default)` 徽标。

    #### 常见 `TERM_PROGRAM` 值

    key 会直接和环境变量按字面匹配 - 当它们包含点号或特殊字符时，请在 TOML 中加引号。

    | Terminal | `TERM_PROGRAM` |
    | --- | --- |
    | Apple Terminal | `Apple_Terminal` |
    | iTerm2 | `iTerm.app` |
    | WezTerm | `WezTerm` |
    | VS Code integrated terminal | `vscode` |
    | Ghostty | `ghostty` |

    #### 解析顺序

    Deep Agents Code 每次启动都会按以下优先级解析主题：

    1. `DEEPAGENTS_CODE_THEME` 环境变量（显式覆盖）。
    2. 当前 `TERM_PROGRAM` 的 `[ui.terminal_themes]` 映射。
    3. 通过 `/theme` 保存的 `[ui] theme` 偏好。
    4. 内置默认值（`langchain`）。
</Accordion>

## 自动更新

Deep Agents Code 默认会自动检查并安装更新。

要关闭自动更新：

<Tabs>
    <Tab title="Config file">
        ```toml
        [update]
        auto_update = false
        ```
    </Tab>
    <Tab title="Environment variable">
        ```bash
        export DEEPAGENTS_CODE_AUTO_UPDATE=0
        ```
    </Tab>
</Tabs>

环境变量优先于配置文件。

启用时（默认），Deep Agents Code 会在会话开始时检查 PyPI 是否有新版本，并自动升级。禁用后，Deep Agents Code 会改为显示一条更新提示，并给出相应的安装命令。

要完全关闭自动更新检查：

<Tabs>
    <Tab title="Config file">
        ```toml
        [update]
        check = false
        ```
    </Tab>
    <Tab title="Environment variable">
        ```bash
        export DEEPAGENTS_CODE_NO_UPDATE_CHECK=1
        ```
    </Tab>
</Tabs>

关闭更新检查也会阻止启动时自动安装更新。

你仍然可以随时通过 `/update` slash command 手动检查并安装更新，它会按需检查并在界面中直接报告成功或失败。

升级后，Deep Agents Code 会在下次启动时显示一个 “what's new” 横幅，并链接到 changelog。

在会话结束时，如果本次会话中检测到了更高版本，也会显示一个更新横幅作为提醒。

## 卸载

要移除 `dcode` 和 `deepagents-code` binaries 以及隔离的工具环境，请运行：

```bash
uv tool uninstall deepagents-code
```

卸载命令不会删除用户配置或会话数据。Deep Agents Code 会把这些文件存放在 `~/.deepagents/` 下，包括 `config.toml`、`hooks.json`、全局 `.env`，以及 `.state/` 内容，例如已保存的 sessions 和凭据。若要连这些数据一起删除，请运行：

```bash
rm -rf ~/.deepagents
```

## Managed deployments

[install script](https://github.com/langchain-ai/deepagents/blob/main/libs/code/scripts/install.sh) 支持以 root 身份运行，适用于 macOS MDM 工具（Kandji、Jamf 等）执行的、处于最小 root 环境中的脚本。

当 `id -u` 为 `0` 时，脚本会：

1. 通过 `/dev/console` 或扫描 `/Users` 目录来解析真实 console user 的 `HOME`
2. 在每个安装步骤之后把创建的文件 `chown` 回目标用户

非 root 安装不受影响：当不是 root 运行时，所有 root 专用代码路径都会直接短路。

### 使用环境变量固定安装版本

install script 会读取一些环境变量，让你可以在整台 fleet 上固定版本、选择 extras，并指定 Python 版本。把它们和 piped install 写在同一行：

```bash
# 固定一个确切版本，便于整个 fleet 进行可复现安装
curl -LsSf https://langch.in/dcode | DEEPAGENTS_CODE_VERSION="0.1.16" bash
```

<ResponseField name="DEEPAGENTS_CODE_VERSION" type="string" post={["optional"]}>
    要安装的精确 package 版本，例如 `0.1.0`（或者像 `0.1.0rc1` 这样的 pre-release）。与 `DEEPAGENTS_CODE_PRERELEASE` 互斥 - 同时设置两者会报错，因为精确 pin 已经选定了唯一版本。
</ResponseField>

<ResponseField name="DEEPAGENTS_CODE_PRERELEASE" type="string" post={["optional"]}>
    在解析最新版本时应用的 uv pre-release 策略：`disallow`、`allow`、`if-necessary`、`explicit` 或 `if-necessary-or-explicit`。与 `DEEPAGENTS_CODE_VERSION` 互斥。
</ResponseField>

<ResponseField name="DEEPAGENTS_CODE_EXTRAS" type="string" post={["optional"]}>
    以逗号分隔的 pip extras，例如 `ollama`、`ollama,groq` 或 `daytona`。可用 extras 见 [`pyproject.toml`](https://github.com/langchain-ai/deepagents/blob/main/libs/code/pyproject.toml)。
</ResponseField>

<ResponseField name="DEEPAGENTS_CODE_PYTHON" type="string" default="3.13" post={["optional"]}>
    安装时使用的 Python 版本。
</ResponseField>

<ResponseField name="DEEPAGENTS_CODE_SKIP_OPTIONAL" type="string" post={["optional"]}>
    设为 `1` 可跳过可选工具检查。
</ResponseField>

<ResponseField name="DEEPAGENTS_CODE_VERBOSE" type="string" post={["optional"]}>
    设为 `1` 可显示 uv 原始 stderr（timing lines、未过滤的 package diff）以及默认静默的状态行（可选工具检查、安装完成页脚）。在排查安装问题时很有用。
</ResponseField>

<ResponseField name="UV_BIN" type="string" post={["optional"]}>
    uv binary 的路径。如果未设置，会自动检测。
</ResponseField>

Managed installs 默认启用 auto-update。要关闭它，可以在用户 shell profile 中设置 `DEEPAGENTS_CODE_AUTO_UPDATE=0`，或者把带 `[update] auto_update = false` 的 `config.toml` 部署到 `~/.deepagents/config.toml`。要完全关闭自动更新和更新检查，请设置 `DEEPAGENTS_CODE_NO_UPDATE_CHECK=1`，或者部署 `[update] check = false`。

要把每个用户的 model traffic 都路由通过 managed gateway（并在整个 fleet 上预置 gateway key 和 base URL），请参见 [Managed gateways](#managed-gateways)。

## 外部编辑器

按 `Ctrl+X` 或输入 `/editor`，就可以在外部编辑器中撰写 prompts。Deep Agents Code 会先检查 `$VISUAL`，然后检查 `$EDITOR`，最后回退到 `vi`（macOS/Linux）或 `notepad`（Windows）。GUI editors（VS Code、Cursor、Zed、Sublime Text、Windsurf）会自动收到 `--wait` flag，这样 Deep Agents Code 会一直阻塞到你关闭文件。

```bash
# 在 shell profile 中设置（例如 ~/.zshrc、~/.bashrc）
export VISUAL="code"    # GUI editor（自动注入 --wait）
export EDITOR="nvim"    # 终端回退
```

## Hooks

Hooks 让外部程序能够对 Deep Agents Code 生命周期事件做出反应。把 command 配置在 `~/.deepagents/hooks.json` 中后，每当某个事件触发，就会把 JSON payload 通过 stdin 发送给每个匹配的 command。

Hooks 以 fire-and-forget 方式在后台线程中运行 - 它们永远不会阻塞 Deep Agents Code，失败也只会被记录下来，不会打断会话。

### 设置

创建 `~/.deepagents/hooks.json`：

```json
{
  "hooks": [
    {
      "command": ["bash", "-c", "cat >> ~/deepagents-events.log"],
      "events": ["session.start", "session.end"]
    }
  ]
}
```

现在每次 session 开始或结束时，Deep Agents Code 都会把事件 payload 追加到 `~/deepagents-events.log`。

### Hook 配置

配置文件包含一个 `hooks` array。每个条目都有：

<ResponseField name="command" type="list[str]" required>
    要运行的命令和参数。不做 shell expansion：如有需要，请使用 `["bash", "-c", "..."]`。
</ResponseField>

<ResponseField name="events" type="list[str]" post={["optional"]}>
    要订阅的事件名称。省略或留空表示接收 **所有** 事件。
</ResponseField>

```json
{
  "hooks": [
    {
      "command": ["python3", "my_handler.py"],
      "events": ["session.start", "task.complete"]
    },
    {
      "command": ["bash", "log_everything.sh"]
    }
  ]
}
```

上面的第二个 hook 没有 `events` 过滤器，因此它会接收 Deep Agents Code 发出的每个事件。

### Payload 格式

每个 hook command 都会通过 stdin 接收一个 JSON object，其中包含一个 `"event"` key 以及事件特有字段：

```json
{
  "event": "session.start",
  "thread_id": "abc123"
}
```

### 事件参考

#### `session.start`

在 agent session 开始时触发（交互式和非交互式模式都会触发）。

<ResponseField name="thread_id" type="string" required>
    session 的 thread identifier。
</ResponseField>

#### `session.end`

在 session 退出时触发。

<ResponseField name="thread_id" type="string" required>
    session 的 thread identifier。
</ResponseField>

#### `user.prompt`

在交互模式下，用户提交聊天消息时触发。

没有额外字段。

#### `input.required`

当 agent 需要人工输入时触发（human-in-the-loop interrupt）。

没有额外字段。

#### `permission.request`

在审批对话框出现之前触发，前提是有一个或多个 tool call 需要用户权限。

<ResponseField name="tool_names" type="list[str]" required>
    请求批准的工具名称。
</ResponseField>

#### `tool.error`

当某个 tool call 返回 error 时触发。

<ResponseField name="tool_names" type="list[str]" required>
    出错的工具名称。
</ResponseField>

#### `task.complete`

当 agent 完成当前 task 时触发（streaming loop 结束，且没有后续 interrupt）。

<ResponseField name="thread_id" type="string" required>
    session 的 thread identifier。
</ResponseField>

#### `context.compact`

在 Deep Agents Code 压缩（总结）对话上下文之前触发。

没有额外字段。

### 执行模型

- **后台线程**：Hook subprocesses 通过 `asyncio.to_thread` 在单独线程中运行，因此主事件循环永远不会被阻塞。
- **并发分发**：当多个 hooks 匹配同一个事件时，它们会在线程池中并发运行。
- **5 秒超时**：每个 command 都有 5 秒超时，超时后会被杀掉。
- **Fire-and-forget**：错误会按 hook 捕获并以 debug/warning 级别记录。某个 hook 失败永远不会让 Deep Agents Code 崩溃或卡住。
- **延迟加载**：配置文件只会在第一次事件分发时读取一次，之后整个 session 都会缓存。
- **不做 shell expansion**：命令直接执行（不是通过 shell）。如果你需要管道或变量展开，请用 `["bash", "-c", "..."]` 包起来。

### Hook 示例

<Accordion title="把所有事件记录到文件">
```json
{
  "hooks": [
    {
      "command": ["bash", "-c", "jq -c . >> ~/.deepagents/hook-events.jsonl"],
      "events": []
    }
  ]
}
```
</Accordion>

```json
  ]
}
```
</Accordion>

<Accordion title="Python handler">
编写一个从 stdin 读取 JSON payload 的 handler 脚本：

```python title="my_handler.py"
import json
import sys

payload = json.load(sys.stdin)
event = payload["event"]

if event == "session.start":
    print(f"Session started: {payload['thread_id']}", file=sys.stderr)
elif event == "permission.request":
    print(f"Approval needed for: {payload['tool_names']}", file=sys.stderr)
```

```json title="~/.deepagents/hooks.json"
{
  "hooks": [
    {
      "command": ["python3", "my_handler.py"],
      "events": ["session.start", "permission.request"]
    }
  ]
}
```
</Accordion>

### 安全注意事项

Hooks 遵循和 Git hooks 或 shell aliases 相同的信任模型 - 任何能写入 `~/.deepagents/hooks.json` 的用户都可以执行任意命令。这是有意为之：

- **无命令注入**：payload 数据只会以 JSON 形式流向 stdin，绝不会进入命令行参数。`json.dumps` 会处理转义。
- **默认不使用 shell**：命令以 `shell=False` 方式运行，从而避免 shell injection。
- **配置格式错误**：无效 JSON 或意外类型只会产生记录的 warning，不会带来安全问题。

<Warning>
    只添加你信任来源的 hooks。hook 拥有和你用户账户相同的权限。
</Warning>
