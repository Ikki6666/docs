异步子代理允许 supervisor agent 启动会立即返回的后台任务。supervisor 可以在子代理并发工作的同时继续与用户交互。supervisor 可以在任何时点检查任务状态、发送后续指令，或取消任务。在 Agent Server 上，子代理还会在完成、失败或需要输入时回报。supervisor 无需主动检查。

这建立在 [子代理](/oss/deepagents/subagents) 之上；后者是同步运行的，会阻塞 supervisor，直到完成。对于耗时较长、可并行化，或者需要在执行过程中动态调整的任务，请使用异步子代理。

要在托管 agent 中运行异步子代理，请用 `async: true` 启用它们。参见 [Managed Deep Agents 中的异步子代理](/langsmith/managed-deep-agents-subagents#async-subagents)。

```mermaid
graph TB
    User([User]) <--> Supervisor[Supervisor Agent]

    Supervisor --> |launch| Researcher[Researcher]
    Supervisor --> |launch| Coder[Coder]

    Researcher -.-> |notify| Supervisor
    Coder -.-> |notify| Supervisor
```

<Note>
异步子代理可在任何实现 [Agent Protocol](https://github.com/langchain-ai/agent-protocol) 的 server 上运行，例如 [LangSmith Deployment](/langsmith/deployment) 或自托管的 Agent Protocol server。每个子代理都独立于 supervisor 运行。supervisor 通过 SDK 启动、检查、更新和取消它。通知和 webhook 需要 [Agent Server](/langsmith/agent-server)。
</Note>

## 比较同步和异步子代理

| 维度 | 同步子代理 | 异步子代理 |
|------|-----------|-----------|
| **执行模型** | supervisor 会阻塞，直到子代理完成 | 立即返回 task ID；supervisor 继续执行 |
| **运行位置** | 在 supervisor 的 run 内部 | 在 server 上自己的线程中（Agent Server 或其他 Agent Protocol server） |
| **并发性** | 并行但阻塞 | 并行且非阻塞 |
| **结果** | 作为工具结果返回 | 在 Agent Server 上，子代理会通知 supervisor；否则由 supervisor 调用 `check_async_task` |
| **任务中更新** | 不支持 | 可通过 `update_async_task` 发送后续指令 |
| **取消** | 不支持（除非停止 supervisor） | 可通过 `cancel_async_task` 取消任务 |
| **状态性** | 无状态 - 多次调用之间没有持久状态 | 有状态 - 在自己的线程上跨交互保持状态 |
| **适用场景** | 需要先等结果再继续的任务 | 在聊天中交互式管理的长耗时复杂任务 |

## 使用异步子代理工具

当配置了异步子代理时，包含在 [Deep Agents 栈](/oss/deepagents/customization#deep-agents-stack) 中的 @[`AsyncSubAgentMiddleware`] 会为 supervisor 提供五个工具：

| 工具 | 作用 | 返回值 |
|------|------|------|
| `start_async_task` | 启动新的后台任务 | Task ID（立即返回） |
| `check_async_task` | 获取任务的当前状态，以及其结果、错误或它正在向用户询问的内容 | 状态，以及结果、错误或待处理的请求 |
| `update_async_task` | 向任务发送新指令 | 后续指令已启动或已排队的确认 |
| `cancel_async_task` | 停止任务 | 确认 |
| `list_async_tasks` | 列出已跟踪的任务及其实时状态，可选按状态筛选 | 每个任务的状态（不含结果） |

supervisor 的 LLM 会像调用其他工具一样调用这些工具。middleware 会自动处理线程创建、run 管理和状态持久化。

### 了解生命周期

典型交互如下：

<Note>
在 Agent Server 上，supervisor 无需检查任务：子代理完成时，任务会通知 supervisor。
</Note>

```mermaid
sequenceDiagram
    participant User
    participant Supervisor
    participant Researcher

    User->>Supervisor: "Research topic X"
    Supervisor->>Researcher: start_async_task("topic X")
    Researcher-->>Supervisor: task_id (immediately)
    Supervisor-->>User: "I have started the research. You can keep chatting while it runs."

    Note over User,Supervisor: User keeps chatting with the supervisor
    Note over Researcher: Researcher working...

    Researcher-->>Supervisor: notification: success + result
    Note over Supervisor: Woken by the notification
    Supervisor-->>User: "The research is done. Here is what it found..."
```

- **Launch** 会在 server 上创建新的线程，并按[启动模式](#choose-a-launch-mode)确定的输入启动一个 run。isolated 模式只发送任务描述；fork 模式还会发送父代理的有效对话历史。`start_async_task` 会把线程 ID 作为 task ID 返回。
- **Check** 会获取任务的当前状态，以及其结果、错误或它正在向用户询问的内容。
- **Update** 会在同一线程上创建一个新的 run。默认情况下它会中断前一个 run，子代理会带着完整对话历史和新的指令重新启动。task ID 保持不变。
- **Cancel** 会调用 server 上的 `runs.cancel()`，并把任务标记为 `"cancelled"`。
- **List** 会遍历所有已跟踪任务。对于非终态任务，它会并行从 server 获取实时状态。对于终态状态（`success`、`error`、`timeout`、`cancelled`、`interrupted`），它使用缓存的状态。

:::python
要让后续指令排队等待，请设置 `update_strategy="enqueue"`。此时 **Update** 会把新的 run 排在当前 run 之后，任务在开始前处于 `pending` 状态。取消该任务也会取消仍然活跃的更早 run。
如果当前 run 在后续指令开始前因等待输入或审批而暂停，后续指令仍会启动，而该请求会被丢弃。

<Note>
`update_strategy` 需要 `deepagents>=0.7.30`。它处于 [**beta**](/oss/versioning) 阶段；API 和行为可能在版本之间发生变化。
</Note>
:::

## 了解状态管理

:::python
任务元数据存储在 supervisor graph 上一个专用的 state channel（`async_tasks`）中，与消息历史分离。这一点很关键，因为 deep agents 在上下文窗口装满时会 [压缩消息历史](/oss/deepagents/context-engineering#summarization)。如果 task ID 只存在于工具消息里，压缩时就会丢失。这个专用 channel 能确保 supervisor 即使经过多轮总结，仍然可以通过 `list_async_tasks` 找回任务。

每个被跟踪的任务都会记录 task ID、agent 名称、thread ID、run ID、状态以及时间戳（`created_at`、`last_checked_at`、`last_updated_at`）。

## 选择传输方式

:::python
### ASGI transport（共置部署）

当子代理规格省略 `url` 字段时，LangGraph SDK 会使用 ASGI transport，SDK 调用会通过进程内函数调用而不是 HTTP 路由。对于基于 LangGraph 的部署，这要求两个 graph 都注册在同一个 `langgraph.json` 里。

ASGI transport 消除了网络延迟，也不需要额外的认证配置。子代理仍然会作为一个拥有自己状态的独立线程运行。这是推荐的默认方式。
:::

:::js
### 同部署（省略 `url`）

当子代理规格省略 `url` 字段时，LangGraph SDK 会使用该 server 提供的地址，与运行此 graph 的 Agent Server 通信。在其他情况下，SDK 默认使用 `http://localhost:8123`。对于基于 LangGraph 的部署，请将两个 graph 注册在同一个 `langgraph.json` 中。

已部署的 Agent Server 从 0.18.0 版本起会提供此地址（`langgraph dev` 已经如此）。在更早的版本中，请将 `url` 设置为部署 URL。
:::

### HTTP transport（远程）

添加 `url` 字段即可切换到 HTTP transport，此时 SDK 调用会通过网络发送到远程 Agent Protocol server：

:::python
<AsyncSubagentsHttpTransportPy />
:::

:::js
```typescript
{
  name: "researcher",
  description: "Research agent",
  graphId: "researcher",
  url: "https://my-research-deployment.langsmith.dev",
}
```
:::

对于 LangGraph 部署，认证由 LangGraph SDK 通过环境变量中的 `LANGSMITH_API_KEY`（或 `LANGGRAPH_API_KEY`）处理。自托管的 Agent Protocol server 可能会使用不同的认证机制。

当子代理需要独立扩展、不同的资源配置，或者由不同团队维护时，请使用 HTTP transport。

## 选择启动模式

每个 @[`AsyncSubAgent`] 规格上的 `mode` 字段控制子代理在任务启动时收到的对话上下文。

| 模式 | 行为 |
|------|------|
| `"isolated"`（默认） | 只发送被委派的任务描述。子代理全新启动，对父代理的对话历史一无所知。 |
| `"fork"` | 启动时先发送父代理对话的快照，然后发送任务描述。子代理可以在后台工作期间使用这些上下文。 |

对于大多数任务，`"isolated"` 是正确的选择。当子代理需要已有的上下文时，请使用 `"fork"`。例如，对于应当按照对话中已经确定的风格和语气来写作的后台起草 agent，请使用 `"fork"`。

### Fork 模式

<Warning>
:::python
Fork 模式是实验性功能，可能会在未来的版本中更改。
:::
:::js
Fork 模式需要 `deepagents>=1.16.0`。它是实验性功能，可能会在未来的版本中更改。
:::
</Warning>

:::python

在任何 `AsyncSubAgent` 规格上设置 `mode="fork"`：

```python
async_subagents=[
    {
        "name": "drafter",
        "description": "Drafts documents based on the conversation context",
        "graph_id": "drafter",
        "mode": "fork",
    }
]
```

:::

:::js

在任何 `AsyncSubAgent` 规格上设置 `mode: "fork"`：

```typescript
const asyncSubagents: AsyncSubAgent[] = [
  {
    name: "drafter",
    description: "Drafts documents based on the conversation context",
    graphId: "drafter",
    mode: "fork",
  },
];
```

:::

启动时，`start_async_task` 会发送父代理有效对话历史的快照，随后发送任务描述。如果父代理已压缩其历史，快照包含的是压缩后的上下文，而不是每条原始消息。父代理之后的消息不会转发给子代理。

子代理在一个新的 server 线程上启动。fork 模式把对话消息作为 run 输入发送，不会复制父代理的 checkpoint 历史或全部父状态。元数据可以把新线程与其 supervisor 关联起来，但这种关联本身并不会传递对话上下文。

**提示缓存复用。** 要在分叉后的对话前缀上获得缓存命中，请为远程 agent 配置与父代理相同的模型、system prompt、工具和提示处理 middleware。Fork 模式只复制对话历史，不会同步这些设置。配置一致是必要但不充分条件：渲染出的前缀必须一致，且缓存命中取决于 provider。

:::js
**卸载媒体。** 如果父代理通过 `offloadBinaryContent` 卸载媒体，fork 模式会发送对这些媒体的引用，而不是媒体本身。子代理必须是共享父代理 backend 的 deep agent 才能看到该媒体；其他 deep agents 会收到一条说明其不可用的提示，其他 graphs 无法使用这些消息。
:::

## 最佳实践

### 为本地开发配置合适的 worker pool

在本地使用 `langgraph dev` 运行时，增大 worker pool 以容纳并发的子代理运行。每个活跃 run 会占用一个 worker slot。一个有 3 个并发子代理任务的 supervisor 需要 4 个 slot（1 个 supervisor + 3 个子代理）。如果配置不足，launch 会进入队列。

### 跟踪子代理运行

在基于 LangGraph 的部署中，每一次异步子代理运行都是一次标准的 LangGraph run，会完整显示在 LangSmith 中。supervisor 的 trace 会展示它的 `start_async_task`、`check_async_task`、`update_async_task`、`cancel_async_task` 和 `list_async_tasks` 调用。默认情况下，每个子代理 run 都会作为单独的 trace 出现。使用 thread ID（task ID）可以把子代理的 trace 与 supervisor 的 trace 匹配起来。

同一部署上的子代理还会收到 supervisor 的 trace header。要把子代理的 run 显示为嵌套在 supervisor 的 trace 下，请让子代理的 graph 采用这些 trace header。参见 [Agent Server 上的分布式 tracing](/langsmith/agent-server-distributed-tracing)。

## 故障排查

### supervisor 在 launch 后立即轮询

**问题**：supervisor 在启动后立刻循环调用 `check_async_task`，把异步执行变成了阻塞执行。

**解决方案**：supervisor 无需检查。在 Agent Server 上，子代理会在任务完成、失败或需要输入时通知 supervisor。`start_async_task` 的工具描述已经告诉模型不要在启动后立即检查状态。如果仍然轮询，请在 supervisor 的 system prompt 中强化这一点：

:::

:::js

:::

### supervisor 报告了过期状态

**问题**：supervisor 报告的是对话中更早的任务状态，而不是再次检查任务。

**解决方案**：`check_async_task` 和 `list_async_tasks` 的工具描述会告诉模型对话历史中的状态是过期的。如果仍然出现这种情况，请增加指令，要求在报告任务状态前调用 `check_async_task` 或 `list_async_tasks`。开启通知后，supervisor 无需检查就能了解每次状态变化。

### task ID 查找失败

**问题**：supervisor 截断或重新格式化了 task ID，导致 `check_async_task` 或 `cancel_async_task` 失败。

**解决方案**：每个工具的 task ID 参数会告诉模型传入完整的 task ID。如果仍然截断，原因通常是模型特定的。请尝试不同的模型，或者在 system prompt 中加入“always show the full task_id, never truncate or abbreviate it”。

### 子代理启动后排队而不是运行

**问题**：启动子代理时卡住或启动很慢。

**解决方案**：worker pool 可能已耗尽。使用 `--n-jobs-per-worker` 增大池大小。另见 [为本地开发配置合适的 worker pool](#size-the-worker-pool-for-local-development)。
