## 概览

<Note>
本概览覆盖的是**基于文本的 embedding model**。LangChain 当前还不支持多模态 embedding。

参阅[热门 embedding model](#top-integrations)。
</Note>

Embedding model 会把原始文本，例如一句话、一段文字或一条推文，转换成定长的数字向量，以捕捉其**语义含义**。这些向量让机器能够基于意义而非精确词面来比较和搜索文本。

在实际场景中，这意味着含义相近的文本会在向量空间中彼此靠近。例如，它不只会匹配 *"machine learning"* 这个短语，还能找出讨论相关概念、但使用不同措辞的文档。

### 工作原理

1. **向量化**：模型把每个输入字符串编码成一个高维向量。
2. **相似度评分**：使用数学度量来比较向量，从而衡量底层文本的相关程度。

### 相似度度量

有几种度量常用于比较 embedding：

* **Cosine similarity**：衡量两个向量之间的夹角。
* **Euclidean distance**：衡量两个点之间的直线距离。
* **Dot product**：衡量一个向量在另一个向量上的投影程度。

下面是一个计算两个向量之间 cosine similarity 的示例：

```python
import numpy as np

def cosine_similarity(vec1, vec2):
    dot = np.dot(vec1, vec2)
    return dot / (np.linalg.norm(vec1) * np.linalg.norm(vec2))

similarity = cosine_similarity(query_embedding, document_embedding)
print("Cosine Similarity:", similarity)
```

## 接口

LangChain 通过 @[Embeddings] 接口，为文本 embedding model（例如 OpenAI、Cohere、Hugging Face）提供统一接口。

主要有两个方法：

* `embed_documents(texts: List[str]) → List[List[float]]`：为一组文档生成 embedding。
* `embed_query(text: str) → List[float]`：为单个查询生成 embedding。

<Note>
这个接口允许对查询和文档采用不同的 embedding 策略，不过大多数提供方在实际中会以相同方式处理两者。
</Note>

### 常见部署模式

在实践中，大多数团队最终都会收敛到以下四种模式之一：

1. 托管式旗舰模型：OpenAI `text-embedding-3-large`、Cohere `embed-english-v3`、Google `gemini-embedding-001`、Voyage `voyage-3`。一次 API 调用即可使用，开箱即有一流质量，不需要本地基础设施。但会带来按调用计费和数据出网依赖。
2. 本地开源模型：`BAAI/bge-*`、`mixedbread-ai/mxbai-embed-*`、`Qwen/Qwen3-Embedding-*`、`nomic-ai/modernbert-embed-*`、`sentence-transformers/all-*`。下载一次，到处运行。没有单次调用成本，数据也不会离开你的环境。在小规模场景下，CPU 可能比托管 API 慢，但在 GPU 上通常具有竞争力，甚至更快。
3. 本地开源专用模型：针对特定领域、语言或任务微调的模型。从强大的开源底座（例如 `BAAI/bge-m3`）出发，即便只用几千组领域内 query/document 对进行微调，也常常能在该领域的检索准确率上超过托管旗舰模型。
4. 生产级自托管：使用 [Text Embeddings Inference (TEI)](https://github.com/huggingface/text-embeddings-inference) 或 Ollama 来部署同样的开源模型（基础版或微调版）。这样既能享受本地推理的成本优势，也能获得类似托管提供方的水平扩展能力和 API 体验。

LangChain 对这四种模式一视同仁：你只需要实例化一个 `Embeddings` 子类，并把它传给 vector store 或 retriever。模式 (2) 和 (3) 使用 `HuggingFaceEmbeddings`，模式 (4) 使用 `HuggingFaceEndpointEmbeddings` 或 `OllamaEmbeddings`。

### 需要权衡的因素

#### 质量

可以先参考 [MTEB leaderboard](https://huggingface.co/spaces/mteb/leaderboard)。MTEB 会在检索、聚类、分类和 reranking 等任务上对 embedding model 进行基准测试，已经成为事实上的行业参考。请按你的语言和任务进行筛选，其中检索是 RAG 中最常见的场景。

不过排行榜成绩未必能完整迁移到你的业务场景，所以在正式采用前，仍然应该先用你自己的数据做一次小规模评测。LangSmith 提供了相关工具，参阅[evaluation guides](/langsmith/evaluation-concepts)。

#### 成本

托管 embedding 通常按每百万 token 收费，价格范围大约在几美分到 0.15 美元左右。对于只嵌入一次、但每天会被查询数千次的语料库，成本往往主要来自查询侧。

本地推理没有单次调用成本，但需要 CPU（较慢）或 GPU（带来资本支出或云成本）。临界点取决于工作负载：低流量个人项目在 CPU 上几乎是零成本；对于中等流量生产环境，一块通过 TEI 提供服务的 GPU 往往能在单位经济性上超过托管服务。

#### 延迟

托管 embedding API 每次请求通常会增加约 50 到 200ms 的网络延迟。本地模型在 CPU 上处理短查询时，小模型（`all-MiniLM-L6-v2` 级别）通常需要 10 到 100ms，更大的模型则需要 50 到 500ms。在 GPU 上，本地推理通常会比请求托管 API 的来回网络耗时更快。

对于批量索引来说，单次请求的延迟没有吞吐量那么关键。TEI 和多进程本地推理都会积极做批处理。比如，在 GPU 上使用 `HuggingFaceEmbeddings` 时，可以考虑设置 `encode_kwargs={"batch_size": 64}` 或更高。

#### 维度

Embedding 维度会影响 vector store 的存储占用和查询计算量。常见维度包括：

- 384（较小的 Sentence Transformers 模型，例如 `all-MiniLM-L6-v2`）
- 768（中型 ST 模型，例如 `all-mpnet-base-v2`、`bge-base`）
- 1024（`bge-large`、Cohere v3、Voyage）
- 1536（OpenAI `text-embedding-3-small`、`Qwen3-Embedding-0.6B`）
- 3072+（OpenAI `text-embedding-3-large`、`Qwen3-Embedding-4B/8B`）

更大的向量通常更准确，但也会消耗更多存储和查询计算。若干现代模型（OpenAI `text-embedding-3-*`、`mixedbread-ai/mxbai-embed-large-v1`、经过 Matryoshka 训练的 ST 模型、Qwen3-Embedding）支持**截断**：把向量裁剪到更小维度，同时保持较平滑的质量下降。这在需要把更多向量塞进更小索引时会很有用。

#### 上下文长度

多数经典 embedding model 的上限是 512 token（例如 `all-mpnet-base-v2`、经典 BGE）。较新的模型支持更长上下文：

- `nomic-ai/modernbert-embed-base`: 8192 tokens
- `Alibaba-NLP/gte-multilingual-base`: 8192 tokens
- `BAAI/bge-m3`: 8192 tokens
- OpenAI `text-embedding-3-*`: 8191 tokens

如果你的 chunk 很长，例如整页技术文档或法律段落，优先考虑长上下文模型。对于短 chunk 来说，512 token 限制通常不是问题。

#### 多语言支持

如果要做多语言检索，请选择在你的目标语言上训练过的模型。常见的强默认选项包括：

- 开源：`BAAI/bge-m3`、`intfloat/multilingual-e5-*`、`Alibaba-NLP/gte-multilingual-*`、`Qwen/Qwen3-Embedding-*`（通过 `HuggingFaceEmbeddings` 使用）
- 托管：Cohere `embed-multilingual-v3`、OpenAI `text-embedding-3-*`

#### 查询和文档提示词

一些现代开源模型（E5、BGE、Qwen3-Embedding、GTE）会为查询和文档使用不同的文本前缀进行训练。查询阶段使用错误前缀，是常见的质量回退原因。使用 `HuggingFaceEmbeddings` 时，请显式传入这些 prompt：

```python
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="intfloat/e5-large-v2",
    encode_kwargs={"prompt": "passage: "},
    query_encode_kwargs={"prompt": "query: "},
)
```

请查看 Hugging Face 上对应模型卡片中的推荐 prompt 字符串。

#### 许可

多数流行的开源 embedding model 都采用宽松许可（Apache 2.0、MIT）。也有少数较新的专用模型在生产场景下需要商业授权。上线前请检查每个模型的许可证。

### 超越单向量稠密 embedding

每个 chunk 一个稠密向量是默认方案，但不是唯一方案。

#### 稀疏检索和混合检索

稠密 embedding 对精确匹配类查询（例如产品编码、命名实体、代码标识符）的处理，通常不如基于关键词的索引。混合检索会把稠密索引与 BM25 或稀疏神经索引（例如 SPLADE、`BAAI/bge-m3` 的稀疏输出）结合起来，以同时覆盖这两类需求。

#### Late-interaction 和多向量

ColBERT 风格的模型会为每个 token 生成一个向量，而不是为每个 chunk 只生成一个向量，然后通过 late interaction 来计算 query 与文档之间的匹配分数。对于复杂查询，这种方法通常比单向量稠密检索更准确，但代价是更高的存储开销和更复杂的索引流程。当前这一方向的开源模型包括 `jinaai/jina-colbert-v2`、`answerdotai/answerai-colbert-small-v1`，以及 `lightonai/LateOn` 等较新的 late-interaction 变体。LangChain 内置 retriever 主要面向单向量 embedding；late interaction 通常需要专门的索引，例如 Vespa、Qdrant 的多向量支持，或 PyLate。

### 起步建议

如果你只想先快速跑起来，可以从下面这些选项开始：

- 快速原型，托管：`OpenAIEmbeddings(model="text-embedding-3-small")`
- 快速原型，本地，无需 API key：`HuggingFaceEmbeddings(model_name="sentence-transformers/all-mpnet-base-v2", encode_kwargs={"normalize_embeddings": True})`
- 生产环境，托管，质量优先：`VoyageAIEmbeddings(model="voyage-3")` 或 `OpenAIEmbeddings(model="text-embedding-3-large")`
- 生产环境，开源，质量优先：通过 TEI 提供服务的 `HuggingFaceEmbeddings(model_name="BAAI/bge-m3", encode_kwargs={"normalize_embeddings": True})`
- 多语言，开源：配置好 query 和 document prompt 的 `HuggingFaceEmbeddings(model_name="intfloat/multilingual-e5-large")`

先在你自己的数据上衡量检索质量，再迭代。

## 缓存

Embedding 可以被持久化存储，或进行临时缓存，以避免重复计算。

缓存 embedding 可以通过 `CacheBackedEmbeddings` 实现。这个包装器会把 embedding 存到键值存储中，对文本做哈希后将哈希值作为缓存 key。

初始化 `CacheBackedEmbeddings` 的主要方式是 `from_bytes_store`。它接受以下参数：

- **`underlying_embedder`**：实际用于生成 embedding 的 embedder。
- **`document_embedding_cache`**：用于缓存文档 embedding 的任意 [`ByteStore`](/oss/integrations/stores/)。
- **`batch_size`**：（可选，默认是 `None`）每进行多少个文档 embedding 后再更新一次 store。
- **`namespace`**：（可选，默认是 `""`）文档缓存使用的命名空间。它可以帮助避免冲突，例如设置为 embedding model 名称。
- **`query_embedding_cache`**：（可选，默认是 `None`）用于缓存查询 embedding 的 [`ByteStore`](/oss/integrations/stores/)，或者传入 `True` 来复用 `document_embedding_cache`。

<Important>
- 使用不同 embedding model 时，请始终设置 `namespace` 参数，以避免冲突。
- `CacheBackedEmbeddings` 默认不会缓存 query embedding。如需启用，请指定 `query_embedding_cache`。
</Important>

```python
import time
from langchain_classic.embeddings import CacheBackedEmbeddings  # [!code highlight]
from langchain_classic.storage import LocalFileStore # [!code highlight]
from langchain_core.vectorstores import InMemoryVectorStore

# Create your underlying embeddings model
underlying_embeddings = ... # e.g., OpenAIEmbeddings(), HuggingFaceEmbeddings(), etc.

# Store persists embeddings to the local filesystem
# This isn't for production use, but is useful for local
store = LocalFileStore("./cache/") # [!code highlight]

cached_embedder = CacheBackedEmbeddings.from_bytes_store(
    underlying_embeddings,
    store,
    namespace=underlying_embeddings.model
)

# Example: caching a query embedding
tic = time.time()
print(cached_embedder.embed_query("Hello, world!"))
print(f"First call took: {time.time() - tic:.2f} seconds")

# Subsequent calls use the cache
tic = time.time()
print(cached_embedder.embed_query("Hello, world!"))
print(f"Second call took: {time.time() - tic:.2f} seconds")
```

在生产环境中，你通常会使用更稳健的持久化存储，例如数据库或云存储。可用选项请参阅[store 集成](/oss/integrations/stores/)。
