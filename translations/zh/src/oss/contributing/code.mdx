### 快速修复：提交 bug 修复

对于简单的 bug 修复，你可以立刻开始：

<Steps>
    <Step title="复现问题">
        甚至在克隆仓库之前，也请先确保你能够稳定复现该 bug。这有助于确认问题存在，并为修复提供起点。维护者和其他贡献者应当能够仅根据你的描述复现问题，而不需要额外的环境设置或修改。
    </Step>

    <Step title="Fork 仓库">
        :::python
        将 [LangChain](https://github.com/langchain-ai/langchain)、[LangGraph](https://github.com/langchain-ai/langgraph) 或 [Deep Agents](https://github.com/langchain-ai/deepagents) 仓库 fork 到你的 <Tooltip tip="如果你 fork 到组织账号，维护者将无法直接编辑，这可能会显著延迟接收流程。">个人 GitHub 账号</Tooltip>
        :::
        :::js
        将 [LangChain](https://github.com/langchain-ai/langchainjs)、[LangGraph](https://github.com/langchain-ai/langgraphjs) 或 [Deep Agents](https://github.com/langchain-ai/deepagentsjs) 仓库 fork 到你的 <Tooltip tip="如果你 fork 到组织账号，维护者将无法直接编辑，这可能会显著延迟接收流程">个人 GitHub 账号</Tooltip>
        :::
    </Step>

    <Step title="克隆并设置环境">
        :::python

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 例如，以 LangChain 为例：
        git clone https://github.com/parrot123/langchain.git
        ```

        <Warning>
            LangChain Python 仓库是一个 **monorepo**——其仓库根目录下没有 `pyproject.toml`。每个包都有自己的配置文件，位于 `libs/` 下（例如 `libs/core/`、`libs/langchain/`、`libs/partners/openai/`）。在运行 `uv` 命令之前，你必须 `cd` 到相应的包目录。
        </Warning>

        ```bash
        # 进入你要处理的包目录，然后安装依赖
        cd libs/core          # 或 libs/langchain、libs/partners/openai 等
        uv sync --all-groups

        # 或者只安装某个特定分组：
        uv sync --group test
        ```

        如果你之前没有安装过 [`uv`](https://docs.astral.sh/uv/)，需要先安装它。请参阅[仓库结构](#repository-structure)一节，获取完整的包及其位置列表。
        :::
        :::js

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 例如，以 LangChain 为例：
        git clone https://github.com/parrot123/langchainjs.git

        # 对于 LangGraph：
        git clone https://github.com/parrot123/langgraphjs.git
        ```

        ```bash
        # 在仓库内安装依赖
        pnpm install
        # 为所有包创建构建，以解析 workspace 依赖
        pnpm build
        ```
        :::
    </Step>

    <Step title="创建分支">
        为你的修复创建一个新分支。这有助于让改动保持有序，也能让之后提交 pull request 更方便。

        ```bash
        git checkout -b your-username/short-bugfix-name
        ```
    </Step>

    <Step title="编写失败测试">
        添加在没有修复时会失败的[单元测试](#test-writing-guidelines)。这样可以验证 bug 确实被修复，并防止回归
    </Step>

    <Step title="进行修改">
        在遵循我们的[代码质量标准](#code-quality-standards)的前提下修复这个 bug。只做解决问题所需的**最小改动**。我们强烈建议你在开始编码前先在 issue 中评论。例如：

        > *"I'd like to work on this. My intended approach would be to [...brief description...]. Does this align with maintainer expectations?"*

        一条 30 秒写完的评论，往往可以避免因为初始思路错误而浪费时间。
    </Step>

    :::js
    <Step title="运行构建">
        运行构建命令，确保该包仍然可以正常构建
        ```bash
        pnpm build
        # 或构建某个特定的 workspace 包
        pnpm --filter @langchain/core build
        ```
    </Step>
    :::

    <Step title="验证修复">
        确保测试通过，且没有引入回归。在提交 PR 之前，请确认所有测试都能在本地通过

        :::python

        ```bash
        make format
        make lint
        make test

        # 对于涉及集成的 bug 修复，还请运行：
        make integration_tests
        # （你可能需要配置 API 测试凭证）
        ```
        :::
        :::js

        ```bash
        pnpm lint
        pnpm test

        # 对于涉及集成的 bug 修复，还请运行：
        pnpm test:int

        # 或在某个特定的 workspace 包中运行测试
        cd libs/langchain-core
        pnpm test
        pnpm lint

        # 或在仓库根目录针对特定包运行测试
        pnpm --filter @langchain/core test
        pnpm --filter @langchain/core lint
        ```
        :::
    </Step>

    <Step title="记录变更">
        如果行为发生变化，请更新 docstring 和/或行内注释
    </Step>

    <Step title="提交 pull request">
        按照提供的 PR 模板填写。如果适用，请使用一个[closing keyword](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)（例如 `Fixes #ISSUE_NUMBER`）来引用你修复的 issue，这样在 PR 合并后 issue 会自动关闭。
    </Step>
</Steps>

## 贡献指南

在你开始为 LangChain 项目做贡献之前，先花一点时间想清楚你为什么要这样做。如果你唯一的目标只是想在简历上加一条 "first contribution"（或者只是想快速完成一次贡献），那你可能更适合去参加 boot camp 或在线教程。

为开源项目做贡献需要投入时间和精力，但它也能帮助你成为更好的开发者，并学到新技能。不过，你也需要知道，这往往会比跟着培训课程学习更难、更慢。尽管如此，如果你愿意花时间把事情做好，那么参与开源是很值得的。

### 向后兼容

<Warning>
    除了关键安全修复之外，不允许对公开 API 引入破坏性变更。

    详情请参阅我们的[版本策略](/oss/versioning)。
</Warning>

请通过以下方式保持兼容性：

<AccordionGroup>
    <Accordion title="稳定接口">
        **始终保留**：

        - 函数签名和参数名
        - 类接口和方法名
        - 返回值结构和类型
        - 公开 API 的导入路径
    </Accordion>

    <Accordion title="安全变更">
        **可接受的修改**：

        :::python
        - 添加新的可选参数
        :::
        :::js
        - 添加新的可选参数或类型参数
        :::
        - 向类中添加新方法
        - 在不改变行为的前提下提升性能
        - 添加新的模块或函数
    </Accordion>

    <Accordion title="修改前请确认">
        - **这会破坏现有用户代码吗？**
        - 检查你的目标是否是公开接口
        :::python
        - 如有需要，它是否已在 `__init__.py` 中导出？
        :::
        - 测试中是否已有既有用法模式？
    </Accordion>
</AccordionGroup>

### 新功能

我们希望对新功能保持较高门槛。一般来说，如果没有现有 issue 证明确实存在迫切需求，我们不会接受外部贡献者新增核心抽象。这同样适用于基础设施和依赖项的变更。

通常，新功能贡献需要满足以下要求：

<Steps>
    <Step title="设计讨论">
        创建一个 issue，并说明：

        - 你要解决的问题
        - 拟议的 API 设计
        - 预期的使用模式
    </Step>

    <Step title="实现">
        - 遵循现有代码模式
        - 包含完整的测试和文档
        - 考虑安全影响
    </Step>

    <Step title="集成层面的考虑">
        - 它会如何与现有功能交互？
        - 是否会带来性能影响？
        - 是否会引入新的依赖？

        我们会拒绝那些可能导致安全漏洞或相关报告的功能。
    </Step>
</Steps>

### 安全指南

<Warning>
    安全至关重要。绝不要引入漏洞或不安全的模式。
</Warning>

安全检查清单：

<AccordionGroup>
    <Accordion title="输入校验">
        - 对所有用户输入进行校验和清洗
        - 在模板和查询中正确转义数据
        :::python
        - 绝不要对用户数据使用 `eval()`、`exec()` 或 `pickle`，这会导致任意代码执行漏洞
        :::
        :::js
        - 绝不要使用 `eval()`，这会导致任意代码执行漏洞
        :::
    </Accordion>

    <Accordion title="错误处理">
        - 使用具体的异常类型
        - 不要在错误消息中暴露敏感信息
        - 实现正确的资源清理
    </Accordion>

    <Accordion title="依赖">
        - 避免添加硬依赖
        - 尽量减少可选依赖
        - 审查第三方包的安全问题
    </Accordion>
</AccordionGroup>

## 开发工作流

### pre-commit 钩子

:::python
[LangChain](https://github.com/langchain-ai/langchain) 和 [Deep Agents](https://github.com/langchain-ai/deepagents) 仓库包含 [pre-commit](https://pre-commit.com/) 钩子，会在每次提交前自动运行格式化、lint 和校验检查。请在仓库根目录安装它们：

```bash
pip install pre-commit  # or: uv tool install pre-commit
pre-commit install
```

这些钩子会强制要求：
- 不允许直接提交到受保护分支
- YAML 和 TOML 语法校验
- 修复行尾空白和文件末尾问题
- 规范化智能引号和非标准空格
- 逐包运行 `make format` 和 `make lint`
:::

### 运行测试

<Info>
    目录路径相对于你正在处理的包。
</Info>

在可能的情况下，我们更倾向于单元测试而不是集成测试。单元测试会在每个 pull request 上运行，因此它们应当快速且可靠。集成测试按计划运行，且需要更多设置，因此应仅用于确认与外部服务的接口点。

#### 单元测试

:::python
**位置**：`tests/unit_tests/`
:::
:::js
**位置**：`src/tests/FILENAME_BEING_TESTED.test.ts`
:::

单元测试覆盖不需要调用外部 API 的模块化逻辑。如果你添加了新逻辑，就应当添加单元测试。在单元测试中，请检查前处理/后处理，并 mock 外部依赖。

**要求**：
- 不允许发起网络调用
- 测试所有代码路径，包括边界情况
- 对外部依赖使用 mock

运行单元测试：

:::python
```bash
make test

# Or directly:
uv run --group test pytest tests/unit_tests

# To run a specific test:
```

        | 最小用法示例 | docstring | 展示基本的实例化模式 |
        | 功能教程 | 本站 | 深入讲解 |

        4. 返回值描述
        5. 可能抛出的异常

### 依赖

LangChain 包区分**硬依赖**和**可选依赖**，以保持包轻量并尽量减少用户的安装开销。

<Tabs>
    <Tab title="可选依赖">
        几乎所有新依赖都应当是可选依赖。请在以下情况下使用可选依赖：

        - 该依赖仅用于特定集成或功能
        - 用户在没有该依赖的情况下仍能有意义地使用该包
        - 该依赖体积较大，或有许多传递依赖

        **要求：**

        - 未安装该依赖的用户必须能够**导入**你的代码且无任何副作用（无警告、无错误、无异常）
        - **不要**修改 `pyproject.toml` 和 `uv.lock`

        **添加可选依赖：**

        1. 将依赖添加到相应的测试依赖文件中（例如 `extended_testing_deps.txt`）
        2. 添加一个单元测试，至少尝试导入新代码。理想情况下，该单元测试使用轻量级 fixture 来测试代码逻辑。
        3. 对任何需要该依赖的单元测试使用 `@pytest.mark.requires("package_name")` 装饰器。
    </Tab>

    <Tab title="硬依赖">
        硬依赖会在用户安装该包时自动安装。仅在以下情况下使用硬依赖：

        - 没有该依赖，包根本无法运行
        - 该依赖体积小且传递依赖极少
        - 没有合理的方式将功能设为可选

        <Warning>
            添加硬依赖会增加所有用户的安装时间，并提高潜在版本冲突的风险。

            维护者会仔细审查硬依赖的新增！
        </Warning>

        **添加硬依赖：**

        1. 创建一个 issue 或讨论，说明为什么该依赖必须是硬依赖而不能是可选的
        2. 将依赖添加到 `pyproject.toml` 的相应部分
        3. 运行 `uv lock` 更新 lockfile
        4. 包含覆盖新功能的完整测试
    </Tab>
</Tabs>

### 测试编写指南

为了编写有效的测试，有一些值得遵循的良好实践：

:::python
- 在 docstring 中用自然语言描述测试
- 使用描述性的变量名
- 断言要详尽
:::
:::js
- 将测试封装在一个描述所测组件的 `describe` 块中
- 用自然语言描述测试名称
- 断言要详尽
- 仅对大小合理的数据对象使用 snapshot
:::

<Tabs>
    <Tab title="单元测试">
        :::python
        ```python
        def test_document_processor_handles_empty_input():
            """Test processor gracefully handles empty document list."""
            processor = DocumentProcessor()

            result = processor.process([])

            assert result.success
            assert result.processed_count == 0
            assert len(result.errors) == 0
        ```
        :::
        :::js
        ```typescript
        describe("DocumentProcessor", () => {
            it("Should handle empty document list", () => {
                const processor = new DocumentProcessor();
                const result = processor.process([]);

                expect(result.success).toBe(true);
                expect(result.processedCount).toBe(0);
                expect(result.errors).toHaveLength(0);
            });
        });
        ```
