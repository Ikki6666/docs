Graph API 把智能体工作流定义为由 [state](#state)、[nodes](#nodes) 和 [edges](#edges) 构成的图。[`Send`](#send) 和 [`Command`](#command) 控制图如何调度工作：`Send` 为扇出动态调用节点，`Command` 在更新状态的同时路由到下一个节点（包括 interrupt 之后的恢复）。如果你需要显式的共享状态和可视化的控制流，请使用 Graph API。

构建过程中需要逐步决策时，请参阅 [Graph API 构建检查清单](/oss/langgraph/use-graph-api)。需要完整演练时，请参阅[用图思考](/oss/langgraph/thinking-in-graph-api)。

## 图

LangGraph 把智能体工作流建模为由三部分构成的图：

1. [`State`](#state)：应用的共享快照，通常是一个带类型的 schema。
2. [`Nodes`](#nodes)：读取状态、执行工作并返回更新的函数。
3. [`Edges`](#edges)：决定下一个节点的固定或条件跳转。

组合节点和边，可以构建序列、分支和循环。节点和边都是普通函数，既可以调用 LLM，也可以执行其他代码。

简而言之：节点负责做事，边决定下一步运行什么。

### Super-step

LangGraph 通过[消息传递](https://en.wikipedia.org/wiki/Message_passing)运行图，风格类似 Google 的 [Pregel](https://research.google/pubs/pregel-a-system-for-large-scale-graph-processing/) 系统。执行以离散的 **super-step** 推进：

- 并行运行的节点共享同一个 super-step。
- 顺序运行的节点使用不同的 super-step。
- 节点在入边收到输入时变为激活状态。
- 一个 super-step 结束后，没有待处理消息的节点变为非激活状态。
- 当所有节点都非激活且没有消息在传输时，运行结束。

### StateGraph

@[`StateGraph`] 是主要的图构建器。用你的状态 schema 参数化它。

## State

State 是节点读取和更新的共享数据。LangGraph 把这些数据存放在 **channel** 中：channel 是状态 schema 里的具名槽位（也就是状态对象的键）。每个 channel 保存一个值，并定义更新如何合并进来。大多数 channel 采用最后写入优先。带 [reducer](#reducers) 的 channel 则会组合值，例如追加到列表。

State 包含两部分：

- 声明图中 channel 的 [schema](#schema)
- 可选的 [reducer](#reducers)，控制更新如何合并到各个 channel

节点返回局部更新，LangGraph 通过每个 channel 的 reducer 应用这些更新。

:::python
使用 [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict)、[`dataclass`](https://docs.python.org/3/library/dataclasses.html)（用于提供默认值）定义状态；需要校验时，可以使用 Pydantic 的 [`BaseModel`](/oss/langgraph/graph-api-state#use-pydantic-models-for-graph-state)。从性能考虑，优先使用 `TypedDict` 或 `dataclass`。

<Info>

### Schema

默认情况下，图的输入和输出 schema 与完整状态一致。当某些键仅用于内部时，可以收窄它们。请参阅[定义输入和输出 schema](/oss/langgraph/graph-api-state#define-input-and-output-schemas)。

#### 多个 schema

大多数图共用一份状态 schema。需要以下任一情形时，请使用多个 schema：

- 供内部节点共享、但不属于图输入或输出的私有 channel
- 显式指定输入和输出 schema，作为完整内部状态的子集

节点可以向图状态中的任意 channel 写入，包括不在其声明输入 schema 中的 channel。只要 schema 已定义，节点也可以引入私有 channel。输入和输出 schema 只约束 `invoke` 接受和返回的内容，默认不会对[流式输出](/oss/langgraph/streaming)隐藏 channel。请参阅[私有 channel 与流式输出](/oss/langgraph/graph-api-state#private-channels-and-streaming)。

示例请参阅[定义输入和输出 schema](/oss/langgraph/graph-api-state#define-input-and-output-schemas)和[在节点之间传递私有状态](/oss/langgraph/graph-api-state#pass-private-state-between-nodes)。

### 重执行与幂等性

使用 [checkpointer](/oss/langgraph/persistence) 时，LangGraph 在 [super-step](#super-steps) 边界保存 checkpoint，而不是在节点函数内部中途保存。经过 [interrupt](/oss/langgraph/interrupts) 或[重试](/oss/langgraph/fault-tolerance#retries)后，受影响的节点会从函数开头重新运行。暂停前的副作用会再次执行。

设计节点逻辑时，要保证重复执行是安全的。优先使用幂等键、upsert，或先读后写检查。重试下需要持久化键和外部副作用时，请参阅[重试边界与幂等性](/oss/langgraph/fault-tolerance#retry-boundaries-and-idempotency)。`interrupt()` 前后的副作用，请参阅[在 `interrupt` 之前调用的副作用必须具备幂等性](/oss/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent)。

可以增删节点和边，而不会破坏已有 thread 的恢复。恢复运行会使用已保存的状态和你当前编译的图。

如果节点调用 [task](/oss/langgraph/functional-api#task) 或 @[`interrupt`]，恢复时会适用更严格的[确定性](/oss/langgraph/functional-api#determinism)规则。已完成的 task 结果会从 checkpointer 恢复。在恢复点之前改变 task 或 interrupt 的顺序，可能导致缓存值不匹配。请参阅[幂等性](/oss/langgraph/functional-api#idempotency)。

<a id="choose-the-unit-of-work"></a>

### 选择工作单元

[节点](#nodes)既是检查点边界，也是重试边界。它同时也是图可以走向不同路径的地方。解析、检索或固定工具链这类确定性工作不需要单独的节点，除非你需要这层边界。

先判断这一步是决定接下来做什么，还是执行已经决定好的事情。然后选择与所需恢复行为相匹配的原语：

| 原语 | 自有检查点 | 恢复或重试时 | 适用场景 |
| --- | --- | --- | --- |
| 节点内的普通函数 | 没有。它在节点的 [super-step](#super-steps) 内运行。 | 节点重新运行时它也会重新运行。 | 该步骤之后没有路由分支，且与节点其余部分一起重复执行可以接受。 |
| [Task](/oss/langgraph/functional-api#task) | 没有新的图检查点。结果与正在运行的 entrypoint 或父检查点一起存储。 | 外层 entrypoint 或节点从头重播。已完成的 task 返回已存储的结果。 | 该步骤有副作用或开销较大，恢复时不能重复执行。 |
| [Subgraph](/oss/langgraph/use-subgraphs) | 有状态模式下有：节点在父线程的命名空间下写入检查点。使用 `checkpointer=False` 编译则不产生子图检查点。 | 有状态模式会在子图内部从被中断或失败的节点处恢复。 | 该单元有自己的路由或状态 schema，或有多个父图复用它。 |
| 图节点 | 有。检查点跟随节点所在的 [super-step](#super-steps) 写入。 | 恢复从该节点开始。更早的节点不会重新运行。 | 该步骤之后可能出现路由分支，或者你需要 interrupt、恢复或[时间旅行](/oss/langgraph/use-time-travel)边界。 |

重试下的副作用请参阅[重试边界与幂等性](/oss/langgraph/fault-tolerance#retry-boundaries-and-idempotency)。task 的重试和超时请参阅[容错](/oss/langgraph/fault-tolerance)。

### 在节点中使用 tasks

当一个节点要执行多个应独立 checkpoint 的操作时，把每个操作用 [task](/oss/langgraph/functional-api#task) 包裹起来，而不是把工作拆到多个节点。使用 checkpointer 时，已完成的 task 结果会被保存，恢复的 thread 因此可以跳过节点内已完成的工作。相关模式和示例请参阅 [Tasks](/oss/langgraph/functional-api#task) 和[常见陷阱](/oss/langgraph/functional-api#common-pitfalls)。

## 边

边决定控制接下来去哪里：

- **普通边**：始终从一个节点走到下一个节点
- **条件边**：调用函数决定下一个（或下一批）节点

- **条件入口点**：用函数从 `START` 路由

</Warning>

## `Send`

当需要按条目逐个运行同一个节点、每次使用各自的输入，且条目数量只有运行时才知道时，请使用 @[`Send`]。这种形态常被称为 map-reduce 或 orchestrator-worker：一个节点生成列表，工作节点并行处理每个条目，随后由另一个节点读取汇总结果。

普通边无法做到这一点。普通边只选择接下来运行哪些节点，但每个被选中的节点仍然接收共享的图状态，而且拓扑在构建图时就已经固定。

从条件边返回一个或多个 `Send` 对象。每个 `Send` 指定目标节点，并传入一个自定义参数作为该次调用的输入。LangGraph 会并行运行这些调用。当工作节点写入共享状态键时，[reducer](#reducers) 会合并它们的更新，例如拼接列表。

`Send` 的第一个参数是目标节点名称，第二个参数是该次调用的状态（或局部状态）。

## `Command`

当单个步骤必须同时更新状态并选择接下来运行什么时，请使用 @[`Command`]。通常这两件事是分开的：节点返回状态更新，由[边](#edges)（或[条件边](#conditional-edges)）决定下一个节点。如果下一跳取决于当前函数刚完成的工作，就从节点返回 `Command`。

`Command` 还覆盖普通返回值和边无法处理的两个场景：在 [interrupt](/oss/langgraph/interrupts) 之后恢复运行，以及在[工具](#return-from-tools)内部更新或路由。

如果只需要路由，优先使用条件边。需要把更新和路由放在一起时（或属于上述 interrupt / 工具场景），再使用 `Command`。

`Command` 接受：

- **`update`**：状态更新（类似普通的节点返回值）
- **`goto`**：下一个（或下一批）节点（类似条件边）
- **`graph`**：从[子图](/oss/langgraph/use-subgraphs)导航时指定的父图目标
- **`resume`**：在 [interrupt](/oss/langgraph/interrupts) 之后恢复运行所用的值

`Command` 有三种使用位置：

- **[从节点返回](#return-from-nodes)**：`update`、`goto` 和 `graph`
- **[作为 `invoke` 或 `stream` 的输入](#input-to-invoke-or-stream)**：interrupt 之后使用 `resume`
- **[从工具返回](#return-from-tools)**：在工具内部更新状态并路由

```python
}), config)  # [!code --]

# Correct: plain dict restarts from START
graph.invoke({  # [!code ++]
    "messages": [{"role": "user", "content": "follow up"}]  # [!code ++]
}, config)  # [!code ++]
```
</Warning>

## 图的迁移

即使 [checkpointer](/oss/langgraph/persistence) 已经保存了 thread 状态，也可以修改图的节点、边和状态 schema。哪些改动是安全的，取决于 thread 已经结束还是处于暂停状态。

**拓扑（节点和边）**

- 已结束的 thread（未被 interrupt）：可以自由增删或重命名节点和边。
- 处于 interrupt 的 thread：可以修改边、添加节点。不要重命名或删除该 thread 即将进入的节点。恢复时，LangGraph 按名称查找该节点，名称缺失会导致运行失败。

**状态 schema**

- 增删键向前和向后兼容。
- 重命名键会丢弃已有 thread 中该键保存的值。
- 对已有键做不兼容的类型变更（例如收窄类型，或要求旧 checkpoint 中缺失的字段）可能破坏旧 thread 的状态。

如果逻辑变更保持 schema 兼容（例如更换工具集），请参阅[业务兼容性](/oss/langgraph/backward-compatibility#business-compatibility)。
