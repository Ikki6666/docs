使用 [Functional API](/oss/langgraph/functional-api) 构建 agent 时，你把流程拆成称为 **task** 的离散工作单元。然后在 **entrypoint** 中用普通的语言控制流（`if`/`else`、循环和函数调用）组合这些 task。值以返回值的形式在 task 之间传递，而不是通过共享的图状态 schema。

本篇 walkthrough 用 Functional API 构建一个客户支持邮件 agent。同一场景使用 Graph API 的实现请参阅 [用 Graph API 思考](/oss/langgraph/thinking-in-graph-api)。要在两种 API 之间做选择，请参阅 [在 Graph API 和 Functional API 之间选择](/oss/langgraph/choosing-apis)。

## 从你要自动化的流程开始

假设你需要构建一个 AI agent 来处理客户支持邮件。产品团队给你的需求如下：

```txt
The agent should:

- Read incoming customer emails
- Classify them by urgency and topic
- Search relevant documentation to answer questions
- Draft appropriate responses
- Escalate complex issues to human agents

Example scenarios to handle:

1. Simple product question: "How do I reset my password?"
2. Bug report: "The export feature crashes when I select PDF format"
3. Urgent billing issue: "I was charged twice for my subscription!"
4. Feature request: "Can you add dark mode to the mobile app?"
5. Complex technical issue: "Our API integration fails intermittently with 504 errors"
```

要用 Functional API 实现一个 agent，请遵循下面五个步骤。第 1 步和第 2 步是规划。第 3 步到第 5 步把这个规划变成可运行的类型、task 和 entrypoint。

## 第 1 步：把工作流拆成离散步骤

先识别流程中的不同步骤。每一步都会变成一个 **task**（只负责做一件事的函数）。然后画出 entrypoint 如何调用这些 task 以及如何分支。请在写代码之前完成这一步。

![Functional API 控制流：左侧收集和起草，右侧审核和发送](/images/langgraph-functional-thinking-flow.svg)

这张草图对应 entrypoint：左侧是顺序调用和 `if`/`else`，右侧是人工审核。Graph API 会把相同的路径编码成 node 和 edge。

组件识别完成后，接下来明确每个步骤需要做什么：

- `Read Email`：提取并解析邮件内容
- `Classify Intent`：使用 LLM 对紧急程度和主题进行分类
- `Doc Search`：在知识库中查询相关信息
- `Bug Track`：在跟踪系统中创建或更新 issue
- `Draft Reply`：生成合适的回复
- `Human Review`：升级给人工客服进行审批或处理
- `Send Reply`：发送邮件回复

<Tip>
有些步骤总是按顺序运行（`Read Email` 之后是 `Classify Intent`）。另一些则是有条件的（`Doc Search` 用于问题和功能请求，`Bug Track` 只用于 bug）。在 entrypoint 中用普通控制流编码这些分支。
</Tip>

### LLM 步骤

当某一步需要理解、分析、生成文本或做推理决策时：

<AccordionGroup>
    <Accordion title="Classify intent">
        - 静态上下文（prompt）：分类类别、紧急程度定义、响应格式
        - 动态上下文（arguments）：邮件内容、发件人信息
        - 目标结果：可驱动后续分支的结构化分类
    </Accordion>

    <Accordion title="Draft reply">
        - 静态上下文（prompt）：语气指南、公司政策、回复模板
        - 动态上下文（arguments）：分类结果、搜索结果
        - 目标结果：可供审核的专业邮件回复
    </Accordion>
</AccordionGroup>

### 数据步骤

当某一步需要从外部来源检索信息时：

<AccordionGroup>
    <Accordion title="Document search">
        - 参数：根据 intent 和 topic 构造的查询
        - 重试策略：需要，针对短暂失败使用指数退避
        - 缓存：可以缓存常见查询，以减少 API 调用
    </Accordion>
</AccordionGroup>

### 动作步骤

当某一步需要执行外部动作时：

<AccordionGroup>
    <Accordion title="Send reply">
        - 执行时机：审批之后（人工或自动）
        - 重试策略：需要，针对网络问题使用指数退避
        - 不应缓存：每次发送都是一次独立动作
    </Accordion>

    <Accordion title="Bug track">
        - 执行时机：只要 intent 是 "bug" 就执行
        - 重试策略：需要，不能丢失 bug 报告
        - 返回值：包含在回复中的 ticket ID
    </Accordion>
</AccordionGroup>

### 用户输入步骤

当某一步需要人工介入时：

<AccordionGroup>
    <Accordion title="Human review">
        - 决策上下文：原始邮件、草稿回复、紧急程度、分类结果
        - 预期输入格式：审批布尔值，外加可选的编辑后回复
        - 触发条件：高紧急度、复杂问题或质量疑虑
    </Accordion>
</AccordionGroup>

## 第 3 步：决定在 task 之间传递哪些数据

在 Functional API 中，没有共享的图状态 schema。每个 task 接收参数并返回一个值。entrypoint 用局部变量保存中间结果，并把它们传给下一个 task。

针对每一条数据，问自己下面这些问题：

<CardGroup cols={2}>
    <Card title="跨 task 共享" icon="check">
        后续的 task 需要这个值吗？如果需要，就从创建它的 task 中 **返回** 它，存到 entrypoint 的局部变量里，再把它作为参数 **传递** 给需要它的 task。
    </Card>

    <Card title="留在单个 task 内部" icon="code">
        它只用于在某个 task 内格式化 prompt 或发起调用吗？如果是，就保留在该 task 的局部作用域内。不要返回它。
    </Card>
</CardGroup>

对于 email agent，entrypoint 需要携带：

- 原始邮件和发件人信息（工作流的输入）
- 分类结果（后续分支和起草步骤需要）
- 搜索结果（重新获取成本高）
- 草稿回复（审核和发送过程中都需要）

<Tip>
保存并传递原始数据，而不是格式化后的 prompt 文本。在调用模型的 task 内部格式化 prompt。这样 task 可以复用，checkpoint 也更容易检查。
</Tip>

为 task 之间交换的值定义类型。它们是普通的 TypedDict 或 TypeScript 类型，不是 Graph API 的 state schema。现在就把它们加入文件；后续步骤中的 task 和 entrypoint 会用到。

:::python
```python
from typing import Literal, TypedDict


class EmailClassification(TypedDict):
    intent: Literal["question", "bug", "billing", "feature", "complex"]
    urgency: Literal["low", "medium", "high", "critical"]
    topic: str
    summary: str


class EmailInput(TypedDict):
    email_content: str
    sender_email: str
```
:::

:::js
```typescript
type EmailClassification = {
  intent: "question" | "bug" | "billing" | "feature" | "complex";
  urgency: "low" | "medium" | "high" | "critical";
  topic: string;
  summary: string;
};

type EmailInput = {
  emailContent: string;
  senderEmail: string;
};
```
:::

## 第 4 步：构建你的 task

把第 1 步中的每个工作单元变成一个 task。Task 会独立保存 checkpoint，可以在失败时重试，并返回 entrypoint 可以等待的值。

:::python
一个 @[`@task`] 是一个 Python 函数，它完成一个工作单元并返回结果。从 entrypoint 调用它，并用 `.result()`（在 async entrypoint 中用 `await`）解析结果。
:::

:::js
一个 @[`task`] 是一个函数，它完成一个工作单元并返回结果。从 entrypoint 调用它；调用会返回一个 promise，你可以 `await`。
:::

### 正确处理错误

在填充 task 主体之前，先考虑每个 task 可能如何失败。针对短暂性错误，在 task 上附加重试。需要人工输入时，在 entrypoint 中使用 `interrupt()`。可以用下表作为参考：

| 错误类型 | 谁来修复 | 策略 | 适用场景 |
|------------|--------------|----------|-------------|
| 短暂性错误（网络问题、限流） | 系统（自动） | task 上的重试策略 | 通常重试后能恢复的临时失败 |
| LLM 可恢复错误（工具失败、解析问题） | LLM | 返回错误，并在 entrypoint 中分支或重试 | 模型可以借助更多上下文调整做法 |
| 用户可修复错误（缺少信息、指令不清） | 人工 | 用 `interrupt()` 暂停 | 需要用户输入才能继续 |
| 未预期错误 | 开发者 | 让运行失败 | 需要修改代码的 bug |

### 实现 email agent 的 task

为第 1 步中的每个步骤添加一个 task（人工审核除外，它在第 5 步的 entrypoint 中使用 `interrupt()`）。下面的 stub 展示了 email agent 的函数签名、返回结构和重试策略。把占位符主体替换为真实的 LLM 调用和 API 集成。把这些 task 与第 3 步的类型放在同一个文件中。

这里的 `read_email` 是一个透传。把它保留为独立的 task，仍然可以在分类前获得一个 checkpoint，并为以后添加真正的 MIME 解析留出位置。

:::python
```python
from langgraph.func import task
from langgraph.types import RetryPolicy


@task
def read_email(email_content: str, sender_email: str) -> dict:
    """Parse and normalize the incoming email."""
    return {
        "email_content": email_content,
        "sender_email": sender_email,
    }


@task
def classify_intent(email_content: str, sender_email: str) -> EmailClassification:
    """Classify intent and urgency with an LLM."""
    # Placeholder: replace with a real LLM call.
    # This heuristic matches the try-out sample so interrupt() runs.
    lowered = email_content.lower()
    if "charged" in lowered or "billing" in lowered:
        return {
            "intent": "billing",
            "urgency": "high",
            "topic": "billing",
            "summary": "Customer reports a billing problem",
        }
    if "crash" in lowered or "bug" in lowered:
        return {
            "intent": "bug",
            "urgency": "medium",
            "topic": "product bug",
            "summary": "Customer reports a bug",
        }
    return {
        "intent": "question",
        "urgency": "low",
        "topic": "general",
        "summary": "Customer question",
    }


@task(retry_policy=RetryPolicy(max_attempts=3))
def search_documentation(topic: str, summary: str) -> list[str]:
    """Query the knowledge base for relevant chunks."""
    return [f"Docs related to {topic}"]


@task(retry_policy=RetryPolicy(max_attempts=3))
def create_bug_ticket(
    email_content: str, sender_email: str, summary: str
) -> str:
    """Create a ticket and return its ID."""
    return "TICKET-123"


@task
def draft_response(
    email_content: str,
    classification: EmailClassification,
    context: list[str],
) -> str:
    """Draft a reply from the email, classification, and gathered context."""
    return f"Thanks for your email about {classification['topic']}."


@task
def send_reply(draft: str, sender_email: str) -> None:
    """Send the approved reply."""
    return None
```

现在你已经有了可调用的 task。接下来，在 entrypoint 中组合它们。

## 第 5 步：组合 entrypoint

entrypoint 就是工作流。把它加在 task 下面。它按顺序调用这些 task，用 `if`/`else` 分支（来自第 1 步的控制流），并用 `interrupt()` 为人工暂停。需要持久化执行和 human-in-the-loop 时，请提供 [checkpointer](/oss/langgraph/persistence)。

:::python
```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint
from langgraph.types import interrupt

checkpointer = InMemorySaver()


@entrypoint(checkpointer=checkpointer)
def email_agent(inputs: EmailInput) -> dict:
    parsed = read_email(inputs["email_content"], inputs["sender_email"]).result()
    classification = classify_intent(
        parsed["email_content"], parsed["sender_email"]
    ).result()

    context: list[str] = []
    if classification["intent"] in ("question", "feature"):
        context = search_documentation(
            classification["topic"], classification["summary"]
        ).result()
    elif classification["intent"] == "bug":
        ticket_id = create_bug_ticket(
            parsed["email_content"],
            parsed["sender_email"],
            classification["summary"],
        ).result()
        context = [f"Ticket created: {ticket_id}"]

    draft = draft_response(
        parsed["email_content"], classification, context
    ).result()

    # Pause for human review on billing, urgent, or complex issues
    if (
        classification["intent"] in ("billing", "complex")
        or classification["urgency"] in ("high", "critical")
    ):
        human_decision = interrupt(
            {
                "email_content": parsed["email_content"],
                "draft_response": draft,
                "classification": classification,
            }
        )
        if not human_decision.get("approved"):
            return {"status": "escalated", "draft": draft}
        draft = human_decision.get("edited_response", draft)

    send_reply(draft, parsed["sender_email"]).result()
    return {"status": "sent", "draft": draft, "classification": classification}
```
:::

:::js
```typescript
import {
  MemorySaver,
  entrypoint,
  interrupt,
} from "@langchain/langgraph";

const checkpointer = new MemorySaver();

const emailAgent = entrypoint(
  { checkpointer, name: "emailAgent" },
  async (inputs: EmailInput) => {
    const parsed = await readEmail(inputs.emailContent, inputs.senderEmail);
    const classification = await classifyIntent(
      parsed.emailContent,
      parsed.senderEmail
    );

    let context: string[] = [];
    if (
      classification.intent === "question" ||
      classification.intent === "feature"
    ) {
      context = await searchDocumentation(
        classification.topic,
        classification.summary
      );
    } else if (classification.intent === "bug") {
      const ticketId = await createBugTicket(
        parsed.emailContent,
        parsed.senderEmail,
        classification.summary
      );
      context = [`Ticket created: ${ticketId}`];
    }

    let draft = await draftResponse(
      parsed.emailContent,
      classification,
      context
    );

    // Pause for human review on billing, urgent, or complex issues
    if (
      classification.intent === "billing" ||
      classification.intent === "complex" ||
      classification.urgency === "high" ||
      classification.urgency === "critical"
    ) {
      const humanDecision = interrupt({
        emailContent: parsed.emailContent,
        draftResponse: draft,
        classification,
      });
      if (!humanDecision?.approved) {
        return { status: "escalated", draft };
      }
      draft = humanDecision.editedResponse ?? draft;
    }

    await sendReply(draft, parsed.senderEmail);
    return { status: "sent", draft, classification };
  }
);
```
:::

### 试运行你的 agent

entrypoint 定义好后，用一封示例邮件调用它。使用上面的占位分类器时，这封紧急账单邮件会被视为高紧急度，因此运行会触发 `interrupt()`，你可以练习恢复。首次调用和恢复调用请使用同一个 `thread_id`。

:::python
```python
from langgraph.types import Command

config = {"configurable": {"thread_id": "customer_123"}}

result = email_agent.invoke(
    {
        "email_content": "I was charged twice for my subscription! This is urgent!",
        "sender_email": "customer@example.com",
    },
    config,
)
# The workflow pauses at interrupt() when urgency is high

# Resume with the human decision
email_agent.invoke(
    Command(
        resume={
            "approved": True,
            "edited_response": "We sincerely apologize for the double charge. I've initiated an immediate refund...",
        }
    ),
    config,
)
```
:::

:::js
```typescript
import { Command } from "@langchain/langgraph";

const config = { configurable: { thread_id: "customer_123" } };

const result = await emailAgent.invoke(
  {
    emailContent: "I was charged twice for my subscription! This is urgent!",
    senderEmail: "customer@example.com",
  },
  config

// The workflow pauses at interrupt() when urgency is high

// Resume with the human decision

  new Command({
    resume: {

      editedResponse:

```
:::

工作流在 `interrupt()` 处暂停，把已完成的 task 结果保存到 checkpointer，然后等待。当你用 `Command(resume=...)` 恢复时，已完成的 task 会从 checkpoint 重新加载，而不是重新运行。`thread_id` 会把这段对话的状态保存在一起。

### Task 粒度权衡

大多数应用可以使用上面的拆分方式。当你在决定是否合并或拆分 task 时，再阅读本节。

LangGraph 在 entrypoint 内的 **task** 边界处 checkpoint。当运行在 interrupt 或失败后恢复时，已完成的 task 结果会从 checkpoint 加载。放在 entrypoint 函数体中、task 之外的工作可能会再次运行。

为什么这种拆分适合 email agent：

- **外部服务隔离：** Doc search 和 bug tracking 是独立的 task，因此重试和失败被限制在这些 API 调用范围内。
- **可见性：** 分类是独立的 task，因此你可以在分支之前检查结构化结果。
- **不同的失败模式：** LLM 调用、数据库查询和邮件发送使用不同的重试策略。
- **测试：** 更小的 task 更容易做单元测试和复用。

把 `read_email` 和 `classify_intent` 合并成一个 task 也是可行的。这样会失去两者之间的 checkpoint，失败时要重复执行这两个操作。对大多数 agent 来说，独立 task 带来的可观测性收益值得这点代价。
