## 概览

构建 agent 的难点在于让它们足够可靠。它们可能在原型阶段表现不错，但在真实场景里经常失效。

### 为什么 agent 会失败？

agent 失败时，通常是因为 agent 里的 LLM 调用做错了动作，或者没有按预期完成任务。LLM 失败通常有两个原因：

1. 底层 LLM 能力不够强
2. 没有把“正确”的上下文传给 LLM

很多时候，真正导致 agent 不可靠的是第二个原因。

**上下文工程（context engineering）** 是把正确的信息和工具，以正确的格式提供给 LLM，让它完成任务。这是 AI 工程师最重要的工作之一。缺少“正确”上下文，是让 agent 更可靠的头号阻碍，而 LangChain 的 agent 抽象就是专门为支持上下文工程而设计的。

<Tip>
如果你刚接触上下文工程，先看 [概念总览](/oss/concepts/context)，了解不同类型的上下文，以及它们各自的使用时机。
</Tip>

### agent 循环

一个典型的 agent 循环由两个主要步骤组成：

1. **模型调用** - 用 prompt 和可用工具调用 LLM，返回响应或执行工具的请求
2. **工具执行** - 执行 LLM 请求的工具，返回工具结果

### 你可以控制什么

要构建可靠的 agent，你需要控制 agent 循环每一步发生什么，以及各步骤之间发生什么。

| 上下文类型 | 你控制什么 | 短期还是持久化 |
|--------------|------------------|-------------------------|
| **[模型上下文](#model-context)** | 进入模型调用的内容（指令、消息历史、工具、响应格式） | 短期 |
| **[工具上下文](#tool-context)** | 工具能访问和产出什么（对 state、store、runtime context 的读写） | 持久化 |
| **[生命周期上下文](#life-cycle-context)** | 模型调用和工具调用之间发生什么（摘要、guardrail、日志等） | 持久化 |

### 数据来源

在这个过程中，agent 会访问（读 / 写）不同的数据来源：

| 数据来源 | 也称为 | 范围 | 示例 |
|-------------|---------------|-------|----------|
| **Runtime Context** | 静态配置 | 对话范围 | 用户 ID、API keys、数据库连接、权限、环境设置 |
| **State** | 短期记忆 | 对话范围 | 当前消息、上传文件、认证状态、工具结果 |
| **Store** | 长期记忆 | 跨对话 | 用户偏好、提取的洞见、记忆、历史数据 |

### 它是如何工作的

LangChain [middleware](/oss/langchain/middleware) 是底层机制，让上下文工程对使用 LangChain 的开发者真正可用。

middleware 允许你在 agent 生命周期的任一步骤中进行钩入，并：

* 更新上下文
* 跳转到 agent 生命周期中的另一步骤

在本指南里，你会频繁使用 middleware API，把它作为实现上下文工程目标的手段。

## 模型上下文

控制每次模型调用里包含什么内容，例如指令、可用工具、要用哪个模型，以及输出格式。这些决策会直接影响可靠性和成本。

### System Prompt

system prompt 决定 LLM 的行为和能力。不同用户、不同上下文或不同对话阶段都需要不同的指令。成功的 agent 会结合记忆、偏好和配置，为当前对话状态提供正确的指令。

    ```python
    from langchain.agents import create_agent

        message_count = len(request.messages)

        if message_count > 10:
            base += "\nThis is a long conversation - be extra concise."

        return base

    agent = create_agent(
        model="gpt-5.5",
        tools=[...],
        middleware=[state_aware_prompt]
    )
    ```

### Messages

Messages 构成了发送给 LLM 的 prompt。
管理 messages 的内容非常关键，因为这能确保 LLM 拿到足够的信息，给出更好的回复。

<Tabs>
  <Tab title="State">
    当当前查询相关时，从 State 注入上传文件的上下文：

    :::python

    ```python
    from langchain.agents import create_agent
    from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
    from typing import Callable

    @wrap_model_call
    def inject_file_context(
        request: ModelRequest,
        handler: Callable[[ModelRequest], ModelResponse]
    ) -> ModelResponse:
        """Inject context about files user has uploaded this session."""
        # Read from State: get uploaded files metadata
        uploaded_files = request.state.get("uploaded_files", [])  # [!code highlight]

        if uploaded_files:
            # Build context about available files
            file_descriptions = []
            for file in uploaded_files:
                file_descriptions.append(
                    f"- {file['name']} ({file['type']}): {file['summary']}"
                )

            file_context = f"""Files you have access to in this conversation:
{chr(10).join(file_descriptions)}

Reference these files when answering questions."""

            # Inject file context before recent messages
            messages = [  # [!code highlight]
                *request.messages,
                {"role": "user", "content": file_context},
            ]
            request = request.override(messages=messages)  # [!code highlight]

        return handler(request)

    agent = create_agent(
        model="gpt-5.5",
        tools=[...],
        middleware=[inject_file_context]
    )
    ```
    :::

    :::js
    ```typescript
    import { createMiddleware } from "langchain";

    const injectFileContext = createMiddleware({
      name: "InjectFileContext",
      wrapModelCall: (request, handler) => {
        // request.state is a shortcut for request.state.messages
        const uploadedFiles = request.state.uploadedFiles || [];  // [!code highlight]

        if (uploadedFiles.length > 0) {
          // Build context about available files
          const fileDescriptions = uploadedFiles.map(file =>
            `- ${file.name} (${file.type}): ${file.summary}`
          );

          const fileContext = `Files you have access to in this conversation:
${fileDescriptions.join("\n")}

Reference these files when answering questions.`;

          // Inject file context before recent messages
          const messages = [  // [!code highlight]
            ...request.messages,  // Rest of conversation
            { role: "user", content: fileContext }
          ];
          request = request.override({ messages });  // [!code highlight]
        }

        return handler(request);
      },
    });

    const agent = createAgent({
      model: "gpt-5.5",
      tools: [...],
      middleware: [injectFileContext],
    });
    ```

    ```python
    from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse

        handler: Callable[[ModelRequest], ModelResponse]

{style.get('example_email', '')}"""

            messages = [

                {"role": "user", "content": style_context}

            request = request.override(messages=messages)  # [!code highlight]

        return handler(request)

    agent = create_agent(

        middleware=[inject_writing_style],

        store=InMemoryStore()
    ```

<Note>
**瞬时更新 vs 持久化更新：**

上面的示例使用 `wrap_model_call` 来做 **瞬时** 更新，也就是只修改单次模型调用实际看到的 messages，而不改写 state 里保存的内容。

如果你需要 **持久化** 更新，可以：

:::python
- 在 `wrap_model_call` 中返回带有 @[`Command`] 的 @[`ExtendedModelResponse`]，从模型调用层写入 state 更新。
- 使用生命周期 hooks，例如 `before_model`、`after_model` 或 `wrap_tool_call`（处理 tool 返回）来更新对话历史。更多细节请参见 [middleware 文档](/oss/langchain/middleware)。
:::

:::js
- 在 `wrapModelCall` 中直接返回 @[`Command`]，从模型调用层写入 state 更新。
- 使用生命周期 hooks，例如 `beforeModel`、`afterModel` 或 `wrapToolCall`（处理 tool 返回）来更新对话历史。更多细节请参见 [middleware 文档](/oss/langchain/middleware)。
:::

更多内容请参见 [State updates](/oss/langchain/middleware/custom#state-updates)。
</Note>

### Tools

工具让模型可以和数据库、API 以及外部系统交互。你如何定义和选择工具，会直接影响模型能否高效完成任务。

#### 定义工具

每个工具都需要清晰的名称、描述、参数名和参数描述。这些不只是元数据，它们会影响模型对何时、如何使用工具的判断。

:::python
```python
from langchain.tools import tool

@tool(parse_docstring=True)
def search_orders(
    user_id: str,
    status: str,
    limit: int = 10
) -> str:
    """Search for user orders by status.

    Use this when the user asks about order history or wants to check
    order status. Always filter by the provided status.

    Args:
        user_id: Unique identifier for the user
        status: Order status: 'pending', 'shipped', or 'delivered'
        limit: Maximum number of results to return
    """
    # Implementation here
    pass
```
:::

:::js
```typescript
import { tool } from "@langchain/core/tools";
import { z } from "zod";

const searchOrders = tool(
  async ({ userId, status, limit }) => {
    // Implementation here
  },
  {
    name: "search_orders",
    description: `Search for user orders by status.

    Use this when the user asks about order history or wants to check
    order status. Always filter by the provided status.`,
    schema: z.object({
      userId: z.string().describe("Unique identifier for the user"),
      status: z.enum(["pending", "shipped", "delivered"]).describe("Order status to filter by"),
      limit: z.number().default(10).describe("Maximum number of results to return"),
    }),
  }
);
```
:::

#### 选择工具

并非每个工具都适用于每种场景。工具太多会让模型负担过重、增加错误；工具太少又会限制能力。动态工具选择会根据认证状态、用户权限、功能开关或对话阶段来调整可用工具集。

<Tabs>
  <Tab title="State">
    只在达到某些对话里程碑后才启用高级工具：

    :::python

    ```python
    from langchain.agents import create_agent
    from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
    from typing import Callable

    @wrap_model_call
    def state_based_tools(
        request: ModelRequest,
        handler: Callable[[ModelRequest], ModelResponse]
    ) -> ModelResponse:
        """Filter tools based on conversation State."""
        # Read from State: check if user has authenticated
        state = request.state  # [!code highlight]
        is_authenticated = state.get("authenticated", False)  # [!code highlight]
        message_count = len(state["messages"])

        # Only enable sensitive tools after authentication
        if not is_authenticated:
            tools = [t for t in request.tools if t.name.startswith("public_")]
            request = request.override(tools=tools)  # [!code highlight]
        elif message_count < 5:
            # Limit tools early in conversation
            tools = [t for t in request.tools if t.name != "advanced_search"]
            request = request.override(tools=tools)  # [!code highlight]

        return handler(request)

    agent = create_agent(
        model="gpt-5.5",
        tools=[public_search, private_search, advanced_search],
        middleware=[state_based_tools]
    )
    ```

### Response format

Structured output can transform unstructured text into validated, structured data. When you need specific fields or output for downstream systems, free-form text is not enough.

**How it works:** When you provide a schema as the response format, the model's final response is guaranteed to conform to that schema. The agent runs the model/tool loop until the model is done calling tools, then coerces the final response into the provided format.

#### Defining formats

Schema definitions guide the model. Field names, types, and descriptions specify exactly what format the output should follow.

:::python
```python
from pydantic import BaseModel, Field

class CustomerSupportTicket(BaseModel):
    """Structured ticket information extracted from customer message."""

    category: str = Field(
        description="Issue category: 'billing', 'technical', 'account', or 'product'"
    )
    priority: str = Field(
        description="Urgency level: 'low', 'medium', 'high', or 'critical'"
    )
    summary: str = Field(
        description="One-sentence summary of the customer's issue"
    )
    customer_sentiment: str = Field(
        description="Customer's emotional tone: 'frustrated', 'neutral', or 'satisfied'"
    )
```

### Tool context

Tools can also use context to access short-term memory, long-term memory, and runtime settings. This makes it possible to write tools that are aware of the current conversation, user, and deployment environment.

### Life-cycle context

Life-cycle context refers to what happens between model calls and tool calls. This includes summarization, guardrails, logging, retries, and other middleware-driven behavior.

### Best practices

1. **Start with static context** - Add dynamics only where they clearly improve reliability.
2. **Keep context small** - Send only the information the model needs for the current turn.
3. **Choose the right storage layer** - Use State for short-term conversation data and Store for durable memory.
4. **Prefer built-in middleware** - Reuse LangChain middleware before writing custom logic.
5. **Measure effects** - Check token usage, latency, and model behavior after every change.
6. **Separate transient from persistent updates** - Temporary prompt changes should not silently mutate state.
