多智能体系统会协调专门组件来处理复杂工作流。不过，并不是每个复杂任务都需要这种方式，一个带着合适工具和提示词的单智能体，通常也能达到类似效果。

<Tip>
要使用内置多智能体支持，请使用 [Deep Agents](/oss/deepagents/overview)：这是一个建立在 LangChain 之上的更高层框架，提供 [subagents](/oss/deepagents/subagents)、[skills](/oss/deepagents/skills)、规划、虚拟文件系统和上下文管理。
</Tip>

## 为什么需要多智能体？

开发者说他们需要“多智能体”时，通常是在寻找以下一种或多种能力：

- <Icon icon="brain" /> **上下文管理**：在不把模型上下文窗口塞满的情况下提供专门知识。如果上下文无限大、延迟为零，你当然可以把所有知识都塞进一个提示词里，但现实并不是这样，所以你需要一些模式来选择性地暴露相关信息。
- <Icon icon="users" /> **分布式开发**：让不同团队独立开发和维护能力，再把它们组合成一个边界清晰的大系统。
- <Icon icon="git-branch" /> **并行化**：为子任务生成专门工作器，并发执行以更快得到结果。

当单个智能体拥有太多 [tools](/oss/langchain/tools) 而很难正确选择时，当任务需要带着大量上下文的专门知识时，或者当你需要强制顺序约束，只有满足某些条件后才能解锁能力时，多智能体模式就特别有价值。

<Tip>
多智能体设计的核心是 **[context engineering](/oss/langchain/context-engineering)**，也就是决定每个智能体能看到什么信息。系统质量取决于你是否能让每个智能体拿到完成任务所需的正确数据。
</Tip>

## 模式

下面是构建多智能体系统的主要模式，它们分别适合不同用例：

| 模式 | 工作方式 |
|--------------|--------------|
| [**Subagents**](/oss/langchain/multi-agent/subagents) | 由主智能体把子智能体当作工具来协调。所有路由都经过主智能体，由它决定何时以及如何调用每个子智能体。 |
| [**Handoffs**](/oss/langchain/multi-agent/handoffs) | 行为会根据状态动态变化。工具调用会更新一个状态变量，从而触发路由或配置变化，切换智能体或者调整当前智能体的工具和提示词。 |
| [**Skills**](/oss/langchain/multi-agent/skills) | 按需加载的专门提示词和知识。单个智能体保持控制权，同时在需要时从 skills 中加载上下文。 |
| [**Router**](/oss/langchain/multi-agent/router) | 通过一个路由步骤对输入分类，并把它导向一个或多个专门智能体。结果会合成为一个组合回复。 |
| [**Custom workflow**](/oss/langchain/multi-agent/custom-workflow) | 用 [LangGraph](/oss/langgraph/overview) 构建定制执行流，把确定性逻辑和智能体行为混合起来。你可以把其他模式嵌进工作流节点里。 |

### 选择模式

用这张表把你的需求和合适的模式对应起来：

<div className="compact-first-col">

| 模式 | 分布式开发 | 并行化 | 多跳 | 直接用户交互 |
|---------|:-----------------------:|:---------------:|:----------:|:-----------------------:|
| [**Subagents**](/oss/langchain/multi-agent/subagents) | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐ |
| [**Handoffs**](/oss/langchain/multi-agent/handoffs) | - | - | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| [**Skills**](/oss/langchain/multi-agent/skills) | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| [**Router**](/oss/langchain/multi-agent/router) | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | - | ⭐⭐⭐ |

</div>

- **分布式开发**：不同团队能否独立维护组件？
- **并行化**：多个智能体能否并发执行？
- **多跳**：该模式是否支持按顺序调用多个子智能体？
- **直接用户交互**：子智能体能否直接和用户对话？

<Tip>
    你可以混合不同模式！例如，**subagents** 架构可以调用会触发自定义工作流或 router 智能体的工具。Subagents 甚至可以使用 **skills** 模式按需加载上下文。可能性很多！
</Tip>

## 性能对比

不同模式有不同的性能特征。理解这些取舍能帮助你根据延迟和成本要求选择正确的模式。

**关键指标：**
- **模型调用次数**：LLM 调用数量。调用越多，延迟越高（尤其是顺序调用时），单次请求 API 成本也越高。
- **处理的 token 数**：所有调用中使用的 [context window](/oss/langchain/context-engineering) 总量。token 越多，处理成本越高，也越容易碰到上下文限制。

### 一次性请求

> **用户：** "Buy coffee"

专门的咖啡智能体或 skill 可以调用 `buy_coffee` 工具。

### 重复请求

> **第 1 轮：** "Buy coffee"
> **第 2 轮：** "Buy coffee again"

用户在同一段对话里重复了相同请求。

<div className="compact-first-col">

| 模式 | 第 2 轮调用次数 | 两轮总计 | 最适合 |
|---------|:------------:|:------------------:|:--------:|
| [**Subagents**](/oss/langchain/multi-agent/subagents) | 4 | 8 | |
| [**Handoffs**](/oss/langchain/multi-agent/handoffs) | 2 | 5 | ✅ |
| [**Skills**](/oss/langchain/multi-agent/skills) | 2 | 5 | ✅ |
| [**Router**](/oss/langchain/multi-agent/router) | 3 | 6 | |

</div>

<Tabs>
  <Tab title="Subagents">
    **再来 4 次调用 → 总计 8 次**

    - Subagents **天生无状态**，每次调用都会走同样的流程
    - 主智能体保留对话上下文，但子智能体每次都会从头开始
    - 这会提供强上下文隔离，但也会重复完整流程
  </Tab>

  <Tab title="Handoffs">
    **2 次调用 → 总计 5 次**

    - 咖啡智能体在第 1 轮后 **仍然处于活跃状态**（状态会保留）
    - 不需要 handoff，智能体直接调用 `buy_coffee` 工具（第 1 次调用）
    - 智能体回复用户（第 2 次调用）
    - **通过跳过 handoff 节省了 1 次调用**
  </Tab>

  <Tab title="Skills">
    **2 次调用 → 总计 5 次**

    - skill 上下文**已经加载**在对话历史里
    - 不需要重新加载，智能体直接调用 `buy_coffee` 工具（第 1 次调用）
    - 智能体回复用户（第 2 次调用）
    - **通过复用已加载的 skill 节省了 1 次调用**
  </Tab>

  <Tab title="Router">
    **再次 3 次调用 → 总计 6 次**

    - Router **无状态**，每次请求都需要一次 LLM 路由调用
    - 第 2 轮：Router LLM 调用（1）→ Milk agent 调用 buy_coffee（2）→ Milk agent 回复（3）
    - 可以通过把它封装成有状态智能体中的工具来优化
  </Tab>
</Tabs>

**关键洞察：** 有状态模式（Handoffs、Skills）在重复请求上可以节省 40-50% 的调用。Subagents 每次请求的成本保持一致，这种无状态设计提供了很强的上下文隔离，但代价是重复的模型调用。

### 多域场景

> **用户：** "比较 Python、JavaScript 和 Rust 在 Web 开发中的表现"

每个语言 agent / skill 都包含大约 2000 token 的文档。所有模式都可以并行发起 tool call。

| 模式 | 模型调用次数 | 总 token | 最适合 |
|---------|:-----------:|:------------:|:--------:|
| [**Subagents**](/oss/langchain/multi-agent/subagents) | 5 | ~9K | ✅ |
| [**Handoffs**](/oss/langchain/multi-agent/handoffs) | 7+ | ~14K+ | |
| [**Skills**](/oss/langchain/multi-agent/skills) | 3 | ~15K | |
| [**Router**](/oss/langchain/multi-agent/router) | 5 | ~9K | ✅ |

<Tabs>
  <Tab title="Subagents">
    **5 次调用 → 总计 9K token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-subagents.png" alt="Subagents 多域场景：5 次调用并行执行" />
    </Frame>

    每个 subagent 都在**隔离**环境中工作，只保留与自己相关的上下文。总计：**9K token**。
  </Tab>

  <Tab title="Handoffs">
    **7+ 次调用 → 总计 14K+ token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-handoffs.png" alt="Handoffs 多域场景：7+ 次串行调用" />
    </Frame>

    Handoffs 是**串行**执行的，没法并行研究三个语言。不断增长的对话历史还会带来额外开销。总计：**~14K+ token**。
  </Tab>

  <Tab title="Skills">
    **3 次调用 → 总计 15K token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-skills.png" alt="Skills 多域场景：3 次调用，累积上下文" />
    </Frame>

    一旦加载完成，**后续每次调用都会处理全部 6K token 的 skill 文档**。由于上下文隔离，Subagents 总体上少处理了 67% 的 token。总计：**15K token**。
  </Tab>

  <Tab title="Router">
    **5 次调用 → 总计 9K token**

    <Frame>
      <img src="/oss/langchain/multi-agent/images/multidomain-router.png" alt="Router 多域场景：5 次调用并行执行" />
    </Frame>

    Router 会先使用 **LLM 进行路由**，然后并行调用各个 agent。它和 Subagents 类似，但多了一个显式的路由步骤。总计：**9K token**。
  </Tab>
</Tabs>

**关键洞察：** 对于多域任务，支持并行执行的模式（Subagents、Router）最有效。Skills 的调用次数更少，但由于上下文会累积，所以 token 开销更高。Handoffs 在这里效率较低，因为它必须串行执行，没法利用并行 tool calling 同时咨询多个领域。

下面是三种场景下各模式的对比：
