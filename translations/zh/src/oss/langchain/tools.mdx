工具可以扩展 [agents](/oss/langchain/agents) 的能力，让它们获取实时数据、执行代码、查询外部数据库，并在现实世界中采取行动。

从底层看，tool 就是带有清晰输入和输出的可调用函数，会被传给 [chat model](/oss/langchain/models)。模型会根据对话上下文决定何时调用 tool，以及传入什么参数。

<Tip>
关于模型如何处理 tool call 的细节，请参见 [Tool calling](/oss/langchain/models#tool-calling)。你可以用 [LangSmith](https://smith.langchain.com) 跟踪 tool call 并调试错误。先按照 [tracing quickstart](/langsmith/trace-with-langchain) 完成接入。

我们还建议你配置 [LangSmith Engine](/langsmith/engine)，它可以监控 traces、检测问题，并提出修复建议。
</Tip>

## 创建工具

### 基础工具定义

:::python
创建 tool 最简单的方式是使用 @[`@tool`] 装饰器。默认情况下，函数的 docstring 会成为 tool 的 description，帮助模型理解何时使用它：

```python
from langchain.tools import tool

@tool
def search_database(query: str, limit: int = 10) -> str:
    """Search the customer database for records matching the query.

    Args:
        query: Search terms to look for
        limit: Maximum number of results to return
    """
    return f"Found {limit} results for '{query}'"
```

类型注解是**必须的**，因为它们定义了 tool 的输入 schema。docstring 应该简洁且信息充足，帮助模型理解 tool 的用途。
:::

:::js
创建 tool 最简单的方式是从 `langchain` package 导入 `tool` 函数。你可以使用 [zod](https://zod.dev/) 定义 tool 的输入 schema：

```ts
import * as z from "zod"
import { tool } from "langchain"

const searchDatabase = tool(
  ({ query, limit }) => `Found  results for ''`,
  {
    name: "search_database",
    description: "Search the customer database for records matching the query.",
    schema: z.object({
      query: z.string().describe("Search terms to look for"),
      limit: z.number().describe("Maximum number of results to return"),
    }),
  }
);
```

:::

<Note>
    **服务端工具使用：** 有些 chat model 提供内置工具，例如 web search 和 code interpreter，并在服务端执行这些工具。更多信息请参见 [Server-side tool use](#server-side-tool-use)。
</Note>

<Warning>
    工具名建议使用 `snake_case`，例如使用 `web_search`，不要使用 `Web Search`。有些模型提供商会因为工具名包含空格或特殊字符而报错或拒绝请求。坚持使用字母数字字符、下划线和连字符，有助于提升跨提供商兼容性。
</Warning>

:::python

### 自定义工具属性

#### 自定义工具名称

默认情况下，工具名称来自函数名。需要更有描述性的名称时，可以覆盖它：

```python
@tool("web_search")  # Custom name
def search(query: str) -> str:
    """Search the web for information."""
    return f"Results for: {query}"

print(search.name)  # web_search
```

#### 自定义工具描述

覆盖自动生成的工具描述，让模型指引更清晰：

```python
@tool("calculator", description="Performs arithmetic calculations. Use this for any math problems.")
def calc(expression: str) -> str:
    """Evaluate mathematical expressions."""
    return str(eval(expression))
```

### 高级 schema 定义

使用 Pydantic model 或 JSON schema 定义复杂输入：

<CodeGroup>
    ```python Pydantic model
    from pydantic import BaseModel, Field
    from typing import Literal

    class WeatherInput(BaseModel):
        """Input for weather queries."""
        location: str = Field(description="City name or coordinates")
        units: Literal["celsius", "fahrenheit"] = Field(
            default="celsius",
            description="Temperature unit preference"
        )
        include_forecast: bool = Field(
            default=False,
            description="Include 5-day forecast"
        )

    @tool(args_schema=WeatherInput)
    def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
        """Get current weather and optional forecast."""
        temp = 22 if units == "celsius" else 72
        result = f"Current weather in {location}: {temp} degrees {units[0].upper()}"
        if include_forecast:
            result += "\nNext 5 days: Sunny"
        return result
    ```

    ```python JSON Schema
    weather_schema = {
        "type": "object",
        "properties": {
            "location": {"type": "string"},
            "units": {"type": "string"},
            "include_forecast": {"type": "boolean"}
        },
        "required": ["location", "units", "include_forecast"]
    }

    @tool(args_schema=weather_schema)
    def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
        """Get current weather and optional forecast."""
        temp = 22 if units == "celsius" else 72
        result = f"Current weather in {location}: {temp} degrees {units[0].upper()}"
        if include_forecast:
            result += "\nNext 5 days: Sunny"
        return result
    ```

### 保留参数名

以下参数名是保留名，不能用作工具参数。使用这些名称会导致运行时错误。

| Parameter name | Purpose |
|----------------|---------|
| `config` | Reserved for passing `RunnableConfig` to tools internally |
| `runtime` | Reserved for `ToolRuntime` parameter (accessing state, context, store) |

如需访问运行时信息，请使用 @[`ToolRuntime`] 参数，而不是把自己的参数命名为 `config` 或 `runtime`。

如果你使用 `InjectedState`、`InjectedStore`、`get_runtime()` 或 `InjectedToolCallId`，请参见 [Migrate from older injection patterns](#migrate-from-older-injection-patterns)。
:::

## 无头工具

有些工具应该在**用户应用运行的地方**执行，通常是浏览器，而不是在进程内部执行。**无头工具（headless tools）** 是一种 tool 定义，它包含 name、description 和参数 schema，由你在**服务端**和 agent 一起注册。真正的**实现**只在**客户端**注册，并在一次短暂的 interrupt/resume 握手之后执行。

这和普通工具不同，普通工具的函数体是在服务端运行的；它也不同于 [server-side tool use](#server-side-tool-use)，后者是模型提供商在远程执行内置工具。

### 何时使用无头工具

当工作依赖于只有客户端才有的**环境、设备或 UI**时就使用它们。例如：

- **Browser APIs:** Geolocation、IndexedDB、Clipboard、Canvas 2D、文件选择器、Battery API 等。
- **隐私和本地性:** 数据保留在设备上，例如存储在 IndexedDB 里的本地“memory”。
- **延迟:** 对纯本地操作，不需要额外的服务端往返。
- **结构化、安全的副作用:** 更适合使用许多小而类型明确的工具，例如每个 canvas primitive 一个工具，而不是把任意代码发给 `eval`。

### 这个模式如何工作

在两个运行时里，模型看到的都是一个正常可调用的 tool，但真正的执行发生在服务端进程之外。

:::python
1. **定义** 一个 headless tool，使用 `langchain.tools` 里的 `tool(name=..., description=..., args_schema=...)`。headless tool 只有 schema，没有进程内实现。
2. **注册** 这个 tool 到 `create_agent` 或你的 LangGraph graph，这样模型就能正常调用它。
3. **处理** 工具被调用时的 interrupt payload。图不会在本地执行，而是暂停，并返回一个形如 `{"type": "tool", "tool_call": {"id", "name", "args"}}` 的 payload。
4. **恢复** 图的执行，在你的应用、另一个服务，或人工步骤完成动作之后再继续。对于基于浏览器的流程，你也可以在前端镜像这个 schema，并在那里挂上 `.implement(...)`。

<Info>
    如果你在 Python 中调用 `tool(...)`，只传 `name`、`description` 和 `args_schema`，LangChain 返回的是 `HeadlessTool`。Python 侧没有 `.implement()` API。
</Info>
:::

:::js
1. **定义** tool，使用 `langchain` 里的 `tool({ name, description, schema })`。这里仅提供元数据和校验，没有服务端 runner。
2. **挂接** 真实行为，用 `.implement(async (args) => { ... })`，它会返回一个 **headless tool implementation**（定义 + `execute` 函数）。
3. **注册** 第 1 步里的定义到 `createAgent` 或你的 graph，这样模型就能在标准 tool-calling loop 中看到这个 tool。
4. **把** 第 2 步的 implementation 传给 streaming hook 的 `tools` 选项。

<Info>
    把**工具定义**（`tool({ name, description, schema })`）和**实现**（`.implement(...)`）放在**不同模块**里。服务端 agent 和前端都从共享定义文件导入，这样 name 和 schema 保持一致；把只在客户端运行的 execute 逻辑放进服务端永远不会加载的 implementation 模块。
</Info>
:::

当模型对这些工具发出 tool call 时，运行会**中断**，而不是在本地执行工具。你的应用可以检查 payload、在正确环境里执行动作，例如浏览器、另一个服务或人工 review，然后用 tool result **恢复** graph。使用受支持的 JS SDK hooks 时，它们可以检测 headless-tool interrupt、运行匹配的客户端实现，并自动提交 resume command。

你可以使用可选的 **`onTool`** 回调来观察生命周期事件（`start`、`success`、`error`），用于 spinner 或 toast 这类 UI 反馈。

## 服务端工具使用

有些 chat model 提供由模型提供商在服务端执行的内置工具。这类能力包括 web search 和 code interpreter，不需要你自己定义或托管工具逻辑。

### Stream writer

在工具执行期间流式输出实时更新。这对长时间运行的操作提供进度反馈很有用。

:::python
使用 `runtime.stream_writer` 输出自定义更新：

```python
from langchain.tools import tool, ToolRuntime

@tool
def get_weather(city: str, runtime: ToolRuntime) -> str:
    """Get weather for a given city."""
    writer = runtime.stream_writer

    # Stream custom updates as the tool executes
    writer(f"Looking up data for city: {city}")
    writer(f"Acquired data for city: {city}")

    return f"It's always sunny in {city}!"
```

<Note>
如果你在 tool 内使用 `runtime.stream_writer`，该 tool 必须在 LangGraph execution context 中被调用。更多细节见 [Streaming](/oss/langchain/streaming)。
</Note>
:::

:::js
使用 `config.writer` 输出自定义更新：

```ts
import * as z from "zod";
import { tool, ToolRuntime } from "langchain";

const getWeather = tool(
  ({ city }, config: ToolRuntime) => {
    const writer = config.writer;

    // Stream custom updates as the tool executes
    if (writer) {
      writer(`Looking up data for city: ${city}`);
      writer(`Acquired data for city: ${city}`);
    }

    return `It's always sunny in ${city}!`;
  },
  {
    name: "get_weather",
    description: "Get weather for a given city.",
    schema: z.object({
      city: z.string(),
    }),
  }
);
```

:::

### Server info

当工具运行在 LangGraph Server 上时，可以通过 `runtime.server_info` 访问 assistant ID、graph ID 和已认证用户：

:::python
```python
from langchain.tools import tool, ToolRuntime

@tool
def get_assistant_scoped_data(runtime: ToolRuntime) -> str:
    """Fetch data scoped to the current assistant."""
    server = runtime.server_info
    if server is not None:
        print(f"Assistant: {server.assistant_id}, Graph: {server.graph_id}")  # [!code highlight]
        if server.user is not None:
            print(f"User: {server.user.identity}")  # [!code highlight]
    return "done"
```

`server_info` 在工具没有运行在 LangGraph Server 上时为 `None`（例如本地开发或测试时）。
:::

```ts
import { tool } from "langchain";
import * as z from "zod";

const getAssistantScopedData = tool(
```

较早的示例使用 `InjectedState`、`InjectedStore`、`get_runtime()` 或 `InjectedToolCallId`。现在请改用 @[`ToolRuntime`]，它为 state、context、store 和执行元数据提供了统一且显式的接口。

#### Previous pattern

```python
from langchain.tools import tool, InjectedState

@tool
def summarize(state: InjectedState) -> str:
    """Summarize the conversation."""
    messages = state["messages"]
    return f"Conversation length: {len(messages)} messages."
```

#### Recommended pattern

```python
from langchain.tools import tool, ToolRuntime

@tool
def summarize(runtime: ToolRuntime) -> str:
    """Summarize the conversation."""
    messages = runtime.state["messages"]
    return f"Conversation length: {len(messages)} messages."
```

如果是 agent 级迁移（例如 `create_react_agent` 和自定义 state），请参见 [LangChain v1 migration guide](/oss/migrate/langchain-v1)。

</Accordion>

## 工具执行

在 LangChain 中，工具由 agent 使用（例如通过 @[`create_agent`]），工具错误处理则通过 [middleware](/oss/langchain/middleware) 配置。

在 LangGraph workflow 中，工具执行由 @[`ToolNode`] 处理。Graph API 的用法请参见 [ToolNode](/oss/langgraph/workflows-agents#toolnode)，包括工具如何访问当前 graph state 和 run-scoped context。

### 工具返回值

你可以为工具选择不同的返回值：

- 返回 `string` 适合给人类可读的结果。
- 返回 `object` 适合让模型解析的结构化结果。
- 当你需要写入 state 时，返回带可选消息的 `Command`。

#### 返回多模态内容

工具并不局限于纯文本。只要模型支持多模态 tool result，工具就可以返回 [standard content blocks](/oss/langchain/messages#standard-content-blocks)，让模型在一次 tool result 中接收文本、图片和其他媒体。

:::python
```python
from langchain.tools import tool


@tool
def capture_screenshot() -> list[dict]:
    """Capture a screenshot of the current page."""
    return [
        {"type": "text", "text": "Screenshot of the current page:"},
        {"type": "image", "url": "https://example.com/page.png"},
    ]
```
:::

:::js
```typescript
import { tool } from "langchain";
import { z } from "zod";

const captureScreenshot = tool(
  async () => [
    { type: "text", text: "Screenshot of the current page:" },
    { type: "image", url: "https://example.com/page.png" },
  ],
  {
    name: "capture_screenshot",
    description: "Capture a screenshot of the current page.",
    schema: z.object({}),
  }
);
```
:::

行为：

- 返回值会转换成带多模态 `content` 的 `ToolMessage`。
- 工具运行后，使用 `message.content_blocks` 读取标准化后的 block 列表。
- 你返回的模态必须被模型支持。在返回图像、音频或视频之前，请先检查 [model's capabilities](/oss/integrations/chat)。

关于 block 类型和 provider 的具体要求，请参见 [Multimodal messages](/oss/langchain/messages#multimodal)。返回图像或混合内容的 MCP tool 也会以相同方式转换；参见 [Multimodal tool content](/oss/langchain/mcp#multimodal-tool-content)。

#### 返回 Command

当工具需要更新 graph state 时，例如设置用户偏好或应用状态，就返回 @[`Command`]。
当 `Command` 指向当前 graph 时，需要在 update 中包含一个 `ToolMessage`，其 tool call ID 与当前 tool call 匹配。
消息历史中的每个 tool call 都必须有对应的 `ToolMessage`。

:::python
用 `runtime.tool_call_id` 作为 `tool_call_id` 参数。`ToolNode` 会强制这一要求：如果 update 中没有与 tool call 匹配的 `ToolMessage`，会抛出 `ValueError`。
:::

:::js
用 `runtime.toolCallId` 作为 `tool_call_id` 参数。
:::

#### 直接从 tool 返回

把 tool 设为 return direct，可以短路 agent loop：agent 会直接把 tool 输出返回给调用方，而不会再送回模型做进一步处理。

:::python

:::

:::js

<ToolReturnDirectJs />

行为：

- 工具正常执行，输出会被包装成 `ToolMessage`。
- agent 会停止循环，并把 tool 输出作为最终回复返回，跳过额外的 model call。
- **多个并行 tool call：** 当模型在一次 step 中调用多个工具时，它们会先全部执行。所有工具执行完成后，只有当该批次中**每一个**工具都设置了 `return_direct=True` 时，agent 才会路由到 `END`。最终回复会包含该 step 中每个被调用工具的 `ToolMessage` 输出。

在以下情况使用：

- 工具输出本身就是完整、可直接给用户的答案，例如查到就能直接展示的结果。
- 你不需要额外推理，也不想多一次 model call。
- 你需要确定性、未经改写的输出，模型不能重写、总结或继续处理 tool result。

<Warning>
    因为模型不会处理 tool 的输出，`return_direct=True` 不适合那些结果还需要进一步推理、总结或和其他 tool call 串联的工具。
</Warning>

<Warning>
    **混合并行调用：** 如果模型把一个 `return_direct=True` 的工具和一些没有设置 `return_direct=True` 的工具一起调用，agent 不会在那一步之后退出。它会带着该批次的所有 `ToolMessage` 路由回模型，让模型对所有结果进行推理。只有当该 step 中的每个 tool call 都设置了 `return_direct=True` 时，`return_direct` 才会短路循环。
</Warning>

:::python

#### 直接从 tool 返回 Command

设置了 `return_direct=True` 的工具也可以返回 @[`Command`]，在 agent 退出前更新 graph state。与普通返回值不同，`Command` 不会自动转换成 `ToolMessage`。当 `Command` 指向当前 graph（`graph` 未设置或为 `None`）时，需要在 `Command.update` 中包含一个与 tool call 的 `tool_call_id` 匹配的 `ToolMessage`。省略它会导致 `ToolNode` 抛出 `ValueError`，因为消息历史中的每个 `AIMessage` tool call 都必须有对应的 `ToolMessage`。

如果要写入父 graph，则设置 `graph=Command.PARENT`。在这种情况下 `ToolMessage` 的要求不再适用，因为执行会完全离开当前 graph。

### State 注入

在工具签名中加入 `runtime: ToolRuntime` 即可访问 state。调用时，@[`ToolNode`] 会自动注入该值；该参数不会包含在发送给模型的工具 schema 中。用 `runtime.state` 读取当前对话 state：

:::python
```python
from langchain.tools import tool, ToolRuntime

@tool
def get_message_count(runtime: ToolRuntime) -> str:
    """Get the number of messages in the conversation."""
    messages = runtime.state["messages"]
    return f"There are {len(messages)} messages."
```

## 动态选择工具

使用动态工具时，agent 可用的工具集合会在运行时修改，而不是一次性全部定义好。并不是每个工具都适合每种情况。工具太多会让模型负担过重、增加出错概率；太少又会限制能力。动态选择工具可以根据认证状态、用户权限、功能开关或对话阶段来调整可用工具集。

根据工具是否提前已知，有两种做法：

<Tabs>
  <Tab title="Filtering pre-registered tools">

    当所有可能的工具在 agent 创建时就已知，你可以预先注册它们，然后根据 state、permissions 或 context 动态过滤模型能看到的工具。

    <Tabs>
      <Tab title="State">
        只有在达到某些对话里程碑后，才启用高级工具：

        ```python
        from langchain.agents import create_agent
        from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
        from typing import Callable

        @wrap_model_call
        def state_based_tools(
            request: ModelRequest,
            handler: Callable[[ModelRequest], ModelResponse]
        ) -> ModelResponse:
            """Filter tools based on conversation State."""
            # Read from State: check if user has authenticated
            state = request.state
            is_authenticated = state.get("authenticated", False)
            message_count = len(state["messages"])

            # Only enable sensitive tools after authentication
            if not is_authenticated:
                tools = [t for t in request.tools if t.name.startswith("public_")]
                request = request.override(tools=tools)
            elif message_count < 5:
                # Limit tools early in conversation
                tools = [t for t in request.tools if t.name != "advanced_search"]
                request = request.override(tools=tools)

            return handler(request)

        agent = create_agent(
            model="gpt-5.5",
            tools=[public_search, private_search, advanced_search],
            middleware=[state_based_tools]
        )
        ```

        ```python
        from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse

            store = request.runtime.store
        ```

        ```python
        from dataclasses import dataclass
        from langchain.agents import create_agent
        from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
        from typing import Callable

        @dataclass
        class Context:
            user_role: str

        @wrap_model_call
        def context_based_tools(
            request: ModelRequest,
            handler: Callable[[ModelRequest], ModelResponse]
        ) -> ModelResponse:
            """Filter tools based on Runtime Context permissions."""
            # Read from Runtime Context: get user role
            if request.runtime is None or request.runtime.context is None:
                # If no context provided, default to viewer (most restrictive)
                user_role = "viewer"
            else:
                user_role = request.runtime.context.user_role

            if user_role == "admin":
                # Admins get all tools
                pass
            elif user_role == "editor":
                # Editors can't delete
                tools = [t for t in request.tools if t.name != "delete_data"]
                request = request.override(tools=tools)
            else:
                # Viewers get read-only tools
                tools = [t for t in request.tools if t.name.startswith("read_")]
                request = request.override(tools=tools)

            return handler(request)

        agent = create_agent(
            model="gpt-5.5",
            tools=[read_data, write_data, delete_data],
            middleware=[context_based_tools],
            context_schema=Context
        )
        ```

    这种方式最适合：
    - 所有可能的工具在编译/启动时就已知
    - 你想根据权限、功能开关或对话状态来过滤工具

    当工具是在运行时发现或创建的，例如从 MCP server 加载、根据用户数据生成，或从远程 registry 拉取时，你需要同时注册这些工具并动态处理它们的执行。

    这需要两个 middleware hook：
    1. `wrap_model_call` - 把动态工具加入 request
    2. `wrap_tool_call` - 处理这些动态加入的工具的执行

    :::python

    ```python
    from langchain.tools import tool
    from langchain.agents import create_agent
    from langchain.agents.middleware import AgentMiddleware, ModelRequest, ToolCallRequest

    # A tool that will be added dynamically at runtime
    @tool
    def calculate_tip(bill_amount: float, tip_percentage: float = 20.0) -> str:
        """Calculate the tip amount for a bill."""
        tip = bill_amount * (tip_percentage / 100)
        return f"Tip: ${tip:.2f}, Total: ${bill_amount + tip:.2f}"

    class DynamicToolMiddleware(AgentMiddleware):
        """Middleware that registers and handles dynamic tools."""

        def wrap_model_call(self, request: ModelRequest, handler):
            # Add dynamic tool to the request
            # This could be loaded from an MCP server, database, etc.
            updated = request.override(tools=[*request.tools, calculate_tip])
            return handler(updated)

        def wrap_tool_call(self, request: ToolCallRequest, handler):
            # Handle execution of the dynamic tool
            if request.tool_call["name"] == "calculate_tip":
                return handler(request.override(tool=calculate_tip))
            return handler(request)

    agent = create_agent(
        model="gpt-5.5",
        tools=[get_weather],  # Only static tools registered here
        middleware=[DynamicToolMiddleware()],
    )

    # The agent can now use both get_weather AND calculate_tip
    result = agent.invoke({
        "messages": [{"role": "user", "content": "Calculate a 20% tip on $85"}]
    })
    ```

    :::

    :::js

    ```typescript
    import { createAgent, createMiddleware, tool } from "langchain";
    import * as z from "zod";

    // A tool that will be added dynamically at runtime
    const calculateTip = tool(
      ({ billAmount, tipPercentage = 20 }) => {
        const tip = billAmount * (tipPercentage / 100);
        return `Tip: $${tip.toFixed(2)}, Total: $${(billAmount + tip).toFixed(2)}`;
      },
      {
        name: "calculate_tip",
        description: "Calculate the tip amount for a bill",
        schema: z.object({
          billAmount: z.number().describe("The bill amount"),
          tipPercentage: z.number().default(20).describe("Tip percentage"),
        }),
      }
    );

    const dynamicToolMiddleware = createMiddleware({
      name: "DynamicToolMiddleware",
      wrapModelCall: (request, handler) => {
        // Add dynamic tool to the request
        // This could be loaded from an MCP server, database, etc.
        return handler({
          ...request,
          tools: [...request.tools, calculateTip],
        });
      },
      wrapToolCall: (request, handler) => {
        // Handle execution of the dynamic tool
        if (request.toolCall.name === "calculate_tip") {
          return handler({ ...request, tool: calculateTip });
        }
        return handler(request);
      },
    });

    const agent = createAgent({
      model: "gpt-5.5",
      tools: [getWeather], // Only static tools registered here
      middleware: [dynamicToolMiddleware],
    });

    // The agent can now use both getWeather AND calculateTip
    const result = await agent.invoke({
      messages: [{ role: "user", content: "Calculate a 20% tip on $85" }],
    });
    ```

    - 工具是在运行时发现的，例如来自 MCP server

    - 你正在对接外部 tool registry

    `wrap_tool_call` hook 对运行时注册的工具是必须的，因为 agent 需要知道如何执行那些原始工具列表里不存在的工具。没有它，agent 就不知道如何调用动态加入的工具。
    </Note>

## 无头工具

有些工具应该在**用户应用运行的地方**执行，通常是浏览器，而不是在进程内部执行。**无头工具（headless tools）** 是一种 tool 定义，它包含 name、description 和参数 schema，由你在**服务端**和 agent 一起注册。真正的**实现**只在**客户端**注册，并在一次短暂的 interrupt/resume 握手之后执行。

这和普通工具不同，普通工具的函数体是在服务端运行的；它也不同于 [server-side tool use](#server-side-tool-use)，后者是模型提供商在远程执行内置工具。

### 何时使用无头工具

当工作依赖于只有客户端才有的**环境、设备或 UI**时就使用它们。例如：

- **Browser APIs:** Geolocation、IndexedDB、Clipboard、Canvas 2D、文件选择器、Battery API 等。
- **隐私和本地性:** 数据保留在设备上，例如存储在 IndexedDB 里的本地“memory”。
- **延迟:** 对纯本地操作，不需要额外的服务端往返。
- **结构化、安全的副作用:** 更适合使用许多小而类型明确的工具，例如每个 canvas primitive 一个工具，而不是把任意代码发给 `eval`。

### 这个模式如何工作

在两个运行时里，模型看到的都是一个正常可调用的 tool，但真正的执行发生在服务端进程之外。

:::python
1. **定义** 一个 headless tool，使用 `langchain.tools` 里的 `tool(name=..., description=..., args_schema=...)`。headless tool 只有 schema，没有进程内实现。
2. **注册** 这个 tool 到 `create_agent` 或你的 LangGraph graph，这样模型就能正常调用它。
3. **处理** 工具被调用时的 interrupt payload。图不会在本地执行，而是暂停，并返回一个形如 `{"type": "tool", "tool_call": {"id", "name", "args"}}` 的 payload。
4. **恢复** 图的执行，在你的应用、另一个服务，或人工步骤完成动作之后再继续。对于基于浏览器的流程，你也可以在前端镜像这个 schema，并在那里挂上 `.implement(...)`。

<Info>
    如果你在 Python 中调用 `tool(...)`，只传 `name`、`description` 和 `args_schema`，LangChain 返回的是 `HeadlessTool`。Python 侧没有 `.implement()` API。
</Info>
:::

:::js
1. **定义** tool，使用 `langchain` 里的 `tool({ name, description, schema })`。这里仅提供元数据和校验，没有服务端 runner。
2. **挂接** 真实行为，用 `.implement(async (args) => { ... })`，它会返回一个 **headless tool implementation**（定义 + `execute` 函数）。
3. **注册** 第 1 步里的定义到 `createAgent` 或你的 graph，这样模型就能在标准 tool-calling loop 中看到这个 tool。
4. **把** 第 2 步的 implementation 传给 streaming hook 的 `tools` 选项。

<Info>
    把**工具定义**（`tool({ name, description, schema })`）和**实现**（`.implement(...)`）放在**不同模块**里。服务端 agent 和前端都从共享定义文件导入，这样 name 和 schema 保持一致；把只在客户端运行的 execute 逻辑放进服务端永远不会加载的 implementation 模块。
</Info>
:::

当模型对这些工具发出 tool call 时，运行会**中断**，而不是在本地执行工具。你的应用可以检查 payload、在正确环境里执行动作，例如浏览器、另一个服务或人工 review，然后用 tool result **恢复** graph。使用受支持的 JS SDK hooks 时，它们可以检测 headless-tool interrupt、运行匹配的客户端实现，并自动提交 resume command。

你可以使用可选的 **`onTool`** 回调来观察生命周期事件（`start`、`success`、`error`），用于 spinner 或 toast 这类 UI 反馈。
