最强大的基于 LLM 的应用之一，是复杂的问答（Q&A）chatbot，它通过为 LLM 提供对一组数据的结构化访问来增强模型。
这些数据可以是私有数据、最新数据，或者并不属于 LLM 训练数据的数据。
这类应用使用一种叫做 Retrieval Augmented Generation，或 [RAG](/oss/langchain/retrieval/) 的技术。

本教程将带你构建一个可以回答长篇非结构化文本问题的应用：

1. **[索引内容](#index-your-content)**：创建一个从数据源摄取数据并完成索引的流水线。
2. **[RAG agent](#rag-agent)**：一个通用实现，会搜索已索引内容，并将相关上下文传给 LLM。
3. **[RAG chain](#rag-chain)**：一个两步实现，每个查询只需要一次 LLM 调用。对于简单查询来说，这是一种快速且有效的方法。

本教程使用 Lilian Weng 的 [LLM Powered Autonomous Agents](https://lilianweng.github.io/posts/2023-06-23-agent/) 博文作为示例。

在完成教程的过程中，可以使用 [LangSmith](/langsmith/observability) 来 [trace](/langsmith/trace-with-langchain) 检索和生成。

## 索引你的内容

在索引阶段，你会把源内容切成若干 _chunks_，再把它们转成数值表示。这个数值表示会捕捉 chunk 的语义。把这些数值表示和文档 chunk 一起存进 `VectorStore`，就能在用户发来查询时根据其自己的数值表示高效检索相关内容。

索引通常分四步：

1. **[Load](#load-documents)**：将数据源加载为 @[`Document`] 对象。
2. **[Split](#split-documents)**：使用 [text splitters](/oss/integrations/splitters) 把大的 `Document` 切成更小的 chunk。这对于索引数据和传给模型都很有用，因为大 chunk 更难搜索，而且要么装不进模型有限的上下文窗口，要么会多消耗不必要的 token。
3. **[Embed](#select-an-embeddings-model)**：[Embeddings](/oss/integrations/embeddings) 模型会把每个 chunk 转成数值向量，捕捉其含义，从而支持相似度搜索。
4. **[Store](#store-chunks-and-embeddings-in-vectorstore)**：使用 [VectorStore](/oss/integrations/vectorstores) 给 chunk 及其 embeddings 建索引，以便后续检索。

![index_diagram](/images/rag_indexing.png)

接下来的步骤会搭建你摄取源内容所需的组件。

下一步是检索和生成：在运行时给定用户问题，从索引中取出相关 chunk，并把它们传给模型生成答案。RAG 应用通常会把这条流程分成两步实现：

1. **检索**：给定用户输入，通过 [Retriever](/oss/integrations/retrievers) 从存储中检索相关 split。
2. **生成**：一个 [model](/oss/langchain/models) 使用包含问题和检索数据的提示词生成答案。

![retrieval_diagram](/images/rag_retrieval_generation.png)

本教程会介绍这条流程的两种实现：一种是需要时调用搜索工具的 [RAG agent](#rag-agent)，另一种是始终检索一次并在单次模型调用中回答的 [RAG chain](#rag-chain)。

## RAG chain

在你创建的 [RAG agent](#rag-agent) 中，你允许 LLM 自主决定是否生成一个 [tool call](/oss/langchain/models#tool-calling) 来帮助回答用户查询。这是一个适用于通用场景的好方案，但它也有一些取舍：

| ✅ 优点                                                                 | ⚠️ 缺点                                                                 |
|-----------------------------------------------------------------------------|----------------------------------------------------------------------------|
| **仅在需要时搜索**：LLM 可以处理问候、追问和简单查询，而不会触发不必要的搜索。 | **两次推理调用**：当执行搜索时，需要一次调用来生成查询，另一次调用来生成最终回复。 |
| **上下文相关的搜索查询**：把搜索当作一个带 `query` 输入的工具，LLM 可以自己构造包含对话上下文的查询。 | **控制力较弱**：LLM 可能在真正需要搜索时跳过搜索，或者在不必要时发起额外搜索。 |
| **允许多次搜索**：LLM 可以为单个用户查询执行多次搜索。 |                                                                            |

另一种常见方式是两步 chain：你始终先运行一次搜索，可能直接使用原始用户查询，然后把结果作为上下文供单次 LLM 查询使用。这样每个查询只需要一次推理调用，以灵活性换取更低延迟。

在这种方式里，我们不再让模型循环调用，而是只做一次单次传递。

## 安全注意事项

<Warning>
RAG 应用容易受到**间接提示注入**影响。检索到的文档可能包含看起来像指令的文本，例如“请以 JSON 格式回答”或“忽略之前的指令”。由于检索到的上下文和 system prompt 共享同一个上下文窗口，模型可能会不小心遵循数据中嵌入的指令，而不是你想要的提示。

例如，本教程索引的博客文章中包含描述 [Auto-GPT](https://lilianweng.github.io/posts/2023-06-23-agent/#case-studies) JSON 响应格式的文本。如果用户查询检索到了那一段，模型可能会输出 JSON，而不是自然语言答案。
</Warning>

为缓解这个问题：

1. **使用防御性提示词**：明确要求模型把检索到的上下文视为数据，并忽略其中的任何指令。本教程里的提示词已经包含了这样的说明。
2. **用分隔符包裹上下文**：使用清晰的结构化标记，例如 `<context>...</context>` 这类 XML tag，把检索到的数据和指令分开，让模型更容易区分它们。
3. **校验响应**：检查模型输出是否符合预期格式，例如纯文本，并优雅处理意外格式。

没有任何缓解手段是万无一失的，这源于当前 LLM 架构的固有限制，因为指令和数据共享同一个上下文窗口。有关这一主题的更多内容，请参见关于 [prompt injection](https://simonwillison.net/series/prompt-injection/) 的研究。
