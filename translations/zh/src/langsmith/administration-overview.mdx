本概览页介绍了在 LangSmith 中管理用户、组织、工作区和应用相关的主题。

## 资源层级

### Organizations

组织是 LangSmith 中用于聚合用户的逻辑单元，它定义了作用于该组织内所有工作区的共享设置。这些设置面向组织级事务，而不是某个工作区中的单个项目。常见的组织级配置包括用户管理、单点登录（SSO）、OAuth provider 配置、自定义角色创建、计费和用量追踪。通常一个公司对应一个组织。一个组织可以拥有多个工作区。更多细节请参阅[设置指南](/langsmith/set-up-hierarchy#set-up-an-organization)。

当你第一次登录时，系统会自动为你创建一个个人组织。如果你想与其他人协作，可以额外创建一个独立组织，并邀请团队成员加入。个人组织和共享组织之间有几个重要区别：

| Feature             | Personal            | Shared                                                                                       |
| ------------------- | ------------------- | -------------------------------------------------------------------------------------------- |
| Maximum workspaces  | 1                   | 取决于方案，数量可变（参见[定价页面](https://www.langchain.com/pricing-langsmith)） |
| Collaboration       | Cannot invite users | Can invite users                                                                             |
| Billing: paid plans | Developer plan only | All other plans available                                                                    |

### Workspaces

<Info>
Workspaces 之前曾被称为 Tenants。在过渡期间，某些代码和 API 中可能仍会引用旧名称。
</Info>

工作区是组织内部用于聚合用户和资源的逻辑单元。工作区通常用于隔离不同团队或业务单元，从而把项目及其相关资源彼此分开。工作区为资源和访问控制划分了信任边界。用户在工作区级别被授予权限，这些权限决定他们可以访问该工作区中的哪些资源，包括 tracing projects、datasets、annotation queues 和 prompts。关于如何设置，请参阅[设置指南](/langsmith/set-up-hierarchy#set-up-a-workspace)；关于权限细节，请参阅 [Workspaces (RBAC)](/langsmith/administration-overview#workspace-roles-rbac)。

我们建议为组织中的每个团队创建独立工作区。若想进一步组织资源，你还可以使用[Applications](#applications)在工作区内部继续分组。关于不同工作区组织模型以及如何根据团队的隔离要求进行选择，请参阅 [Workload isolation](/langsmith/workload-isolation)。

### Applications

应用是工作区内部对资源的逻辑分组。应用通常对应 agents，但你也可以用它来表示团队中的任意项目。应用通过只展示当前上下文中与该应用相关的资源，帮助 UI 保持整洁。

应用构建在[资源标签](/langsmith/administration-overview#resource-tags)之上，并可结合 [ABAC](/langsmith/organization-workspace-operations#access-policies) 对资源访问进行控制。

你可以在 [LangSmith UI](https://smith.langchain.com) 主导航侧栏中切换应用，使用侧栏顶部的 **Application** 下拉框选择目标应用。

任何资源都可以在不绑定到应用标签的情况下创建。当选择 **All applications** 选项时，这类资源也会显示出来。

### Resources

资源是用于构建、运行和观察应用与 agents 的具体实体，例如 tracing projects、prompts、datasets 和 deployments。资源总是归属于某个具体应用。

### 资源标签

资源标签允许你在工作区内进一步分隔资源，并配合 [ABAC](/langsmith/organization-workspace-operations#access-policies) 使用。每个标签都是一个 key-value 对，可以分配给某个资源。

LangSmith 的资源标签与云服务（例如 [AWS](https://docs.aws.amazon.com/tag-editor/latest/userguide/tagging.html)）中的标签概念非常相似。

在 [LangSmith UI](https://smith.langchain.com) 中进入 **Settings**，然后在侧栏选择 **Resource tags** 页面。

## 用户管理与 RBAC

### Users

用户是指可以访问 LangSmith 的人。一个用户可以同时属于一个或多个组织，以及这些组织中的一个或多个工作区。

组织成员在 **Settings** 页面的 **Members and roles** 中管理。

工作区成员则在 **Settings** 下的 **Workspaces** 页面中管理。

### API keys

<Warning>
我们已在 2024 年 10 月 22 日停止支持以 `ls__` 开头的旧版 API keys，转而使用 personal access tokens（PATs）和 service keys。所有新的集成都必须使用 PATs 和 service keys。以 `ls__` 开头的 API keys 自 2024 年 10 月 22 日起将不再可用。
</Warning>

#### 过期时间

创建 API key 时，你可以选择设置过期时间。给 key 增加过期时间有助于提升安全性，并降低未授权访问的风险。例如，你可以为某些需要临时提升权限的任务所使用的 key 设置过期时间。

默认情况下，key 永不过期。一旦过期，API key 将失效，不能重新激活，也无法修改其过期时间。

#### Personal access tokens (PATs)

Personal Access Tokens（PATs）用于对 LangSmith API 请求进行认证。它们由用户创建，并且作用域绑定在用户本身。PAT 的权限与创建它的用户权限相同。我们不建议用它来认证应用中的请求，更推荐用于个人脚本或与 LangSmith API 交互的工具。如果与该 PAT 绑定的用户被移出组织，该 PAT 也会失效。

PATs 以前缀 `lsv2_pt_` 开头。

#### Service keys

Service keys 与 PATs 类似，但它们用于代表 service account 对 LangSmith API 发起认证。只有管理员可以创建 service keys。我们建议将其用于需要与 LangSmith API 交互的应用或服务，例如 LangGraph agents 或其他集成。Service keys 可以作用于单个工作区、多个工作区，或整个组织，并且可以用来认证它有权限访问的任意工作区请求。

Service keys 以前缀 `lsv2_sk_` 开头。

<Warning>
请使用 `X-Tenant-Id` header 指定目标工作区。

- **使用 PATs 时**：如果省略该 header，请求会默认落到该 key 关联的默认工作区。
- **使用组织级 service key 时**：访问工作区级资源时必须包含 `X-Tenant-Id` header。否则请求会以 `403 Forbidden` 失败。
</Warning>

<Note>
如需了解如何创建 service key 或 Personal Access Token，请参阅[设置指南](/langsmith/create-account-api-key)。
</Note>

### Organization roles

组织角色不同于[企业版工作区 RBAC](#workspace-roles-rbac)，它用于多[工作区](#workspaces)场景。你的组织角色决定了你在工作区中的成员资格特征，以及你的[组织级权限](/langsmith/organization-workspace-operations)。

所选组织角色还会如下影响工作区成员资格：

- [Organization Admin](/langsmith/rbac#organization-admin) 拥有管理所有组织配置、用户、计费和工作区的完整权限。
    - Organization Admin 自动拥有该组织中所有工作区的 `Admin` 权限。
- [Organization User](/langsmith/rbac#organization-user) 可以读取组织信息，但不能在组织级别执行任何写操作。Organization User 可以创建 [Personal Access Tokens](#personal-access-tokens-pats)。
    - 如果启用了 RBAC，Organization User 可以像往常一样被添加到部分工作区，并被分配工作区角色，这些角色决定其工作区级别权限。
- [Organization Viewer](/langsmith/rbac#organization-viewer) 与 Organization User 类似，但**不能**创建 Personal Access Tokens。（在自托管场景中，Helm chart 版本 `0.11.25+` 可用。）

<Info>
<OrgWorkspaceRole/>

如需禁用整个组织的 PAT 创建，请参阅[安全设置](/langsmith/manage-organization-by-api#security-settings)。
</Info>

如需进一步了解如何设置组织和工作区，请参阅[组织设置指南](/langsmith/set-up-hierarchy#organization-roles)。

### Workspace roles (RBAC)

<Note>
RBAC（Role-Based Access Control）仅适用于 Enterprise 客户。如果你对该功能感兴趣，请[联系销售团队](https://www.langchain.com/contact-sales)。其他方案默认所有用户都使用 Admin 角色。
</Note>

角色用于定义用户在工作区中所拥有的一组权限。系统内置了三个不可编辑的角色：

- [Workspace Admin](/langsmith/rbac#workspace-admin) 对工作区中的所有资源拥有完整访问权限。
- [Workspace Editor](/langsmith/rbac#workspace-editor) 拥有除工作区管理（添加/移除用户、更改角色、配置服务密钥）之外的完整权限。
- [Workspace Viewer](/langsmith/rbac#workspace-viewer) 对工作区中的所有资源拥有只读访问权限。

[Organization admins](/langsmith/rbac#organization-admin) 还可以创建或编辑自定义角色，为不同资源配置特定权限。

你可以在 **Organization Settings** > **Members and roles** 中选择 **Roles** 标签页来管理这些角色。

- 如需查看完整的角色与权限文档，请参阅 [Role-based access control](/langsmith/rbac) 指南。
- 如需了解如何分配和创建角色，请参阅 [User Management](/langsmith/user-management) 指南。

## 最佳实践

### 环境隔离

请使用[资源标签](#resource-tags)，通过默认标签 key `Environment` 以及不同环境值（例如 `dev`、`staging`、`prod`）来组织资源。我们不建议为环境隔离使用独立工作区，因为资源无法跨工作区共享，这会导致你无法在不同环境间推广资源（例如 prompts）。

<Note>
**用于 prompt 管理时，资源标签与 commit tags 的区别**

虽然这两类标签都可以使用 `dev`、`staging`、`prod` 之类的环境术语，但它们用途不同：

- **资源标签**（`Environment: prod`）：用于在工作区内*组织和过滤*资源。你可以把资源标签应用到 tracing projects、datasets 以及其他资源（包括 prompts），从而按环境进行归组，并支持在 UI 中进行过滤。
- [Commit tags](/langsmith/manage-prompts#commit-tags)（`prod` 标签）：用于管理代码引用的是哪个[prompt 版本](/langsmith/prompt-engineering)。Commit tags 是指向 prompt 历史中某次具体 commit 的标签。当你的代码按标签名拉取 prompt（例如 `client.pull_prompt("prompt-name:prod")`）时，它会获取当前该标签所指向的那次 commit。若要把某个 prompt 从 `staging` 推进到 `prod`，只需把 commit tag 移动到目标版本即可。

资源标签用来组织**哪些资源**属于某个环境。Commit tags 则让你可以控制代码引用的是 prompt 的**哪个版本**，而无需修改代码本身。
</Note>

## 用量与计费

### 数据保留

本节介绍 LangSmith 中数据保留的工作方式，以及它如何影响计费。

#### 为什么数据保留很重要

* **隐私**：许多数据隐私法规，例如欧洲的 GDPR 或加州的 CCPA，都要求组织在个人数据不再用于最初采集目的后及时删除。设置保留周期有助于满足这些法规要求。
* **成本**：LangSmith 对低保留时长的 traces 收费更低。更多信息请参阅如何[实施支出限制](/langsmith/billing#enforce-spend-limits)。

<Tip>
在开始发送 traces 之前，先规划好你的保留层级。变更只会影响新 traces，已有 traces 会保留原有层级。参阅[修改项目级默认保留设置](/langsmith/billing#change-project-level-default-retention)。
</Tip>

#### 工作原理

LangSmith 基于 Data Retention 把 traces 分为两个层级，其特点如下：

|                      | Base             | Extended       |
| -------------------- | ---------------- | -------------- |
| **Price**            | [见定价页](https://www.langchain.com/pricing-langsmith) | [见定价页](https://www.langchain.com/pricing-langsmith) |
| **Retention Period** | 14 天          | 400 天       |

<Note>
Enterprise 客户可以按工作区自定义 extended retention period。变更只影响新 traces，不影响已有 traces。参阅[自定义扩展保留策略](/langsmith/data-purging-compliance#customize-extended-retention-policy)。
</Note>

**保留期结束后的数据删除**

达到指定保留期后，trace 将无法再通过 tracing project UI 或 API 访问。与该 trace 相关的所有用户数据（例如输入和输出）随后会在一天内从我们的内部系统中删除。某些与 trace 关联的元数据可能会为了分析和计费目的被长期保留。

#### 数据保留自动升级

<Warning>
自动升级会影响你的账单。请仔细阅读本节，以完整理解 LangSmith tracing 的预估成本。
</Warning>

当你在 `base` 层级 traces 上使用某些功能时，其数据保留会自动升级为 `extended` 层级。这会同时增加保留时长和该 trace 的成本。

以下场景都会触发 trace 升级：

* 对 trace 中任意 run（或同一 thread 中任意 trace）添加了**Feedback**，无论是通过[手动标注](/langsmith/annotate-traces-inline)、[在线 evaluator](/langsmith/online-evaluations-llm-as-judge)自动生成，还是通过[SDK](/langsmith/attach-user-feedback)以编程方式添加。
* 某个 **[annotation queue](/langsmith/annotation-queues#assign-runs-and-threads-to-a-single-run-queue)** 接收了该 trace 中任意一个 run 或 thread。
* 某条 **[automation rule](/langsmith/rules#create-a-rule)** 匹配到了该 trace 中任意一个 run。匹配单个 run 会升级整个 trace，而不仅仅是该 run。条目类型为 **Threads** 的规则会升级匹配 thread 中的每条 trace，而不只是最近的那条。

**为什么要自动升级 traces？**

我们采用自动升级模型有两个原因：

1. 我们认为满足这些条件的 traces，本质上比其他 traces 更有价值，因此让用户可以更长时间地保留它们是合理的。
2. 从理念上讲，我们希望对那些可能不会被深入交互的 traces 收取更低一个数量级的价格。自动升级使我们的定价模型能更好地和 LangSmith 实际带来的价值对齐，也就是说，只有那些被有意义地使用过的 traces，才会以更高价格计费。

如果你对我们的定价模型有疑问或反馈，欢迎通过 [support.langchain.com](https://support.langchain.com) 联系支持团队。

**数据保留会如何影响下游功能？**

* **Annotation Queues、Run Rules 和 Feedback**：一旦使用这些功能，对应 traces 就会被[自动升级](#data-retention-auto-upgrades)。
* **Monitoring**：即使 base 层级 trace 的保留期结束后，monitoring 标签页仍然可用。它依赖的是可保留超过 30 天的 trace metadata，因此即便使用 `base` 层级 traces，你的监控图表仍会保持准确。
* **Datasets**：数据集的数据保留期是无限期的。换句话说，如果你把某条 trace 的输入和输出加入数据集，它们将不会被删除。如果你用 LangSmith 做数据收集，建议充分利用 datasets 功能。

#### 计费模型

**可计费指标**

在 LangSmith 发票中，你会看到两个收费指标：

* LangSmith Traces（基础费用）
* LangSmith Traces（扩展数据保留升级费用）

第一个指标包含所有 traces，不区分层级。第二个指标只统计扩展保留的 traces 数量。

**为什么不是直接统计 base traces 和 extended traces？**

一个很自然的问题是，为什么发票上不直接显示 `base` 层级 traces 数量和 `extended` 层级 traces 数量？

虽然这样看起来更直接，但它无法正确处理 trace 升级场景。比如某条 `base` 层级 trace 记录于 6 月 30 日，并在 7 月 3 日升级为 `extended` 层级。它的 `base` 费用属于 6 月计费周期，而升级行为属于 7 月计费周期。因此，我们必须把这两个事件拆开计量，才能正确计费。

如果某条 trace 在创建时就是 extended retention trace，那么 `base` 和 `extended` 两个指标会在同一时间戳下同时计入。

### 速率限制

LangSmith 设计了一套速率限制机制，以保障所有用户都能稳定使用服务。

为了保证访问和稳定性，当超出速率或用量上限时，LangSmith 会返回 HTTP 状态码 429。以下是几种典型情况：

#### 负载均衡器层面，按 1 分钟窗口计算的临时吞吐上限

这种 429 来自应用负载均衡器，表示某个 service key 或 PAT 在 1 分钟窗口内超过了固定的 API 调用次数限制。这个窗口的起始时间可能会有轻微偏移，不一定与自然分钟整点对齐，并且也可能因应用部署事件而变化。

达到上限后，系统会持续返回 429，直到距离该评估窗口开始已满 60 秒，然后重新开始计算。

这一限制与方案无关，对所有 LangSmith 用户统一生效，用于保障服务连续性。

| Method            | Endpoints     | Limit | Window   |
| ----------------- | ------------- | ----- | -------- |
| `DELETE`          | `/sessions*`  | 30    | 1 minute |
| `POST` OR `PATCH` | `/runs*`      | 5000  | 1 minute |
| `GET`             | `/runs/:id`   | 30    | 1 minute |
| `POST`            | `/feedbacks*` | 5000  | 1 minute |
| `*`               | `*`           | 2000  | 1 minute |

<Note>
LangSmith SDK 会尽量减少你触达这些 run 相关端点限制的概率，例如它会把同一个 session ID 下最多 100 个 runs 批量合并为一次 API 调用。
</Note>

#### 方案级每小时 trace event 上限

这种 429 表示你已达到每小时可摄入的 events 数量上限。它以 UTC 每个整点开始固定窗口计算，并在下一个整点重置。

这里的 event 指的是创建或更新一个 run。如果某个 run 在同一小时窗口内先被创建、随后又被更新，那么它会计作 2 个 events。

这个限制由应用层抛出，并且会因方案不同而变化。Startup/Plus 和 Enterprise 方案的组织会有更高的每小时限制，而 Free 和 Developer 方案则更适合个人使用，因此限制更低。

| Plan                             | Limit          | Window |
| -------------------------------- | -------------- | ------ |
| Developer（未绑定支付方式）   | 50,000 events  | 1 小时 |
| Developer（已绑定支付方式） | 250,000 events | 1 小时 |
| Startup/Plus                     | 500,000 events | 1 小时 |
| Enterprise                       | Custom         | Custom |

#### 方案级每小时 trace 数据摄入上限

这种 429 表示你已达到每小时 trace 输入、输出和 metadata 的总摄入量上限。它同样以 UTC 每个整点开始固定窗口计算，并在下一个整点重置。

通常情况下，输入、输出和 metadata 会在 run 创建和更新时一并发送。如果某个 run 在同一小时窗口内创建时为 2.0MB，更新后为 3.0MB，那么它会计入 5.0MB 的存储量。

该限制也由应用层抛出，并因方案不同而变化。Startup/Plus 和 Enterprise 方案拥有更高上限，而 Free 和 Developer 方案的限制更低。

| Plan                             | Limit  | Window |
| -------------------------------- | ------ | ------ |
| Developer（未绑定支付方式）   | 500MB  | 1 小时 |
| Developer（已绑定支付方式） | 2.5GB  | 1 小时 |
| Startup/Plus                     | 5.0GB  | 1 小时 |
| Enterprise                       | Custom | Custom |

#### 方案级每月唯一 traces 上限

这种 429 表示你已达到每月可摄入的唯一 traces 数量上限。它以 UTC 每个自然月开始固定窗口计算，并在下个月开始时重置。

这个限制仅适用于未绑定支付方式的 Developer 方案，由应用层抛出。

| Plan                           | Limit        | Window  |
| ------------------------------ | ------------ | ------- |
| Developer（未绑定支付方式） | 5,000 traces | 1 个月 |

#### 自定义每月用量上限

这种 429 表示你已达到组织管理员配置的用量上限。它以每个自然月为窗口，并在新一个月开始时重置。

这一限制由应用层抛出，具体阈值取决于各个组织自己的配置。

### 用量上限

LangSmith 允许你为 tracing 配置用量上限。请注意，这里是 *usage* limits，而不是 *spend* limits，也就是说它们限制的是某类事件发生的数量，而不是你的总花费。

LangSmith 支持设置两种每月上限，这两项与前面数据保留章节中提到的计费指标一一对应：

* All traces limit
* Extended data retention traces limit

它们分别限制总 traces 数量，以及 extended data retention traces 的数量。

<Note>如果你要专门限制 evaluator runs 的 *spend*，请参阅[跟踪并限制 evaluator 支出](/langsmith/evaluator-spend)。</Note>

#### 用量限制的特性

用量限制是近似值，我们不保证它在绝对数值上完全精确。在极少数情况下，超过阈值后可能仍会有一小段时间继续处理额外 traces，然后限制才会真正生效。

#### Extended data retention traces 上限的副作用

Extended data retention traces 上限会带来一些副作用。一旦该上限已达成，任何可能触发 tracing 层级自动升级的功能都会无法继续使用。因为自动升级会再创建一条新的 extended retention trace，而这本身就不应再被允许。因此，你将无法继续：

1. 匹配 run rules
2. 向 traces 添加 feedback
3. 向 annotation queues 添加 runs

这些功能都可能触发自动升级，因此达到上限后我们会将其关闭。

#### 更新用量上限

你可以在 `Settings` 页面下的 `Usage and Billing` 中更新用量上限。上限值有缓存，因此新设置生效可能需要一两分钟。

#### 按项目和按用户的 trace 上限

除了[工作区范围的上限](#用量上限)之外，你还可以为单个 tracing project 或单个工作区成员设置每月 trace 数量上限。这样可以避免某一个项目或用户消耗掉工作区 tracing 预算中不成比例的一大部分。

要配置这些上限，请打开 **Settings**，进入 **Usage configuration**，然后选择 **Project & user limits** 标签页。选择 **Add limit**，然后设置：

* **Scope**：选择 **Project** 以限制单个 tracing project，或选择 **User** 以限制单个工作区成员。
* **Workspace**：选择该项目或成员所在的工作区。
* **Project** 或 **User**：选择要施加上限的目标。
* **Monthly trace limit**：设置每个自然月允许的最大 trace 数量。

更新这些上限需要与工作区 usage limit 相同的权限，也就是 `Update usage limits`。

和工作区上限一样，按项目和按用户的上限也是按 UTC 自然月计算，并在每个新月份开始时重置。一旦某个项目或用户达到其上限，新产生的 traces 会被丢弃，在上限重置前不会再次摄入。执行是近似的，因此在上限真正生效前，可能仍会有少量 traces 超过阈值被处理。这些上限同时适用于 [Cloud](/langsmith/cloud) 和 [Self-hosted](/langsmith/self-hosted)。

<Note>
按项目和按用户的上限，是在工作区级上限和方案级上限之上的**额外**限制。某条 trace 只有同时满足所有适用上限，才会被摄入。

按用户上限只统计归属于某个特定工作区成员的 traces。通过未绑定到成员的 API key 或 service key 发送的 traces，不会计入按用户上限。

上限值会被缓存，因此新建或修改后的上限可能需要一两分钟才会生效。
</Note>
