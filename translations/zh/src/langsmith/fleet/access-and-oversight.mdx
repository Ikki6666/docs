Fleet 为你提供了在整个组织内扩展 agent 的控制层，包括分级权限、凭证管理、human-in-the-loop 监督，以及对 agent 操作的审计轨迹。

## 权限与共享

Fleet 从两个维度为每个 agent 提供细粒度控制：**谁可以访问**，以及**他们可以做什么**。

- **谁**：可以共享给单个用户，或整个工作区
- **做什么**：共有三种权限级别：
  - **Clone**：复制并自定义该 agent
  - **Run**：使用但不能修改
  - **Edit**：可完全访问并修改指令、工具和设置

这些权限可以叠加使用。你可以给核心团队编辑权限，向更广泛的组织仅共享运行权限，并且随时撤销。

关于设置说明，请参阅[更改 agent 访问权限](/langsmith/fleet/manage-agent-settings#change-access-to-the-agent)。

## Agent 身份与凭证

Fleet 提供两种凭证模型，用于控制 agent 如何向外部工具进行身份验证：

- **固定凭证，Claws**：无论谁运行 agent，它都使用同一组凭证。适合共享资源型 agent，例如一个团队 Slack bot，所有人都通过同一个账户与之交互
- **用户凭证，Assistants**：agent 会代表触发它的具体用户执行操作。每个用户都通过 OAuth 用自己的账户完成认证。适合那些不同用户具有不同访问级别的工具，例如个人邮件助手

这项能力可以按 agent 单独配置，因此你可以为每种场景选择合适的模型。

关于设置说明，请参阅[Agent identity](/langsmith/fleet/agent-identity)。

## 工具访问控制

Fleet 为工具提供分层访问控制，同时覆盖**自定义 MCP servers**，也就是用户添加、工作区级作用域的工具，以及**内置 integrations**，也就是平台提供的集成，例如 Gmail、Slack 和 GitHub：

- **[基于角色的访问控制，RBAC](#role-based-permissions)**：在角色级别控制访问
- **[基于属性的访问控制，ABAC](#attribute-based-access-control)**：在 RBAC 之上增加资源级粒度
- **[工作区集成策略](#workspace-integration-policy)**：为内置 integrations 提供由管理员控制的启用或禁用开关

<Note>
工具访问控制属于 Enterprise 功能。如果你对该功能感兴趣，请[联系销售团队](https://www.langchain.com/contact-sales)。
</Note>

### 基于角色的权限

基于角色的访问控制，RBAC，会根据用户角色，对工作区中的所有 MCP servers 和 integrations 授予或拒绝访问。角色可在 **Settings > Roles** 中配置。

以下权限可用于 MCP servers 和 integrations：

| Permission | Description |
|------------|-------------|
| `mcp-servers:read` | 发现并列出 MCP servers 和 integrations |
| `mcp-servers:invoke` | 执行 MCP servers 和 integrations 中的工具，包括 OAuth connect 或 disconnect |
| `mcp-servers:create` | 创建新的 MCP server 配置 |
| `mcp-servers:update` | 修改 MCP server 配置 |
| `mcp-servers:delete` | 删除 MCP server 配置 |

<Note>
如果某个角色同时拥有 `mcp-servers:read` 和 `mcp-servers:invoke`，那么它可以查看并使用该工作区中的所有 MCP servers 和 integrations。
</Note>

关于 RBAC 的更多内容，请参阅[Role-based access control](/langsmith/rbac)。

#### 创建带工具权限的角色

<Steps>
  <Step title="打开角色设置">
    进入 **Settings > Roles**，点击 **Create role**。
  </Step>
  <Step title="配置 MCP Servers 权限">
    展开 **MCP Servers** 区块，选择要包含的权限。例如，对于只需要使用工具而不需要管理 server 配置的用户，可以授予 `Read` 和 `Invoke`。
  </Step>
  <Step title="分配角色">
    在 **Settings > Members** 中，把该角色分配给工作区中的用户。
  </Step>
</Steps>

### 基于属性的访问控制

基于属性的访问控制，ABAC，会在 RBAC 之上增加资源级粒度。管理员可以为单个 MCP server 或 integration 打标签，并基于这些标签创建策略，用于授予或限制访问。

ABAC 在工具场景中作用于两类资源：

| Resource type | Applies to |
|---------------|-----------|
| `mcp_server` | 添加到工作区中的自定义 MCP servers |
| `fleet_integration` | 内置 integrations，例如 Gmail、Slack、GitHub 等 |

<Note>
即使某个角色没有任何 `mcp-servers:*` 的 RBAC 权限，它仍然可以通过 ABAC allow policy 被授予对特定打标资源的访问权，例如只允许访问 Notion 和 Gmail。反过来，拥有宽泛 RBAC 访问权的角色，也可以通过 ABAC deny policy 被限制访问某些特定资源。
</Note>

关于策略结构、操作符，以及如何通过 API 管理策略的细节，请参阅[Attribute-based access control](/langsmith/abac)。

### 工作区集成策略

内置 integrations 还有额外的一层控制：工作区级别的启用或禁用开关，可在 **Settings > Integrations > Access control** 中管理。它会作为管理员控制的基础门槛，并在用户级 RBAC 和 ABAC 之前先运行。

如果某个 integration 在工作区级别被禁用，那么无论用户角色或 ABAC 策略如何，都无法访问它。

<Note>
只有管理员用户可以看到 Access control 页面，也就是需要 `workspaces:manage` 权限。
</Note>

### 策略求值顺序

这三层会按顺序依次求值。对于自定义 MCP servers 和内置 integrations，顺序略有差异：

**自定义 MCP servers：**

```
ABAC deny → RBAC → ABAC allow
```

**内置 integrations：**

```
Workspace policy gate → ABAC deny → RBAC → ABAC allow
```

在每个步骤中：
1. **Workspace policy gate**，仅适用于 integrations：如果 integration 被禁用，则直接拒绝访问，不再继续后续求值
2. **ABAC deny**：如果有 deny policy 命中，则拒绝访问。deny 总是优先
3. **RBAC**：如果用户角色授予了所需权限，则允许访问，除非还需要第 4 步
4. **ABAC allow**：如果 RBAC 没有授予访问权，allow policy 仍然可以对特定打标资源放行

## 可观测性与审计轨迹

Fleet 中的 agent 操作都会记录到结构化的 [LangSmith trace](/langsmith/observability) 中，包括工具调用、决策过程和输出。你可以对 traces 进行查看、搜索和导出。

结合 agent identity 和 permissions，tracing 可以帮助你知道：哪个 agent 执行了操作、它是代表谁执行的、用了什么凭证，以及它在每一步具体做了什么。

## Human-in-the-loop 监督

Fleet 提供了一个[集中式收件箱](https://smith.langchain.com/agents/inbox)，用于审查所有 agent 发起的操作。你可以把 agent 配置为：在执行某些特定操作前暂停并请求批准，然后在一个地方统一查看、批准、编辑或拒绝。

关于设置说明，请参阅[Human-in-the-loop](/langsmith/fleet/essentials#human-in-the-loop)。
