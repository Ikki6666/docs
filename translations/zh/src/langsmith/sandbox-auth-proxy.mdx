auth proxy 让 sandbox 中的代码可以调用外部 API，例如 OpenAI、Anthropic、GitHub，而无需硬编码凭证。当你在 sandbox 上配置好它后，一个运行在 sandbox 之外的 egress proxy 会自动把身份验证请求头注入到匹配的出站请求中，所需凭证来自工作区密钥，或者来自你在 proxy 配置中提供的只写凭证。

<Warning>
在创建引用这些密钥的 sandbox 之前，你必须先在 LangSmith [workspace](/langsmith/administration-overview#workspaces) 设置中配置好相关密钥，例如 `OPENAI_API_KEY`。
</Warning>

## 委托 LangSmith 访问

访问委托让 sandbox 中的代码无需在 sandbox 内使用 API key 即可调用 LangSmith API。auth proxy 会为发往你的 LangSmith API 主机的请求注入凭证。

使用 `POST /v2/sandboxes/boxes` 创建 sandbox 时，在请求体顶层设置 `access_delegation`：

- **`INHERIT`**：设置 `{"mode": "INHERIT"}` 以继承调用方当前可委托的权限。不要包含 `permissions`。
- **`EXPLICIT`**：设置 `{"mode": "EXPLICIT", "permissions": ["sandboxes:read"]}` 以将访问限制为你持有的特定权限。列表不能为空。

两种模式在每次请求时都仍受调用方当前权限的约束。workspace 和 organization 管理权限无法委托。工作区服务密钥也可以委托访问；收窄其角色会收窄 sandbox 的访问权限，删除该密钥则会撤销访问。

在 sandbox 内部，直接调用 HTTPS LangSmith API 端点，无需提供自己的凭证。在委托授权下运行的 sandbox 不能向另一个 sandbox 授予访问权限。

## 出站与网络访问控制

用于注入凭证的同一个 `proxy_config`，也控制 sandbox 可以访问哪些目标。访问控制在 sandbox 主机上按连接强制执行，因此对 `access_control` 的更改会立即生效。

### 出站如何工作

- **访问控制作用于每一条出站 TCP 连接**，无论是不是 HTTP。
- **匹配到规则或 callback 的主机的 HTTPS 流量会被 proxy 解密**，以便注入 headers；sandbox 信任 proxy 的 CA。未匹配主机的 HTTPS 流量以及所有非 HTTP 连接（包括 PostgreSQL、SSH 和 Redis）则原样透传。80 和 443 端口保留给 HTTP 和 TLS；在这两个端口上运行非 HTTP 协议无法工作。
- **按主机名寻址目标。** 到字面 IP 地址的非 HTTP 端口直接原始 TCP 连接会被丢弃，即使该 IP 在 `allow_list` 上也是如此。到字面 IP 的 HTTPS 也会被丢弃，因为 proxy 需要 TLS 握手中的主机名。只有 80 端口上的明文 HTTP 可以针对字面 IP 工作。
- **只有 TCP 会离开 sandbox。** UDP（包括 QUIC）和 ICMP 会被丢弃。

### 默认出站策略

在没有 `access_control` 的情况下，**每个主机名在每个 TCP 端口上都可达**，除非你的组织处于[受限出站](#organization-level-restricted-egress)状态。唯一的例外是解析到私有、回环或云元数据地址的主机，proxy 会拒绝拨号到这些地址。对于使用 `access_delegation` 创建的 sandbox，你的 LangSmith API 主机豁免于私有地址检查，因此主机名解析到私有地址的自托管安装（例如内部负载均衡器）仍可以服务委托请求。除此之外不会打开任何其他私有目标，回环和云元数据地址仍被阻止。添加一个 `access_control` 可以收紧这一策略。

要在允许任意主机的 HTTP 和 HTTPS 的同时阻止所有其他端口，可以使用带端口限定的允许列表。`*` 匹配每个主机名：

```json
{
  "access_control": {
    "allow_list": ["*:80", "*:443"]
  }
}
```

在此基础上添加 `host:PORT` 条目即可开放特定的原始 TCP 目标，例如 `db.example.com:5432`。

### 允许列表与拒绝列表

在 `proxy_config` 中添加一个 `access_control` 对象，并配置 **二选一** 的 `allow_list` 或 `deny_list`，不能同时设置，否则请求会被拒绝：

| Mode | Behavior |
|------|----------|
| `allow_list` | **默认拒绝。** 只有列出的目标才可访问，不限协议。列出 sandbox 需要的每个主机，包括你的 `rules` 和 `callbacks` 所针对的 HTTP(S) 主机 |
| `deny_list` | **默认允许。** 除被列出的目标之外，其余所有目标在任何协议下都可访问 |

两个列表对 HTTP、HTTPS 和原始 TCP 一视同仁。两种模式都不区分协议；使用端口后缀可以把一个条目限制到单个端口。

<Warning>
`deny_list` 只会阻止你列出的主机。`{"deny_list": ["example.com"]}` 会在每个端口上阻止 `example.com`，并让其他所有主机在每个端口上都可达，包括 DNS、SSH 和数据库端口。要在所有地方关闭原始 TCP，请使用 `["*:80", "*:443"]` 这样的 `allow_list`。
</Warning>

### 模式语法

每个 `allow_list` 或 `deny_list` 条目支持以下形式：

| Pattern | Meaning |
|---------|---------|
| `host` | 纯主机名，对应**所有端口** |
| `host:PORT` | 指定主机的精确 `PORT`。`db.example.com:5432` 只覆盖 5432；其他端口需要另加条目 |
| `*.example.com` | Glob，遵循 RFC 1034 风格。它**不包含**顶级域名本身，即不包括 `example.com`。可以带端口 |
| `~regex` | 针对主机名的正则匹配，覆盖所有端口。不会进一步解析端口后缀 |
| `1.2.3.4` / `[::1]` | 字面 IP。可以带端口：`1.2.3.4:443`、`[::1]:22` |
| `10.0.0.0/8` | CIDR。不能带端口 |

匹配针对的目标与 sandbox 寻址它的方式完全一致。主机名条目匹配对那个主机名发出的请求；IP 或 CIDR 条目匹配对字面 IP 地址发出的请求。两者都不会被解析：`deny_list: ["203.0.113.0/24"]` 不会阻止 `foo.example.com`，即使它解析到该范围内；`allow_list: ["203.0.113.7"]` 也不会放行它。由于到字面 IP 的原始 TCP 和 HTTPS 会在访问控制运行前被丢弃（参见[出站如何工作](#how-egress-works)），IP 和 CIDR 条目只会影响直接指名该 IP 的、80 端口上的明文 HTTP 请求。

无法解析的条目（例如 `example.com:abc`、`example.com:99999`，或带端口的 CIDR）会在创建或更新 sandbox 时被拒绝。

### 组织级受限出站

受限出站会把 sandbox 连接限制到一个由 LangSmith 管理的主机和端口允许列表。它默认适用于非 Enterprise 组织，也适用于主动申请的组织。获得批准豁免的组织可以使用不受限的出站。

该允许列表支持常见开发任务，包括安装软件包、访问源代码仓库和调用模型 API。它包括 PyPI、npm、GitHub、OpenAI、Anthropic 和 LangSmith，主要通过 443 端口上的 HTTPS 访问。部分软件包仓库也允许 80 端口上的 HTTP。

当你的组织启用了受限出站时，LangSmith 会阻止该允许列表之外的目标。组织策略会替换调用方提供的 `access_control` 设置，并禁用 `no_proxy` 绕过。把一个目标加入你 sandbox 的 `allow_list`，或为它配置凭据，都不会授予超出组织策略的访问权限。

组织策略变更不会自动更新已有的 sandboxes。启动或唤醒已有 sandbox 会复用其存储的网络配置。

### 申请不受限访问

如果你的 sandbox 需要托管允许列表之外的目标，请[提交支持工单](https://support.langchain.com)为你的组织申请不受限出站。请包含以下细节：

- **组织**：你的组织或 workspace ID 以及部署区域。
- **网络要求**：目标主机名、端口，以及用例描述。
- **受影响的 sandbox**：对于已有 sandbox，其 ID 和连接错误。

获得批准的豁免会移除组织管理的允许列表要求。你 sandbox 自身的访问控制，以及平台针对访问私有或保留 IP 地址的保护仍然适用。豁免不会自动更改已有的 sandbox 配置。

### 连接数据库，原始 TCP

如果你的组织启用了受限出站，在连接托管允许列表之外的数据库之前，请先[申请不受限访问](#request-unrestricted-access)。

如果你希望 sandbox 中的代码能通过 `psql`、`dbt` 或任意驱动连接外部 PostgreSQL 数据库，就要把对应主机和端口加入 allow-list。由于 `allow_list` 是默认拒绝，你还必须同时列出 sandbox 需要访问的任何 HTTP(S) 主机。除非你还需要其他端口，否则请把它们固定到 `:443`：

```bash
curl -X POST "$LANGSMITH_ENDPOINT/v2/sandboxes/boxes" \
  -H "x-api-key: $LANGSMITH_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "db-sandbox",
    "proxy_config": {
      "access_control": {
        "allow_list": [
          "db.example.com:5432",
          "api.openai.com:443"
        ]
      }
    }
  }'
```

到 `db.example.com:5432` 的连接会在 TCP 层直接透传，不做拦截，因此 PostgreSQL wire protocol，以及其上的 TLS、host-key checking 和其他端到端协议都能原样工作。

<Note>
创建 sandbox 时会启动它，并在其报告 `ready` 后返回，因此无需额外添加等待步骤。如果之后需要再次检查状态，可通过 `GET /api/v2/sandboxes/boxes/{name}/status` 查看当前状态。
</Note>

## 配置 auth proxy 规则

创建 sandbox 时添加 `proxy_config`，或者通过 patch 更新现有 sandbox 的 `proxy_config`。一个 `proxy_config` 包含：

| Field | Description |
|-------|-------------|
| `rules` | Header 注入规则和 provider 认证规则。启用的 header 规则按列表顺序 first-match-wins；`aws` 和 `gcp` 规则无论位置如何都会匹配其 provider 的主机 |
| `callbacks` | 动态凭证查找；参见 [Callback 凭证示例](#callback-凭证示例) |
| `access_control` | `allow_list` 或 `deny_list`；参见[允许列表与拒绝列表](#允许列表与拒绝列表) |
| `description` | 可选，最多 1024 个字符。这份配置允许 sandbox 访问什么，便于交给 agent |

每条规则都可以指定：

| Field | Description |
|-------|-------------|
| `name` | 必填。规则的标识符 |
| `type` | header 注入规则省略；provider 认证规则设为 `aws` 或 `gcp` |
| `match_hosts` | header 规则必填；在 `aws` 和 `gcp` 规则上会被拒绝。纯主机名，或在可注册域名前的 `*.` 通配符（`*.github.com`，而不是 `*.com` 或 `*`）。不带 scheme、路径或端口。通配符不匹配顶级域名 |
| `match_paths` | 要匹配的路径，为空则表示所有路径。仅限 header 规则 |
| `headers` | 要注入的请求头，每个都包含 `name`、`type` 和 `value`。仅限 header 规则 |
| `aws` / `gcp` | Provider 凭据；参见[对 AWS 请求进行身份验证](#对-aws-请求进行身份验证)和[对 GCP 请求进行身份验证](#对-gcp-请求进行身份验证) |
| `env_vars` | 在该规则启用期间为 sandbox 设置的环境变量 |
| `enabled` | 默认为 `true` |
| `description` | 可选，最多 1024 个字符。这条规则允许 sandbox 访问什么 |

### Header 类型

每个 header 都带有一个必填的 `type`，用于控制其值如何存储和展示：

| Type | Description |
|------|-------------|
| `workspace_secret` | 使用 `{KEY}` 语法引用一个工作区密钥。在应用 proxy 配置时解析 |
| `plaintext` | 原样存储并原样返回。适用于非敏感 header |
| `opaque` | 只写。值会静态加密保存，且永远不会通过 API 返回 |

### 从规则设置环境变量

一条规则的 `env_vars` 是明文环境变量，在该规则启用期间会为 sandbox 中的每个 command 设置。当某个工具拒绝运行，除非存在某个凭据环境变量时（即使 proxy 会在传输中注入真实凭据）可以使用：给变量设置一个占位值让 command 启动，而由 proxy 提供真实凭据。

这些值是明文的，且会通过 API 返回，因此切勿将 secret 放入 `env_vars`。请改用 `workspace_secret` 或 `opaque` 类型的 header。

环境变量按以下顺序解析，从最低优先级到最高优先级：

1. **snapshot 镜像的 `ENV`**，当 sandbox 选择加入 `apply_image_config` 时。
2. **已启用的 proxy 规则**：当两条已启用的规则声明了相同的名称时，`rules` 中靠后的规则优先。
3. **sandbox 自身的 `env_vars`**：显式按 sandbox 设置的值会覆盖来自规则的值。

由已启用的 AWS 或 GCP auth 规则管理的变量（`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_EC2_METADATA_DISABLED`、`AWS_CA_BUNDLE`；`CLOUDSDK_AUTH_ACCESS_TOKEN`、`CLOUDSDK_CORE_CUSTOM_CA_CERTS_FILE`）位于此顺序之外：当匹配的 auth 规则启用时，声明了这些名称之一的规则或 sandbox `env_vars` 条目会被拒绝。

每个 sandbox 还拥有指向系统信任存储的常见 CA-bundle 环境变量，其中包括 proxy 的 CA，因此固定自己 bundle 的工具仍然可以校验 proxy 注入的主机。你可以自行设置其中任何一个来覆盖。

```json
{
  "name": "github-api",
  "match_hosts": ["api.github.com"],
  "headers": [
    {"name": "Authorization", "type": "opaque", "value": "Bearer <github-token>"}
  ],
  "env_vars": {"GH_TOKEN": "proxy-injected"}
}
```

## 对 AWS 请求进行身份验证

当 sandbox 中的代码需要通过 AWS SDK 或 CLI 调用 AWS 服务时，可使用 AWS auth 规则。proxy 会把真实 AWS 凭证保留在 sandbox 外，并对到 `*.amazonaws.com` endpoint 的出站 HTTPS 请求应用 AWS SigV4 签名。

当 agent 代码需要查看 S3 对象、调用 Bedrock，或访问其他 AWS endpoint 时，这很有用，因为你不需要把长期 AWS access keys 暴露在 sandbox 文件、环境变量、shell 历史或日志中。sandbox 会收到占位式的 `AWS_ACCESS_KEY_ID` 和 `AWS_SECRET_ACCESS_KEY` 值（外加 `AWS_EC2_METADATA_DISABLED=true` 和 `AWS_CA_BUNDLE`），让 SDK 的凭证发现逻辑能正常工作，而 proxy 会把请求携带的内容替换为真实的 SigV4 签名。只有 `service.region.amazonaws.com` 主机、S3 virtual-hosted 和 path-style 主机，以及少数全局 endpoint（例如 `iam`、`sts` 和 `s3`）会被签名；到匹配 AWS 主机的明文 HTTP 会被以 `403` 拒绝。

<Warning>
不要把真实 AWS access keys 设置为 sandbox 环境变量。请通过 `workspace_secret` 或 `opaque` 的 proxy 值来配置它们。明文 AWS 凭证值会被拒绝。
</Warning>

AWS auth 规则与 header 注入规则不同：

- `type` 必须设置为 `aws`
- 凭证需要放在 `aws` 对象下
- 不要再设置 `match_hosts`、`match_paths` 或 `headers`，因为 AWS 主机匹配逻辑内建在 proxy 中
- 每个 sandbox 最多只能配置一个 AWS auth 规则。该上限会计入所有 AWS 规则，包括已禁用的规则。

```bash
curl -X POST "$LANGSMITH_ENDPOINT/v2/sandboxes/boxes" \
  -H "x-api-key: $LANGSMITH_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "aws-sandbox",
    "proxy_config": {
      "rules": [
        {
          "name": "aws",
          "type": "aws",
          "enabled": true,
          "aws": {
            "access_key_id": {
              "type": "workspace_secret",
              "value": "{AWS_ACCESS_KEY_ID}"
            },
            "secret_access_key": {
              "type": "workspace_secret",
              "value": "{AWS_SECRET_ACCESS_KEY}"
            }
          }
        }
      ]
    }
  }'
```

### 通过 SDK 配置 AWS auth

<CodeGroup>

```python Python
from langsmith.sandbox import (
    SandboxClient,
    aws_auth,
    proxy_config,
    workspace_secret,
)

client = SandboxClient()

client.create_sandbox(
    name="aws-sandbox",
    proxy_config=proxy_config(
        rules=[
            aws_auth(
                access_key_id=workspace_secret("AWS_ACCESS_KEY_ID"),
                secret_access_key=workspace_secret("AWS_SECRET_ACCESS_KEY"),
            )
        ]
    ),
)
```

```ts TypeScript
import {
  SandboxClient,
  awsAuth,
  proxyConfig,
  workspaceSecret,
} from "langsmith/sandbox";

const client = new SandboxClient();

await client.createSandbox({
  name: "aws-sandbox",
  proxyConfig: proxyConfig({
    rules: [
      awsAuth({
        accessKeyId: workspaceSecret("AWS_ACCESS_KEY_ID"),
        secretAccessKey: workspaceSecret("AWS_SECRET_ACCESS_KEY"),
      }),
    ],
  }),
});
```

</CodeGroup>

sandbox 就绪后，可以在其中正常使用 AWS SDK 或 CLI。SDK 或 CLI 会发现这些占位式 AWS 环境变量，而 proxy 会为出站 AWS 请求附加真实 SigV4 签名。proxy 不会设置区域：请通过 sandbox 的 `env_vars` 或规则的 `env_vars` 设置 `AWS_REGION`，否则大多数 SDK 和 CLI 调用会在到达 proxy 之前失败。

<Note>
静态 AWS auth 接受 access key ID 和 secret access key，但不接受调用方提供的 session token。启用了 AWS proxy 角色认证的 deployment 还支持如下所述的 IAM 角色。
</Note>

### 使用 IAM 角色进行认证

AWS proxy 角色让 LangSmith 可以承担一个客户 IAM 角色，并使用可续期的临时凭证为受支持的 AWS HTTPS 请求签名。它可以在有或没有 [S3 挂载](/langsmith/sandbox-mounts#authenticate-with-an-iam-role)的情况下工作，不会把真实凭证暴露给 sandbox 代码。

此选项要求 deployment 支持 AWS proxy 角色认证。ECR registry 角色认证是一个独立的功能。在 **Create sandbox > Network** 中，启用 AWS 认证并选择 **AWS IAM role**。表单会显示客户角色必须信任的确切 LangSmith principal 和 workspace External ID。按照链接的设置说明配置 trust 和 permissions policies，然后在 **AWS role ARN** 中输入客户角色。

<Note>
下面的 SDK 示例要求一个支持 Python 的 `aws_auth(role_arn=...)` 或 TypeScript 的 `awsAuth({ roleArn })` 的版本。仅后端支持并不会把这些 helper 添加到较旧的 SDK 版本中。
</Note>

要在不使用挂载的情况下配置角色，请把它传入 proxy 配置：

<CodeGroup>

```python Python
from langsmith.sandbox import SandboxClient, aws_auth, proxy_config

client = SandboxClient()

sandbox = client.create_sandbox(
    name="aws-role-sandbox",
    proxy_config=proxy_config(
        rules=[
            aws_auth(role_arn="arn:aws:iam::123456789012:role/LangSmithSandbox")
        ]
    ),
)
```

```ts TypeScript
import { SandboxClient, awsAuth, proxyConfig } from "langsmith/sandbox";

const client = new SandboxClient();

const sandbox = await client.createSandbox({
  name: "aws-role-sandbox",
  proxyConfig: proxyConfig({
    rules: [
      awsAuth({ roleArn: "arn:aws:iam::123456789012:role/LangSmithSandbox" }),
    ],
  }),
});
```

</CodeGroup>

```bash

  -H "x-api-key: $LANGSMITH_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "aws-role-sandbox",
    "proxy_config": {
      "rules": [
        {
          "name": "aws",
          "type": "aws",
          "enabled": true,
          "aws": {
            "role_arn": "arn:aws:iam::123456789012:role/LangSmithSandbox"
          }
        }
      ]
    }
  }'
```

请把示例 ARN 替换为你配置的客户角色。单规则上限仍然适用。角色认证在创建时配置：更新可以保留现有角色，但不能添加、移除、更改或禁用它。要更改角色认证，请创建一个新的 sandbox。

该角色的有效 AWS 权限会作用于所有受支持的请求。LangSmith 不会为这条规则添加由挂载派生的 session policy。只读 S3 挂载会阻止文件系统写入，而不是阻止 IAM 允许的直接 S3 API 写入。请把客户角色限制到 sandbox 所需的服务、资源和操作。

LangSmith 会按需续期临时凭据，并在停止/启动后重新获取。如果续期暂时不可用，缓存的凭据只在过期之前可用。授权被拒绝或凭据过期会按 fail closed 处理，不会回退到静态 keys。

## 对 GCP 请求进行身份验证

当 sandbox 中的代码需要通过 Google SDK 或 CLI 调用 Google APIs 时，可使用 GCP auth 规则。proxy 会把 service account JSON 保留在 sandbox 外，并对到 `googleapis.com` 及其子域的出站 HTTPS 请求完成身份验证。

当 agent 代码需要查看 GCS 对象，或调用其他 Google API，同时又不想把 service account JSON 暴露在 sandbox 文件、环境变量、shell 历史或日志中时，这非常有用。sandbox 会收到占位式的 `CLOUDSDK_AUTH_ACCESS_TOKEN`（外加 `CLOUDSDK_CORE_CUSTOM_CA_CERTS_FILE`），让 `gcloud` 可以运行，而 proxy 会把请求携带的授权替换为从配置的 service account 签发的 token。通过 Application Default Credentials 发现凭据的 Google 客户端库不会读取这些变量，会找不到凭据；只有 `gcloud` 和直接 HTTPS 调用受支持。

<Warning>
不要把真实 service account JSON 设置为 sandbox 环境变量。请把它配置为 `workspace_secret` 或 `opaque` 的 proxy 值。明文 GCP 凭证值会被拒绝。
</Warning>

GCP auth 规则与 header 注入规则不同：

- `type` 必须设置为 `gcp`
- 凭证需要放在 `gcp.service_account_json` 下
- `gcp.scopes` 必须是一个非空的 OAuth scopes 列表
- proxy 会自动匹配 `googleapis.com` 及其子域，并使用配置好的 service account 为这些请求进行身份验证。`google.com` 下的主机不会被匹配。到匹配主机的明文 HTTP 会被以 `403` 拒绝
- 每个 sandbox 最多只能配置一个 GCP auth 规则。该上限会计入所有 GCP 规则，包括已禁用的规则。

SDK 中的 `gcp_auth` 和 `gcpAuth` 辅助函数会生成相同的规则结构。

```bash
curl -X POST "$LANGSMITH_ENDPOINT/v2/sandboxes/boxes" \
  -H "x-api-key: $LANGSMITH_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "gcp-sandbox",
    "proxy_config": {
      "rules": [
        {
          "name": "gcp",
          "type": "gcp",
          "enabled": true,
          "gcp": {
            "service_account_json": {
              "type": "workspace_secret",
              "value": "{GCP_SERVICE_ACCOUNT_JSON}"
            },
            "scopes": [
              "https://www.googleapis.com/auth/devstorage.read_only"
            ]
          }
        }
      ]
    }
  }'
```

## GitHub 示例

[Open SWE](https://github.com/langchain-ai/open-swe/blob/main/agent/integrations/langsmith.py) 会在 sandbox 外部签发一个短期有效的 GitHub App installation token，然后通过 patch 的方式把只写型 `opaque` proxy 规则注入 sandbox。这能让短期有效的 GitHub access token 既不会出现在 sandbox 文件系统中，也不会落在部署环境变量里。

配置两条规则：

| Host | Header |
|------|--------|
| `api.github.com` | `Authorization: Bearer <github-token>`，供 `gh` 和 REST API 调用使用 |
| `github.com`, `*.github.com` | `Authorization: Basic <base64("x-access-token:<github-token>")>`，供 Git over HTTPS 的 clone、fetch 和 push 等操作使用 |

```python Python
import base64
import os
from typing import Any

import httpx


def github_proxy_rules(github_token: str) -> list[dict[str, Any]]:
    basic_auth = base64.b64encode(
        f"x-access-token:{github_token}".encode()
    ).decode()

    return [
        {
            "name": "github-api",
            "match_hosts": ["api.github.com"],
            "headers": [
                {
                    "name": "Authorization",
                    "type": "opaque",
                    "value": f"Bearer {github_token}",
                }
            ],
            "env_vars": {"GH_TOKEN": "proxy-injected"},
        },
        {
            "name": "github",
            "match_hosts": ["github.com", "*.github.com"],
            "headers": [
                {
                    "name": "Authorization",
                    "type": "opaque",
                    "value": f"Basic {basic_auth}",
                }
            ],
        },
    ]


def configure_github_proxy(sandbox_name: str, github_token: str) -> None:
    endpoint = os.environ.get(
        "LANGSMITH_ENDPOINT", "https://api.smith.langchain.com"
    )
    response = httpx.patch(
        f"{endpoint}/v2/sandboxes/boxes/{sandbox_name}",
        headers={"x-api-key": os.environ["LANGSMITH_API_KEY"]},
        json={"proxy_config": {"rules": github_proxy_rules(github_token)}},
        timeout=180.0,
    )
    response.raise_for_status()
```

在创建 sandbox 之后，或重新附着到一个 sandbox 之后，调用 `configure_github_proxy`。由于 GitHub App installation tokens 会过期，因此每次你为新一轮运行复用 sandbox 时，都需要刷新 proxy 配置。

<Warning>
`PATCH` 会整体替换已存储的 `proxy_config`。如果 sandbox 还使用了 `access_control` 或 `callbacks`，请把它们包含在每次更新中，否则会被丢弃。你留空的 opaque header 值会从当前配置沿用。
</Warning>

`github-api` 规则会把 `GH_TOKEN` 设置为一个非敏感占位值，从而满足 `gh` CLI 的本地凭据检查。命令随后无需逐条加前缀即可运行：

```bash
gh repo view langchain-ai/langchain
gh pr list --repo langchain-ai/langchain
gh repo clone langchain-ai/langchain
```

该占位值永远不会离开 sandbox。真正的 `Authorization` 请求头由 proxy 注入到出站请求中。

## Callback 凭证示例

静态的 `workspace_secret` 规则会在应用 proxy 配置时从工作区读取凭证，而 `opaque` 规则则允许你的应用像上面的 [GitHub token 示例](#github-example) 那样注入短期有效凭证。如果某类凭证必须在 proxy 执行时由你自己的服务动态解析，请使用 **callback**。proxy 会向你提供的 URL 发起 POST 请求，你的端点返回要注入的 headers，proxy 会对结果做缓存。

callbacks 与 rules 一样，都配置在 `proxy_config` 下：

| Field | Description |
|-------|-------------|
| `match_hosts` | 要拦截的主机，语法与 rules 相同，支持 `*.github.com` 这样的 glob |
| `url` | 你的 callback endpoint。必须是解析到公共地址的 `http://` 或 `https://` URL；私有、回环、Kubernetes 内部和云元数据目标会被拒绝 |
| `request_headers` | proxy 发往 callback 时附带的 headers，例如用于验证请求的 HMAC 或共享密钥。这里只允许 `plaintext` 和 `opaque` 类型，不允许 `workspace_secret` |
| `ttl_seconds` | 必填。解析出的 headers 缓存多久后失效并重新触发 callback，范围必须在 60 到 3600 之间 |
| `full_request` | 设为 `true` 时，对匹配主机的每个请求都会触发 callback（不缓存），并且 body 包含一个 `request` 快照：`method`、`url`、`scheme`、`host`、`path`、`query`、`headers`，以及最多 1 MiB 的 body（作为 `body_base64`，`body_truncated` 标记被截断） |

**静态 rules 优先。** 如果一条启用的 header 注入规则同时匹配了主机和路径，那么该请求的 callback 就会被跳过。`rules` 内部是 first-match-wins，多个 callbacks 之间也是同样规则。

### Callback 协议

每当 proxy 需要为一个匹配主机在缓存未命中的情况下解析凭证时，它会发起如下请求：

```
POST <callback.url>
Content-Type: application/json
X-LangSmith-Signature-JWT: <signature>
<request_headers from your config, attached verbatim except Content-Type and X-LangSmith-Signature-JWT, which the proxy always sets>

{
  "host": "api.example.com",
  "port": 443,
  "identity": {
    "tenant_id": "<workspace-uuid>",
    "sandbox_id": "<sandbox-uuid>",
    "organization_id": "<organization-uuid>",
    "ls_user_id": "<creator-uuid>"
  }
}
```

`identity` 告诉你的端点是哪个 sandbox 在询问，因此一个 callback URL 可以服务多个 sandbox，并按 sandbox 或按用户签发凭据。`ls_user_id` 是创建用户，当 sandbox 是用 workspace 或 service key 创建时会被省略。忽略你不认识的字段和 headers；proxy 可能会添加更多。

你的端点必须返回 `2xx`，并带有如下 JSON：

```json
{
  "headers": {
    "Authorization": "Bearer <token>",
    "X-Org-Id": "..."
  }
}
```

proxy 会把响应中的每个 header 都注入 sandbox 的出站请求，并按 `ttl_seconds` 缓存结果。任何非 2xx 响应、传输错误或格式错误的 JSON 都会按 fail closed 处理，也就是 sandbox 请求会以 `502 callback resolution failed` 被拒绝，不会注入任何 header，也不会缓存结果。重定向不会被跟随，并算作失败。

### 校验 callback 请求

`request_headers` 让你的端点检查你自己选择的共享密钥。要验证请求来自 LangSmith 且在传输中未被篡改，请检查 `X-LangSmith-Signature-JWT` header。它是一个使用 Ed25519 密钥签名的 JWT（`alg: EdDSA`），其公钥发布在 `<LANGSMITH_ENDPOINT>/.well-known/jwks.json`，由 token 的 `kid` 选择。

| Claim | Expected value |
|-------|----------------|
| `iss` | 你的 LangSmith endpoint origin，例如 `https://api.smith.langchain.com` |
| `sub` | `langsmith-sandbox-callback` |
| `aud` | 你的 callback URL，与配置完全一致 |
| `exp` | 签发后五分钟；拒绝过期的 token |
| `body_sha256` | 原始请求 body 的十六进制 SHA-256 |

对照 JWKS 验证签名，检查上面的每个 claim，对你收到的 body 求哈希并与 `body_sha256` 比较。然后信任 body 中的 `identity`。
