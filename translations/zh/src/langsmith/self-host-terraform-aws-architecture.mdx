了解 [AWS Terraform modules](https://github.com/langchain-ai/terraform/tree/main/modules/aws) 会预配哪些内容，以及各部分如何协同工作，这样你就可以在运行 `make apply` 之前规划容量、加固安全并自定义 LangSmith 部署。

在规划上线或排查现有部署时，可以将本页作为参考。本页涵盖：

- 平台分层与应用核心服务。
- AWS 托管服务、IRSA 角色和集群基础设施。
- 网络拓扑、ingress 选项以及 TLS/DNS 策略。
- LangSmith Deployment add-on。
- module 依赖图与可选的安全 module。

如果已准备好安装，请从[部署流程指南](/langsmith/self-host-terraform-aws-deploy)开始。

## 平台分层

LangSmith 在 AWS 上分两个阶段部署，外加一个可选 add-on。基础设施阶段预配云基础，应用阶段安装 LangSmith Helm chart。LangSmith Deployment add-on 为可选项，它添加 host-backend、listener 和 operator 服务，用于在 UI 中管理 LangGraph 应用。

<img src="/images/self-hosted-terraform/aws-architecture.png" alt="LangSmith on AWS service layout" />

| 阶段 | 分层 | 新增内容 |
|---|---|---|
| Infrastructure | AWS infrastructure | VPC + 私网/公网子网 + 单 NAT gateway、EKS 集群 + 托管节点组 + cluster autoscaler、RDS PostgreSQL、ElastiCache Redis、S3 bucket + VPC Gateway Endpoint、ALB + ALB controller + EBS CSI driver + metrics server、k8s-bootstrap（KEDA、ESO、默认启用 Envoy Gateway）。可选：Network Firewall、WAF、CloudTrail、ALB access logs、SmithDB、sandboxes。 |
| Application | LangSmith application | backend、frontend、playground、queue、ace-backend、clickhouse。存储：RDS PostgreSQL（metadata）+ S3（经 VPC endpoint 的 trace blobs）。Ingress：Terraform ALB 转发到 Envoy Gateway（默认）、Istio 或 NGINX。设置 `enable_envoy_gateway = false` 时，ALB controller 会为 Ingress 自行预配一个 ALB。 |
| Add-on（`enable_deployments = true`） | LangSmith Deployment | host-backend、listener、operator。每个已部署 graph：api-server、queue、redis、postgres（由 operator 管理）。需要 KEDA（随基础设施通过 k8s-bootstrap 一同安装）。 |

## 组件与存储的对应关系

| 组件 | 存储后端 | 访问方式 |
|---|---|---|
| `backend` | RDS PostgreSQL | 私网子网、安全组 |
| `backend` | S3 bucket | IRSA + VPC Gateway Endpoint |
| `clickhouse` | EBS volume（GP3，EKS PVC） | 本地 |
| `redis` | ElastiCache 或 in-cluster | 私网子网、安全组 |
| LGP operator | RDS PostgreSQL（共享） | 私网子网、安全组 |

## 应用核心服务

这些 pods 运行在每个部署中。它们都会写入日志和指标；负载较重的组件（backend、queue、ingest-queue）支持水平扩缩容。

| 服务 | 用途 | 端口 | HPA | IRSA | 依赖 |
|---|---|---|---|---|---|
| `langsmith-frontend` | React UI | 3000 | 1 到 10 | 否 | `backend`、`platform-backend` |
| `langsmith-backend` | 主 API（traces、runs、projects、API keys、feedback） | 1984 | 3 到 10 | 是（S3） | Postgres、Redis、ClickHouse、S3 |
| `langsmith-platform-backend` | 组织与用户管理、认证、计费、设置 | 1986 | 1 到 10 | 是（S3） | Postgres、Redis、S3 |
| `langsmith-playground` | LLM prompt playground UI | 3001 | 1 到 10 | 是（Bedrock，当 `enable_bedrock_access = true`） | `backend` |
| `langsmith-queue` | Trace ingestion worker（Redis 到 ClickHouse + S3） | 无 | 3 到 10 + KEDA | 是 | Redis、ClickHouse、S3 |
| `langsmith-ingest-queue` | 专用的高吞吐量 ingestion worker | 无 | 3 到 10 + KEDA | 是 | Redis、S3 |
| `langsmith-ace-backend` | 异步计算（dataset runs、evaluations、后台任务） | 无 | 1 到 5 | 否 | Postgres、Redis |
| `langsmith-clickhouse` | 列式存储（trace spans、run metadata、eval 结果） | 无 | StatefulSet，单副本 | 否 | EBS GP3 PVC |

<Warning>
In-cluster ClickHouse 仅适用于 dev/POC（单 pod、无副本、无备份）。生产环境请使用 [LangChain Managed ClickHouse](/langsmith/langsmith-managed-clickhouse) 或自行管理的外部集群。
</Warning>

<Note>
[SmithDB](https://www.langchain.com/blog/introducing-smithdb?utm_source=docs) 是 LangSmith 专用的 observability 后端，chart v16 起可用于 self-hosted（参见 [self-hosted support](/langsmith/smithdb-sdk-migration#about-self-hosted)）。AWS module 默认预配 ClickHouse。设置 `enable_smithdb = true` 还会预配 SmithDB 的依赖：一个专用的 metastore RDS PostgreSQL 实例（`smithdb_metastore_source = "create"`，默认值）、一个 S3 object-store bucket、一个 IRSA role，以及用于 NVMe instance-store 节点的 Karpenter NodePool。ClickHouse 在 chart v16 和 v17 上保持启用。参见部署指南中的 [SmithDB](/langsmith/self-host-terraform-aws-deploy#smithdb)。
</Note>

### 一次性任务

Helm chart 在安装和升级时会运行三个 job：

| Job | 用途 |
|---|---|
| `langsmith-backend-migrations` | PostgreSQL schema 迁移 |
| `langsmith-backend-ch-migrations` | ClickHouse schema 迁移 |
| `langsmith-backend-auth-bootstrap` | 使用 `langsmith-config` 中的 `initial_org_admin_password` 创建初始组织和 admin 账号 |

## LangSmith Deployment add-on

当 `enable_deployments = true` 时，会额外安装三个服务，并注册一个 `LangGraphPlatform` CRD。用户在 LangSmith UI 中创建的每个 deployment 都会在 `langsmith` namespace 中产生一个由 operator 管理的 Kubernetes Deployment。

| 服务 | 用途 |
|---|---|
| `langsmith-host-backend` | LangGraph control plane API。管理 deployment 生命周期，提供 deployment metadata。IRSA 用于 S3 访问。 |
| `langsmith-listener` | 监听 host-backend 的 deployment 状态变化，创建和更新 `LangGraphPlatform` CRD。IRSA 用于 S3 访问。 |
| `langsmith-operator` | Kubernetes operator。调谐（reconcile）`LangGraphPlatform` CRD，为每个 agent 创建和删除 Deployment 与 Service。 |

## AWS 托管服务

当 `postgres_source = "external"` 且 `redis_source = "external"`（推荐的生产设置）时，Terraform 会预配以下 AWS 托管服务。

当 Fleet、LangSmith Chat 或 Insights 使用外部存储时，它们共享同一个 RDS 实例和 Redis 集群。一个 in-cluster Job 会创建各功能的逻辑数据库，每个功能拥有自己的 Redis DB index：1 给 Fleet，2 给 LangSmith Chat，3 给 Insights。DB 0 属于主安装。

### RDS PostgreSQL

- 默认规格：`db.t3.large`，私网子网，端口 5432。
- 默认配置：PostgreSQL 16，存储加密，10GB 自动扩容至 100GB，7 天备份，开启删除保护，启用 IAM 数据库认证。
- 存储组织、用户、projects、API keys、设置。
- 密钥流转：`setup-env.sh` 将密码存储在 SSM `/langsmith/{base_name}/postgres-password` 并传给 Terraform，Terraform 将其设置到实例上，并把 `connection_url` 写入 `langsmith-postgres` Kubernetes Secret。

### ElastiCache Redis

- 默认规格：`cache.m6g.xlarge`，私网子网，TLS 端口 6379。
- Redis 7.1，单一缓存节点，静态与传输中加密。
- Trace ingestion queue、pub/sub、短期缓存。
- 密钥流转：`setup-env.sh` 将 auth token 存储在 SSM `/langsmith/{base_name}/redis-auth-token` 并传给 Terraform，Terraform 将其设置到 replication group 上，并把 `connection_url` 写入 `langsmith-redis` Kubernetes Secret。

### Sandbox JuiceFS Redis

当 `enable_sandboxes = true` 时，Terraform 会为 JuiceFS sandbox 文件系统预配第二个专用的 ElastiCache Redis（`{base_name}-jfs-redis`，默认 `cache.m6g.large`，`noeviction` parameter group，7 天快照）。它还会添加一个 `sandbox-host` 托管节点组（默认 `m5d.metal`，带有 `sandbox.langsmith.com/host` taint）。

### S3 bucket

- Trace payload：大型输入与输出、附件。
- 通过 `langsmith_irsa_role` 使用 IRSA（无静态密钥）。VPC Gateway Endpoint，不经公共互联网。
- 使用 SSE-S3 加密，设置 `s3_kms_key_arn` 时使用 SSE-KMS。公共访问被阻止，bucket policy 通过 VPC endpoint 授予 LangSmith IRSA role 访问权限。
- 前缀：`ttl_s/`（短 TTL）和 `ttl_l/`（长 TTL）。
- 无论层级如何，S3 bucket 都是必需的。禁用 blob storage 会在大 payload 时导致集群故障。

### SSM Parameter Store

- 所有 LangSmith 机密的集中式 secret store。
- 流转：`source infra/scripts/setup-env.sh` 将机密写入 SSM。ESO `ClusterSecretStore` 读取这些机密，并投影出一个 `langsmith-config` Kubernetes Secret，Helm chart 通过 `config.existingSecretName` 挂载它。
- 前缀：`/langsmith/{name_prefix}-{environment}/`。

## 集群基础设施

两个 Terraform module 会安装 LangSmith 依赖的集群级服务。`eks` module 通过 `eks-blueprints-addons` 安装 AWS 集成 controller，并将 EBS CSI driver 作为 EKS add-on 安装；`k8s-bootstrap` module 安装工作负载依赖和 ingress gateway（参见 [Ingress 选项](#ingress-options)）：

| 服务 | 安装者 | Namespace | IRSA | 用途 |
|---|---|---|---|---|
| `aws-load-balancer-controller` | `eks` | `kube-system` | 是 | 通过 `TargetGroupBinding` 将 pods 注册到 Terraform 管理的 ALB，并在 ALB Ingress 模式下根据 Kubernetes Ingress 对象预配 ALB。 |
| `cluster-autoscaler` | `eks` | `kube-system` | 是 | 根据 pod 调度压力扩缩 EC2 节点组。 |
| `ebs-csi-driver` | `eks` | `kube-system` | 是 | 为 PersistentVolumeClaim 预配 EBS 卷（ClickHouse 使用）。 |
| Karpenter | `eks` | `karpenter` | 是 | 预配 SmithDB 的 NVMe instance-store 和计算节点。仅在 `enable_smithdb = true` 时安装。 |
| KEDA | `k8s-bootstrap` | `keda` | 否 | Kubernetes 事件驱动自动扩缩容。根据 Redis queue 深度扩缩 `queue` 和 `ingest-queue`。LangSmith Deployment add-on 必需。 |
| Envoy Gateway | `k8s-bootstrap` | `envoy-gateway-system` | 否 | ALB 后面的默认 ingress gateway。选择 Istio、NGINX 或 ALB Ingress 时会跳过。 |
| cert-manager | `k8s-bootstrap` | `cert-manager` | 可选 | 自动化 TLS 证书签发。`tls_certificate_source = letsencrypt` 时通过 ALB 使用 HTTP-01 issuer，无需 IRSA。`create_cert_manager_irsa = true` 时通过 Route 53 使用 DNS-01 并配有 IRSA role。仅在这两种情况下安装。 |
| External Secrets Operator | `k8s-bootstrap` | `external-secrets` | 是 | 将 SSM 参数同步到 `langsmith-config` Kubernetes Secret。 |

## IRSA 角色

IRSA 取代了静态凭证。IAM 信任 EKS 集群的 OIDC issuer；`langsmith`、`kube-system`、`external-secrets`、`cert-manager` 以及（启用 SmithDB 时的）`karpenter` 中的 service account 会被标注 role ARN，pods 通过 EKS token webhook 获取临时凭证。

| 角色 | 定义位置 | 使用者 | 权限 |
|---|---|---|---|
| `langsmith_irsa_role`（`{cluster_name}-irsa-role`） | `modules/eks` | LangSmith namespace 中的任意 service account：`backend`、`platform-backend`、`queue`、`ingest-queue`、`playground`、host-backend、listener、operator，以及 Fleet、LangSmith Chat 和 Insights worker | LangSmith bucket 上的 `s3:GetObject`、`s3:PutObject`、`s3:DeleteObject`、`s3:ListBucket`，当 `enable_bedrock_access = true` 时还包括 `bedrock:InvokeModel*`、`bedrock:ListFoundationModels` 和 `bedrock:GetFoundationModel` |
| `aws_iam_role.eso` | `aws/infra/main.tf` | ESO controller | 部署区域中 `/langsmith/{base_name}/*` 上的 `ssm:GetParameter`、`ssm:GetParameters`、`ssm:GetParametersByPath` |
| `aws_iam_role.cert_manager` | `modules/cert-manager` | `cert-manager` | zone 上的 Route 53 `ChangeResourceRecordSets` 和 `ListResourceRecordSets`，以及 `GetChange` 和 `ListHostedZonesByName`。仅在 `create_cert_manager_irsa = true` 时存在。 |
| `aws_iam_role.smithdb` | `modules/smithdb` | SmithDB pods | SmithDB bucket 上的读取、写入和 multipart 访问权限，设置该 key 时还包括 KMS。仅在 `enable_smithdb = true` 时存在。 |
| `AmazonEKSTFEBSCSIRole-*` | `modules/eks` | `ebs-csi-controller-sa` | EBS 卷管理 |

## 网络拓扑

### VPC 与私有 endpoint

设置 `create_vpc = true` 时，module 会构建一个跨最多三个可用区的 `10.0.0.0/16` VPC，并且可以在 `us-west-1` 这类双可用区 region 中工作。它使用 /21 私网和公网子网以及单个 NAT gateway。

module 会创建一个 VPC endpoint，即 S3 gateway endpoint。当你自带没有 NAT 或互联网出口的 VPC（`create_vpc = false`）时，请创建启用 private DNS 的 `com.amazonaws.<region>.ecr.api` 和 `com.amazonaws.<region>.ecr.dkr` interface endpoint，并将其挂到允许来自 VPC CIDR 的 TCP 443 流量的安全组上，这样节点才能拉取镜像。

设置 `alb_existing_security_group_id`、`postgres_existing_security_group_id`、`redis_existing_security_group_id` 或 `bastion_existing_security_group_id` 可以挂载你自行管理的安全组。Terraform 只会挂载它，从不向其中写入规则。

### 带 Network Firewall 的出站路径

当 `create_firewall = true` 时，来自私网子网的所有出站互联网流量在到达 NAT gateway 之前都会被检查：

```txt
EKS pods / RDS / ElastiCache (private subnets)
  → AWS Network Firewall (TLS SNI + HTTP Host inspection)
     ALLOWLIST: firewall_allowed_fqdns (default: beacon.langchain.com)
     DROP: all other established connections
  → NAT Gateway (public subnet)
  → Internet
```

Pod 到 pod、pod 到 RDS、pod 到 ElastiCache 的流量使用本地 VPC 路由，不会经过防火墙。

## Ingress 选项

这些 module 提供四种互斥的 ingress 选项。Terraform 管理的 ALB 位于 Envoy Gateway、NGINX 和 Istio 前面。在 ALB Ingress 模式下，AWS Load Balancer Controller 会自行预配 ALB，Terraform ALB 则不会被使用。这一选择决定了是否支持分离式 dataplane（agent pods 位于独立 namespace）。

| 选项 | 变量 | 分离式 | 流量路径 | 适用场景 |
|---|---|---|---|---|
| Envoy Gateway | _默认_（`enable_envoy_gateway` 未设置） | 是 | `ALB → TGB → Envoy pods:10080 → HTTPRoute → services` | 默认。跨 namespace 的 HTTPRoute 路由与分离式 dataplane。 |
| ALB Ingress（AWS LBC） | `enable_envoy_gateway = false` | 否 | `ALB（由 controller 管理，target 类型 ip）→ frontend pods` | 希望使用普通 Kubernetes Ingress 的单 namespace 部署。 |
| NGINX Ingress | `enable_nginx_ingress = true` | 否 | `ALB → TGB → NGINX controller → frontend ClusterIP` | 当 NGINX 是你所在组织的标准 ingress 时。 |
| Istio | `enable_istio_gateway = true` | 是 | `ALB → TGB → istio-ingressgateway:80 → VirtualService → services` | 已安装 Istio 的集群，或需要 mTLS mesh 时。 |

除非设置 `enable_istio_gateway` 或 `enable_nginx_ingress`，否则 Envoy 处于启用状态。要使用 ALB Ingress，请显式设置 `enable_envoy_gateway = false`。

### 为什么 ALB Ingress 无法支持分离式 dataplane

标准 Kubernetes Ingress 以 namespace 为作用域。ALB controller 只路由到与 Ingress 资源处于同一 namespace 的服务。`langsmith-agents` 中的 agent pods 对 `langsmith` 中的 Ingress 不可见。Envoy Gateway 和 Istio 都通过 Kubernetes Gateway API 支持跨 namespace 路由。

### 位于 Envoy Gateway 前面的 ALB

在默认布局中，ALB 处理 TLS 和 DNS，Envoy Gateway 位于其后。可选的 WAF 挂载到 ALB 上：

```txt
Internet
  → ALB (TLS, DNS, optional WAF)
    → Envoy proxy pods (ClusterIP Service, TargetGroupBinding from k8s-bootstrap)
       → HTTPRoute → langsmith namespace        (control plane)
       → HTTPRoute → langsmith-agents namespace (split dataplane)
```

ALB target group 将流量转发到 Envoy proxy pods 的 10080 端口。无需 values overlay；`make init-values` 会写入 gateway 设置。

## TLS 与 DNS

`tls_certificate_source` 变量控制证书策略：

| 模式 | 行为 | 兼容的 gateway |
|---|---|---|
| `none` | 仅 HTTP，无证书 | 任意 |
| `acm` | HTTPS:443 带 HTTP 到 HTTPS 重定向。ACM 证书，可自动预配或自带。 | 任意（TLS 在 ALB 处终止） |
| `letsencrypt` | 通过 cert-manager 和 Let's Encrypt 提供 HTTPS，使用经 ALB 解决的 HTTP-01 challenge | 仅 ALB Ingress |

### 为什么选 ACM 还是 cert-manager

ACM 证书不可导出。AWS 会将其直接挂载到 ALB 上，因此当 TLS 在 ALB 处终止时，ACM 是正确选择。使用这些 module 的 gateway 时，TLS 仍在 ALB 处终止，因此 ACM 可与 Envoy、Istio 和 NGINX 配合使用。只有当你希望 TLS 在集群内部终止时才需要 cert-manager。

`letsencrypt` source 是 ALB 路径的参考实现：它安装 cert-manager，并将一个 Let's Encrypt HTTP-01 `ClusterIssuer` 绑定到 ALB ingress class。对于 Istio 上的集群内 TLS，请改用 `create_cert_manager_irsa = true`，它使用经 Route 53 验证的 DNS-01 `ClusterIssuer`。HTTP-01（经 ALB）与 DNS-01（经 Route 53）互斥。在生产环境中，可以将 `ClusterIssuer` 替换为任何兼容 cert-manager 的 issuer。

| Issuer | 适用场景 |
|---|---|
| Let's Encrypt _（默认）_ | 公共域名、可访问互联网、免费 |
| ACM Private CA（`aws-privateca-issuer`） | AWS 原生、适配隔离环境、私有域名、付费 |
| Venafi（`cert-manager-venafi`） | 企业 PKI、受监管环境 |
| HashiCorp Vault（`cert-manager-vault`） | 自托管 PKI |
| DigiCert、Sectigo 等 | ACME 或自定义 issuer 插件 |

设置 `create_cert_manager_irsa = true` 时，Terraform module 会预配 cert-manager IRSA 角色和 Route 53 权限。不同 issuer 之间只有 `ClusterIssuer` manifest 会变化。

### 自动预配的 DNS

当设置了 `langsmith_domain` 且 `acm_certificate_arn` 为空时，Terraform 会激活 `dns` module，它会创建：

- 该域名的 Route 53 公共 hosted zone；或者在设置 `dns_create_zone = false` 和 `dns_existing_zone_id` 时，在现有公共 zone 中创建记录（可以是该 zone 本身或其父 zone，无需 NS 委托）。
- 带 DNS 验证记录的 ACM 证书。设置 `dns_include_wildcard_san = true` 可添加 `*.<domain>` SAN。
- 将域名指向 Terraform 管理的 ALB 的 Route 53 alias 记录。在 ALB Ingress 模式下该 ALB 不会被使用，因此需要你自行将域名指向 Ingress hostname（`kubectl get ingress -n langsmith`）。

**分阶段部署模式：** 先设置 `langsmith_domain` 并使用 `tls_certificate_source = "none"`。Terraform 会创建 hosted zone 和证书，且不会因等待验证而阻塞。在你的注册商处委托 NS 记录，然后在后续 apply 中切换到 `tls_certificate_source = "acm"`。Terraform 会阻塞直到证书验证完成，并将其接入 HTTPS listener。

### 自带证书

直接设置 `acm_certificate_arn` 即可跳过 `dns` module。对于在集群内部终止的 TLS，请手动创建 Kubernetes TLS Secret，并在 Gateway 或 VirtualService 中引用它。

## module 依赖图

```txt
vpc ─► firewall (optional, create_firewall = true)
│
├─► eks ─► k8s-bootstrap (KEDA, ESO, Envoy Gateway [default])
│            └─► cert-manager (optional: HTTP-01 via ALB, or DNS-01 via the cert_manager IRSA module)
│
├─► postgres    (RDS, private subnets from VPC)
├─► redis       (ElastiCache, private subnets from VPC)
├─► storage     (S3 bucket + VPC Gateway Endpoint)
├─► alb         (always created; public subnets, or private when alb_scheme = internal)
│     └─► alb_access_logs (S3 bucket for access logs, opt-in)
├─► dns         (Route 53 zone + ACM cert, optional)
├─► cert_manager (IRSA role for DNS-01, create_cert_manager_irsa = true)
├─► sandbox_juicefs_redis (dedicated ElastiCache, enable_sandboxes = true)
├─► smithdb     (metastore RDS + S3 + IRSA, enable_smithdb = true)
├─► bastion     (jump host for private EKS access, optional)
├─► cloudtrail  (audit logging, optional)
└─► waf         (WAF ACL on ALB, optional)
       all ─► langsmith (root module)
```

### 可选安全 module

| module | 变量 | 默认值 | 用途 |
|---|---|---|---|
| Network Firewall | `create_firewall` | `false` | 基于 FQDN 的出站过滤。仅允许 `firewall_allowed_fqdns` 中的域名（TLS SNI + HTTP Host）。需要 `create_vpc = true`。成本约 `$0.40/hr/endpoint + $0.065/GB processed`。 |
| ALB access logs | `alb_access_logs_enabled` | `false` | 流量分析与合规 |
| CloudTrail | `create_cloudtrail` | `false` | API 调用日志。如果组织级 trail 已存在，可跳过。 |
| WAF | `create_waf` | `false` | WAFv2 Web ACL：OWASP Top 10、IP 信誉、已知恶意输入 |

## 默认资源规格

| 资源 | 默认值 | vCPU | 内存 |
|---|---|---|---|
| EKS 节点 | `m5.4xlarge` | 16 | 64 GB |
| RDS PostgreSQL | `db.t3.large` | 2 | 8 GB |
| ElastiCache Redis | `cache.m6g.xlarge` | 4 | 13.07 GB |
| RDS 存储 | 10 GB | 不适用 | 不适用 |

`terraform.tfvars.production`、`terraform.tfvars.dev` 和 `terraform.tfvars.minimum` 会改变这些规格。Production 使用 `db.r6g.xlarge`。Dev 使用 `m5.2xlarge` 节点，搭配 `db.t3.medium` 和 `cache.t3.medium`。Minimum 使用 `m5.xlarge`，搭配 `db.t3.small` 和 `cache.t3.small`。`sizing_profile`（`production`、`production-large`、`dev`、`minimum` 或 `default`）会选择匹配的 Helm sizing overlay；`default` 则保留 chart 默认值。

生产环境的容量规划建议，请参见[扩缩容指南](/langsmith/self-host-scale)和 [AWS 部署指南](/langsmith/self-host-terraform-aws-deploy#cluster-sizing-reference)。

## 已验证的行为与已知约束

这些约束在 2026 年 4 月的 gateway 组合测试运行中经过验证。

| # | 领域 | 约束或修复 |
|---|---|---|
| 1 | ACM wildcard SAN | `langchain.com` 有 `0 issue "amazon.com"` CAA 但没有 `0 issuewild "amazon.com"`。wildcard SAN 会因 `CAA_ERROR` 失败。`dns` module 默认只请求 apex 域名。`dns_include_wildcard_san = true` 会添加 `*.<domain>`，这需要针对 Amazon 的 `issuewild` CAA 记录。 |
| 2 | In-cluster Redis | LangSmith Helm chart 部署 Redis 时未启用 `requirepass`。`k8s_bootstrap` module 写入 `redis://langsmith-redis:6379`。除非同时配置 Helm chart 的 Redis values，否则不要添加 auth token。 |
| 3 | `name_prefix` 长度 | 最长 15 个字符。`dz-nginx-tst`（12 个字符）这样的名称是有效的。 |
| 4 | Istio 端口 | Istio 1.23 或更高版本的 ingressgateway 通过 `NET_BIND_SERVICE` 监听 80 端口，而非 8080。ALB TGB 健康检查和安全组规则必须指向 80 端口。 |
| 5 | NGINX TGB 端口 | NGINX ingress-nginx controller pods 监听 80 端口。TargetGroupBinding 的 target 类型为 `ip`。 |
| 6 | Envoy Gateway 端口 | Envoy proxy pods 监听 10080 端口（Gateway 的 80 端口加上 Envoy 为非 root 运行使用的 10000 偏移量）。ALB target group 和节点安全组规则使用 10080；TargetGroupBinding 引用 Envoy 的 `ClusterIP` Service（端口 80），target 类型为 `ip`。 |
| 7 | 销毁顺序 | 先运行 `make uninstall`，再运行 `make destroy`。完整顺序（包括应用删除保护和清空 trace bucket）请参见 [Teardown](/langsmith/self-host-terraform-aws-quick-reference#teardown)。不要预先删除 namespace：Helm 无法在正在终止的 namespace 中干净地卸载，因此 `helm_release` 资源会超时。 |
| 8 | 卡在 terminating 状态的 namespace | KEDA 过期的 `external.metrics.k8s.io/v1beta1` API group 会导致 `NamespaceDeletionDiscoveryFailure`。修复：清除 namespace 的 `spec.finalizers`，并使用 `kubectl replace --raw "/api/v1/namespaces/<ns>/finalize" -f -` 将结果提交到 finalize 子资源，然后重新运行 `make destroy`。 |

## 验证命令

```bash
# EKS cluster status
aws eks describe-cluster --name <cluster-name> --query "cluster.status"

# Node health
kubectl get nodes -o wide

# ALB target registration and routes (default Envoy Gateway mode)
kubectl get targetgroupbinding -A

  --query "DBInstances[?DBInstanceIdentifier=='<db-id>'].DBInstanceStatus"

aws elasticache describe-replication-groups \
  --query "ReplicationGroups[?ReplicationGroupId=='<group-id>'].Status"

kubectl run s3-test --rm -it --image=amazon/aws-cli -n langsmith \
  --overrides='{"spec":{"serviceAccountName":"<annotated-service-account>"}}' -- \
  s3 ls s3://<bucket-name>
```
