本页介绍 LangSmith 中的用户管理功能，包括访问控制、认证以及自动化用户开通：

- [设置访问控制](#set-up-access-control)：配置基于角色的访问控制（RBAC），以管理工作区内的用户权限，包括创建自定义角色并将其分配给用户。
- [SAML SSO（Enterprise 计划）](#set-up-saml-sso-for-your-organization)：为 Enterprise 客户使用 SAML 2.0 配置单点登录认证，包括常见身份提供商的配置方法。
- [SCIM 用户开通（Enterprise 计划）](#set-up-scim-for-your-organization)：使用 SCIM 在你的身份提供商与 LangSmith 之间自动完成用户开通与停用。

## Set up access control

<Note>
RBAC（Role-Based Access Control，基于角色的访问控制）仅对 Enterprise 客户可用。如果你对该功能感兴趣，请[联系销售团队](https://www.langchain.com/contact-sales)。其他计划默认对所有用户使用 [`Admin` 角色](/langsmith/administration-overview)。
</Note>

<Check>
在开始设置访问控制之前，建议先阅读[管理概览](/langsmith/administration-overview)页面。
</Check>

LangSmith 依赖 RBAC 来管理 [workspace](/langsmith/administration-overview#workspaces) 内的用户权限。这样你就可以控制谁能访问你的 LangSmith workspace，以及他们在其中可以执行哪些操作。拥有 `workspaces:manage` 权限的用户可以管理工作区设置，拥有 `workspaces:manage-members` 权限的用户可以添加、移除和更新工作区成员。内置的 Workspace Admin 角色同时包含这两项权限。

关于工作区角色及其权限的完整参考，请参阅 [Role-based access control](/langsmith/rbac#workspace-roles) 指南。关于每种角色具体可以执行哪些操作，请参阅 [Organization and workspace operations reference](/langsmith/organization-workspace-operations)。

### Create a role

默认情况下，LangSmith 提供一组系统角色：

- `Admin`：对工作区中的所有资源拥有完整访问权限。
- `Viewer`：对工作区中的所有资源拥有只读权限。
- `Editor`：除工作区管理外拥有完整权限，例如不能添加或移除用户、不能更改角色、也不能配置 service keys。

如果这些角色不符合你的访问模型，`Organization Admins` 可以创建适合你需求的自定义角色。

要创建角色，请前往 [Organization settings page](https://smith.langchain.com/settings) 中 **Members and roles** 部分的 **Roles** 标签页。请注意，你创建的新角色可在组织内的所有工作区中使用。

点击 **Create Role** 按钮即可创建新角色。系统会打开 **Create role** 表单。

![Create Role](/langsmith/images/create-role.png)

为你希望控制访问的不同 LangSmith 资源分配权限。

### Assign a role to a user

当角色设置完成后，你就可以将它们分配给用户。要为用户分配角色，请前往 [Organization settings page](https://smith.langchain.com/settings) 中 `Workspaces` 部分的 `Workspace members` 标签页。

每位用户旁边都会有一个 **Role** 下拉菜单，你可以用它为用户分配角色。

![Assign Role](/langsmith/images/assign-role.png)

你也可以在邀请新用户时直接指定角色。

![Invite User](/langsmith/images/invite-user.png)

## Set up SAML SSO for your organization

Single Sign-On（SSO，单点登录）功能面向 **Enterprise Cloud** 客户开放，让用户可以通过单一认证来源访问 LangSmith。这样管理员就能集中管理团队访问权限，并提升信息安全性。

LangSmith 的 SSO 配置基于 SAML（Security Assertion Markup Language）2.0 标准。SAML 2.0 可以将身份提供商（IdP）连接到你的组织，从而带来更便捷、更安全的登录体验。

SSO 服务允许用户使用一组凭证（例如用户名或电子邮件地址与密码）访问多个应用。该服务只对最终用户进行一次认证，随后用户在同一会话中切换应用时无需再次输入凭证。SSO 的优势包括：

- 为组织所有者简化跨系统的用户管理。
- 使组织能够强制执行自身安全策略，例如 MFA。
- 免去终端用户记忆和管理多个密码的需求，并通过单一入口登录多个应用来简化使用体验。

### Just-in-time (JIT) provisioning

LangSmith 在使用 SAML SSO 时支持 Just-in-time provisioning。这允许用户在通过 SAML SSO 登录时，自动作为成员加入组织和选定工作区。有关管理 JIT provisioning 和用户邀请的详细信息，请参阅 [Manage user access in SSO organizations](/langsmith/jit-invite-sso)。

<Note>
JIT provisioning 仅对新用户生效，也就是尚未通过[其他登录方式](/langsmith/authentication-methods#cloud)使用相同邮箱获得组织访问权限的用户。
</Note>

### Login methods and access

在完成组织的 SAML SSO 配置后，用户除了可以通过 SAML SSO 登录外，还可以使用[其他登录方式](/langsmith/authentication-methods#cloud)，例如用户名和密码或 Google Authentication：

- 当用户通过 SAML SSO 登录时，只能访问已配置 SAML SSO 的对应组织。
- 仅以 SAML SSO 作为登录方式的用户不会拥有[个人组织](/langsmith/administration-overview#organizations)。
- 当用户通过其他任意方式登录时，既可以访问已配置 SAML SSO 的组织，也可以访问其所属的其他组织。

### Enforce SAML SSO only

<Note>
在强制仅允许 SAML SSO 的组织中，不支持用户邀请。初始的工作区成员资格和角色由 [JIT provisioning](/langsmith/jit-invite-sso#jit-provisioning) 决定，后续变更可在 UI 中管理。
如果你需要更灵活的自动化用户管理能力，LangSmith 还支持 SCIM。
</Note>

如果要确保用户只有在通过 SAML SSO 登录时才能访问组织，而不能通过其他方式访问，请选中 **Login via SSO only** 复选框并点击 **Save**。设置生效后，当前通过非 SSO 方式登录且访问该组织的用户将被要求重新使用 SAML SSO 登录。若要恢复允许所有登录方式，请取消选中该复选框并点击 **Save**。

<Note>
要将该设置更新为 `Only SAML SSO`，你必须当前就是通过 SAML SSO 登录。这样可以确保 SAML 设置有效，避免将用户锁定在组织之外。
</Note>

如需排查问题，请参阅 [SAML SSO FAQs](/langsmith/faq#saml-sso-faqs)。如果在配置 SAML SSO 时遇到问题，请通过 [support.langchain.com](https://support.langchain.com) 联系 LangChain 支持团队。

### Prerequisites

<Note>
SAML SSO 仅对使用 [Enterprise plan](https://www.langchain.com/pricing-langsmith) 的组织开放。请[联系销售](https://www.langchain.com/contact-sales)了解更多信息。
</Note>

- 你的 Identity Provider（IdP）必须支持 SAML 2.0 标准。

关于如何结合 SAML 使用 SCIM 来进行用户开通与停用，请参阅 [SCIM setup](#set-up-scim-for-your-organization)。

### Supabase Attribute Mapping

<Note>
Supabase Attribute Mapping 是一个[仅适用于 cloud](/langsmith/cloud)的功能。[Self-hosted](/langsmith/self-hosted) 部署会直接通过 IdP 配置 SAML/OIDC attributes，请参阅 [Set up SSO with OAuth2.0 and OIDC](/langsmith/self-host-sso)。
</Note>

LangSmith cloud 使用 [Supabase](/langsmith/cloud) 作为 SAML SSO 后端。Supabase 会自动将一小部分标准 SAML attributes（例如 `email` 和 `sub`）传递到用户的 JWT 中。你的 IdP 发出的任何额外的非标准 SAML attribute（例如用于 [SSO Groups Sync](#sso-groups-sync-alternative) 的 `groups`）都必须先通过 Supabase 显式转发，LangSmith 才能读取。

**Attribute flow（1:1）：**

1. **IdP**：发出配置名称的 SAML attribute（例如 `groups`）。
2. **Supabase**：仅当该 attribute 名称出现在 SSO provider 的 **Supabase Attribute Mapping** 表中时，才会将其转发到用户 JWT。标准 attributes 会自动转发，非标准 attributes 若未显式列出则会被丢弃。
3. **LangSmith**：按 claim 名称读取 JWT（例如 [SSO Groups Sync](#sso-groups-sync-alternative) 中 **Groups claim field** 的值）。

该 attribute 名称会在整个链路中保持不变：IdP attribute 名称、Supabase Attribute Mapping 条目，以及下游 LangSmith 设置都使用同一个字符串。

#### Configuration

在 **Settings** → **Members and roles** → **SSO Configuration** 中，滚动到 **Supabase Attribute Mapping** 部分，并为每个你希望转发的非标准 attribute 添加一行：

| Column | Description |
| --- | --- |
| **Attribute name** | 你的 IdP 发出的 SAML attribute 名称。它必须与 LangSmith 在下游期望的 JWT claim 名称一致（对于 SSO Groups Sync，这个值与 **Groups claim field** 相同）。 |
| **Array** | 如果该 attribute 是多值的（字符串列表），请勾选。对于标量（单值）attribute 则不要勾选。例如，`groups` 应勾选，`full_name` 不应勾选。 |

对每个额外 attribute 点击 **Add row**，然后点击 **Save**。若映射表为空，则不会有任何非标准 attributes 流入 JWT。

### Entra ID (Azure)

4. 更新 **Basic SAML Configuration**：

   1. `Identifier (Entity ID)`：

### Google

如需更多信息，请参阅 Google 的[文档](https://support.google.com/a/answer/6087519)。

**Step 1: Create and configure the Google Workspace SAML application**

1. 确保你已登录具有相应权限的管理员账号。

2. 在 Admin console 中，前往 **Menu** -> **Apps** -> **Web and mobile apps**。

3. 点击 **Add App**，然后选择 **Add custom SAML app**。

4. 输入应用名称，并可选择上传图标。点击 **Continue**。

5. 在 Google Identity Provider details 页面下载 **IDP metadata**，保存以供第 2 步使用。然后点击 **Continue**。

6. 在 `Service Provider Details` 窗口中，输入：

   1. `ACS URL`：
      <SaasRegionUrls prefix="auth" suffix="/auth/v1/sso/saml/acs" />

   2. `Entity ID`：
      <SaasRegionUrls prefix="auth" suffix="/auth/v1/sso/saml/metadata" />

   3. 将 `Start URL` 和 `Signed response` 复选框留空。
   4. 将 `Name ID` format 设为 `EMAIL`，并将 `Name ID` 保持为默认值（`Basic Information > Primary email`）。
   5. 点击 `Continue`。

7. 使用 `Add mapping` 确保必需 claims 存在：
   1. `Basic Information > Primary email` -> `email`

**Step 2: Set up LangSmith SSO Configuration**

按照 [initial configuration](#initial-configuration) 中 `Fill in required information` 步骤的说明，使用上一步中的 `IDP metadata` 作为 metadata XML 完成配置。

**Step 3: Turn on the SAML app in Google**

1. 在 `Menu -> Apps -> Web and mobile apps` 下选择该 SAML 应用。

2. 点击 `User access`。

3. 启用该服务：

   1. 若要为组织中的所有人启用，请点击 `On for everyone`，然后点击 `Save`。

   2. 若要为某个 organizational unit 启用：

      1. 在左侧选择该 organizational unit，然后点击 `On`。
      2. 如果 Service status 为 `Inherited`，且你希望即使父级设置变化也保留当前更新，请点击 `Override`。
      3. 如果 Service status 为 `Overridden`，你可以点击 `Inherit` 恢复为与父级一致，或点击 `Save` 保留新的设置，即使父级设置以后变化也不受影响。

   3. 若要为横跨或位于某些 organizational units 内的一组用户启用服务，请选择一个 access group。详见 [Use groups to customize service access](https://support.google.com/a/answer/9050643)。

4. 确保用户登录 LangSmith 时使用的邮箱地址，与其登录 Google 域时使用的邮箱地址一致。

**Step 4: Verify the SSO setup**

让一个有访问权限的用户通过 **SSO Configuration** 页面上的专属登录 URL 登录，或在 Google 的 SAML 应用页面中点击 **TEST SAML LOGIN**。

## Set up SCIM for your organization

<Note>
如果你希望采用比 SCIM 更轻量的方式，而且不需要 IdP 管理员参与推送 groups，请参阅下方的 [SSO Groups Sync](#sso-groups-sync-alternative)。它会在登录时直接从 SSO token 中读取 group memberships，并复用相同的命名约定。
</Note>

SCIM（System for Cross-domain Identity Management）是一项用于自动化用户开通的开放标准。借助 SCIM，你可以在身份提供商与 LangSmith 的[organization 和 workspaces](/langsmith/administration-overview)之间自动完成用户开通与停用，使用户访问权限始终与组织中的身份系统保持同步。

<Note>
SCIM 仅对使用 [Enterprise plan](https://www.langchain.com/pricing) 的组织开放。请[联系销售](https://www.langchain.com/contact-sales)了解更多信息。

SCIM 可用于 Helm chart 版本 0.10.41（应用版本 0.10.108）及更高版本。

SCIM 仅支持 API 方式（见下方说明）。
</Note>

SCIM 可以免去手动用户管理的需求，并确保用户访问权限始终与组织身份系统保持最新同步。它带来的优势包括：

- **自动化用户管理**：根据用户在 IdP 中的状态，自动在 LangSmith 中添加、更新和移除用户。
- **降低管理开销**：无需在多个系统之间手动管理用户访问。
- **提升安全性**：离开组织的用户会自动从 LangSmith 中停用。
- **一致的访问控制**：用户属性和群组成员关系会在系统之间同步。
- **可扩展的团队访问控制**：可高效管理拥有大量工作区和自定义角色的大型团队。
- **角色分配**：可为不同用户组分配特定的 [Organization Roles](/langsmith/rbac#organization-roles) 和 [Workspace Roles](/langsmith/rbac#workspace-roles)。

### Requirements

#### Prerequisites

- 你的组织必须使用 Enterprise 计划。
- 你的 Identity Provider（IdP）必须支持 SCIM 2.0。
- 只有 [Organization Admins](/langsmith/administration-overview#organization-roles) 可以配置 SCIM。
- 对于 cloud 客户：[SAML SSO](#set-up-saml-sso-for-your-organization) 必须可为你的组织配置。
- 对于 self-hosted 客户：必须启用 [OAuth with Client Secret](/langsmith/self-host-sso#with-client-secret-recommended) 认证模式。
- 对于 self-hosted 客户，必须允许从身份提供商到 LangSmith 的网络流量：
  - Microsoft Entra ID 支持通过 IP allowlisting 或基于 agent 的方案提供连接。
    （[details](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups#ip-ranges)）
  - Okta 支持 IP 或域名 allow-listing（[details](https://help.okta.com/en-us/content/topics/security/ip-address-allow-listing.htm)）
    或通过基于 agent 的方案（[details](https://help.okta.com/en-us/content/topics/provisioning/opp/opp-main.htm)）提供连接。

<Note>
SCIM 连接通常要求 HTTP/1.1 或更高版本。如果客户端使用 HTTP/1.0，可能会遇到 `426 Upgrade Required` 错误。
</Note>

#### Role precedence

当用户同时属于同一工作区的多个群组时，优先级规则如下：

1. **Organization Admin groups** 优先级最高。属于这些群组的用户会在所有工作区中成为 `Admin`。
2. **最近创建的工作区特定群组** 优先级高于其他工作区群组。

<Note>
当群组被删除，或者用户被移出某个群组时，他们的访问权限会根据其剩余群组成员关系并遵循上述优先级规则进行更新。

SCIM 群组成员关系会覆盖手动分配的角色以及通过 Just-in-time（JIT）provisioning 分配的角色。为了避免冲突，建议关闭 JIT provisioning。更多信息请参阅 [Manage user access in SSO organizations](/langsmith/jit-invite-sso#scim-integration)。
</Note>

#### Email verification

仅在 cloud 中，通过 SCIM 创建新用户时会向该用户发送一封电子邮件。
用户必须点击邮件中的链接来验证邮箱地址。
该链接会在 24 小时后过期，如有需要，可以通过 SCIM 移除后重新添加该用户来重新发送。

### Attributes and mapping

#### Group naming convention

<Warning>
SCIM **不支持**重命名群组。群组名称必须保持持久不变，因为它们需要与 LangSmith 中的角色名称和/或工作区名称匹配。
</Warning>

群组成员关系会根据特定的命名约定映射到 LangSmith 的工作区成员关系和工作区角色。默认情况下，组成部分之间的分隔符为冒号（`:`），但你也可以为组织[配置自定义分隔符](#configure-custom-separator)。

<Note>
你可以在**organization role name** 这一段省略空格。这对不允许群组名中出现空格的身份提供商很有帮助。例如，LangSmith 会将 `OrganizationAdmins` 和 `OrganizationUser` 视为 `Organization Admins` 和 `Organization User` 的等价写法。这个灵活性仅适用于 organization role name 这一 token。Workspace names 和 workspace role names 会将空格视为字面字符，因此省略空格的变体不会匹配带空格的名称。
</Note>

**Organization Admin Groups**

格式：`<optional_prefix>Organization Admin` 或 `<optional_prefix>Organization Admins`

示例：

- `LS:Organization Admins`
- `LS:OrganizationAdmins`（省略空格，适合不允许群组名中包含空格的 IdP）
- `Groups-Organization Admins`
- `Organization Admin`

**Workspace-Specific Groups**

格式：`<optional_prefix><org_role_name><separator><workspace_name><separator><workspace_role_name>`

默认分隔符为 `:`（冒号）。支持的分隔符包括：`:`（冒号）、`-`（连字符）、`_`（下划线）、` `（空格）以及 `&`（与号）。

使用默认冒号分隔符的示例：

- `LS:Organization User:Production:Annotators`
- `LS:OrganizationUser:Production:Annotators`（在 role name token 中省略空格）
- `Groups-Organization User:Engineering:Developers`
- `Organization User:Marketing:Viewers`

使用连字符分隔符的示例：

- `LS-Organization User-Production-Annotators`
- `LS-OrganizationUser-Production-Annotators`（在 role name token 中省略空格）
- `Organization User-Engineering-Developers`

<Note>
如果你的 workspace 名称中本身包含分隔符字符（例如 workspace `my-team`，分隔符为 `-`），LangSmith 会自动尝试所有可能的切分方式，以找到有效的 workspace 与 role 组合。
</Note>

#### Configure custom separator

要修改组织的 SCIM 群组名称分隔符，请使用 `PATCH /api/v1/orgs/current/info` [endpoint](/langsmith/smith-api/orgs/update-current-organization-info)。对于区域化 SaaS 部署，请向对应区域 host（`eu.api.smith.langchain.com`、`apac.api.smith.langchain.com` 或 `aws.api.smith.langchain.com`）上的相同路径发送请求：

```bash
curl -X PATCH $LANGCHAIN_ENDPOINT/api/v1/orgs/current/info \
  -H "X-Api-Key: $LANGCHAIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"scim_group_name_separator": "-"}'
```

分隔符必须是单个字符，并且只能是以下之一：`:`（冒号）、`-`（连字符）、`_`（下划线）、` `（空格）或 `&`（与号）。默认值为 `:`（冒号）。

<Note>
修改分隔符不会重命名现有的 SCIM 群组。如果你修改了分隔符，也必须同步更新身份提供商中的群组名称，使其使用新的分隔符。
</Note>

### Step 1 - configure SAML SSO (Cloud only)

关于 [SAML SSO](#set-up-saml-sso-for-your-organization) 配置，有两种情况：

1. 如果你的组织已经配置了 SAML SSO，那么应跳过最初添加应用的步骤（[Add application from Okta Integration Network](#add-application-okta-oin) 或 [Create a new Entra ID application integration](#create-application-entra-id)），因为你的应用已经配置完成，只需要启用 provisioning。
1. 如果你是第一次同时配置 SAML SSO 和 SCIM，请先按照说明[设置 SAML SSO](#set-up-saml-sso-for-your-organization)，_然后_再按照此处说明启用 SCIM。

#### NameID format

LangSmith 使用 SAML NameID 来识别用户。NameID 是 SAML 响应中的必填字段，并且大小写不敏感。

NameID 必须：

1. 对每个用户唯一。
2. 是一个永不变化的持久值，例如随机生成的唯一用户 ID。
3. 在每次登录时都完全一致，不应依赖用户输入。

NameID 不应使用 email address 或 username，因为 email 和 username 更容易随时间变化，而且可能区分大小写。

除非你使用的字段（例如 email）要求不同格式，否则 NameID format 必须为 `Persistent`。

### Step 2 - disable JIT provisioning

在启用 SCIM 之前，请关闭 [Just-in-time (JIT) provisioning](/langsmith/jit-invite-sso#jit-provisioning)，以防止自动开通与手动开通之间发生冲突。

#### Disabling JIT for cloud

使用 `PATCH /orgs/current/info` [endpoint](/langsmith/smith-api/orgs/update-current-organization-info)。对于区域化 SaaS 部署，请向对应区域 host（`eu.api.smith.langchain.com`、`apac.api.smith.langchain.com` 或 `aws.api.smith.langchain.com`）上的相同路径发送请求：

```bash
curl -X PATCH $LANGCHAIN_ENDPOINT/orgs/current/info \
  -H "X-Api-Key: $LANGCHAIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jit_provisioning_enabled": false}'
```

#### Disabling JIT for Self-Hosted

从 LangSmith chart 版本 **0.11.14** 开始，你可以为使用 SSO 的自托管组织禁用 JIT provisioning。要禁用，请设置以下值：

```yaml
commonEnv:
  - name: SELF_HOSTED_JIT_PROVISIONING_ENABLED
    value: "false"
```

### Step 3 - generate SCIM bearer token

<Note>
在 self-hosted 环境中，下方完整 URL 可能类似 `https://langsmith.yourdomain.com/api/v1/platform/orgs/current/scim/tokens`（没有子域名，注意 `/api/v1` 路径前缀），也可能类似 `https://langsmith.yourdomain.com/subdomain/api/v1/platform/orgs/current/scim/tokens`（有子域名）。更多信息请参阅 [ingress docs](/langsmith/self-host-ingress)。
</Note>

为你的组织生成一个 SCIM Bearer Token。你的 IdP 将使用该 token 对 SCIM API 请求进行认证。请确保 env vars 已正确设置，例如：

```bash

  -H "X-Api-Key: $LANGCHAIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"description": "Your description here"}'
```

请注意，SCIM Bearer Token 的值仅会出现在该请求的响应中，之后无法再次获取。可用的其他 endpoints 包括：

- `GET /v1/platform/orgs/current/scim/tokens`
- `GET /v1/platform/orgs/current/scim/tokens/{scim_token_id}`
- `PATCH /v1/platform/orgs/current/scim/tokens/{scim_token_id}`（仅支持 `description` 字段）
- `DELETE /v1/platform/orgs/current/scim/tokens/{scim_token_id}`

### SSO Groups Sync (alternative)

<Note>
SSO Groups Sync 对已配置 SAML SSO（cloud）或 OIDC（self-hosted）的 [Enterprise plan](/langsmith/pricing-plans) 组织开放。请[联系销售](https://www.langchain.com/contact-sales)了解更多信息。
</Note>

对于无法或不想配置 SCIM group push 的组织，SSO Groups Sync 是比 [SCIM](#set-up-scim-for-your-organization) 更简单的一种替代方案。它不会在独立的同步周期中从 IdP 推送 groups 到 LangSmith，而是在登录时直接从可配置的 SSO token claim 中读取 group memberships，并使用与 SCIM 相同的[命名约定](#group-naming-convention)来应用组织级和工作区级角色分配。

#### When to use SSO Groups Sync vs. SCIM

从技术上讲，SSO Groups Sync 和 SCIM 可以共存（它们各自只管理带有自身 provisioning method 标签的 identities），但为了避免令人困惑的优先级行为，建议**每个组织只选择一种机制**，而不是同时使用两者。

| | SSO Groups Sync | SCIM |
| --- | --- | --- |
| **Sync trigger** | 每次 SSO 登录时 | 由 IdP 主动推送（约 1 小时节奏） |
| **IdP admin involvement** | 极少，只需在 SSO token 中包含 groups | 必需，需要配置 SCIM provisioning app |
| **Deprovisioning** | 会延迟到下次登录时生效 | 通过 IdP 推送近实时生效 |
| **Naming convention** | 复用 [SCIM convention](#group-naming-convention) | [SCIM convention](#group-naming-convention) |
| **Custom separator** | 复用组织级 [`scim_group_name_separator`](#configure-custom-separator) | [`scim_group_name_separator`](#configure-custom-separator) |

当你希望 IdP 管理员参与度较低，且可以接受登录时才进行的被动同步时，请选择 **SSO Groups Sync**。当你需要主动开通/停用以及近实时的群组成员关系更新时，请选择 **SCIM**。

#### Configuration

1. 在你的 IdP 中：将用户所属 groups 写入 SSO token 的 claim 中（默认 claim 名称为 `groups`）。Group names 必须遵循 [SCIM naming convention](#group-naming-convention)。
2. 在 LangSmith 中：前往 **Settings** → **Members and roles** → **SSO Configuration** → **SSO Groups Sync**，并配置以下项目：

   | Setting | Description |
   | --- | --- |
   | **Enable SSO Groups Sync** | 根据 SSO token 中的群组成员关系自动分配工作区角色。 |
   | **Groups claim field**（默认 `groups`） | SSO token 中包含群组成员关系的 claim 名称。 |
   | **Sync workspace/role assignments** | 在每次 SSO 登录时，根据 group names 更新工作区成员关系和角色。 |
   | **Require matching group to sign in** | 如果 SSO token 中没有任何符合命名约定的 groups，则阻止登录。 |

你也可以通过 API 配置这些设置，方法是向 SSO settings endpoint 发送 `PATCH` 请求：

```bash
curl -X PATCH $LANGCHAIN_ENDPOINT/api/v1/orgs/current/sso-settings/$SSO_PROVIDER_ID \
  -H "X-Api-Key: $LANGCHAIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "sso_groups_enabled": true,
    "sso_groups_claim_field": "groups",
    "sso_groups_role_sync_enabled": true,
    "sso_groups_required": false
  }'
```

<Warning>
关闭 SSO Groups Sync 不会移除现有访问权限。通过 SSO groups provision 的用户会保留当前访问权限，直到他们下一次登录。
</Warning>

#### Configure your IdP to emit a groups SAML attribute (cloud)

<Note>
本节仅适用于 **enterprise cloud**。Self-hosted 客户应直接在其 OIDC IdP 中配置 groups，请参阅 [SSO Groups Sync on self-hosted](/langsmith/self-host-sso#sso-groups-sync)。
</Note>

为了让用户的 group memberships 在登录时对 LangSmith 可见，你需要完成两件事：

1. 配置 IdP 的 SAML 应用，使其发出一个多值的 group attribute。
2. 在 [Supabase Attribute Mapping](#supabase-attribute-mapping) 中添加对应条目，使该 attribute 能流入 JWT（并勾选 **Array**）。

**Requirements:**

- IdP attribute 名称（例如 `groups`）必须同时匹配 **Supabase Attribute Mapping** 条目和 **Groups claim field** 的值（默认也是 `groups`）。
- 该 attribute 必须是**多值**的（字符串列表），而不是单个分隔字符串。如果你的 IdP 只支持单值 attribute，就需要为每个 group 发出一条独立的 attribute statement。
- 每个值都必须是符合 [SCIM naming convention](#group-naming-convention) 的 group name。
- 只有名称符合该约定的群组才会被处理。LangSmith 会忽略不符合命名约定的 groups，例如组织范围的目录群组或应用分配群组。你不需要在 IdP 侧过滤这些群组，可以全部发出，由 LangSmith 跳过无关项。

**Per-IdP setup:**

<Tabs>
<Tab title="Okta">

在 LangSmith SAML 应用中：

1. 前往 **Directory** → **Profile Editor** → 选择 LangSmith 应用的用户 profile。
2. 添加一个名为 `groups` 的自定义 attribute，**Type** 设为 `string array`。
3. 前往 **Sign On** → 编辑 SAML 设置，并添加一个 attribute statement：
   - **Name**：`groups`
   - **Name format**：`Unspecified`（或 `Basic`）
   - **Filter**：使用 `Matches regex` 和 `.*` 来发送所有 groups，或者使用更严格的 regex（例如 `^LS:.*`）仅发送带有 LangSmith 前缀的 groups。

</Tab>
<Tab title="Entra ID (Azure)">

在 LangSmith Enterprise Application 中：

1. 前往 **Single sign-on** → **Attributes & Claims** → **Add a group claim**。
2. 选择要发出的群组（通常选 **Groups assigned to the application**）。
3. 将 **Source attribute** 设为 `Cloud-only group display names`，这样发送的就是 group name（它必须符合[命名约定](#group-naming-convention)），而不是 object ID。
4. 将 claim 的 **Name** 设为 `groups`（或你配置的 **Groups claim field** 值），并且不要设置 namespace。

</Tab>
<Tab title="Google Workspace">

Google 的 SAML SSO 并不会原生将 Google Group memberships 作为 SAML attribute 发出。若想在 Google Workspace 中使用 SSO Groups Sync，你必须：

- 通过能将 groups 暴露为 SAML attribute 的目录同步工具来管理群组成员关系，或
- 改用 [SCIM](#set-up-scim-for-your-organization)，因为它支持从 Google Workspace 推送 groups。

</Tab>
</Tabs>

#### Group naming examples

Group names 遵循 [SCIM naming convention](#group-naming-convention)。其中 `<workspace_role>` 这一段既可以使用内置角色名称，也可以使用[自定义工作区角色](/langsmith/rbac#custom-roles)名称。

| Intent | Example group name |
| --- | --- |
| Org admin（在所有工作区中授予 workspace admin） | `LS:Organization Admins` |
| `Production` 中的 Workspace admin | `LS:Organization User:Production:Admin` |
| `Engineering` 中的 Workspace editor | `LS:Organization User:Engineering:Editor` |
| `Marketing` 中的 Workspace viewer | `LS:Organization User:Marketing:Viewer` |
| `Production` 中的自定义角色 `Annotators` | `LS:Organization User:Production:Annotators` |

#### Behavior

- **Naming convention**：群组名称遵循与 SCIM 相同的格式（例如 org admin 使用 `LS:Organization Admins`，工作区范围角色使用 `LS:Organization User:Production:Editor`）。完整格式请参阅 [Group naming convention](#group-naming-convention)。分隔符通过组织级 [`scim_group_name_separator`](#configure-custom-separator) 配置，并与 SCIM 共用。
- **Malformed group names**：不符合命名约定的群组名称会被静默跳过（会记录日志），不会阻止有效群组完成登录。
- **Login gate**：当启用 **Require matching group to sign in**，且 SSO token 中没有任何匹配的群组时，登录会被阻止。
- **Precedence**：SSO Groups Sync 不会修改 SCIM 来源、手动分配或 JIT provisioning 产生的成员关系。对于它自己管理的分配，它是完全权威的，并会在每次登录时根据 token 中的群组成员关系进行替换。
- **Org admin propagation**：如果某用户通过其群组获得 org admin 角色，那么他们会在所有工作区中被授予 workspace admin（行为与 SCIM 相同）。

#### Things to note

- **Deprovisioning lag**：不同于 SCIM 的主动推送，SSO Groups Sync 只会在登录时更新。如果用户在 IdP 中被移出某个群组，他们会一直保留现有工作区访问权限，直到下次登录 LangSmith。**Require matching group to sign in** 这一登录闸门可以缓解该问题，因为它会在下次登录时直接阻止用户进入。
- **No retroactive sync**：修改角色映射或启用该功能，不会立即更新现有用户；他们必须再次登录后才会生效。
- **Naming convention required**：客户必须按 SCIM 约定为其 IdP 群组命名。如果你的 IdP 群组遵循不同的命名策略，那么使用基于 `description` 映射的 SCIM（见 [Group attributes](#group-attributes)）可能更合适。
