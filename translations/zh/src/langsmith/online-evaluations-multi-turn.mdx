多轮在线 evaluators 可以评估人类与 agent 之间的整段对话，而不只是单次交互。它们衡量的是一个 thread 中所有轮次上的端到端交互质量。

<Tip>如需使用由 LangChain 管理的 thread-level judge，而无需配置 model、API key 或 prompt，请参阅 [LangChain Tuned Evaluators](/langsmith/tuned-evaluators)。</Tip>

你可以用多轮评估衡量：
1. Semantic Intent：用户想要完成什么。
2. Semantic Outcome：实际发生了什么，任务是否成功。
3. Trajectory：对话是如何展开的，包括工具调用轨迹。

<Note> 运行多轮在线 evals 会自动将 thread 中的每条 trace 升级为[extended data retention](/langsmith/usage-and-billing#data-retention-auto-upgrades)。这会影响 trace 计费，但能确保符合评估条件的 traces（通常也是最值得分析的那些）被保留下来以供调查。 </Note>

## 工作原理

多轮在线 evaluators 遵循以下评估生命周期：

1. **Trace 摄取**：对话中的每一轮都作为单独 run 被追踪，并通过共享的 thread ID 关联到同一个 thread。
2. **空闲时间检测**：当 thread 中最后一条 trace 被摄取后，LangSmith 会等待配置好的空闲时间结束。这个空闲期表示对话已经完成，可以开始评估。
3. **消息组装**：LangSmith 会从 thread 中每条 trace 收集 `messages`，并将其组装成一份完整的对话历史。如果每条 trace 只包含最新消息，LangSmith 会跨轮次把消息拼接起来；如果每条 trace 已经包含完整历史，LangSmith 就直接使用。由于同一 thread 中相邻 traces 往往会重复发送已有历史，LangSmith 会对重叠消息去重，保证每条消息只出现一次。最终结果是一份 OpenAI chat 格式的消息列表（`{"role": ..., "content": ...}`），这也是 prompt 中 `all_messages` 变量所解析到的内容。
4. **LLM-as-a-judge 评估**：组装后的整段对话会传给你配置好的 LLM-as-a-judge prompt。Evaluator 会依据你的标准，对完整 thread 进行 semantic intent、outcome 或 trajectory 打分。
5. **记录反馈**：Evaluator 会使用你配置的 feedback key，将 feedback 写入 LangSmith，并与该 thread 关联。

这意味着多轮 evaluators 是每个已完成 thread 运行一次，而不是每条 trace 运行一次。如果你想按单条 trace 做评估，请使用[run-level 在线 evaluators](/langsmith/online-evaluations-llm-as-judge)。

## 前置条件

- 你的 tracing project 或 agent environment 必须使用了 [threads](/langsmith/threads)。
- Thread 中每条 trace 的顶层 inputs 和 outputs 都必须包含一个 `messages` 键，其值为消息列表。我们支持 [LangChain](/langsmith/log-llm-trace#messages-format)、[OpenAI Chat Completions](https://platform.openai.com/docs/api-reference/chat/create) 和 [Anthropic Messages](https://platform.claude.com/docs/en/api/messages) 格式的消息。
    - 如果每条 trace 的顶层 inputs 和 outputs 只包含对话中的最新消息，LangSmith 会自动把各轮消息合并成一个 thread。
    - 如果每条 trace 的顶层 inputs 和 outputs 已包含完整对话历史，LangSmith 会直接使用它。

<Note>
如果你的 traces 不符合上述格式，thread 级 evaluator 将无法工作。你需要调整 trace 到 LangSmith 的方式，确保每条 trace 的顶层 inputs 和 outputs 都包含 `messages` 列表。

更多信息请参阅[故障排查](/langsmith/online-evaluations-multi-turn#troubleshooting)部分。
</Note>

## 配置

1. 进入 **Tracing** 页面，并选择一个 tracing project 或 agent environment。
2. 点击 **Evaluators** 标签页，然后点击 **+ Evaluator**。在 **Create from scratch** 下选择 **LLM-as-a-Judge Evaluator**。在 **Source** 下选择 **Threads**。
3. **命名 evaluator**。
4. 应用 **Filters** 或 **Sampling Rate**。<br />
使用 filters 或 sampling 控制 evaluator 成本。例如，只评估轮次数少于 *N* 的 threads，或对所有 threads 抽样 10%。
5. **配置空闲时间**。

    第一次配置 thread-level evaluator 时，你可以定义 idle time，也就是 thread 中最后一条 trace 之后，要等待多久才视为对话完成并进入评估。这个值应反映应用中用户交互的典型长度。空闲时间默认为 10 分钟，且不能设置为低于 2 分钟。
    <Note>
    空闲时间是项目级设置。它作用于项目中每个 thread-level evaluator，以及条目类型为 **Threads** 的每条[自动化规则](/langsmith/rules#set-the-thread-idle-time)。
    </Note>
    <Tip>
    首次测试 evaluator 时，可以先用较短的 idle time，这样能更快看到结果，但需以 2 分钟为下限。验证通过后，再将其调大到符合实际用户交互长度的值。
    </Tip>
6. **配置模型。**<br />
选择 evaluator 使用的 provider 和 model。由于 threads 往往较长，因此应选择上下文窗口更大的模型，以避免触发限制。例如，OpenAI 的 GPT-5.4 mini 或 Gemini 2.5 Flash 都是不错的选择，因为它们都具备 1M+ token 的上下文窗口。

7. **配置你的 LLM-as-a-judge prompt。**<br />
定义希望评估的内容。该 prompt 将用于评估整个 thread。你还可以通过 `all_messages` 变量配置要传给 evaluator 的对话内容部分，以控制其接收的数据：
    - All messages：以 OpenAI chat 格式的 JSON 消息对象列表（`{"role": ..., "content": ...}`）传入完整对话，每条消息都会渲染成带缩进的 JSON，并用空行分隔。
    - Human and AI pairs：只传入 user 和 assistant 消息，格式为 `<user>...</user>` 与 `<assistant>...</assistant>`，不包含 system messages、tool calls 或其他角色。
    - First human and last AI：只传入第一条用户消息和最后一条 assistant 回复。

9. **设置 feedback 配置。**<br />
配置 feedback key 的名称、希望收集的 feedback 格式，并可选启用对 feedback 的 reasoning。

<Warning>
为 thread-level evaluator 和 run-level evaluator 使用同一个 feedback key **并不可取**，因为很难区分两者的结果。
</Warning>

8. **保存 evaluator。**

保存后，evaluator 会出现在 **Evaluators** 标签页中。对新建 thread 而言，一旦 idle time 过去，就可以开始测试该 evaluator。

## 评估 trajectory

`trajectory` 是 thread evaluator 可以使用的变量之一，与 `all_messages`、`human_ai_pairs` 和 `first_human_last_ai` 并列。它解析为对话的 [trajectory](/langsmith/observability-concepts#trajectories)：从开始到结束的扁平、有序消息列表，包括 tool calls 及其结果。用它来给 agent 走过的路径打分，例如是否选对了工具、是否按计划执行，以及是否没有浪费步骤。

<Note>
在 [LangSmith Cloud](/langsmith/cloud) 上，`trajectory` 变量仅在 GCP US 区域（[smith.langchain.com](https://smith.langchain.com)）可用。GCP EU、GCP APAC 和 AWS US 区域以及 [BYOC](/langsmith/byoc) 部署不可用。

[Self-hosted](/langsmith/self-hosted) 安装在 LangSmith v0.17 或更高版本上支持 `trajectory` 变量，前提是你已[将查询切换到 SmithDB](/langsmith/self-host-smithdb-install#step-6-switch-queries-to-smithdb)。请参见 [SmithDB 功能可用性](/langsmith/self-host-smithdb-features)。
</Note>

这些变量在 judge 接收到的内容上有所不同：

- **`all_messages`、`human_ai_pairs` 和 `first_human_last_ai`** 解析为从 thread 中每个 root run 的 inputs 和 outputs 组装出的对话。发生在 child runs 中的工作（例如中间 model calls、tool calls 和 tool results）不会被包含，除非某个 root run 自身的 inputs 或 outputs 中包含这些内容。human_ai_pairs 和 first_human_last_ai 会进一步缩小到仅包含 user 和 assistant 消息。
- **`trajectory`** 解析为从每条 trace 内部的 model calls 和 tool calls 构建出的 trajectory。其他视图省略的 tool calls 和 tool results 在这里会保留。

关于每个变量解析到的消息结构，请参见 [Thread message variables](/langsmith/prompt-template-format#thread-message-variables)。

<Warning>
trajectory 通常比其他任何视图都大，因为它同时涵盖 root runs 和 child runs。请按照[配置](#configuration)第 6 步中的说明，选择上下文窗口较大的模型，并预期每次评估会消耗更多 token。
</Warning>

### 使用 trajectory 变量

按照上文的[配置](#configuration)步骤操作，其中有两处变化：

1. 在 **Source** 下选择 **Threads**。该变量只在针对 tracing project 运行的 evaluator 上可用，不支持针对 dataset 运行。
2. 在 prompt 中引用 `{{trajectory}}`，并将该变量映射到 `trajectory` source。变量必须命名为 `trajectory`：指向该 source 的其他名称的变量会被拒绝。种子默认 prompt 和映射已经这样做了，因此新建的 evaluator 在这里无需任何更改。

在 **Runs** 和 **Threads** 之间切换 **Source** 时，只有在你尚未编辑默认 prompt 的情况下，默认 prompt 才会被重新播种。一旦你编辑了 prompt，就会保留你的版本，由你自己映射变量。

`{{trajectory}}` 不能与 `{{all_messages}}`、`{{human_ai_pairs}}` 或 `{{first_human_last_ai}}` 同时出现。一旦你映射了 trajectory source，变量 source 下拉菜单中的其他 source 就会被禁用；而一旦你映射了其他 source，trajectory source 就会被禁用。无论哪种情况，下拉菜单都会说明 trajectory 变量与非 trajectory 变量不能一起使用。保存混用两者的 evaluator 时也会以同样的方式失败。

Evaluator 完成后，LangSmith 会将 feedback 写入 thread 中最近的一个 root run（使用你配置的 feedback key），并将该 feedback 与该 thread 关联。之后要找到它，请参见 [View feedback](/langsmith/threads#view-feedback)。

关于一个可以改编的完整 prompt，请参见 [Example with trajectory context](/langsmith/prompt-template-format#example-with-trajectory-context)。

<Warning>
这个选择在创建 evaluator 时就已固定。要将现有 evaluator 在 `trajectory` 与其他 thread 变量之间切换，请删除它并重新创建。
</Warning>

### 设置与限制

使用 `trajectory` 的 evaluator 支持以下设置：

- **Filters**：限制 evaluator 在哪些 threads 上运行。
- **Sampling rate**：按比例评估符合你的 filters 的 threads。
- **Idle time**：项目级 thread idle time，作用于项目中的每个 thread-level evaluator。

以下选项不可用，包含其中任何一项的配置都会被拒绝：

- 以 datasets 和 experiments 作为 source。
- 对现有 threads 进行 backfill。
- Trace filters 和 tree filters。
- Few-shot examples、extended stats 和 dataset corrections。
- 同一条自动化规则上的 code evaluators，以及非 evaluator 动作（例如将 threads 添加到 annotation queue）。

trajectory 不是 run，因此任何读取 run-level 字段的选项都不可用。

## 限制

以下是当前 thread-level 处理的限制（后续可能调整）。它们适用于多轮在线 evaluators，以及条目类型为 **Threads** 的[自动化规则](/langsmith/rules#set-the-item-type-to-runs-or-threads)。如果你遇到这些限制，请联系我们。

- **Runs 必须小于一周**：当 thread 进入 idle 状态时，只有过去 7 天内的 runs 会参与评估。
- **一次最多处理 500 个 threads**：单次执行最多处理 500 个匹配的 threads，按最近的活动排序。
- **每个工作区最多 10 个多轮在线 evaluators**

## 故障排查

**检查 evaluator 状态** <br />
可以进入 tracing project 或 agent environment 内的 **Evaluators** 标签页，点击所创建 evaluator 的 **Logs** 按钮，查看其运行历史，从而确认 evaluator 上次运行的时间。

**检查发送给 evaluator 的数据** <br />
进入 tracing project 或 agent environment 内的 **Evaluators** 标签页，点击所创建的 evaluator，然后进入 **Evaluator traces** 标签页，即可检查发送给 evaluator 的数据。

在该标签页中，可以看到传给 LLM-as-a-judge evaluator 的输入。如果消息没有被正确传入，那么在 inputs 中会看到空值。这通常是因为消息未采用[预期格式之一](/langsmith/online-evaluations-multi-turn#prerequisites)。
