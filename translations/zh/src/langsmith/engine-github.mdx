将 GitHub 连接到 Engine，让 Engine 在分析 traces 时读取你的源码。Engine 使用代码来理解 agent 的行为，并提出修复方案作为 pull requests。

- **LangSmith Cloud**：使用 LangChain 管理的 GitHub App。请从[连接 repositories](#connect-repositories) 开始。
- **Self-hosted LangSmith**：操作员先针对你的 GitHub 实例完成 [Self-hosted configuration](#self-hosted-configuration)。然后，workspace 用户按照下方相同的 repository 连接步骤操作。

<a id="langsmith-cloud"></a>

## 连接 repositories

这些步骤适用于 LangSmith Cloud，以及已配置好 GitHub App 的 self-hosted deployments。

在你的 tracing project 或 agent environment 上启用 [Engine](/langsmith/engine)。你需要在该 project 中配置 Engine 的权限，以及在你的 LangSmith workspace 中连接 GitHub integration 的权限。如果这些操作不可用，请询问 workspace 管理员。

在 GitHub 上，你需要权限在想要连接的 repositories 上安装该 App，或者已有安装的访问权限。你的 GitHub organization 或 enterprise 可能要求管理员批准该安装。出现提示时，请完成所在组织的 SSO 登录。

<Note>
对于 Enterprise Managed Users，请连接组织拥有的 repositories。GitHub 不允许将此 App 安装到受管用户的个人账户上。关于 GitHub.com 和 `ghe.com` 上的要求，请参阅 [Enterprise Managed Users](#enterprise-managed-users)。
</Note>

对于 fix，repository 必须允许 Engine 的分支和 draft PRs。在测试 fix 之前，请先阅读 [Repository policies](#repository-policies)。

要将 repositories 连接到已有的 Engine project：

1. 打开该 tracing project 或 agent environment。在其 **Engine** 标签页中，选择 **Configure Engine**。
2. 在 **Code repository** 下，选择 **Connect GitHub**。如果你的 workspace 已有连接，则会直接显示 repository picker。
3. 在 GitHub 中，授权为你的 LangSmith deployment 配置的 App。将其安装在拥有你的代码的 organization 或账户上，并选择它可以访问的 repositories。如果 App 已经安装，LangSmith 可能会要求你选择一个已有的 installation。
4. 完成所有 GitHub 批准提示并返回 LangSmith。授权 App 和安装 App 是两个独立的步骤：授权标识你的 GitHub 账户；安装则授予 App 对 repositories 的访问权。
5. 在 repository picker 中，按账户或 repository 名称搜索，选择一个 repository，然后点击 **Connect repository**。
6. 对更多 repositories 重复上述步骤。每个 repository 可以有自己的分支和子文件夹。

你也可以在首次设置 Engine 时连接 repositories，位于 **Connect your agent's code repository** 下。

### 选择分支和子文件夹

对于每个已连接的 repository：

- **Branch**：选择 Engine 应读取并作为 fix 基础的分支。留空则使用 repository 的默认分支。
- **Subfolder**：（可选）让 Engine 只关注 repository 中包含你的 agent 的部分。此设置不会限制 GitHub App 对 repository 的访问。

Engine 会在已连接的 repository 中创建 fix 分支，并针对所选的基础分支打开 draft pull requests。请通过你常用的 GitHub 流程审核并合并这些 pull requests。Engine 不会替你合并它们。

### 连接另一个 organization 或账户

一个 GitHub App 可以在多个 organizations 或账户中分别拥有 installation。来自这些 installations 的 repositories 可以连接到同一个 Engine project。

在 repository picker 中，选择 **Install on another GitHub organization or repository...**。完成 GitHub 流程，返回 LangSmith，然后连接更多 repositories。在 self-hosted LangSmith 上，App 的[所有权和可见性](#choose-who-owns-the-app)决定了 GitHub 会提供哪些账户作为安装目标。

在 self-hosted LangSmith 上，所有连接的 repositories 必须属于同一个 GitHub 实例。连接到不同的 LangSmith workspace 也需要在该 workspace 中连接相应的 installation。

### 管理 repository 访问

在 **Only select repositories** 上安装 App 不会自动包含之后创建的 repositories。在 picker 中，选择 **Missing a repo? Manage repo access for ...** 或 **Manage app access →**。在 GitHub 中添加该 repository，保存 installation 设置，然后重新加载 picker。

从某个 Engine project 中移除一个 repository 会让 Engine 停止在该 project 中使用它。它不会卸载该 GitHub App，也不会移除其对其他 project 的访问权。请在 GitHub 中管理 App installation 以撤销 repository 访问权。

### 验证连接

使用一个测试 repository 和一个带有代表性 traces 的 Engine project。在 self-hosted LangSmith 上，请让你的操作员在此测试期间[验证 webhook 投递](#verify-webhook-delivery)。

要验证连接：

1. 运行一次 Engine 分析，确认它可以使用 repository 的源码。
2. 为某个 issue 生成一个 fix，检查其 diff，然后点击 **Open PR**。确认 **View PR** 能在预期的 GitHub 实例、repository 和基础分支上打开一个 draft PR。
3. 审核并合并该测试 PR。确认对应的 Engine issue 变为完成状态。

要自动创建 PRs，请在 **Code repository** 设置中启用 **Open a draft pull request for every fix**。

### Repository policies

Repositories 必须支持 draft PRs，并允许 Engine 推送 fix 分支。Engine 不使用基于 fork 的贡献工作流。

Engine 的 Git commits 是未签名的。要求 fix 分支上有已签名 commits 的规则可能会拒绝推送。分支名称规则、推送限制和 GHES pre-receive hooks 也可能拒绝某个 fix。在 LangSmith v0.17 中，fix 分支使用 `issues-agent/` 前缀。

请审核适用于这些分支和 App identity 的策略。在目标分支上保留你通常的审核和合并要求。目标分支上的要求在人工合并时可能仍然需要满足；配置该 App 不会绕过 repository 策略。

Engine 不会获取 Git LFS 文件内容，也不会初始化 Git submodules。

### 排查 repository 选择问题

| 症状 | 检查内容 |
| --- | --- |
| GitHub 未配置，或连接在 GitHub 打开之前失败 | 在 self-hosted LangSmith 上，请让你的操作员检查 [deployment configuration](#configure-langsmith)。 |
| 你的 organization 不是安装目标 | 确认你的 GitHub 角色、organization 批准策略，以及 App 的可见性。一个 private App 只能安装在其所属账户上。 |
| 你的受管用户账户不是安装目标 | 使用组织拥有的 repository。受管用户的个人 repository 无法使用此集成。 |
| App 已安装，但 LangSmith 没有连接 | 在 LangSmith 中开始 **Connect GitHub**，包括在管理员批准安装之后、或你直接从 GitHub 安装之后。在 self-hosted LangSmith 上，如果授权未完成，请让你的操作员[检查设置](#troubleshoot-setup)。 |
| 缺少 installation 或 repository | 检查你授权的是哪个 GitHub 账户、App 所选的 repositories，以及该 installation 是否连接到了这个 LangSmith workspace。出现提示时，请完成所在组织的 SSO 授权。 |
| 授权成功，但 repository 无法读取 | 检查 App 的 repository 访问权。在 self-hosted LangSmith 上，还应让你的操作员检查 [GitHub API 和 sandbox 网络访问](#allow-network-access)。浏览器登录不会测试这些连接。 |
| fix 无法推送 | 检查适用于新 fix 分支的规则，包括已签名 commit 要求、分支限制和 pre-receive hooks。请参阅 [Repository policies](#repository-policies)。 |

## Self-hosted 配置

由操作员注册一个 GitHub App、配置 LangSmith，并验证连接。每个 LangSmith installation 完成一次此设置。然后 workspace 用户使用该 App [连接 repositories](#connect-repositories)。

此配置与 LangSmith Deployments builds 和 previews 的 GitHub 设置是分开的。

{/* 发布前置条件：待 https://github.com/langchain-ai/helm/pull/1133 在 v17 chart train 上发布后再发布此设置。版本分配后在此处添加最低 chart 版本；chart 0.17.0 和 0.17.1 在没有 LangSmith Deployments 的情况下不支持此设置。 */}

使用随 Helm chart release 提供的 LangSmith application images。

### 开始之前

你需要：

- **Engine 和 Sandboxes**：一个可正常工作的 [self-hosted Engine deployment](/langsmith/engine-self-hosted)，以及更新其 Helm values、secrets 和 workloads 的权限。
- **GitHub 管理**：在目标 repositories 上注册并安装 App 的权限。Enterprise 或 organization 策略可能要求批准。
- **网络访问**：浏览器、服务和 sandbox 连通性，以及一条 GitHub 可访问的 webhook 路由。请参阅 [Allow network access](#allow-network-access)。

### 选择你的 GitHub 环境

为每个 LangSmith installation 配置一个 GitHub 实例和一个 App。

将 `ENGINE_GITHUB_WEB_BASE_URL` 设置为你的 GitHub 实例的 web 地址：

| GitHub 环境 | 示例 web 地址 |
| --- | --- |
| GitHub.com，包括 Enterprise Cloud | `https://github.com` |
| 带数据驻留的 Enterprise Cloud | `https://example.ghe.com` |
| GitHub Enterprise Server (GHES) | `https://<ghes-hostname>` |

将示例 enterprise 地址或 GHES hostname 占位符替换为你自己的值。GHES 在云端基础设施和本地部署上使用相同的配置。

使用 443 端口上的 HTTPS 和完全限定 hostname，不要带 `/api/v3` 这类路径或 organization 名称。LangSmith 会自动确定 API endpoints。不支持 SSH Git URLs 和自定义 GitHub 端口。

#### 允许网络访问

{/* 图表：待共享的 self-hosted Engine 架构图包含 GitHub 后再链接。展示浏览器授权与回调、LangSmith 服务调用 GitHub API、sandbox 主机通过 HTTPS 克隆与推送，以及 GitHub 向 LangSmith 发送 pull-request webhooks。保持 GitHub 与 model-provider 路径分离。如果共享图未添加，则保留下方表格作为完整的网络参考。 */}

所有连接都使用 HTTPS。为每个来源配置 DNS、路由和证书信任：

| 来源 | 目标 | 用途 |
| --- | --- | --- |
| 用户浏览器 | GitHub web 主机和 LangSmith 授权回调 URL | 登录、App 授权和安装。 |
| LangSmith 服务和 Engine workers | GitHub web 和 API 主机 | 授权、repository 信息、分支和 diff 操作、PR 创建/状态，以及 App identity。 |
| Sandbox 主机 | GitHub web 主机 | 克隆 repositories 并推送 fix 分支。 |
| GitHub | LangSmith webhook URL | 将 PRs 关联到 issues，并在合并后完成 issues。 |

对于 API 访问，请允许你的 GitHub 环境对应的主机：

- **GitHub.com**：`api.github.com`。
- **带数据驻留的 Enterprise Cloud**：web 地址为 `https://example.ghe.com` 时对应 `api.example.ghe.com`。
- **GHES**：与 web 地址相同的主机，`<ghes-hostname>`。

GitHub.com 和 `ghe.com` 从你的网络外部发送 webhooks；GHES 则从你的 GHES 环境中发送。webhook URL 必须能从该来源访问。通过 VPN 的浏览器访问并不能建立 webhook 访问。

对于 GitHub IP allow lists，请包含 LangSmith 服务和 sandbox 主机的出站地址，包括所有 NAT gateway 地址。

Sandbox Git 流量需要到 GitHub 的直接路由。不支持强制上游 HTTP/HTTPS forward proxies；LangSmith API pods 上的 `HTTPS_PROXY` 不会配置 sandbox Git 访问。

对于私有 IP 地址或私有 CA，请在下方配置 LangSmith 时包含 [private-GHES settings](#private-ghes-deployments)。

### 注册 GitHub App

在托管你的 repositories 的 GitHub 实例上注册该 App。在 GitHub.com 上注册的 App 不能在 GHES 或 `ghe.com` enterprise 上复用。

对于 `ghe.com`，请通过你的 enterprise 的 identity provider 登录。在注册和安装的全过程中都使用该站点；你的个人 GitHub.com 账户及其 Apps 是独立的。

#### 选择 App 的所有者

App 的 **owner** 管理其注册和凭证。**installation** 授予对某个 organization 或账户中所选 repositories 的访问权。

根据 Engine 需要的 repositories 选择所有权和可见性：

| 要连接的 repositories | App 配置 |
| --- | --- |
| 单个 organization 中的 repositories | 在该 organization 中创建 App。如果它不需要其他地方的 installations，请选择 **Only on this account**。 |
| 一个 enterprise 内多个 organizations 中的 repositories | 创建一个 enterprise 拥有的 App，并在每个 organization 中安装它。这样可以将 installation 限制在该 enterprise 内。 |
| 多个 organizations 中的 repositories，或 organizations 与个人账户的混合，且没有受管用户 | 创建一个 **Any account** 的 organization 拥有的 App，然后在每个目标账户中安装它。在 GHES 上，**Any account** 仅在该 server 范围内适用。 |
| 由单个个人账户拥有的 repositories，且没有受管用户 | 在该个人账户中创建 App 并选择 **Only on this account**。 |

Public 可见性允许其他账户安装该 App。它不会将 repositories 设为公开，也不会在没有 installation 的情况下授予访问权。

Enterprise 拥有的 App 具有内部可见性，不能安装在个人账户上。请在每个 organization 中安装；enterprise 账户的 installation 不会授予 repository 访问权。

<Accordion title="Enterprise 可见性与受管用户" id="enterprise-managed-users">
  只有 enterprise 成员才能授权 enterprise 拥有的 App。如果外部协作者需要连接 repositories，请在选择该所有权类型之前审核他们的 enterprise 访问权。请参阅 GitHub 的 [App visibility rules](https://docs.github.com/en/enterprise-cloud@latest/apps/creating-github-apps/registering-a-github-app/making-a-github-app-public-or-private) 或 [GHES 等价文档](https://docs.github.com/en/enterprise-server@3.20/apps/creating-github-apps/registering-a-github-app/making-a-github-app-public-or-private)，并选择你所用 server 的文档版本。

  [GitHub Enterprise Cloud with data residency](https://docs.github.com/en/enterprise-cloud@latest/admin/data-residency/about-github-enterprise-cloud-with-data-residency) 使用 Enterprise Managed Users (EMU)。GitHub.com 上的 Enterprise Cloud 也可以使用 EMU；仅使用 SSO 并不意味着一个 enterprise 使用了 EMU。

  对于 EMU，请连接组织拥有的 repositories。受管用户可以注册 App，但此 Engine App 不能安装在受管用户的个人账户上。请参阅 GitHub 的 [managed-user restrictions](https://docs.github.com/en/enterprise-cloud@latest/admin/managing-iam/understanding-iam-for-enterprises/abilities-and-restrictions-of-managed-user-accounts#github-apps)。

  在 EMU enterprise 中，GitHub 可能显示 **This enterprise** 而不是 **Any account**。**Only on this account** 会将 organization 拥有的 App 限制在该 organization 内。每个目标 organization 都需要自己的 installation。

  Organization owner 可以安装该 App。在 EMU enterprise 中，repository 管理员只有在它不请求 organization 权限且 enterprise 策略允许安装时才能安装它。

#### 完成注册表单

对于所有 GitHub 环境和 App 所有者，使用以下设置。字段定义请参阅 [Register a GitHub App](https://docs.github.com/en/enterprise-cloud@latest/apps/creating-github-apps/registering-a-github-app/registering-a-github-app)。将 `https://langsmith.example.com` 替换为你的 LangSmith deployment 的浏览器端 URL。

GitHub 将授权回调字段标记为 **Callback URL** 或 **Redirect URI**。两个名称都指 GitHub 在授权之后将用户返回到的 URL。

如果 LangSmith 使用了 base path，请将其包含在内。例如，位于 `https://langsmith.example.com/langsmith` 的 deployment 使用 `https://langsmith.example.com/langsmith/api-host/v1/integrations/forge/github/callback` 作为其授权回调 URL。

| GitHub 设置 | 值 |
| --- | --- |
| **GitHub App name** | 你的 deployment 的唯一名称，例如 `acme-langsmith-engine`。 |
| **Homepage URL** | 你的 LangSmith URL，例如 `https://langsmith.example.com`。 |
| **Callback URL** / **Redirect URI** | `https://langsmith.example.com/api-host/v1/integrations/forge/github/callback` |
| **Allow wildcard matching** | 如果显示，保持禁用。 |
| **Request user authorization (OAuth) during installation** | 启用。Engine 需要授权回调来完成 installation 的连接。 |
| **Expire user authorization tokens** | 如果显示，保持启用。 |
| **Enable Device Flow** | 保持禁用。 |
| **Setup URL** | 保持未设置。当安装期间的 OAuth 启用时，GitHub 会使用授权回调 URL，并可能禁用此字段。 |
| **Redirect on update** | 启用。用户更新 installation 后返回 LangSmith。 |
| **Webhook: Active** | 启用。 |
| **Webhook URL** | `https://langsmith.example.com/api-host/v1/integrations/forge/github/webhook` |
| **Webhook secret** | 一个单独生成的随机 secret，同时在 LangSmith 中配置。 |
| **SSL verification** | 启用。 |
| **Where can this GitHub App be installed?** | 在 [Choose who owns the App](#choose-who-owns-the-app) 中选择的可见性。Enterprise 拥有的 App 不显示此字段。 |

对于已有的 App，在 **Optional Features** > **User-to-server token expiration** 下管理 token 过期。请参阅 [GitHub 的 token 过期设置](https://docs.github.com/en/enterprise-cloud@latest/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens#configuring-your-app-to-use-user-access-tokens-that-expire)。

{/* 截图：在 GHEC 上展示标记为 "Redirect URI"、或在 GHES 上标记为 "Callback URL" 的授权回调字段，并启用 "Request user authorization (OAuth) during installation"。如果显示，包含处于禁用状态的 "Allow wildcard matching" 和不可用的 Setup URL。URL 使用 https://langsmith.example.com。排除 client secrets、private keys 和 webhook-secret 值。 */}

使用加密安全的生成器或你的 secret manager 生成 webhook secret，至少使用 32 个随机字节。保存它以供 LangSmith 配置使用。

在 **Permissions** > **Repository permissions** 下，配置：

| 权限 | 访问级别 | 用途 |
| --- | --- | --- |
| **Contents** | Read and write | 读取代码并推送 Engine 的 fix 分支。 |
| **Pull requests** | Read and write | 创建 draft PRs 并读取其状态。 |
| **Metadata** | Read-only，自动选中 | 标识 repositories。 |

不要设置 organization、account 和 enterprise 权限。Engine 的标准调查和 fix 工作流不需要 administration、workflow 或 Checks 权限。

在 **Subscribe to events** 下，选择 **Pull request**。这些事件让 Engine 能关联外部创建的、包含 Engine issue 引用的 PRs，并在合并后标记 issues 为完成。

{/* 截图：展示 Contents 和 Pull requests 设为 Read and write、Metadata 设为 Read-only，以及 Pull request 事件被选中。裁剪到这些设置；不要包含任何凭证。 */}

选择 **Create GitHub App**。

#### 保存 App 值

创建 App 之后，打开其设置并准备凭证：

1. 在 **Client secrets** 下，选择 **Generate a new client secret** 并立即保存。
2. 在 **Private keys** 下，选择 **Generate a private key**。保留下载的 PEM 文件；LangSmith 需要其完整内容，包括换行符。
3. 使用你的 secret manager 或加密安全的生成器生成一个至少 32 个随机字节的独立 **OAuth state secret**。仅在 LangSmith 中使用它；不要输入到 GitHub 中，也不要复用 webhook secret。

配置 LangSmith 时使用以下映射：

| 值 | LangSmith environment variable |
| --- | --- |
| GitHub 实例的 web 地址 | `ENGINE_GITHUB_WEB_BASE_URL` |
| **App ID**（数字） | `ENGINE_GITHUB_APP_ID` |
| **Public link**（完整 URL） | `ENGINE_GITHUB_APP_PUBLIC_LINK` |
| **Client ID** | `ENGINE_GITHUB_APP_CLIENT_ID` |
| **Client secret** | `ENGINE_GITHUB_APP_CLIENT_SECRET` |
| **Private key**（PEM 内容） | `ENGINE_GITHUB_APP_PRIVATE_KEY` |
| **Callback URL** / **Redirect URI** | `ENGINE_GITHUB_OAUTH_REDIRECT_URI` |
| **Webhook secret** | `ENGINE_GITHUB_APP_WEBHOOK_SECRET` |
| **OAuth state secret** | `ENGINE_GITHUB_OAUTH_STATE_SECRET` |

复制数字形式的 **App ID**，而不是 Client ID 或 installation ID。精确复制 **Public link**，包括其完整路径；不要使用 developer settings URL 或以 `/installations/new` 结尾的 installation URL。

使用你在 GitHub 中输入的确切授权回调 URL 和 webhook secret。回调 URL 中要包含所有 LangSmith base path。GitHub web 地址是在 [Choose your GitHub environment](#choose-your-github-environment) 中选择的那一个。

### 配置 LangSmith

#### 存储凭证

使用你[现有的 secret 管理工作流](/langsmith/self-host-using-an-existing-secret)，在 LangSmith 命名空间中为 Client secret、private key、webhook secret 和 OAuth state secret 创建 Kubernetes Secrets。Helm 示例引用了一个名为 `langsmith-engine-github` 的 Secret。你可以选择不同的 Secret 名称和 keys；相应更新 `secretKeyRef` 条目。

将凭证存储在 Secrets 中，而不是提交到版本控制的 Helm values 或命令行参数中。App IDs、Client IDs 和 URLs 可以包含在 Helm values 中。

<a id="enable-the-github-integration-routes"></a>

#### 设置 Helm values

启用 `hostBackend`，并将所有 `ENGINE_GITHUB_*` 设置放在 `commonEnv` 中。将以下内容与你的现有 Helm values 合并，保留无关条目。替换占位符和示例 URLs：

```yaml
commonEnv:
  - name: ENGINE_GITHUB_WEB_BASE_URL
    value: "https://<ghes-hostname>"
  - name: ENGINE_GITHUB_APP_ID
    value: "<app-id>"
  - name: ENGINE_GITHUB_APP_PUBLIC_LINK
    value: "<public-link-copied-from-github>"
  - name: ENGINE_GITHUB_APP_CLIENT_ID
    value: "<client-id>"
  - name: ENGINE_GITHUB_OAUTH_REDIRECT_URI
    value: "https://langsmith.example.com/api-host/v1/integrations/forge/github/callback"
  - name: ENGINE_GITHUB_APP_CLIENT_SECRET
    valueFrom:
      secretKeyRef:
        name: langsmith-engine-github
        key: client_secret
  - name: ENGINE_GITHUB_APP_PRIVATE_KEY
    valueFrom:
      secretKeyRef:
        name: langsmith-engine-github
        key: private_key
  - name: ENGINE_GITHUB_OAUTH_STATE_SECRET
    valueFrom:
      secretKeyRef:
        name: langsmith-engine-github
        key: oauth_state_secret
  - name: ENGINE_GITHUB_APP_WEBHOOK_SECRET
    valueFrom:
      secretKeyRef:
        name: langsmith-engine-github
        key: webhook_secret

hostBackend:
  enabled: true
```

将这些变量从组件专属的 `extraEnv` 列表中移除，包括 `hostBackend.deployment.extraEnv`，以避免重复定义。共享配置会向 API 和后台 workloads 提供相同的值。

chart 的 `config.hostname`、`config.frontendHostname`（如果使用）和 `config.basePath` 也必须描述用户在浏览器中打开的 URL。

#### Private GHES deployments

如果 GHES 使用私有 IP 地址或私有 CA，请在应用 values 文件之前包含以下适用的设置。

<a id="ghes-on-a-private-network"></a>

**私有网络上的 GHES**

对于解析到私有 IP 地址的 GHES hostname，请配置从 LangSmith 和 sandbox 主机出发的私有 DNS 和网络路由。同时通过列出的 Helm values 设置以下 environment variables：

| Helm environment 列表 | 变量 | 值 |
| --- | --- | --- |
| `platformBackend.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_ENGINE` | `"true"` |
| `ingestQueue.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_ENGINE` | `"true"` |
| `sandboxes.sandboxHost.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_EGRESS` | `"true"` |

这些设置允许相应组件访问私有地址；它们不会创建 DNS 记录或网络路由。它们影响的不只是这个 GitHub hostname。请为你 deployment 实际需要的目标保留网络限制，并保持对 metadata、loopback 和 Kubernetes 内部地址的保护处于启用状态。

<a id="ghes-with-a-private-certificate-authority"></a>

**使用私有证书颁发机构的 GHES**

LangSmith 服务和 sandbox 主机必须信任签署你的 GHES 证书的 CA。只在你的浏览器或某个 sandbox 内部配置信任是不够的。

按照 [Mount internal CAs for TLS](/langsmith/self-host-custom-tls-certificates#mount-internal-cas-for-tls) 配置 `config.customCa.secretName` 和 `config.customCa.secretKey`。在 bundle 中包含你的私有 CA，以及其他出站连接所需的公共根证书。

同时在 `hostBackend.deployment.extraEnv` 中将 `REQUESTS_CA_BUNDLE` 设置为 `/etc/ssl/certs/custom-ca-certificates.crt`，即 chart 挂载该 bundle 的路径。除了 chart 的 TLS 配置之外，GitHub integration 还需要此设置。

检查 bundle 是否到达 GitHub integration、platform API 和 workers、Engine execution workers 以及 sandbox 主机。保持 TLS 验证启用。sandbox 代理自身的 CA 与用于验证 GHES 的 CA 是分开的。

#### 应用配置

通过你正常的部署流程应用完整的 values 文件，使用匹配的 LangSmith image 和 chart release。Helm 升级请参阅 [Upgrade a self-hosted deployment](/langsmith/self-host-upgrades)。

在连接 repositories 之前，等待受影响的 API 和 worker rollouts 完成。就地更新 Secret 不会重新加载运行中 containers 的环境变量；凭证更改后请重启受影响的 workloads。

<a id="verify-the-integration"></a>

### 验证 webhook 投递

Rollout 完成后，[连接一个测试 repository 并验证连接](#verify-the-connection)。在创建和合并测试 PR 的过程中，检查该 App 的 webhook 投递：

1. 在 GitHub App 的设置中，打开 **Advanced** > **Recent deliveries**。
2. 确认 **pull_request** 投递成功到达 LangSmith。当 LangSmith 接受一个有效的已签名投递时，它会返回 HTTP 202。

仅凭 webhook 响应成功并不能证明事件匹配到了某个 Engine issue。请完成 [Verify the connection](#verify-the-connection) 中的合并检查。

### 排查设置问题

| 症状 | 检查内容 |
| --- | --- |
| **GitHub 未配置** | 确认已设置 App ID、Client ID、Client secret、private key、state secret 和 App 的 public link。检查 GitHub URL 格式并完成 rollout。此提示仅标识缺失的配置；它不会测试凭证是否有效。 |
| 授权之后 GitHub 暂时不可用 | 确认 Client secret 和 private key 属于所配置的 App ID 和 Client ID。检查 GitHub 连通性和证书信任，然后重新开始 **Connect GitHub**。 |
| GitHub 授权打开了错误的实例 | 检查共享配置中的 `ENGINE_GITHUB_WEB_BASE_URL`，并移除冲突的组件级覆盖。 |
| 回调返回 HTML 或 404 | 检查 `/api-host` 路由、LangSmith base path 和确切的授权回调 URL。 |
| 安装后未返回 LangSmith | 启用 **Request user authorization (OAuth) during installation**。检查确切的授权回调 URL，并确认 Client ID 和 Client secret 属于此 App。然后在 LangSmith 中重新开始 **Connect GitHub**。 |
| Repositories 已显示，但克隆或推送失败 | 检查 sandbox 主机的 DNS、路由、私有 IP 设置、证书信任，以及 GitHub 的 IP/推送策略。 |
| 推送成功后 PR 创建失败 | 检查 **Pull requests: Read and write**、draft PR 可用性，以及所选的基础分支。 |
| 合并未将 issue 标记为完成 | 检查 **Pull request** 事件订阅、webhook 可达性、匹配的 webhook secret，以及 **Recent deliveries**。纠正原因后重新投递失败的事件。 |

如果 GitHub 无法投递 webhooks，repository 读取、fixes 和 PR 创建仍然可以工作。由 webhook 驱动的 PR 关联和合并后自动完成 issue 则不工作。恢复投递，并从 GitHub 的 App 设置中重新投递错过的事件。

对于使用外部 coding assistant 创建的 PRs，请在 PR 描述中保留来自 **Copy Fix Context** 的 issue 引用。该引用让 Engine 能将 PR 关联到 issue。

关于缺失的 organizations 或 repositories，请参阅 [Troubleshoot repository selection](#troubleshoot-repository-selection)。

寻求帮助时，请附上你的 LangSmith 和 Helm chart 版本、GitHub 环境和 GHES 版本（如适用）、App 所有权类型，以及失败的步骤。不要包含 private keys、client secrets、webhook secrets 或 access tokens。

### 更改或轮换配置

轮换 private key 时，在 GitHub 中添加新 key，更新 deployment Secret，并重启受影响的 workloads。在移除旧 key 之前先验证连接。在 GitHub 支持多个 client secrets 的地方，采用同样的重叠方式。

轮换 webhook secret 时，需要协调 GitHub 和 LangSmith 两边的值。不匹配期间的投递会签名验证失败。在两边都使用新 secret 后，查看 **Recent deliveries** 并重新投递失败的事件。

更换 App 需要安装替代 App，并重新连接受影响的 LangSmith workspaces。请为 repository 访问恢复之前的间断做好准备。转移 App 所有权也可能改变它可以安装的位置及其 public link；在做出更改之前，请先了解 GitHub 的转移行为。

不要在已连接的现有 deployment 上将更改 `ENGINE_GITHUB_WEB_BASE_URL` 作为迁移手段。更改 URL 不会迁移 repository 连接或已有的 PR 引用。在切换 GitHub 实例之前，请与 LangChain 支持团队一起规划迁移。
