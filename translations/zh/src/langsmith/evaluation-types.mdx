本页介绍 LangSmith 中评估的两个维度：

1. **[评估类型](#offline-evaluation-types)**：_何时_评估、_为什么_评估。包括用于部署前测试的离线评估类型（benchmarking、unit tests、regression tests），以及用于生产环境的在线评估类型（monitoring、anomaly detection）。
1. **[Evaluator 实现方式](#implement-evaluators)**：_如何_评估。包括可用的 evaluator 方法（LLM-as-judge、code、composite、summary、pairwise），以及它们应配置在何处（UI 或 SDK，offline 或 online）。

理解这两个维度，能帮助你建立一套更完整的评估策略，既能在部署前验证功能，也能在生产中持续监控质量。

## 离线评估类型

离线评估会在部署前，基于精心整理的数据集测试应用。通过在带参考输出的 examples 上运行评估，团队可以对比不同版本、验证功能，并在把变更暴露给用户前建立信心。

你可以通过 LangSmith SDK（@[Python][langsmith-python] 或 @[TypeScript][langsmith-js]）在 client 侧运行离线评估，也可以通过 [Playground](/langsmith/prompt-engineering-concepts#playground) 在 server 侧运行，或者通过[把 evaluators 绑定到 dataset](/langsmith/bind-evaluator-to-dataset)来完成。

![Offline](/langsmith/images/offline.png)

### Benchmarking

_Benchmarking_ 用于在一个精心整理的数据集上比较多个应用版本，从而找出表现最好的版本。这个过程通常包括：创建具有代表性的输入数据集、定义性能指标，然后测试每个版本。

Benchmarking 需要准备带 gold-standard reference outputs 的数据集，以及设计合理的比较指标。示例包括：
- **RAG Q&A bot**：数据集包含问题和参考答案，使用 LLM-as-judge evaluator 检查实际答案和参考答案在语义上是否等价。
- **ReAct agent**：数据集包含用户请求和参考 tool calls，使用启发式 evaluator 验证是否执行了所有预期 tool calls。

### Unit tests

_Unit tests_ 用于验证系统中单个组件的正确性。在 LLM 场景中，[unit tests 往往体现为基于规则的断言](https://hamel.dev/blog/posts/evals/#level-1-unit-tests)，例如验证 LLM 生成的代码是否能编译、JSON 是否能成功解析等，这些检查用来保证基础功能正常。

Unit tests 通常期望稳定通过，因此很适合纳入 CI pipeline。在 CI 中运行时，建议配置 caching，以减少 LLM API 调用次数和相应成本。

更多信息请参阅 [Pytest](/langsmith/pytest) 和 [Vitest/Jest](/langsmith/vitest-jest) 页面。

### Regression tests

_Regression tests_ 用于衡量应用在不同版本之间的性能一致性。它们保证新版本不会让当前版本已经正确处理的场景变差，同时最好还能相对 baseline 有所提升。这类测试通常在你进行可能影响用户体验的更新时运行，例如更换模型或调整架构。

LangSmith 的 comparison view 会相对于 baseline 高亮 regressions（红色）和 improvements（绿色），便于快速定位变化点。

![Comparison view](/langsmith/images/comparison-diff-view-light.png)

### Backtesting

_Backtesting_ 会把新版本应用到历史生产数据上进行评估。通常是先把生产日志转成数据集，再让新版本处理这些 examples，从而判断它在真实历史用户输入上的表现。

这种方式常用于评估新模型发布。例如，当一个新模型可用后，你可以用它跑最近的生产 runs，并把结果和真实生产结果进行对比。

### Pairwise evaluation

_Pairwise evaluation_ 会比较两个版本的输出，直接判断哪一个更好，而不是分别给它们打绝对分数。对于某些任务来说，[判断“版本 A 比 B 更好”](https://www.oreilly.com/radar/what-we-learned-from-a-year-of-building-with-llms-part-i/)往往比独立评分更容易。

这种方式尤其适合主观任务上的 LLM-as-judge 评估。例如在摘要任务中，判断“哪一个摘要更清晰、更简洁”，通常比给每一个摘要分别打清晰度分数更容易。

学习[如何运行 pairwise evaluation](/langsmith/evaluate-pairwise)。

## 在线评估类型

在线评估会近实时地评估生产环境中的应用输出。由于没有 reference outputs，这类评估更侧重于发现问题、监控质量趋势，并识别那些应被纳入未来离线测试的边缘场景。

在线 evaluators 通常运行在服务端。LangSmith 提供可配置的内置 [LLM-as-judge evaluators](/langsmith/llm-as-judge)，同时也支持在 LangSmith 内运行自定义 code evaluators。

![Online](/langsmith/images/online.png)

### 实时监控

随着用户持续和系统交互，持续监控应用质量。在线评估会自动运行在生产流量上，对每次交互提供即时反馈。这样可以在问题影响到大量用户之前，及时发现质量下降、异常模式或意外行为。

### 异常检测

识别偏离预期模式的 outliers 和 edge cases。在线 evaluators 可以标记那些具有异常特征的 runs，例如特别长或特别短的回答、异常错误率，或者未通过安全检查的输出，并将其交由人工审查，或加入离线数据集。

### 生产反馈闭环

把生产环境中获得的洞察用于改进离线评估。在线评估会暴露真实世界中的问题和使用模式，而这些内容往往不会出现在精心整理的数据集中。那些失败的生产 runs 会成为潜在的 dataset examples，从而形成一个迭代闭环：生产经验不断反哺测试覆盖面。

## 实现 evaluators

上面这些评估类型描述的是 _何时_评估。LangSmith 还提供了多种 _如何_实现 evaluator 的方式，它们可以跨不同评估类型使用。

### LLM-as-a-judge

使用一个 LLM，根据 prompt 中定义的标准来给输出打分。这种方法特别适合评估 tone、clarity、semantic correctness 等难以通过确定性规则描述的主观质量。

常见用法包括：在离线场景中，基于 reference outputs 检查事实准确性；在在线场景中，检查生产回答是否带有 toxicity。例如，在 benchmark 一个 RAG 系统时，你可以使用一个 LLM-as-judge evaluator 来检查生成答案和参考答案在语义上是否等价。

可以通过以下方式配置 LLM-as-a-judge evaluators：
- 程序化离线评估：[使用 SDK](/langsmith/llm-as-judge-sdk)
- 面向 datasets 的离线评估：[在 UI 中](/langsmith/llm-as-judge)
- 面向生产 traces 的在线评估：[在 UI 中](/langsmith/online-evaluations-llm-as-judge)

### Code evaluators

编写基于规则、确定性的函数来检查特定条件。这类 evaluators 会执行自定义逻辑，用于验证结构、查找模式，或应用业务规则。

Code evaluators 特别适合 unit tests，例如验证生成代码是否能编译、JSON 是否能正确解析、必填字段是否存在。在 regression testing 中，它们也可以用来跟踪结构化输出的一致性；在在线监控中，则能实时捕捉格式违规问题。

可以通过以下方式定义 code evaluators：
- 面向 datasets 的离线评估：[在 UI 中](/langsmith/code-evaluator-ui)
- 程序化离线评估：[使用 SDK](/langsmith/code-evaluator-sdk)
- 面向生产 traces 的在线评估：[在 UI 中](/langsmith/online-evaluations-code)

### Composite evaluators

将多个 evaluator 的分数通过加权平均或求和，组合成一个单一指标。这样可以创建一个同时反映多个维度的聚合质量分数。

在 benchmarking 中，composite score 有助于在多个维度上比较不同版本，例如 70% accuracy + 20% clarity + 10% conciseness。在在线监控中，它们可以为 dashboard 和 alerts 提供一个统一指标。例如，把整体 chatbot 质量定义为 helpfulness、correctness 和 tone 分数的加权组合。

配置 composite evaluators 的方式包括：
- 带预定义聚合规则的离线评估：[在 UI 中](/langsmith/composite-evaluators-ui)
- 带自定义聚合逻辑的离线评估：[使用 SDK](/langsmith/composite-evaluators-sdk)
- 面向生产 traces 的在线评估：[在 UI 中](/langsmith/online-evaluations-composite)

### Summary evaluators

对整个 experiment 进行指标计算，而不是逐条 example 计算。这类 evaluators 会拿到整个 dataset 的所有输出，并计算 precision、recall、F1 score 或分布分析等聚合统计。

当你需要的是 dataset 级别指标，例如比较不同版本的整体表现，而不是逐个 example 的分数时，summary evaluators 就非常重要。由于它们需要处理完整 dataset，因此只适用于离线评估。

实现 summary evaluators 的方式：
- 自定义离线评估聚合函数：[使用 SDK](/langsmith/summary)

### Pairwise evaluators

比较两个版本的输出，以判断哪一个相对更好。正如前面在 [pairwise evaluation](#pairwise-evaluation) 中提到的，当绝对打分很困难，但判断“哪个更好”却很容易时，这种方式非常有用。

运行 pairwise evaluations 的方式：
- 比较已有 experiments：[使用 SDK](/langsmith/evaluate-pairwise)
