当你在 [Microsoft Azure](https://azure.microsoft.com/) 上运行 LangSmith 时，[self-hosted](/langsmith/self-hosted) 模式会部署一个包含 observability 功能的完整 LangSmith 平台。

本页包含：

- 部署到 AKS、配置托管服务以及设置认证所需的[初始步骤](#initial-setup)。
- Azure 专属的[参考架构](#reference-architecture)模式与参考图。
- [Azure 上的计算与网络](#compute-and-networking-on-azure)指导和最佳实践。
- Azure deployments 的[安全与访问控制](#security-and-access-control)建议。

<Note>
LangChain 发布了生产可用的 [Azure Terraform modules](https://github.com/langchain-ai/terraform/tree/main/modules/azure)，可在单一流程中预配 AKS、Azure Database for PostgreSQL、Azure Managed Redis、Blob Storage 和 Key Vault。请先阅读 [Deploy with Terraform 概览](/langsmith/self-host-terraform)，在 Terraform 和仅 Helm 两种方式之间做出选择。
</Note>

## 参考架构

我们建议使用 Azure 的托管服务，以提供可扩展、安全且具备弹性的运行平台。下列架构同时适用于 self-hosted 和 hybrid deployments。

| | Components | How it's installed |
|---|---|---|
| **LangSmith Helm release** | Frontend, backend, queue, platform backend, Playground, ACE, and optionally the LangSmith Deployment control/data plane | One `helm upgrade --install` from the [`langchain/langsmith`](https://github.com/langchain-ai/helm/tree/main/charts/langsmith) chart |
| **You provision** | AKS, PostgreSQL, Managed Redis, Blob Storage, Key Vault, ingress, and ClickHouse | Your IaC tooling (Terraform, ARM templates, or Azure portal) before installing LangSmith |

**Installation order:** 先预配 Azure 基础设施 → 预配或订阅 ClickHouse → 配置 Entra ID 和 Workload Identity → 运行 `helm upgrade --install`。LangSmith Deployment、Fleet、Insights 和 Chat 都通过同一个 Helm release 启用，而不是分别单独安装。

**Compliance surface:** LangSmith chart 及其 container images 需要一次应用审核，每个 Azure 托管资源则采用标准 Azure 服务审核。ClickHouse Cloud 还会额外引入一次第三方 SaaS 审核。

- **Client interfaces**：用户通过浏览器或 LangChain SDK 与 LangSmith 交互。所有流量都终止于 [Azure Load Balancer](https://azure.microsoft.com/en-us/products/load-balancer/)，随后被路由到 [AKS](https://azure.microsoft.com/en-us/products/kubernetes-service/) 集群中的 frontend（NGINX），必要时再转发到集群内其他服务。
- **Storage services**：平台需要为 traces、metadata 和缓存提供持久化存储。在 Azure 上推荐使用：
    - <Icon icon="database" /> **[Azure Database for PostgreSQL (Flexible Server)](https://azure.microsoft.com/en-us/products/postgresql/)**，用于事务型数据（例如 runs、projects）。Azure 的高可用选项会在另一个 zone 中预配 standby replica；数据会同步提交到 primary 和 standby servers。LangSmith 要求 PostgreSQL 14 及以上版本。
    - <Icon icon="database" /> **[Azure Managed Redis](https://azure.microsoft.com/en-us/products/managed-redis/)**，用于 queues 和缓存。最佳实践包括：存储尽量小的 values，将大对象拆分为多个 keys，使用 pipelining 提升吞吐量，并确保 client 与 server 位于同一区域。你也可以使用 [Azure Cache for Redis](https://azure.microsoft.com/en-us/products/cache)，以单实例或集群模式运行。LangSmith 要求 Redis OSS 5 及以上版本。
    - <Icon icon="chart-line" /> **ClickHouse**，用于 traces 的高吞吐分析。我们建议使用[外部托管的 ClickHouse 方案](/langsmith/self-host-external-clickhouse)。如果出于安全或合规原因不能这样做，则可使用开源 operator 在 AKS 上部署 ClickHouse cluster。请确保跨[availability zones](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview)复制，以保证持久性。Hybrid deployment 不要求 Clickhouse。
    - <Icon icon="cube" /> **[Azure Blob Storage](https://azure.microsoft.com/en-us/products/storage/blobs/)**，用于存储大体积 artifacts。建议使用具备冗余能力的存储配置，如 read-access geo-redundant (RA-GRS) 或 geo-zone-redundant (RA-GZRS) storage，并设计应用在故障期间从 secondary region 读取数据。

## Azure 上的计算与网络

### Azure Kubernetes Service (AKS)

[AKS](https://azure.microsoft.com/en-us/products/kubernetes-service/) 是生产部署推荐的计算平台。本节概述规划环境时的关键考量。

#### 网络模型

生产集群请使用 [Azure CNI](https://learn.microsoft.com/en-us/azure/aks/configure-azure-cni) 网络。该模型会把集群整合进已有虚拟网络，为每个 pod 和 node 分配 IP，并允许其直接连接到本地环境或其他 Azure 服务。请确保子网为 nodes 和 pods 预留足够 IP，避免地址段重叠，并为横向扩容预留额外 IP 空间。

#### Ingress 与负载均衡

使用 Kubernetes Ingress resources 和 controllers 分发 HTTP/HTTPS 流量。Ingress controllers 在第 7 层工作，可按 URL path 路由流量并处理 TLS termination。相比第 4 层负载均衡器，它们可以减少公共 IP 地址数量。建议使用 [application routing add-on](https://learn.microsoft.com/en-us/azure/aks/app-routing)，通过托管 NGINX ingress controllers 集成 [Azure DNS](https://azure.microsoft.com/en-us/products/dns/) 和 [Key Vault](https://azure.microsoft.com/en-us/products/key-vault/) 以管理 SSL certificates。

#### Web Application Firewall (WAF)

为了增强防护，可部署 [WAF](https://learn.microsoft.com/en-us/azure/web-application-firewall/overview)，例如 [Azure Application Gateway](https://azure.microsoft.com/en-us/products/application-gateway/)。WAF 会使用 OWASP 规则过滤流量，并可在流量进入 AKS cluster 之前终止 TLS。

#### 网络策略

使用 [Kubernetes network policies](https://learn.microsoft.com/en-us/azure/aks/use-network-policies) 限制 pod-to-pod 流量，从而降低工作负载被攻破后的影响。在创建集群时启用 network policy 支持，并基于应用连通性设计规则。

#### 高可用性

请让 node pools 跨[availability zones](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview)部署，并为所有 deployments 配置 Pod Disruption Budgets (PDB) 与多个 replicas。为 pods 设置 resource requests 和 limits；[AKS resource management best practices](https://learn.microsoft.com/en-us/azure/aks/developer-best-practices-resource-management) 建议设置 CPU 与内存限制，以防 pods 占满所有资源。使用 [Cluster Autoscaler](https://learn.microsoft.com/en-us/azure/aks/cluster-autoscaler) 与 [Vertical Pod Autoscaler](https://learn.microsoft.com/en-us/azure/aks/vertical-pod-autoscaler) 自动扩展 node pools 并调整 pod 资源。

### 网络与身份

#### 虚拟网络集成

将 AKS 部署到其独立的[虚拟网络](https://azure.microsoft.com/en-us/products/virtual-network/)中，并为 cluster、database、Redis 和存储 endpoints 分别创建子网。使用 [Private Link](https://azure.microsoft.com/en-us/products/private-link/) 与 [service endpoints](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview)，让流量保持在虚拟网络内部，避免暴露到公共互联网。

#### 认证

将 LangSmith 与 [Microsoft Entra ID](https://www.microsoft.com/en-us/security/business/identity-access/microsoft-entra-id)（Azure AD）集成，以实现单点登录。使用 Azure AD OAuth2 bearer tokens，并通过角色分配控制对 UI 与 API 的访问。

## 存储与数据服务

### Azure Database for PostgreSQL

#### 高可用性

使用启用了高可用模式的 [Flexible Server](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/overview)。Azure 会在同一 availability zone 内（zonal）或跨 zones（zone-redundant）预配 standby replica。数据会同步提交到 primary 和 standby servers，从而确保已提交的数据不会丢失。Zone-redundant 配置会将 standby 放在不同 zone，以防 zone 故障，但可能增加写入延迟。

#### 备份与灾难恢复

启用[自动备份](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-backup-restore)，并配置 geo-redundant backup storage，以抵御区域级故障。对于关键应用，可在 secondary region 创建 read replicas。

#### 扩展

选择适配你工作负载的 SKU；Flexible Server 支持独立扩展计算与存储。使用 [Azure Monitor](https://azure.microsoft.com/en-us/products/monitor/) 监控指标并配置告警。

### Azure Managed Redis

#### 持久化与冗余

选择支持复制与持久化的 tier。为保证数据耐久性，请配置 Redis persistence 或数据备份。若要实现高可用，可依据所选 tier 使用 [active geo-replication](https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication) 或 zone-redundant caches。

### Azure 上的 ClickHouse

ClickHouse 用于分析型工作负载（traces 和 feedback）。如果你无法使用外部托管方案，可以通过 Helm 或官方 operator，在 AKS 上部署 ClickHouse cluster。为增强弹性，请跨 nodes 和 availability zones 复制数据。可考虑使用 [Azure Disks](https://azure.microsoft.com/en-us/products/storage/disks/) 作为本地存储，并以 StatefulSets 挂载。

### Azure Blob Storage

#### 冗余

请根据恢复目标选择合适的冗余配置。建议使用 [read-access geo-redundant (RA-GRS) 或 geo-zone-redundant (RA-GZRS) storage](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy)，并设计应用在 primary region 故障期间切换到 secondary region 读取。

#### 命名与分区

使用有助于提升分区负载均衡的命名约定，并为最大并发客户端数量预做规划。遵守 Azure 的可扩展性和容量目标，必要时将数据分散到多个 storage accounts。

#### 网络

通过[private endpoints](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints)访问 blob storage，或结合 SAS tokens 与 CORS rules 启用直接客户端访问。

## 安全与访问控制

### Azure Key Vault

#### 按应用与环境分离 vault

将数据库连接字符串、API keys 等 secrets 存储在 [Azure Key Vault](https://azure.microsoft.com/en-us/products/key-vault/) 中。为每个应用和环境（dev、test、prod）分别使用独立 vault，以降低安全事件的影响范围。

#### 访问控制

使用 [RBAC permission model](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-guide)，在 vault 作用域内分配角色，并将访问限制在必要主体上。通过 Private Link 和 firewall 限制网络访问。

#### 数据保护与日志

启用 [soft delete and purge protection](https://learn.microsoft.com/en-us/azure/key-vault/general/soft-delete-overview)，防止误删。开启日志记录，并为 Key Vault 访问事件配置告警。

### 网络安全

#### Ingress 隔离

只通过 ingress controller 或 WAF 暴露 frontend service。其他服务应保持内部可见，仅通过 cluster networking 通信。

#### RBAC 与 pod 安全

使用 [Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/) 控制谁可以部署、修改或读取资源。启用 [pod security admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/)，以强制执行 baseline、restricted 或 privileged profiles。

#### Secrets 管理

使用 [CSI Secret Store](https://learn.microsoft.com/en-us/azure/aks/csi-secrets-store-driver)，把 Key Vault 中的 secrets 挂载到 pods 中。避免把 secrets 存在环境变量或配置文件里。

## 可观测性与监控

配置你的 LangSmith 实例以[导出 telemetry data](/langsmith/export-backend)，这样你就可以使用 Azure 的服务对其进行监控。

### Azure Monitor

使用 [Azure Monitor](https://azure.microsoft.com/en-us/products/monitor/) 处理指标、日志和告警。主动式监控包括围绕关键指标配置告警，例如 node CPU/内存利用率、pod 状态和服务延迟。当超过预设阈值时，Azure Monitor alerts 会发出通知。

### 托管 Prometheus 与 Grafana

启用 [Azure Monitor managed Prometheus](https://learn.microsoft.com/en-us/azure/azure-monitor/essentials/prometheus-metrics-overview)，收集 Kubernetes 指标。结合 [Grafana dashboards](https://azure.microsoft.com/en-us/products/managed-grafana/) 做可视化。请定义 service-level objectives (SLOs) 并据此配置告警。

### Container Insights

安装 [Container Insights](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/container-insights-overview)，采集 AKS nodes 与 pods 的日志和指标。使用 [Azure Log Analytics workspaces](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-overview) 查询和分析日志。

### 应用日志

确保 LangSmith 服务将日志输出到 stdout/stderr，并通过 [Fluent Bit](https://fluentbit.io/) 或 Azure Monitor agent 进行转发。
