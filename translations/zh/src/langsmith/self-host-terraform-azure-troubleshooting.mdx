## 基础设施阶段

### 资源名称已被全局占用

**症状：** `terraform apply` 失败，报 `The name 'langsmith-redis-dev' is not available`、`StorageAccountAlreadyTaken` 或 `VaultAlreadyExists`。

**原因：** Postgres、Redis、Storage 和 Key Vault 的名称在所有 Azure 租户之间全局唯一。设为 `unique_resource_names = false`（默认值）时，这些名称仅由 `name_prefix` 派生，因此另一个使用相同 `name_prefix` 的部署可能已经占用了它们。之前 `terraform destroy` 产生的 soft-deleted Key Vault 也会占用其名称，直到保留期结束。

**修复：**

- 新部署：在 `terraform.tfvars` 中设置 `unique_resource_names = true`。这会把基础名称从 `langsmith` 切换为 `ls`，并在四个全局名称后面追加订阅 ID 和 `name_prefix` 的哈希。
- 已有部署：不要更改 `unique_resource_names`，那会重命名并重建每个资源。只用 `postgres_name`、`redis_name`、`storage_account_name` 或 `keyvault_name` 固定冲突的名称。
- 设为 `unique_resource_names = true` 的首次 apply 失败：设置 `name_suffix_salt = "2"` 来轮换全部四个哈希名称。在已运行的部署上，这会销毁并重建 Postgres、Redis、Storage 和 Key Vault。

apply 之前先运行 `make preflight`。它会通过 Azure 的可用性 API 检查 Postgres、Storage 和 Key Vault 名称以及 `dns_label`。Redis 名称没有可用性检查。

### `K8sVersionNotSupported`：版本仅支持 LTS

**症状**

```txt
Error: creating Kubernetes Cluster ... unexpected status 400
"code": "K8sVersionNotSupported"
"message": "Managed cluster ... is on version 1.32.x, which is only available for Long-Term Support (LTS).
If you intend to onboard to LTS, please ensure the cluster is in Premium tier ..."
```

**原因：** Azure 会定期把次要版本从 Standard 层级支持中退役，转为仅 LTS。截至 2026 年 4 月，`eastus` 中 1.32 及以下版本仅支持 LTS。Standard 层级集群必须使用 1.33 或更高版本。

**修复：** 将 `aks_kubernetes_version` 设置为支持 `KubernetesOfficial` 的版本。module 默认为 `1.35`。

```bash
az aks get-versions --location eastus -o table
# Versions with KubernetesOfficial in SupportPlan column work on Standard tier
```

移除或更新 `terraform.tfvars` 中任何 `aks_kubernetes_version` 锁定，然后 `make apply`。已有的 1.32 集群会继续运行；这只阻塞新集群的创建。

### vCPU 配额超限

**症状（autoscaler 退避，pods 处于 Pending）：**

```txt
Warning  FailedScheduling     pod/langsmith-backend-xxx  0/1 nodes are available: 1 Too many pods.
Normal   NotTriggerScaleUp    pod/langsmith-backend-xxx  pod didn't trigger scale-up: 2 in backoff after failed scale-up
```

**症状（节点池轮换）：**

```txt
Error: creating temporary Agent Pool ... "code": "ErrCode_InsufficientVCPUQuota",
"message": "Insufficient vcpu quota requested 8, remaining 2 for family standardDSv5Family for region eastus."
```

**原因：** 每个 VM 系列按 region 的 vCPU 配额。`eastus` 中 `standardDSv5Family` 的默认值通常是 10 核。一个 `Standard_D8s_v5` 节点（module 默认规格）占用 8 核，只剩 2 核。

**为什么 `max_pods = 30` 会触发它：** 基础安装会运行约 37 个 pods（约 17 个 LangSmith pods 加约 20 个系统 pods），超过 AKS 默认的每节点 30 个，因此 autoscaler 会添加第二个节点，撞上配额并进入退避。module 默认值 `default_node_pool_max_pods = 60` 可以让所有 pods 放进单个节点。检查 `terraform.tfvars` 没有把它调低。

**多 dataplane（3 个 dataplane）的推荐配额：** 32 核。

**申请提高配额：**

```bash
# Azure portal usually auto-approves within minutes:
# Portal > Subscriptions > <sub> > Usage + Quotas > search "DSv5" > eastus > Request increase > 32

# Or via CLI
az quota update \
  --resource-name "standardDSv5Family" \
  --scope /subscriptions/<sub-id>/providers/Microsoft.Compute/locations/eastus \
  --limit-object value=32 limit-type=Independent \
  --resource-type dedicated

az vm list-usage --location eastus --query "[?contains(name.value,'DSv5')]" -o table
```

**替代方案，DSv5 配额耗尽时更换 VM 系列：** 设置 `default_node_pool_vm_size = "Standard_D8s_v3"`，并在 `additional_node_pools` 中为 `large` 节点池使用 `Standard_D16s_v3`。vCPU 和内存相同，只是配额池不同。配额到位后再迁回 v5。不要回退到 DSv2（`Standard_DS4_v2`、`Standard_DS5_v2`），Azure 已将其退役。

<Note>
`max_pods` 在已有节点池上不可修改。请在首次 `terraform apply` 之前设置。
</Note>

### `LocationIsOfferRestricted`：该区域阻止 Postgres Flexible Server

**症状：** AKS 创建成功，随后 Postgres 失败，报 `Status: "LocationIsOfferRestricted"` 或 `ParameterOutOfRange: The value of the 'Version' should be in: []`。

**原因：** Azure 阻止某些订阅 offer 类型（Free Trial、Visual Studio 和 MSDN credit、Azure Pass、部分赞助订阅）在高需求区域预配 PostgreSQL Flexible Server。决定结果的是订阅类型，而不是区域。`make preflight` 会在 apply 开始前报告这一点。

**修复：** 按优先顺序使用以下方式之一：

1. 将订阅转换为 Pay-As-You-Go。
2. 在 [aka.ms/postgres-request-quota-increase](https://aka.ms/postgres-request-quota-increase) 申请豁免。
3. 对于 dev 或 demo 部署，设置 `postgres_source = "in-cluster"`。不适合生产环境。
4. 更改 `terraform.tfvars` 中的 `location`。Postgres 必须与 VNet 位于同一区域，因此整个部署都要迁移。

### 数据库 SKU 系列在该区域没有配额

**症状：** apply 构建了资源组、VNet 和 AKS，随后在 Flexible Server 上失败，报出某个 vCPU 系列和区域的配额错误，例如 `eastus` 中的 `standardDDSv5Family`。

**原因：** Postgres Flexible Server 消耗 `Microsoft.Compute` 按系列的 vCPU 配额。新订阅的某些系列上限通常为 0。`make preflight` 会把 `postgres_sku_name` 映射到其所属系列，并在 apply 开始前对零上限报错。

**修复：** 在 [aka.ms/postgres-request-quota-increase](https://aka.ms/postgres-request-quota-increase) 申请提高配额，或把 `postgres_sku_name` 设为有配额系列中的 SKU：

```bash
az vm list-usage -l eastus --only-show-errors --query "[?limit=='0'].name.value" -o tsv
```

### `roleAssignments/write` 上的 `AuthorizationFailed`

**症状：** 资源正常创建，随后某个角色分配失败，报 `does not have authorization to perform action 'Microsoft.Authorization/roleAssignments/write'`。

**原因：** 部署身份持有 Contributor 但没有角色分配角色。module 会为其自身的 managed identity 创建角色分配，而 Contributor 无法做到。如果该身份已持有 User Access Administrator，订阅可能把该权限限制在基于 `principalType` 的 ABAC 条件之后，同样会返回这条消息。

**修复：**

- 在订阅范围授予 `Role Based Access Control Administrator`，或用 `Owner` 代替这两个角色。apply 之前运行 `make preflight` 检查部署身份的角色。
- 对于 `principalType` 条件，交互式 `az login` 时设置 `terraform_principal_type = "User"`，CI 中设置为 `"ServicePrincipal"`。如果条件只允许 service principal，设置 `keyvault_manage_terraform_admin_assignment = false` 和 `keyvault_manage_secrets = false`。让租户 admin 在 vault 上授予你 Key Vault Secrets Officer，然后用 `make seed-secrets` 写入机密。

完整的权限清单参见 [PERMISSIONS.md](https://github.com/langchain-ai/terraform/blob/main/modules/azure/PERMISSIONS.md)。

### `terraform plan` 期间读取操作上的 `AuthorizationFailed`

**症状：** 对已应用的部署运行 `terraform plan` 时在刷新阶段失败，某个 `read` 操作（如 `Microsoft.Network/publicIPAddresses/read`）返回 403。

**原因：** 刷新会读取 state 中的每个资源。当之前可用的读取开始失败时，最常见的原因是 Privileged Identity Management（PIM）激活过期。重新运行 `az login` 不能解决这个问题。

**修复：** 在 Azure 门户中重新激活该角色（PIM > My roles > Activate），激活时长要长于 apply 所需时间。`make preflight` 会打印活动 PIM 激活的剩余时间。

### 创建私有 endpoint 时的 `LinkedAuthorizationFailed`

**症状：** 设置了 `storage_private_dns_zone_id` 或 `keyvault_private_dns_zone_id` 时，`make apply` 创建私有 endpoint 失败，报 `LinkedAuthorizationFailed`。

**原因：** 该 endpoint 会在你提供的 zone 中注册记录，这需要对该 zone 拥有 `Microsoft.Network/privateDnsZones/join/action`。位于 module 未创建的子网中的 endpoint，还需要对该子网拥有 `Microsoft.Network/virtualNetworks/subnets/join/action`。新授权可能需要 12 到 40 分钟才生效，在此之前 Azure 会判该 endpoint 失败。

**修复：** 在首次 apply 之前，在该 zone 的资源组授予 `Private DNS Zone Contributor`，在 endpoint 子网上授予 `Network Contributor`。如果授权已存在，等待后重新运行 `make apply`。参见 [PERMISSIONS.md](https://github.com/langchain-ai/terraform/blob/main/modules/azure/PERMISSIONS.md#private-dns-zones-you-own)。

### Istio addon 版本不受支持

**症状：** `terraform apply` 拒绝 Istio 版本（`Revision asm-1-XX is not supported`）。Azure 会定期退役旧的 ASM 版本。

**修复：** 检查当前可用的版本并更新 `istio_addon_revision`：

```bash
az aks mesh get-revisions --location eastus -o table
```

在 `terraform.tfvars` 中设置该值并重新 apply。

### Key Vault 清除保护启用后无法禁用

**症状**

```txt
Error: updating Key Vault "langsmith-kv-dz":
once Purge Protection has been Enabled it's not possible to disable it
```

**原因：** 通过 `terraform destroy` 删除 Key Vault 时，Azure 会将其 soft-delete 90 天。下一次使用同名 `terraform apply` 会静默恢复旧的 Key Vault，包括其原有的 `purge_protection_enabled = true`。清除保护是单向的（启用后无法禁用）。

**修复（接受清除保护，测试环境）：**

```hcl
keyvault_purge_protection = true
```

**修复（需要 `purge_protection = false`）：** 清除保护在保留期结束前也会阻塞 `az keyvault purge`，因此被恢复的 vault 无法通过 purge 释放其名称。改为给部署一个新的 vault 名称：

```hcl
keyvault_name = "<new-unique-name>"   # 24 characters or fewer
```

运行 `make apply`，然后运行 `make seed-secrets`，把 LangSmith 应用机密写入新 vault。

### Key Vault 机密已存在但不在 Terraform state 中

**症状**

```txt
Error: a resource with the ID "https://<vault>.vault.azure.net/secrets/langsmith-license-key/..."
already exists - to be managed via Terraform this resource needs to be imported into the State.
```

**原因：** 有东西在 Terraform 之外把该机密写入了 Key Vault，或 state 文件丢失了该资源。Terraform 只管理两个机密：`postgres-admin-password` 和 `langsmith-license-key`。设为 `keyvault_manage_secrets = false` 时，`make seed-secrets` 改为写入这两个机密，因此之后再把它设回 `true` 就会导致这种冲突。通过 `create_keyvault = false` 附加、且已持有其中任一机密的现有 vault 也会导致该错误。LangSmith 应用机密没有 Terraform 资源，永远不会产生这个错误。

**修复：** 导入冲突的机密，然后重新 apply。`<vault>` 可通过 `make tf ARGS="output keyvault_name"` 获取。

```bash
terraform -chdir=infra import \
  'module.keyvault.azurerm_key_vault_secret.langsmith_license_key[0]' \
  "$(az keyvault secret show --vault-name <vault> --name langsmith-license-key --query id -o tsv)"

make apply
```

对于 `postgres-admin-password`，导入到 `module.keyvault.azurerm_key_vault_secret.postgres_admin_password[0]`。要让 Terraform 完全不接触 vault 的机密，设置 `keyvault_manage_secrets = false`，让 `make seed-secrets` 写入全部机密。在已 apply 过的部署上，先从 state 中移除这两个机密，否则 Terraform 会把它们从 vault 中删除。

### 已有 Key Vault：apply 创建了角色分配，随后在机密上返回 403

**症状：** 设为 `create_keyvault = false` 时，apply 通过了 `azurerm_role_assignment`，却在第一个 `azurerm_key_vault_secret` 上失败，报 `StatusCode=403`。`make seed-secrets` 也以同样方式失败。

**原因：** 三者之一：

1. vault 防火墙拒绝了 apply 主机的 IP。消息会指明 `ForbiddenByFirewall` 或客户端地址。
2. 部署身份在 vault 上没有 Key Vault Secrets Officer。Terraform 不会为它未创建的 vault 创建该授权。
3. 授权已存在但尚未传播。

**修复：**

```bash
# 1. Check the firewall, then allowlist the apply host
az keyvault show --name <vault> --query "properties.networkAcls" -o json
az keyvault network-rule add --name <vault> --ip-address "<apply-host-ip>/32"

# 2. Check the deploying identity's roles on the vault
az role assignment list --assignee "$(az ad signed-in-user show --query id -o tsv)" \
  --scope "$(az keyvault show --name <vault> --query id -o tsv)" \
  --include-inherited --query "[].roleDefinitionName" -o tsv

# 3. Confirm data-plane access, then re-run make apply
az keyvault secret list --vault-name <vault> --query "length(@)"
```

对于原因 2，让 vault 所有者授予部署身份 Key Vault Secrets Officer。对于原因 3，等待几分钟后重新运行 `make apply`。设置 `keyvault_manage_secrets = false` 会让 Terraform 退出 vault 的数据平面，随后 `make seed-secrets` 会用你自己的凭证写入机密，那些凭证同样需要 Key Vault Secrets Officer。

### `make plan` 或 `make apply` 停止：`ingress_controller is not set`

**症状：** `make plan`、`make apply` 或 `make tf ARGS="apply"` 在 Terraform 运行之前退出，报 `ingress_controller is not set, and this deployment runs ingress-nginx.`

**原因：** `ingress_controller` 的默认值从 `nginx` 变更为 `envoy-gateway`。从未设置该变量的部署仍运行 ingress-nginx，应用新默认值会移除 ingress-nginx 及其负载均衡器，改变公网 IP。一个 guard 脚本会停止运行，直到你做出选择。

**修复：** 在 `terraform.tfvars` 中设置 `ingress_controller`：

- 保留 NGINX：`ingress_controller = "nginx"`。
- 迁移到 Envoy Gateway：`ingress_controller = "envoy-gateway"`，然后连续运行 `make apply`、`make init-values` 和 `make deploy`。在 deploy 完成之前，apply 期间 LangSmith 无法访问。更新所有指向旧 IP 的 DNS A 记录。

## 应用阶段

### `Could not read aks_resource_group_name`

**症状：** 升级 module 之后，`make kubeconfig`、`make deploy` 或 `make uninstall` 停止，报 `Could not read aks_resource_group_name. Run 'make apply' to record it.`

**原因：** 脚本从 `aks_resource_group_name` output 读取集群的资源组，而早期 module 版本的 apply 没有记录它。

**修复：** 运行 `make apply`，然后重新运行该命令。

### `dns_label` 子域名无法解析：TLS 证书卡在 pending

**症状：** `nslookup langsmith-demo.eastus.cloudapp.azure.com` 返回 NXDOMAIN。cert-manager ACME challenge 无法完成；TLS 证书停留在 `READY: False`。

**原因：** 只有当 ingress controller 的 LoadBalancer service 带有 `service.beta.kubernetes.io/azure-dns-label-name` 标注时，Azure 才会把 DNS label 分配给公网 IP。`make deploy` 会设置它；直接运行 `helm upgrade` 则不会。

**`ingress_controller = "envoy-gateway"`（默认值）的修复：** EnvoyProxy `langsmith-proxy` 携带该标注，Envoy Gateway 会把它复制到 proxy service 上。检查两者：

```bash
kubectl get envoyproxy langsmith-proxy -n envoy-gateway-system \
  -o jsonpath='{.spec.provider.kubernetes.envoyService.annotations}'
kubectl get svc -n envoy-gateway-system \
  -l gateway.envoyproxy.io/owning-gateway-name=langsmith-gateway \
  -o jsonpath='{.items[0].metadata.annotations.service\.beta\.kubernetes\.io/azure-dns-label-name}'
```

如果任一缺失，在 `terraform.tfvars` 中设置 `dns_label`，然后运行 `make init-values` 和 `make deploy`，它们会重新应用 EnvoyProxy。当 `terraform.tfvars` 与生成的 values 在 `dns_label` 上不一致时，`make deploy` 会停止。DNS 解析正常后，按照 NGINX 修复中的方法删除卡住的证书。

**`ingress_controller = "nginx"` 的修复：**

```bash
kubectl annotate svc ingress-nginx-controller -n ingress-nginx \
  service.beta.kubernetes.io/azure-dns-label-name=<dns_label> \
  --overwrite

# Wait 1-2 minutes, verify DNS resolves
nslookup <dns_label>.eastus.cloudapp.azure.com

# Delete the stuck cert to trigger re-issue
kubectl delete certificate langsmith-tls -n langsmith
```

### `istio-addon`：80/443 端口超时，TLS 握手被重置

**症状：** 使用 `ingress_controller = "istio-addon"` 执行 `make deploy` 后站点不可达。80 端口超时，443 端口被重置。

`istio-addon` 不支持 `tls_certificate_source = "letsencrypt"`，因为该 add-on 不为 HTTP-01 solver 创建 IngressClass。请使用自定义域名的 `dns01`、`existing` 或 `none`。

**原因（两个叠加的问题）：**

1. **Gateway 标签错误。** 使用 `ingressClassName: istio` 的 Kubernetes Ingress 会指向带 `istio: ingressgateway` 标签的 pods。AKS 托管的外部 gateway 使用 `istio: aks-istio-ingressgateway-external`。
2. **TLS secret 在错误的 namespace。** Istio SDS 从 gateway pod 的 namespace（`aks-istio-ingress`）读取，而不是应用 namespace（`langsmith`）。

**修复：** 当前脚本中 `make deploy` 会自动处理这两项。如果手动部署，请创建一个指向 `istio: aks-istio-ingressgateway-external` 的 Istio `Gateway`，把 `langsmith-tls` 同步到 `aks-istio-ingress` namespace，并创建一个路由到 LangSmith frontend 的 `VirtualService`。完整的 YAML 请参见 [TROUBLESHOOTING.md 源文件](https://github.com/langchain-ai/terraform/blob/main/modules/azure/TROUBLESHOOTING.md)。

### `letsencrypt-prod` ClusterIssuer 缺失

**症状：** `kubectl describe certificate langsmith-tls -n langsmith` 显示 `clusterissuers.cert-manager.io "letsencrypt-prod" not found`。

**原因：** 当 `tls_certificate_source` 为 `letsencrypt` 或 `dns01` 时，`deploy.sh` 会应用 `letsencrypt-prod` ClusterIssuer。Terraform 从不创建它。出现此问题时，`make deploy` 还没有运行、你直接运行了 `helm upgrade`，或者 `dns01` 分支因 `langsmith_domain` 为空或 `cert_manager_identity_client_id` output 缺失而跳过了 issuer（两种情况下 `make deploy` 都会打印警告）。

**手动修复：** `ingress_controller = "envoy-gateway"` 时，把此命令中的 `ingress:` solver 替换为紧随其后的 `gatewayHTTPRoute` solver。

```bash
kubectl apply -f - <<EOF
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: you@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
    - http01:
        ingress:
          ingressClassName: nginx   # use "istio" with self-managed istio
EOF

kubectl delete certificate langsmith-tls -n langsmith
```

`ingress_controller = "envoy-gateway"` 的 solver：

```yaml
    solvers:
    - http01:
        gatewayHTTPRoute:
          parentRefs:
          - name: langsmith-gateway
            namespace: langsmith
            kind: Gateway
```

### `langsmith-backend-auth-bootstrap` 卡在 `CreateContainerConfigError`

**原因：** 该 Job 使用 key `initial_org_admin_password` 读取管理员密码。如果 Secret 创建时使用了不同的 key 名（例如 `admin_password`），容器无法启动。

**修复**

```bash
kubectl delete secret langsmith-config-secret -n langsmith
make k8s-secrets   # recreates with correct key names
make deploy
```

### 无法回滚到旧的 chart 版本

**原因：** LangSmith 数据库迁移只向前推进。降级 chart 会让数据库停留在一个旧版应用镜像无法定位的 revision 上。

**修复：** 向前滚动回你使用的版本（或更新版本）。在 `terraform.tfvars` 中设置 `langsmith_helm_chart_version` 并重新部署。在 `v0.17.*` module tag 上，`make deploy` 只接受 chart 0.17 线。已运行 chart 0.17 的部署无法回退到 0.16。`v0.16.*` tag 面向从未离开 0.16 的安装。升级生产环境之前，务必在单独的环境中测试新 chart 版本。

### `make deploy` 失败：`does not resolve to the chart 0.17 line`

**原因：** `CHART_VERSION` 环境变量或 `langsmith_helm_chart_version` 指定了 0.17 线之外的 chart，例如之前部署遗留的 0.16 版本。`v0.17.*` module tag 只部署 chart 0.17。

**修复：** 清除两者以使用最新的 0.17 补丁（`unset CHART_VERSION`），或指定 0.17 补丁版本如 `0.17.0`。要继续留在 chart 0.16，请改用 `v0.16.*` module tag。

### `make init-values` 失败：`enable_sso_oidc = true but the following Key Vault secrets are missing`

**原因：** `enable_sso_oidc = true` 会禁用基本认证，因此 backend 需要 OIDC client ID、client secret 和 issuer URL。至少一个 `langsmith-oauth-*` 机密不在 Key Vault 中。

**修复：** 写入缺失的机密，然后重新创建 Kubernetes secret 并部署：

```bash
./infra/scripts/manage-keyvault.sh set langsmith-oauth-client-id '<client-id>'
./infra/scripts/manage-keyvault.sh set langsmith-oauth-issuer-url '<issuer-url>'
make keyvault   # set langsmith-oauth-client-secret; the prompt hides the value
make k8s-secrets
make init-values
make deploy
```

客户端 secret 通过 `make keyvault` 设置，而不要在命令行上传入，后者会让 secret 显示在进程列表和 shell 历史中。

### Helm 安装超时

**原因：** `langsmith-backend-auth-bootstrap` 在每次 `helm upgrade` 时都运行数据库迁移；首次安装最多需要 5 分钟。如果不带 `--timeout 20m`，即使安装最终成功，Helm 也会报告失败。

**修复：** `make deploy` 已经使用 `--timeout 20m`。手动运行 Helm 时，务必带上 `--timeout 20m`。

## add-on

### Pods 一直停留在 `DEPLOYING`，始终无法达到 `HEALTHY`

**原因：** 启用 TLS 时，`config.deployment.url` 为空或 `config.deployment.tlsEnabled` 为 `false`。operator 会根据这些值构建 agent endpoint URL。

**修复：** `init-values.sh` 在从示例复制后会自动注入 `url` 和 `tlsEnabled`。如果手动部署：

```yaml
config:
  deployment:
    enabled: true
    url: "https://langsmith-demo.eastus.cloudapp.azure.com"   # must include https://
    tlsEnabled: true   # must be true when tls_certificate_source = letsencrypt, dns01, or existing
```

### Insights add-on：`backend-ch-migrations` 处于 `CreateContainerConfigError`

**症状：** 启用 `enable_insights = true` 后多个 pods 失败，报 `CreateContainerConfigError`。日志：`secret "langsmith-clickhouse" not found`。

**原因：** 由旧版 `init-values.sh` 写入的 `langsmith-values-insights.yaml` 设置了 `clickhouse.external.enabled: true` 和 `existingSecretName: langsmith-clickhouse`。这会覆盖 in-cluster ClickHouse 配置，并期待一个不存在的外部 secret。

**修复：** `init-values.sh` 不再把任何 ClickHouse 配置放进 Insights 文件。对于已存在此问题的部署，覆盖该文件并重新部署：

```bash
cat > helm/values/langsmith-values-insights.yaml << 'EOF'
insights:
  enabled: true
EOF
make deploy
```

对于外部 ClickHouse，设置 `clickhouse_source = "external"` 并重新运行 `make init-values`，它会提示输入连接详情并创建 `langsmith-clickhouse` secret。当手工创建的 secret 缺少 key 时也会出现同样的症状。chart 要求全部七个：`clickhouse_host`、`clickhouse_port`、`clickhouse_native_port`、`clickhouse_user`、`clickhouse_password`、`clickhouse_db` 和 `clickhouse_tls`。

### Polly 显示 "Unable to connect to LangGraph server"

**症状：** Polly 聊天组件显示连接错误。浏览器控制台：`POST http://localhost:8123/threads net::ERR_FAILED` 和 CORS 错误。

**原因 A：frontend 在 `langsmith-polly-config` 创建之前就已启动。** 携带 `VITE_POLLY_DEPLOYMENT_URL` 的 ConfigMap 在 Polly 注册之后才写入。来自 ConfigMap 的环境变量在 pod 启动时加载，而不是动态加载。

**修复**

```bash
kubectl rollout restart deployment langsmith-frontend -n langsmith
kubectl exec -n langsmith deploy/langsmith-frontend -- env | grep POLLY
# expect: VITE_POLLY_DEPLOYMENT_URL=https://<hostname>/lgp/smith-polly-<hash>
```

**原因 B：在 `polly.agent.extraEnv` 中设置了 `LANGCHAIN_ENDPOINT`。** `LANGCHAIN_ENDPOINT` 是保留字段。设置它会让注册 Polly 失败，报 `400 Bad Request: 'LANGCHAIN_ENDPOINT' is reserved`。Polly 永远不会被创建。

**修复：** 完全移除 `polly.agent.extraEnv` 区块。operator 会自动注入 `LANGCHAIN_ENDPOINT`。

### 启用 LangSmith Deployment 后 `listener` 和 `operator` pods 始终不出现

**原因：** 设置了 `config.deployment.url` 但省略了 `config.deployment.enabled: true`。当 `enabled` 为 false（默认值）时，chart 会静默跳过创建 `listener` 和 `operator`。

**修复：** 在 `deployment` 区块内添加 `enabled: true`：

```yaml
config:
  deployment:
    enabled: true          # required; url alone is not enough
    url: "https://<your-hostname>"
```

### 重复的顶层 `config:` key 静默丢弃值

**原因：** YAML 不允许重复的顶层 key。第二个 `config:` 区块会静默丢弃其中一个。

**修复：** 始终把新的配置区块添加到现有 `config:` key 内部。可通过 `helm get values langsmith -n langsmith` 验证。

### 加密密钥在首次部署后绝不能更改

在首次使用之后更改 `deployments_encryption_key`、`agent_builder_encryption_key`、`insights_encryption_key` 或 `polly_encryption_key`，会永久损坏它们保护的数据。无法恢复。

- 不要轮换这些 key。
- 不要在 `values-overrides.yaml` 中内联设置 `config.agentBuilder.encryptionKey`、`fleet.encryptionKey`、`insights.encryptionKey` 或 `polly.encryptionKey`。chart 通过 `existingSecretName` 从 `langsmith-config-secret` 读取它们。内联设置会覆盖 secret 引用。

### `fleet-tool-server` 或 `polly` 处于 CrashLoopBackOff

**症状：** Pod 无限重启。没有 traceback。日志反复显示 "Child process died"。

**原因：** 导入时的 settings 校验错误会让 uvicorn worker 以退出码 0 退出，父进程则吞掉了 traceback。常见触发条件：`BASIC_AUTH_ENABLED = true` 但 `BASIC_AUTH_JWT_SECRET` 为空，或 `langsmith-config` 中缺少必需的功能开关 key。

**诊断**方式是在调试 pod 中运行该 server，`envFrom` 指向 `langsmith-config`，并设置 `PYTHONUNBUFFERED=1`。**修复：** 把缺失的 key 加入 Key Vault，重新运行 `make k8s-secrets`，重启 deployment。

## 拆除与清理

### 在 `make destroy` 之前运行 `make clean` 导致基础设施成为孤儿

**症状：** 在 `make clean` 之后运行 `make destroy` 失败，报 `No state file was found!`。Azure 资源仍在运行，但 Terraform 已失去追踪。

**原因：** `make clean` 会删除 `terraform.tfvars`、`secrets.auto.tfvars`，以及本地的 `terraform.tfstate` 及其备份。当 state 仍在跟踪资源时它会发出警告，但在你确认后继续。`make clean-force` 会替你给出该确认。

**正确的拆除顺序**

```txt
1. make uninstall   ← Helm release, then the namespace if you confirm
2. make destroy     ← Azure infra (needs tfstate + tfvars)
3. make clean       ← local secrets and generated files (LAST)
```

`make uninstall` 在删除 namespace 之前会询问，默认答案为 No。回答 `y` 可移除 namespace 及其中遗留的一切。

**tfstate 丢失时的恢复**

```bash
az group delete --name langsmith-rg-<name_prefix> --yes --no-wait
az group show --name langsmith-rg-<name_prefix> 2>&1 | grep -E "provisioningState|ResourceGroupNotFound"
```

设为 `unique_resource_names = true` 时，资源组名为 `ls-rg-<name_prefix>`。设为 `create_resource_group = false` 时不要删除该组，因为 module 并未创建它。

如果之后复用相同的 `name_prefix`，Azure 可能在下一次 `terraform apply` 时恢复 soft-deleted 的 Key Vault。当 `keyvault_purge_protection = false` 时，请先清除它。用 `az keyvault list-deleted -o table` 找到它的名称，然后运行 `az keyvault purge --name <vault> --location <region>`。

### `terraform destroy` 在 VNet/子网删除时卡住

**原因：** ingress controller 的 LoadBalancer service 对应的 Azure Load Balancer（`envoy-gateway` 为 Envoy proxy service，`nginx` 为 `ingress-nginx-controller`）不由 Terraform 追踪。LB 持有子网引用期间，Azure 会阻塞 VNet 删除。

**修复：** 先运行 `make uninstall`。使用 `envoy-gateway` 时，它会删除 Gateway，从而移除 proxy service 及其 LB。使用 `nginx` 时，还要卸载 ingress-nginx。

```bash
make uninstall
helm uninstall ingress-nginx -n ingress-nginx --wait   # only with ingress_controller = "nginx"
kubectl delete namespace langsmith --timeout=60s
make destroy
```

### 升级到 chart 0.16 后遗留孤儿的 `langsmith-agent-bootstrap` Job

**症状：** 从 chart 0.15 升级后，namespace 中仍有一个 Completed 状态的 `langsmith-agent-bootstrap` Job，且 `helm uninstall` 不会移除它。

**原因：** chart 0.16 移除了捆绑的 agent-bootstrap Job，因此 Helm 不再拥有 0.15 release 创建的那个对象。Azure 的 `deploy.sh` 不会删除它。

**修复：** 该 Job 不会阻塞任何操作。删除它以保持 namespace 干净：

```bash
kubectl delete job langsmith-agent-bootstrap -n langsmith --ignore-not-found
```

### `listener` pods 被 OOMKilled

**原因：** `make deploy` 在 add-on overlay 之后加载 sizing 文件，因此它的 listener 限制会覆盖 `langsmith-values-agent-deploys.yaml` overlay。`dev` 和 `production` profile 将 listener 上限设为 `2Gi`，`minimum` 设为 `1536Mi`。持续的 Deployments 负载可能超出该限制。

**修复：** 在 `terraform.tfvars` 中设置 `sizing_profile = "production-large"`，它为 listener 提供 `4Gi`，然后运行 `make init-values` 和 `make deploy`。要留在你的 profile 上，在 `helm/values/langsmith-values-sizing-<profile>.yaml` 中提高 `listener.deployment.resources.limits.memory` 并运行 `make deploy`。`make init-values` 会再次复制 sizing 文件，因此每次运行后都要重复该编辑。

<Note>
chart 读取 `listener.deployment.resources` 作为容器限制，而不是扁平的 `listener.resources`。任何 overlay 文件中的 `listener.resources` 都会被静默忽略。
</Note>

### 过期的 HPA 把 `listener` 或 `host-backend` 扩到最大副本数

**原因：** 先前的 Helm revision 创建了一个 HPA。Helm 不会在 hook 失败时清理它。以 `enabled: false` 重新部署时，过期的 HPA 仍然存在并覆盖 `replicas`。

**修复**

```bash
kubectl delete hpa langsmith-listener langsmith-host-backend -n langsmith 2>/dev/null || true
kubectl scale deployment langsmith-listener -n langsmith --replicas=1
kubectl scale deployment langsmith-host-backend -n langsmith --replicas=1
make deploy
```

## AGIC (Application Gateway Ingress Controller)

### AGIC pod CrashLoopBackOff：AGW GET 返回 403

**症状：** `ingress-appgw-deployment` 处于 CrashLoopBackOff。日志：`ErrorApplicationGatewayForbidden: does not have authorization to perform action Microsoft.Network/applicationGateways/read`。

**原因：** AGIC add-on 的 managed identity（`MC_` 资源组中的 `ingressapplicationgateway-<cluster>`）需要约 5 分钟才能在 Microsoft Entra ID 中完成注册，其角色分配才会生效。

**修复：** `k8s-cluster` module 会在集群创建后等待 300 秒（`time_sleep.agic_identity_propagation`），并自动创建三个必需的角色分配。如果 `make apply` 之后 AGIC 仍然 403：

```bash
az aks update --name <CLUSTER> --resource-group <RG> --yes
kubectl delete pod -n kube-system -l app=ingress-azure
```

手动角色分配（RG 上的 Reader、AGW 上的 Contributor、VNet 上的 Network Contributor）请参见 [TROUBLESHOOTING.md 源文件](https://github.com/langchain-ai/terraform/blob/main/modules/azure/TROUBLESHOOTING.md#agic-pod-crashloopbackoff--403-on-agw-get)。

### AGIC：`ApplicationGatewayInsufficientPermissionOnSubnet`

**原因：** AGIC add-on 身份缺少 VNet 上的 Network Contributor。

**修复**

```bash
AGIC_OID=$(az aks show -g <RG> -n <CLUSTER> \
  --query "addonProfiles.ingressApplicationGateway.identity.objectId" -o tsv)
VNET_ID=$(az network vnet show -g <RG> -n <VNET> --query id -o tsv)

az role assignment create --role "Network Contributor" --scope "$VNET_ID" \
  --assignee-object-id "$AGIC_OID" --assignee-principal-type ServicePrincipal

kubectl rollout restart deployment/ingress-appgw-deployment -n kube-system
```

### AGIC：TLS secret 报 `SecretNotFound`

**原因：** AGIC 在 cert-manager 签发 TLS 证书之前就看到了 Ingress。

**修复：** 触碰 Ingress 以触发重新同步：

```bash
kubectl get certificate langsmith-tls -n langsmith   # verify cert is ready
kubectl annotate ingress langsmith-ingress -n langsmith touch="$(date +%s)" --overwrite
```

### AGIC 拒绝 `ingressClassName: azure/application-gateway`

**原因：** 旧式标注 `kubernetes.io/ingress.class: azure/application-gateway`（带斜杠）不是有效的 `ingressClassName`。AKS 创建的 `IngressClass` 是 `azure-application-gateway`（带连字符）。

**修复：** 使用 `ingressClassName: azure-application-gateway`。`make init-values` 会自动设置。

## Istio（自托管 Helm）

### Istio 站点返回 connection refused / 无路由

**症状：** Connection refused。`pilot-agent request GET config_dump` 显示 `LDS: PUSH resources:0`。

**根本原因（三项都必须修复）：**

1. 未设置 `meshConfig.ingressControllerMode`。默认是 `DEFAULT`，它会忽略 `ingressClassName`。必须设为 `STRICT`。
2. 缺少 `istio` IngressClass 资源。
3. 未把 `meshConfig.ingressClass` 设为 `istio`。

**修复：** 三项都已自动化。`meshConfig` 在 istiod Helm release（Terraform）中设置，`deploy.sh` 创建 IngressClass。手动修复：创建 IngressClass 并重启 istiod。

### Istio HTTPS 返回 "no peer certificate available"

**原因：** istiod 通过 SDS（`kubernetes://langsmith-tls`）读取 TLS secret。该 secret 必须存在于 `istio-system`（gateway pod 的 namespace）中。cert-manager 把它签发到 `langsmith` namespace；它不会被自动复制。

**修复：** `deploy.sh` 会在部署后同步该 secret。手动修复：把 secret 复制到 `istio-system`。

### `istio-addon` 遗留的 CRD 阻塞自托管 Helm 安装

**症状：** `make apply` 失败：`CustomResourceDefinition "wasmplugins.extensions.istio.io" exists and cannot be imported into the current release: invalid ownership metadata`。

**修复**

```bash
kubectl get crd | grep "istio.io" | awk '{print $1}' | xargs kubectl delete crd
make apply
```
