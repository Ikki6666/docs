LangSmith 中的 [Evaluators](/langsmith/evaluation-concepts#evaluators) 是[工作区级别](/langsmith/administration-overview#workspaces)资源。可以将一个 evaluator 附加到多个 [trace containers](/langsmith/observability-concepts#trace-containers) 和[datasets](/langsmith/evaluation-concepts#datasets)上，因此能在整个工作中复用一致的评估逻辑，而不必每次重新创建。

evaluator 附加到什么，取决于工作区的组织方式。

<AgentBasedNote />

evaluator 附加到某个 [agent](/langsmith/agents) 的某个[环境（environment）](/langsmith/agent-environments#environment-names)。只附加到 **Production**，即可仅对生产流量打分，而不对本地 runs 打分。

<ProjectBasedNote />

evaluator 附加到某个 [tracing project](/langsmith/observability-concepts#tracing-projects)。

<Tip>
Evaluator 分数是 [LangSmith Engine](/langsmith/engine) 的高优先级信号：它在选择要分析的内容时会拉取低分 traces，因此把 evaluator 附加到项目上，能让 Engine 在该项目中找到的问题更精准。
</Tip>

## 查看 evaluators

在 [LangSmith UI](https://smith.langchain.com) 中，点击左侧边栏的 **Evaluators**，即可查看工作区中的所有 evaluators。

Evaluators 表格包含以下列：

| Column | Description |
|--------|-------------|
| Name | evaluator 名称 |
| Type | **LLM as a judge** 或 **Code**。Composite score evaluators 仅作用于单个 tracing project 和 dataset，因此不会显示在这里。 |
| Feedback Key | evaluator 产出的 feedback key |
| Projects & Datasets | 该 evaluator 关联的 tracing projects 和 datasets。在基于 agent 的工作区中，该列为 **Environments & Datasets**，列出 agent environments 和 datasets。 |
| Evaluator Trace Count (this week) | 该 evaluator 在过去一周运行过的 traces 数量。仅在启用 spend tracking 时显示；对于 Code evaluators 或没有附加规则的 evaluators 显示为 **–**。 |
| Spend (this week) | 该 evaluator 在过去一周的预估美元花费。仅在启用 spend tracking 时显示；对于 Code evaluators 或没有附加规则的 evaluators 显示为 **–**。 |
| Spend Status | evaluator 当前是 **Under limits**、**Unlimited**，还是已触达一个或多个配置的花费限制。仅在启用 spend tracking 时显示；对于 Code evaluators 显示为 **–**。 |
| Created By | 创建该 evaluator 的工作区成员 |
| Updated At | 上次修改时间 |
| Created At | 创建时间 |

## 创建 evaluator

可以在 [LangSmith UI](https://smith.langchain.com) 中创建 evaluator，也可以通过 [SDK](#使用-sdk-创建-evaluator) 以编程方式创建。无论通过哪种方式创建，evaluator 都是工作区级资源，并会显示在 **Evaluators** 表中。

### 在 UI 中创建 evaluator

1. 在 [LangSmith UI](https://smith.langchain.com) 中，点击左侧边栏的 **Evaluators**。
1. 点击 **+ Evaluator** 打开新 evaluator 面板。
1. 该面板允许你：
   - **Create from scratch**：新建一个 [LLM-as-a-Judge](/langsmith/llm-as-judge)、[Decision Model](/langsmith/decision-model-evaluator) 或 [Code](/langsmith/online-evaluations-code) evaluator。
   - **Add a LangChain Tuned Evaluator**：为一个兼容的 tracing project 关联一个[由 LangChain 管理的专用 judge](/langsmith/tuned-evaluators)，无需配置 prompt、model 或 API key。
   - **Create from a template**：从现成 evaluator（也称 prebuilt evaluator）模板开始，适用于常见评估模式。面板中会先显示一个 **Recommended** 区域，列出热门模板，其余模板按类别分组：Security、Safety、Quality、Conversation、Trajectory、Image Evaluations 和 Voice Evaluation。每个模板的评分内容请参阅 [Prebuilt evaluator 模板](#prebuilt-evaluator-模板)。

也可以直接在 [tracing project](/langsmith/observability-concepts#tracing-projects)、agent environment 或 [dataset](/langsmith/evaluation-concepts#datasets) 中添加 evaluator。在这个流程里，还可以从工作区中**附加一个已有 evaluator**，或者创建一个 [Composite](/langsmith/composite-evaluators-ui) evaluator。可参阅[设置 LLM-as-a-judge 在线 evaluators](/langsmith/online-evaluations-llm-as-judge)和[在实验上自动运行 evaluators](/langsmith/bind-evaluator-to-dataset)。

### 使用 SDK 创建 evaluator

可以使用 LangSmith SDK 以编程方式创建 evaluator。SDK 提供 [Python](/langsmith/smith-python-sdk) 和 [TypeScript](/langsmith/smith-js-ts-sdk) 版本。通过 SDK 创建的 evaluator 也会与通过 UI 创建的 evaluator 一样，显示在 **Evaluators** 表中。

SDK 暂不支持 [decision model evaluators](/langsmith/decision-model-evaluator)。要创建一个，请使用 UI。

<Note>
通过 SDK 管理 evaluators 需要 `langsmith>=0.9.8`（Python，PyPI）或 `langsmith>=0.7.16`（TypeScript，npm）。
</Note>

<CodeGroup>
```python Python
import asyncio

from langsmith import Client


async def main():
    client = Client()

    created = await client.evaluators.create(
        name="Correctness evaluator",
        type="code",
        code_evaluator={
            "code": "def perform_eval(run, example):\n    return {'score': 1}",
            "language": "python",
        },
    )
    print("Created evaluator:", created.evaluator.id)


asyncio.run(main())
```
```typescript TypeScript
import { Client } from "langsmith";

const client = new Client();

const created = await client.evaluators.create({
  name: "Correctness evaluator",
  type: "code",
  code_evaluator: {
    code: "def perform_eval(run, example):\n    return {'score': 1}",
    language: "python",
  },
});
console.log("Created evaluator:", created.evaluator?.id);
```
</CodeGroup>

若要创建 LLM-as-a-judge evaluator，以及检索、更新、列出或删除 evaluator，请参阅[使用 SDK 管理 evaluators](/langsmith/manage-evaluators-sdk)。

## Prebuilt evaluator 模板

Prebuilt evaluator 模板是面向常见检查（例如幻觉、prompt 注入和任务完成度）的现成 evaluators。每个模板都是一个起点，你可以在将它保存到工作区之前编辑它的 prompt 和评分 schema。

大多数模板是 [LLM-as-a-judge](/langsmith/llm-as-judge) evaluators，其 prompt 来自开源的 [openevals](https://github.com/langchain-ai/openevals) 包。有两个例外：Assertions 使用在 LangSmith 中定义的 prompt，Exact Match 则是一个 [code evaluator](/langsmith/online-evaluations-code)。

每个 LLM-as-a-judge 模板都会在其 feedback key 下写入一个分数，并附带一个包含 judge 推理过程的 `comment`。Language 和 Support Intent 只返回标签，不返回 `comment`。

`true` 分数并不总是表示通过。用于检测问题的模板在发现问题时返回 `true`：Security 和 Safety 模板、Hallucination、Perceived Error、Image 模板以及 Audio Quality。其余模板在输出通过时返回 `true`。各表格中的 **Score** 列说明了 `true` 的含义。

模板读取的数据各不相同：

- **整个线程**：Conversation 和 Trajectory 模板会读取线程中的每条消息。当你把这类模板添加到 tracing project 时，LangSmith 会将它配置为 thread-level evaluator。更多信息请参阅[设置多轮在线 evaluators](/langsmith/online-evaluations-multi-turn)。
- **参考输出**：Correctness、Assertions 和 Exact Match 会将输出与参考输出进行比较，参考输出来自 [dataset](/langsmith/evaluation-concepts#datasets) 示例。
- **计划**：Plan Adherence 除了线程消息之外，还会读取一个 `plan` 变量。
- **附件**：Image 和 Voice 模板会读取 run 的附件。更多信息请参阅[使用附件进行评估](/langsmith/evaluate-with-attachments)。

### Security

Security 模板检测泄露、注入和对抗性输入。

| Template | What it scores | Score |
|----------|----------------|-------|
| PII Leakage | 输入或输出中是否包含可能识别或伤害个人的信息。 | `pii_leakage`（boolean）：发现 PII 时为 `true`。 |
| Prompt Injection | 输入中是否包含针对 AI 系统的嵌入式指令。仅读取输入。 | `prompt_injection`（boolean）：发现注入尝试时为 `true`。 |
| Code Injection | 输入中是否包含嵌入在数据中的可执行代码。仅读取输入。 | `code_injection`（boolean）：发现注入尝试时为 `true`。 |

### Safety

Safety 模板评估内容安全和审核表现。

| Template | What it scores | Score |
|----------|----------------|-------|
| Toxicity | 内容中是否包含有毒元素，例如人身攻击或仇恨言论。 | `toxicity`（boolean）：发现有毒内容时为 `true`。 |
| Bias & Fairness | 内容中是否包含刻板印象、排他性语言或歧视性表述。 | `fairness`（boolean）：发现偏见或公平性违规时为 `true`。 |

### Quality

Quality 模板衡量输出质量和准确性。

| Template | What it scores | Score |
|----------|----------------|-------|
| Hallucination | 输出中是否包含输入上下文不支持的断言，例如矛盾、臆测细节或不准确的事实。 | `hallucination`（boolean）：输出包含幻觉时为 `true`。 |
| Correctness | 输出是否事实准确、完整，并与参考输出一致。 | `correctness`（boolean）：输出正确时为 `true`。 |
| Assertions | 输出是否满足参考输出中的每条断言。judge 会从参考输出中读取一个 `assertions` 列表，其中每个条目包含一个 `key` 和一个 `comment`。列表缺失或为空时得分为 `false`。 | `assertions_passed`（boolean）：仅当每条断言都通过时为 `true`。 |
| Conciseness | 输出传达所请求信息的效率如何，对含糊其辞、客套话、元评论和冗余加以惩罚。 | `conciseness`（数字，0 到 10）：输出仅包含必要信息时为 `10`。 |
| Code Checker | 代码是否解决了输入中的每项要求、处理了边界情况，并且能够不出错地运行。 | `code_checker`（boolean）：代码完整且正确时为 `true`。 |
| Answer Relevance | 输出是否直接回应了输入问题，没有离题内容。 | `answer_relevance`（boolean）：输出相关时为 `true`。 |
| Exact Match | run 的输出是否与参考输出完全一致。该模板以代码方式运行，不发起 LLM 调用。 | `exact_match`（boolean）：输出一致时为 `true`。 |

### Conversation

Conversation 模板评估整个线程的对话质量和用户体验。

| Template | What it scores | Score |
|----------|----------------|-------|
| Perceived Error | 用户信号（例如沮丧情绪或反复纠正）是否表明用户认为 agent 犯了错误。 | `perceived_error`（boolean）：用户感知到造成明显沮丧的错误时为 `true`。 |
| Language | 对话的主要语言。 | `language`（字符串）：英文语言名称，例如 `Spanish`。 |
| Support Intent | 客服对话的主要意图。 | `intent`（类别）：`Account & Billing`、`Order Management`、`Technical Support`、`Product Inquiry`、`Policy Inquiry`、`Status Check`、`Complaint & Feedback`、`Escalation` 或 `Other` 之一。 |
| User Satisfaction | 用户的语气和满意度指标是否表明用户感到满意。 | `user_satisfaction`（boolean）：用户看起来满意时为 `true`。 |
| Tone | agent 的语气是否适合上下文且前后一致。 | `agent_tone`（boolean）：语气得当时为 `true`。 |
| Task Completion | agent 是否完成了对话中的每一项用户请求。 | `task_completion`（boolean）：每项请求都完成时为 `true`。 |
| Knowledge Retention | agent 是否记住并运用了对话前文中的事实，没有矛盾或忽略上下文。 | `knowledge_retention`（boolean）：agent 记住了先前的可信事实时为 `true`。 |

### Trajectory

Trajectory 模板评估整个线程中 agent 的工具使用和决策路径。

| Template | What it scores | Score |
|----------|----------------|-------|
| Plan Adherence | agent 的步骤是否遵循了它声明的计划。 | `plan_adherence`（boolean）：agent 遵循了计划时为 `true`。 |
| Tool Selection | agent 是否以合理的顺序选择了正确的工具，没有不必要的调用。 | `tool_selection`（boolean）：工具选择准确且高效时为 `true`。 |
| Trajectory Accuracy | agent 的路径是否合乎逻辑、进展清晰且效率合理。 | `trajectory_accuracy`（boolean）：轨迹准确且高效时为 `true`。 |

### Image Evaluations

Image 模板评估图像内容质量与安全性。

| Template | What it scores | Score |
|----------|----------------|-------|
| Explicit Content | 图像中是否包含裸露、色情内容或血腥暴力。 | `explicit_content`（boolean）：发现露骨内容时为 `true`。 |
| Sensitive Imagery | 图像中是否包含有害、冒犯性或不当的符号或描绘。 | `sensitive_imagery`（boolean）：发现敏感图像时为 `true`。 |

### Voice Evaluation

Voice 模板评估语音和音频交互质量。

| Template | What it scores | Score |
|----------|----------------|-------|
| Audio Quality | 音频中是否包含削波、失真或毛刺等有损收听体验的问题。 | `audio_quality`（boolean）：发现质量问题时为 `true`。 |
| Transcription Accuracy | 语音转文字的转录是否准确反映了所说的内容。 | `transcription_accuracy`（boolean）：转录准确时为 `true`。 |
| User Interrupts | agent 是否妥善处理了用户的打断。 | `user_interrupts`（boolean）：打断得到优雅处理时为 `true`。 |
| Vocal Affect | agent 的声音温度、韵律和情感语气是否恰当自然。 | `vocal_affect`（boolean）：声音表现恰当时为 `true`。 |

## 查看 evaluator 详情

点击表格中的任意 evaluator，即可打开详情视图。详情视图包含四个标签页：

- **Overview**：evaluator 的反馈配置，以及 prompt 或代码定义。
- **Traces**：该 evaluator 在所有已附加资源上处理过的 traces。
- **Logs**：该 evaluator 在所有已附加资源上的执行日志。
- **Projects & Datasets**（在基于 agent 的工作区中为 **Environments & Datasets**）：该 evaluator 当前附加到的 tracing projects、agent environments 和 datasets，以及每个附加项对应的[每周支出与限制](/langsmith/evaluator-spend)。

## 编辑 evaluator

打开某个 evaluator。在 **Overview** 标签页中，点击 **Edit evaluator** <Icon icon="pencil"/> 图标，打开 **Configure Evaluator** 面板。更新 evaluator 配置后，点击 **Save**。

由于 evaluator 是共享资源，修改会应用到它附加的所有 trace containers 和 datasets。

## 管理 evaluator trace retention

当在线 evaluator 为某条 trace 打分时，它会将 feedback 附加到该 trace 上，这会[自动将 trace 升级为 extended retention](/langsmith/usage-and-billing#data-retention-auto-upgrades)。Extended retention 会让 trace 保留更久，但成本也更高。为 [tracing project](/langsmith/observability-concepts#tracing-projects) 或 agent environment 设置在线 evaluator 时，可以选择退出这个升级，使已评分 traces 继续保持项目的基础保留策略。

只有当项目的[默认保留策略](/langsmith/billing#change-project-level-default-retention)是[base tier](/langsmith/usage-and-billing#how-it-works)时，这个控制项才可用。如果项目默认就是 extended retention（[可在项目级或工作区级设置](/langsmith/data-purging-compliance#data-retention)），那么 evaluator 打分后的 traces 会沿用该默认值，并且这个选项会被锁定。

若要关闭已评分 traces 的 retention 延长：

1. 在[创建](#create-an-evaluator)或[编辑](#edit-an-evaluator)在线 evaluator 时，将 source 设为一个 [tracing project](/langsmith/observability-concepts#tracing-projects) 或 agent environment，而不是 [dataset](/langsmith/evaluation-concepts#datasets)。
1. 展开 evaluator 配置面板中的 **Advanced** 区域。
1. 取消选中 **Extend trace retention**。

这一变更只会影响保存之后被该 evaluator 打分的新 traces。已有已评分 traces 会保留当前的 retention tier。

## 纳入扩展统计信息

在 [run-level evaluator](/langsmith/online-evaluations-llm-as-judge) 中使用 **Include extended stats (feedback, costs, tokens)**，可以评估来自该 run 的 feedback 统计信息、token 用量或成本数据。`feedback_stats` 字段包含 feedback 统计信息，包括每个 feedback key 的数量和平均值。此选项不适用于[multi-turn（thread-level）evaluator](/langsmith/online-evaluations-multi-turn)。

LangSmith 会为启用了此选项的 evaluator 额外拉取数据。仅当你的评估逻辑或 prompt 需要这些字段时才启用它。

要纳入扩展统计信息：

1. 在[创建](#create-an-evaluator)或[编辑](#edit-an-evaluator) run-level evaluator 时，展开 evaluator 配置面板中的 **Advanced** 区域。
1. 选中 **Include extended stats (feedback, costs, tokens)**。

### 访问扩展统计信息

[Code evaluators](/langsmith/online-evaluations-code) 会在 `run` 对象中接收到这些字段，包括 `feedback_stats`、`total_tokens` 和 `total_cost`。无论是否启用扩展统计信息，它们都会在 `run["feedback"]` 中收到[单条 feedback 记录](/langsmith/feedback-data-format)。对于 [LLM-as-a-judge evaluator](/langsmith/online-evaluations-llm-as-judge)，请将对应的 `run.*` 字段映射到某个 prompt 变量。例如，把 `{{correctness_average}}` 映射到 `run.feedback_stats.correctness.avg`，即可在 prompt 中纳入 `correctness` feedback 的平均值。可用的 `run.*` 字段还包括 prompt 和 completion 的 token、成本以及 detail 字段。完整的 run 数据 schema 请参阅 [Run data format](/langsmith/run-data-format)。

## 链式 evaluator

链式 evaluator 是一种在线 evaluator，只会在已被其他 evaluator 打过分的 run 上触发。通过链式，你可以使用更有针对性的 evaluator，或者把更昂贵的 evaluator 留给真正需要它的 run。例如，你可以让某个 [LLM-as-a-judge evaluator](/langsmith/online-evaluations-llm-as-judge) 只在先前的 `correctness` 分数低于某个阈值时才运行。

第二个 evaluator 必须是 run-level evaluator，因为 [multi-turn（thread-level）evaluator](/langsmith/online-evaluations-multi-turn) 无法按 feedback 过滤。第一个 evaluator 可以是任意一种类型。multi-turn evaluator 会把它的 feedback 附加到线程中的最后一个 run 上，因此链在其后的第二个 evaluator 评估的是该 run，而不是整个线程。

要将第二个 evaluator 链式接到第一个 evaluator 之后：

1. 创建或打开第二个 evaluator，并展开它的过滤器。更多信息请参阅 LLM-as-a-judge evaluator 的[为触发 evaluator 的 run 应用过滤器](/langsmith/online-evaluations-llm-as-judge#apply-a-filter-to-runs-that-trigger-the-evaluator)，或 code evaluator 的[创建过滤器](/langsmith/online-evaluations-code#3-create-a-filter)。
1. 按第一个 evaluator 的 feedback key 进行过滤。过滤器匹配的是 key，而非产生它的 evaluator，因此任何来源只要使用了该 key，其 feedback 都会触发第二个 evaluator，[用户 feedback](/langsmith/attach-user-feedback) 也不例外。请使用只有第一个 evaluator 会产生的 key。
   - 要在第一个 evaluator 打过分的每个 run 上都触发，只按 key 过滤即可：

     ```text
     eq(feedback_key, "correctness")
     ```

   - 要只在分数满足某个条件时触发，请将 key 与 `feedback_score` 的比较组合使用。例如，要只在 `correctness` 低于 `0.5` 时触发：

     ```text
     and(eq(feedback_key, "correctness"), lt(feedback_score, 0.5))
     ```

1. 如果第二个 evaluator 会读取第一个分数，请[纳入扩展统计信息](#include-extended-stats)。LLM-as-a-judge evaluator 必须启用它，code evaluator 则可借助它可靠地读取分数。更多信息请参阅[读取第一个分数](#read-the-first-score)。
1. 保存该 evaluator。

只有当第一个 evaluator 的分数已附加到某个 run 之后，第二个 evaluator 才会处理该 run，因此两个 evaluator 的运行先后顺序无关紧要。完整的过滤器语法请参阅 [Trace query syntax](/langsmith/trace-query-syntax)。

### 读取第一个分数

第二个 evaluator 如何读取第一个 evaluator 的分数，取决于它的类型：

- **LLM-as-a-judge evaluator**：[纳入扩展统计信息](#include-extended-stats)，然后将某个 prompt 变量映射到 `run.feedback_stats.<feedback_key>.avg`。例如，把 `{{correctness_average}}` 映射到 `run.feedback_stats.correctness.avg`。
- **Code evaluator**：在 `run["feedback"]` 中读取 `key` 为第一个 evaluator 的 feedback key 的那条 [feedback 记录](/langsmith/feedback-data-format)，并使用它的 `score`。`run["feedback"]` 在该 evaluator 处理的每批 run 中最多保留 100 条 feedback 记录，最早的记录会最先被丢弃，因此当一批 run 携带大量 feedback 记录时，该分数可能缺失。要可靠地读取分数，请纳入扩展统计信息，并从 `run["feedback_stats"]["<feedback_key>"]["avg"]` 读取平均值。

`avg` 字段对该 run 上使用该 key 的所有 feedback 记录取平均，因此只有当 run 上只有一条使用该 key 的记录时，它才等于第一个 evaluator 的分数。另一条使用相同 key 的记录（例如用户 feedback）会改变平均值。

## 删除 evaluator

当 evaluator 仍附加在某个 trace container 或 dataset 上时，无法删除。要删除 evaluator：

1. 在 [LangSmith UI](https://smith.langchain.com) 中，点击左侧边栏的 **Evaluators**。
1. 选择你要删除的 evaluator。
1. 打开 **Projects & Datasets** 标签页（在基于 agent 的工作区中为 **Environments & Datasets**）。对于其中列出的每个附加项，在该行右侧的 **Actions** 菜单中选择 **Detach**。
1. 返回 **Evaluators** 页面，点击页面顶部的 **Delete**。
