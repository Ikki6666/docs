<Info>
自托管版 Engine 需要 LangSmith Helm chart `0.16.0` 或更高版本，并且需要包含 Engine 授权的 license。在更早的 chart 版本上不可用。[联系销售团队](https://www.langchain.com/contact-sales)，将该授权添加到你的订单中。
</Info>

LangSmith Engine 是 LangSmith 内的一个 agent，它会监控你的生产 traces，将它们聚类成 issues，结合你的源代码诊断每个问题，提出一个修复 PR，并识别应添加到 datasets 中的 ground truth evals。关于产品概览，请参阅 [Engine](/langsmith/engine-overview)。

在自托管 LangSmith 中，Engine 的编排逻辑（包括其 detect、fix 和 verify 循环）作为 LangSmith 的一部分运行在你的 VPC 内。模型工作无法完全运行在你的 VPC 中：Engine 会将其所需的内容发送到 LangSmith Intelligence（LSI），一个由 LangChain 托管的零数据保留（ZDR）服务。

本页涵盖两部分内容：Engine 在你的环境之外依赖什么，以及如何在你的实例上[安装 Engine](#install-engine)。若要将其连接到你的源代码，请按[将 Engine 连接到 GitHub](/langsmith/engine-github) 中的说明创建并配置你自己的 GitHub App。

Engine 会处理三类数据：

- **Code**（可选）**：**你的 agent 源代码，Engine 会读取它来诊断问题并提出修复方案。
- **Traces：**来自 agents 的运行时数据，其中可能包含用户消息、工具输出和 PII。
- **Model：**Engine 为执行诊断、生成修复方案和编写 evaluators 而发起的 LLM 调用。

## 按云和区域的可用性

Engine 在 LSI 可用的地方提供：

| 云 | 区域 | 状态 |
| --- | --- | --- |
| AWS | US | 可用 |
| GCP | US | 可用 |

关于其他区域的可用性，请[联系销售团队](https://www.langchain.com/contact-sales)。

## 工作原理

LSI 是为 Engine 提供支持的 LangChain 托管服务。

流程如下：

- 你的自托管 Engine 向其所在云的 LSI gateway 发送 HTTPS 请求，本页后续的各云小节中列出了这些 gateway。
- Engine 使用在 LangSmith license 校验期间获得的短期 license JWT 进行认证。你无需提供单独的模型提供商凭据。
- LSI 校验该 JWT，并通过 LangChain 环境内部的私有网络将请求路由到模型提供商。
- LSI 将响应返回给你的自托管 Engine。

每次请求都会携带 Engine 工作所需的 trace 内容、代码和中间输出。LSI 和模型提供商会处理这些内容以服务该请求。

你的集群必须允许到该 gateway 的出站 HTTPS。该连接可以使用公共 egress 或私有连接。在 AWS 上，请按照[通过 AWS PrivateLink 连接](#connect-with-aws-privatelink)将 Engine 流量保持在私有网络上。

如果到 LSI 的连接不可用，Engine 会停止并返回错误，而不是降级到较低质量的输出。集群内没有模型，也没有备用提供商可以回退。你的 LangSmith 部署的其余部分不受影响，Engine 会在下一次计划扫描时重试。

## LangSmith Intelligence 保留了什么

LSI 不会持久化 prompt 或模型响应的内容。它会保留以下用于使用量归因和计费的元数据：

- 用于归因使用量的 Account、workspace 和 project 标识符。
- 用于计费的模型和 token 使用量元数据。

关于模型提供商的保留和训练承诺，请参阅 [Engine security](/langsmith/engine-security)。

## 按云连接

### AWS（美国可用）

gateway 主机为 [`beacon.aws.langchain.com`](#allow-egress-to-langsmith-intelligence)。LSI 会将请求路由到 LangChain AWS 环境中的 AWS Bedrock。

#### 通过 AWS PrivateLink 连接

在配置 PrivateLink 之前，请先完成[安装 Engine](#install-engine)，包括其 Helm 和 egress 配置。

[AWS PrivateLink](https://docs.aws.amazon.com/vpc/latest/privatelink/) 会将 Engine 流量从你的 VPC 路由到 LSI，而不会将该流量暴露到公共互联网。LSI endpoint service 托管在 `us-east-2` 中，AWS 支持从其他区域的 VPC 访问。

在开始之前，请收集你的 AWS 账户 ID、VPC ID、私有子网 ID，以及用于 interface endpoint 的安全组。将该 endpoint 安全组配置为仅允许来自运行 Engine 的节点或工作负载所关联安全组的入站 TCP 443 端口流量，或来自包含它们的最小私有 CIDR。不要允许 `0.0.0.0/0`。

要将你的 VPC 连接到 LSI：

<Steps>
  <Step title="申请访问">
    联系你的客户代表或 [sales@langchain.dev](mailto:sales@langchain.dev) 并提供你的 AWS 账户 ID。LangChain 会将你的账户添加到 endpoint service 的 allowed principals 列表中。
  </Step>

  <Step title="创建 interface VPC endpoint">
    为包含你的 VPC 的区域配置 AWS provider。请将 `service_region` 保持为 `us-east-2`，即使你的 VPC 位于其他区域。每个可用区选择一个私有子网。

    <Note>
    `service_region` 参数需要 HashiCorp AWS provider `5.82.0` 或更高版本。
    </Note>

    ```hcl
    resource "aws_vpc_endpoint" "langsmith_intelligence" {
      vpc_id              = var.vpc_id
      service_name        = "com.amazonaws.vpce.us-east-2.vpce-svc-054f37092752bff6b"
      service_region      = "us-east-2"
      vpc_endpoint_type   = "Interface"
      subnet_ids          = var.private_subnet_ids
      security_group_ids  = [var.security_group_id]
      private_dns_enabled = false
    }
    ```
  </Step>

  <Step title="等待 LangChain 接受连接">
    在 LangChain 接受连接之后，endpoint 状态会从 `pendingAcceptance` 变为 `available`。请等待几分钟让更改传播，然后再测试连通性。
  </Step>

  <Step title="将 LSI 主机名路由到该 endpoint">
    为你的 VPC 启用 DNS resolution 和 DNS hostnames。然后创建一个 Route 53 私有托管区和别名记录，使 `beacon.aws.langchain.com` 在你的 VPC 内解析到该 VPC endpoint。保持此主机名不变，以便 TLS 证书校验成功。该私有托管区还可以防止在 endpoint 不可用时回退到公共 DNS。

    ```hcl
    resource "aws_route53_zone" "langsmith_intelligence" {
      name = "beacon.aws.langchain.com"

      vpc {
        vpc_id = var.vpc_id
      }
    }

    resource "aws_route53_record" "langsmith_intelligence" {
      zone_id = aws_route53_zone.langsmith_intelligence.zone_id
      name    = "beacon.aws.langchain.com"
      type    = "A"

      alias {
        name                   = aws_vpc_endpoint.langsmith_intelligence.dns_entry[0].dns_name
        zone_id                = aws_vpc_endpoint.langsmith_intelligence.dns_entry[0].hosted_zone_id
        evaluate_target_health = true
      }
    }
    ```

    如果工作负载使用企业 DNS 解析器而不是 Amazon 提供的解析器，请配置到 Route 53 Resolver 的条件转发，或为 `beacon.aws.langchain.com` 创建等效的私有 DNS 覆盖，指向该 endpoint 的 DNS 名称。
  </Step>

  <Step title="验证私有连接">
    从运行 Engine 的节点或容器中解析 gateway 主机名：

    ```bash
    getent ahostsv4 beacon.aws.langchain.com
    ```

    确认结果中包含分配给该 endpoint 网络接口的私有 IP 地址。然后启动一次分析，并确认它能成功完成。如果分析未能完成，请检查 Engine 安装和 egress 配置。
  </Step>
</Steps>

## 模型选择与质量

Engine 会为不同角色使用不同模型，分别用于聚类 issues、结合代码诊断根因、生成修复方案，以及编写用于验证修复的 evaluator。LangChain 会针对质量和 token 效率调优这些模型，并随着更优秀模型的推出进行更新。

Engine 使用托管推理，而不是自带 key（bring-your-own-key）的方式。这使 Engine 的行为保持一致，并随着 LangChain 更新模型而持续改进。如果采用自带 key 的方式，模型选择、调优和 token 效率可能会因请求不同而波动。

## Engine 在哪里处理数据

在自托管部署中，Engine 将数据处理分为你的环境和 LangChain 的环境两部分：

- **你的环境：**Engine 编排逻辑和 LangSmith 存储的 traces 保留在你的自托管环境中。
- **LangChain 的环境：**Engine 发送的内容由 LSI 和模型提供商处理。LSI 会保留上文所述的计费元数据。

Engine 与部署无关的数据处理方式——包括与每家模型服务商之间的零数据保留，以及不会使用客户数据来训练或微调模型——已在 [Engine security](/langsmith/engine-security) 中说明。

## 安装 Engine

Engine 默认处于禁用状态。它需要 [Sandboxes](/langsmith/deploy-self-hosted-full-platform#enable-sandboxes)、与 [LangSmith Intelligence](#allow-egress-to-langsmith-intelligence) 的连接、一个可从外部访问的 [`config.hostname`](#verify-your-hostname-is-externally-reachable)，以及一个 [Engine 加密 key](#generate-the-engine-encryption-key)。在启用 Engine 之前，请先完成这些前置条件。

Engine 和 [Insights](/langsmith/deploy-self-hosted-full-platform#enable-fleet-insights-and-chat) 使用同一镜像并共享同一个 deployment。Engine 不需要 Insights。如果你的安装已经在运行 Insights，启用 Engine 只是增加配置，不会新增 pods。

### 组件

启用 Engine 会创建或复用：

- `standalone-insights-api-server`：同时服务 `engine` 和 `insights` 两个 graph。
- `standalone-insights-queue`：Engine 和 Insights 的后台 run 处理。
- 一个专用于该共享 deployment 的 PostgreSQL 和 Redis 实例，两者都可以替换为外部实例。
- [启用 Sandboxes](/langsmith/deploy-self-hosted-full-platform#enable-sandboxes) 中描述的 sandbox 组件。

Engine 还会在 `platform-backend` 和 `ingest-queue` 中添加配置，由它们负责调度 Engine 的 runs。

### 前置条件

<Steps>
  <Step title="启用 Sandboxes">
    首先完成[启用 Sandboxes](/langsmith/deploy-self-hosted-full-platform#enable-sandboxes)，包括支持 KVM 的 node pool 和 JuiceFS 存储。

    Engine 的 sandboxes 关联到单个 workspace。带 Engine 的安装必须有一个[共享组织](/langsmith/administration-overview#organizations)。如果共享组织只有一个 workspace，LangSmith 会使用该 workspace。如果共享组织有多个 workspace，LangSmith 不会自动选择，你必须将 `engine.sandboxTenantId` 设置为对应的 workspace ID。

    <Warning>
    请使用一个专供 Engine 使用的 workspace：

    - Engine 的 sandboxes 不在 Sandboxes 产品上计费，因为 Engine 以 LCU 为单位计量自己的用量。
    - Engine 的 sandboxes 与该 workspace 中的其他 sandboxes 共用相同的并发 sandbox、CPU 和内存配额。如果 workspace 接近上限，Engine 运行可能失败，或减少交互式 sandboxes 可用的容量。
    - Engine 的 sandboxes 会列在该 workspace 中，任何有访问权限的人都可以停止它们。
    - 每个 sandbox 都会运行 agent 生成的代码。
    - 仓库凭据保存在 sandbox auth proxy 中，sandbox 内部运行的代码无法访问。
    </Warning>
  </Step>

  <Step title="确认 license 授权">
    Engine 与 Sandboxes 一样单独授权。你的 license 必须包含 Engine 授权。LangSmith 会在启动时和之后定期向 `https://beacon.langchain.com` 校验你的 license key，因此只要该授权被加入你的订单，无需更改任何配置即可生效。
  </Step>

  <Step title="允许到 LangSmith Intelligence 的 egress" id="allow-egress-to-langsmith-intelligence">
    允许集群向你所在云对应的 LangSmith Intelligence gateway URL 发起出站 HTTPS 连接，并把这个 URL 作为 `engine.intelligenceBaseUrl` 的值。

    | 云 | `engine.intelligenceBaseUrl` |
    | --- | --- |
    | AWS | `https://beacon.aws.langchain.com/intelligence` |
    | GCP | `https://beacon.langchain.com/intelligence` |

    在 GCP 上，这里使用的是 LangSmith 已经用于 license 校验和计费遥测的同一主机，因此 Engine 只是新增一条路径，而不是一个新的 egress 目标。

    <Note>
    自托管部署仅支持 **AWS US** 和 **GCP US** 区域。在规划上线前，请查看[云和区域的可用性](#availability-by-cloud-and-region)，并与[我们的销售团队](https://www.langchain.com/contact-sales)确认覆盖情况。
    </Note>

    请把 gateway 作为单独的 allowlist 条目添加，而不要开放一般性 egress。要让 AWS 流量走私有网络，请参阅[通过 AWS PrivateLink 连接 LangSmith Intelligence](#connect-with-aws-privatelink)。请求使用在 LangSmith license 校验期间获得的短期 license JWT。即使共享主机，Engine 的流量也与[配置 egress](/langsmith/self-host-egress) 中描述的计费与运维遥测相互独立。

    <Note>
    离线（air-gapped）安装无法运行 Engine。集群内没有任何可以回退的模型。
    </Note>
  </Step>

  <Step title="确认主机名可从外部访问" id="verify-your-hostname-is-externally-reachable">
    Engine 的 sandboxes 会使用 `langsmith` CLI 调用你的 LangSmith 安装，因此 `config.hostname` 必须能从 sandbox 网络访问。Helm 校验会拒绝 `localhost` 和集群内的 `*.svc` 地址。

    如[设置 ingress](/langsmith/self-host-ingress) 中所述，通过 ingress 以 TLS 方式提供该主机名。Engine 不要求你暴露超出自己用户已可访问地址之外的任何内容。Sandbox egress 只允许访问你的 LangSmith 主机名、`github.com`、`api.github.com` 和 Python 包仓库。每次运行的凭据由 sandbox 之外的 proxy 注入，而不是在 sandbox 内部可读。
  </Step>

  <Step title="生成 Engine 加密 key" id="generate-the-engine-encryption-key">
    Engine 使用自己的 Fernet key 加密 LangSmith 传给它的 run 载荷，这些载荷携带短期凭据。生成方式：

    ```bash
    python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
    ```

    请把它以 `engine_encryption_key` 的形式存入你预定义的 Kubernetes Secret，而不是写在配置文件里。参见[使用已有 secret](/langsmith/self-host-using-an-existing-secret#parameters)。

    日后轮换 key 时，请把当前值复制到 `engine_encryption_key_previous`，并把新 key 设为 `engine_encryption_key`。旧 key 只用于解密，因此在切换前一刻加密的 runs 仍能正常完成。
  </Step>
</Steps>

### 通过 Helm 启用

将以下内容添加到你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中，与[启用 Sandboxes](/langsmith/deploy-self-hosted-full-platform#enable-sandboxes) 给出的完整 Sandboxes 值放在一起。以下示例只展示 Engine 相关的值和 `sandboxes.enabled` 开关。

<Tabs>
  <Tab title="使用 Kubernetes secrets（推荐）">
    按名称引用你已有的 Secret，chart 会自动从中读取 `engine_encryption_key`。

    ```yaml
    config:
      existingSecretName: "<your-secret-name>"
      # 必须能从 sandbox 网络访问。
      hostname: "https://langsmith.example.com"

    engine:
      enabled: true
      intelligenceBaseUrl: "https://beacon.aws.langchain.com/intelligence"

    sandboxes:
      enabled: true
    ```
  </Tab>
  <Tab title="使用内联值">
    直接在配置文件中设置加密 key。

    <Warning>
    这会把一份有效凭据写进配置文件。不要将它提交到版本控制，优先使用 Kubernetes Secret。
    </Warning>

    ```yaml
    config:
      hostname: "https://langsmith.example.com"

    engine:
      enabled: true
      intelligenceBaseUrl: "https://beacon.aws.langchain.com/intelligence"
      encryptionKey: "<engine-encryption-key>"

    sandboxes:
      enabled: true
    ```
  </Tab>
</Tabs>

<Note>
如果你的安装具有含多个 workspace 的共享组织，请设置掌管 Engine sandboxes 的 workspace：
</Note>

```yaml
engine:
  sandboxTenantId: "<workspace-id>"
```

<Warning>
从较旧的 Insights 镜像固定版本升级时需要额外检查一项：如果你的配置把 `images.engineInsightsAgentImage.repository` 固定到了已弃用的 `langsmith-clio` 镜像，请移除或更新该固定项。Engine 和 Insights 现在运行在 `langsmith-insights-engine` 上，chart 会拒绝 `langsmith-clio`。更多信息见[为你的 LangSmith 安装做镜像](/langsmith/self-host-mirroring-images#additional-images-for-engine)。
</Warning>

应用之前，先校验更新后的 chart：

```bash
helm template langsmith langchain/langsmith \
  --values langsmith_config.yaml \
  --version <version> \
  --namespace <namespace>
```

chart 会在渲染时校验 Engine 配置，缺失某个值时会报错并指明该值，因此这条命令能在配置进入集群之前发现配置错误。

应用更新后的 chart：

```bash
helm upgrade -i langsmith langchain/langsmith \
  --values langsmith_config.yaml \
  --version <version> \
  --namespace <namespace> \
  --wait
```

### 验证安装

确认共享的 Engine 和 Insights deployment 正在运行：

```bash
kubectl get pods -n <namespace> | grep standalone-insights
```

API server 和 queue pods 都应处于 `Running` 状态。然后确认 `platform-backend` 是健康的，因为它负责调度 Engine 的 runs：

```bash
kubectl rollout status deployment/langsmith-platform-backend -n <namespace>
```

如果在这之后 Engine 没有出现在 LangSmith UI 中，最常见的原因是 license 中没有 Engine 授权，以及[在 LangSmith 中开启 Engine](#turn-on-engine-in-langsmith) 中描述的组织级开关。

在 LangSmith UI 中[启用并配置 Engine](#turn-on-engine-in-langsmith) 之后，请启动一次 Engine 分析，并确认该 tracing project 出现了结果。这样才能验证经过 Engine、Sandboxes 和 LangSmith Intelligence 的完整链路。仅有处于运行状态的 pods 并不能验证这条链路。

如果分析未能完成，请检查 Engine pods 是否在运行、sandbox workspace 是否还有可用配额，以及集群能否访问配置在 `engine.intelligenceBaseUrl` 中的 LangSmith Intelligence gateway URL。

### 在 LangSmith 中开启 Engine

在 Helm 中启用 Engine 只是让该功能可用，并不会开始任何扫描。启用 chart 值之后，请在 LangSmith 中完成设置：

1. 由[组织管理员](/langsmith/rbac#organization-admin)在 **Settings > Engine enablement** 下为该组织开启 Engine。更多信息见[查找并修复 issues](/langsmith/engine#enable-engine-for-your-organization)。
1. 任何用户都可以从 tracing project 的 **Engine** 标签页为该 project 设置 Engine。更多信息见[为 tracing project 设置 Engine](/langsmith/engine#set-up-engine-for-a-tracing-project)。

连接 GitHub 仓库是可选的，但可以改进 Engine 的诊断和修复质量。没有连接时，Engine 无法读取你的源代码，也无法发起 pull request。要创建 GitHub App 并配置 `host-backend`，参见[将 Engine 连接到 GitHub](/langsmith/engine-github#self-hosted)。

### 禁用 Engine

将 `engine.enabled` 设为 `false` 并重新应用：

```yaml
engine:
  enabled: false
```

Engine 会停止调度 runs。Insights 与 Engine 共享同一 deployment，因此在 `insights.enabled` 为 `true` 时，`standalone-insights` pods 会继续运行。
