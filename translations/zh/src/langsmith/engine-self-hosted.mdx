<Info>
自托管版 Engine 需要 LangSmith Helm chart `0.16.0` 或更高版本，并且需要包含 Engine 授权的 license。在更早的 chart 版本上不可用。[联系你的客户团队](https://www.langchain.com/contact-sales)，将该授权添加到你的订单中。
</Info>

LangSmith Engine 是 LangSmith 内的一个 agent，它会监控你的生产 traces，将它们聚类成 issues，结合你的源代码诊断每个问题，提出一个修复 PR，并识别应添加到 datasets 中的 ground truth evals。关于产品概览，请参阅 [Engine](/langsmith/engine-overview)。

本页解释 Engine 在自托管 LangSmith 中如何运行、它在你的环境之外依赖什么，以及这对你的数据意味着什么。安装方式请参见[启用 Engine](/langsmith/deploy-self-hosted-full-platform#enable-engine)。若要将其连接到你的源代码，请按[将 Engine 连接到 GitHub](/langsmith/engine-github) 中的说明创建并配置你自己的 GitHub App。

Engine 会处理三类数据：

- **Code**（可选）**：**你的 agent 源代码，Engine 会读取它来诊断问题并提出修复方案。
- **Traces：**来自 agents 的运行时数据，其中可能包含用户消息、工具输出和 PII。
- **Model：**Engine 为执行诊断、生成修复方案和编写 evaluators 而发起的 LLM 调用。

在自托管 LangSmith 中，Engine 的编排逻辑作为 LangSmith 的一部分运行在你的 VPC 内：读取 traces、读取代码，并执行 detect、fix、verify 循环。但它无法完全在其中运行。Engine 依赖 LangSmith Intelligence（LSI），一个由 LangChain 托管的零数据保留（ZDR）服务，并向 LSI 发送其工作所需的内容。

## 按云和区域的可用性

Engine 依赖 LSI 的覆盖范围。该覆盖范围正在扩展，因此可用性因云和区域而异：

| 云 | 区域 | 状态 |
| --- | --- | --- |
| AWS | US | 可用 |
| GCP | US | 可用 |
| AWS | EU | 计划中 |
| Azure | US | 计划中 |

请联系你的客户团队，确认你所在区域的覆盖情况及当前时间安排。

## 工作原理

LSI 是为 Engine 提供支持的 LangChain 托管服务。

流程如下：

- 你的自托管 Engine 向其所在云的 LSI gateway 发送 HTTPS 请求，本页后续的各云小节中列出了这些 gateway。
- Engine 使用在 LangSmith license 校验期间获得的短期 license JWT 进行认证。你无需提供单独的模型提供商凭据。
- LSI 校验该 JWT，并通过 LangChain 环境内部的私有网络将请求路由到模型提供商。
- LSI 将响应返回给你的自托管 Engine。

每次请求都会携带 Engine 工作所需的 trace 内容、代码和中间输出。LSI 和模型提供商会处理这些内容以服务该请求。LSI 不会持久化 prompt 或 completion body。

你的集群必须允许到该 gateway 的出站 HTTPS。本文档不假设从你的环境到 LSI 的连接使用 AWS PrivateLink。如果你的安全策略要求私有连接，请在启用 Engine 之前联系你的客户团队，确认可用性和设置方式。

如果到 LSI 的连接不可用，Engine 会 fail closed。集群内没有模型，也没有备用提供商可以回退，因此受影响的 run 会以错误结束，而不是降级到较低质量的输出。你的 LangSmith 部署的其余部分不受影响，Engine 会在下一次计划扫描时重试。

## LangSmith Intelligence 保留了什么

LSI 不会持久化 prompt 或 completion body。它会保留以下用于使用量归因和计费的元数据：

- 用于归因使用量的 Account、workspace 和 project 标识符。
- 用于计费的模型和 token 使用量元数据。

关于模型提供商的保留和训练承诺，请参阅 [Engine security](/langsmith/engine-security)。

### AWS（美国可用）

gateway 主机为 `beacon.aws.langchain.com`。LSI 会将请求路由到 LangChain AWS 环境中的 AWS Bedrock。

## 模型选择与质量

模型选择在很大程度上决定了 Engine 的效果。Engine 会为工作流中的不同步骤使用不同模型，并进行不同调优，例如聚类 issues、结合代码诊断根因、生成修复方案，以及编写用于验证修复的 evaluator。LangChain 会针对质量和 token 效率同时调优这些模型，并随着更优秀模型的发布进行升级。

托管推理正是实现这一点的关键。由于 Engine 始终使用 LangChain 为各步骤调优后的模型，所以其行为能够保持一致，并随着这些模型升级而持续改进。如果采用自带 key（bring-your-own-key）的方式，Engine 就会受限于你配置的模型，因此调优效果和 token 效率会因请求不同而波动。

## 这对你的数据意味着什么

在自托管部署中，Engine 将数据处理分为你的环境和 LangChain 的环境两部分：

- **你的环境：**Engine 编排逻辑和 LangSmith 存储的 traces 保留在你的自托管环境中。
- **LangChain 的环境：**Engine 发送的内容由 LSI 和模型提供商处理。LSI 会保留上文列出的计费元数据，但不会持久化 prompt 或 completion body。

Engine 与部署无关的数据处理方式——包括与每家模型服务商之间的零数据保留，以及不会使用客户数据来训练或微调模型——已在 [Engine security](/langsmith/engine-security) 中说明。
