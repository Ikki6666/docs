[Agent2Agent (A2A)](https://a2a-protocol.org/latest/) 是 Google 提出的协议，用于让对话式 AI agents 之间进行通信。[LangSmith 实现了 A2A 支持](https://docs.langchain.com/langsmith/server-api-ref#tag/a2a/post/a2a/{assistant_id})，让你的 agents 可以通过标准化协议，与其他兼容 A2A 的 agents 通信。

[Agent Server](/langsmith/agent-server) 在 `/a2a/{assistant_id}` 提供 A2A 端点。

## 协议版本

Agent Server 使用 A2A **v1.0** JSON-RPC 绑定，同时也接受 v0.3 的方法名，因此已有的 v0.3 客户端可以继续工作。agent card 会声明一个接口：

```json
"supportedInterfaces": [
  {
    "url": "https://your-deployment/a2a/{assistant_id}",
    "protocolBinding": "JSONRPC",
    "protocolVersion": "1.0"
  }
]
```

<Warning>
你发送的方法名还会决定响应中枚举值的大小写。v1.0 方法名返回 SCREAMING_SNAKE_CASE（`TASK_STATE_WORKING`、`ROLE_AGENT`）；v0.3 方法名返回小写形式（`working`、`agent`）。每个客户端选定一种命名体系并保持不变。

响应外层结构因方法而异，而不是因命名体系而异：`SendMessage` 会把 task 包在 `result.task` 中，而 `GetTask` 和所有 v0.3 方法都直接放在 `result` 上返回。`ListTasks` 返回 `result.tasks`。
</Warning>

## 支持的方法

| v1.0 名称 | v0.3 名称 | 是否支持 |
|---|---|---|
| `SendMessage` | `message/send` | 支持 |
| `SendStreamingMessage` | `message/stream` | 支持——Server-Sent Events |
| `GetTask` | `tasks/get` | 支持 |
| `CancelTask` | `tasks/cancel` | 支持 |
| `ListTasks` | — | 支持 |
| `GetExtendedAgentCard` | — | 支持，仅限 v1.0 方法名 |
| `SubscribeToTask` | — | 暂不支持——返回 `-32601` |
| `*TaskPushNotificationConfig` | — | 暂不支持——返回 `-32601` |

只接受这四个 v0.3 方法名：`message/send`、`message/stream`、`tasks/get` 和 `tasks/cancel`。其他任何方法名——包括 `agent/getAuthenticatedExtendedCard` 和 `tasks/resubscribe`——都会返回 `-32601 Method not found`。

只有 JSON-RPC 绑定可用。gRPC 和 HTTP+JSON 均未实现。

### 响应中的任务历史

一个 context 可以包含多个 task。默认情况下，`SendMessage`、`GetTask` 和 `ListTasks` 返回的是**整个 context** 的历史，而不仅仅是所询问的那个 task。context 中的第二个 task 会重放第一个 task 的消息，因此渲染每一条历史记录的客户端会再次显示之前的轮次，包括更早的工具结果和 A2UI payload。

将 `historyScope` 设为 `task`，即可只返回属于所询问 task 的消息。默认值保持为 `context`，因此已有集成不受影响。

该选项放在哪里取决于方法。`SendMessage` 从 `configuration` 中读取：

```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "SendMessage",
  "params": {
    "message": {
      "role": "ROLE_USER",
      "parts": [{"text": "Second request"}],
      "messageId": "message-2",
      "contextId": "8b1f0e5c-9a3d-4f27-b0c8-2e6a5d4c1b7a"
    },
    "configuration": {"historyScope": "task"}
  }
}
```

`GetTask` 和 `ListTasks` 直接从 `params` 中读取：

```json
{"jsonrpc": "2.0", "id": "2", "method": "GetTask",
 "params": {"id": "<taskId>", "historyScope": "task"}}
```

如果你的客户端无法在请求体中添加字段，可以改为发送 header。请求中的显式值优先于 header。

```
LangGraph-A2A-History-Scope: task
```

agent card 会在 `capabilities.extensions` 中声明这一能力，因此你可以检测它是否受支持，而不是凭空假设：

```json
{
  "uri": "https://langchain.com/a2a/extensions/history-scope/v1",
  "description": "Choose task-only or full-context response history",
  "required": false,
  "params": {
    "header": "LangGraph-A2A-History-Scope",
    "values": ["context", "task"],
    "default": "context",
    "methods": ["SendMessage", "GetTask", "ListTasks"]
  }
}
```

三个值得了解的限制：

- 流式传输会忽略这两个历史选项。`SendStreamingMessage` 既不读取 `historyScope` 也不读取 `historyLength`，即使发送了它们也不会报错，因此不要在 SSE 上依赖其中任何一个。
- `historyLength` 上限为 10。更大的值会返回 `-32602`，并附带消息 `historyLength cannot exceed 10`。
- Scope 会在 `historyLength` 之前应用，因此你拿到的是**该 task** 的最后 N 条消息。

无法识别的值会返回 `-32602`，并附带消息 `historyScope must be 'context' or 'task'`。大小写错误的键（例如 `historyscope`）并不是错误，它会被忽略，你会静默拿到完整 context 的历史，因此如果发现过滤似乎没有生效，请检查拼写。

<Warning>
不要重发来自已完成 task 的 `taskId`。每一轮新对话都会在同一个 context 中开启一个新的 task，只需发送 `contextId`。指向已终止 task 的消息会被 `-32004` 拒绝，由其他 agent 生成的 `taskId` 会被 `-32001` 拒绝。
</Warning>

## Agent card 发现

每个 assistant 都会自动暴露一个 A2A Agent Card，用于描述其能力，并提供其他 agents 连接所需的信息。你可以使用以下方式获取任意 assistant 的 agent card：

```
GET /.well-known/agent-card.json?assistant_id={assistant_id}
```

agent card 中包含 assistant 的名称、描述、可用技能、支持的输入/输出模式，以及用于通信的 A2A 端点 URL。

## 可选能力

这些能力通过 Assistants API 上的 `metadata.a2a` 按 assistant 配置。`langgraph.json` 无法设置 assistant metadata，因此请在部署后 patch assistant。

### 声明输入和输出模式

```json
{
  "metadata": {
    "a2a": {
      "input_modes": ["text/plain", "application/pdf"],
      "output_modes": ["text/plain", "application/pdf"]
    }
  }
}
```

这些值既会填充 card 的 `defaultInputModes`/`defaultOutputModes`，也会填充生成的 skill 的模式。它们只是声明信息，未声明的模式仍会被接受。替换是按字段进行的，因此如果两者都要覆盖，请同时发送这两个字段；注意空列表会被拒绝。

### File parts

`FilePart` 双向可用。入站的 file、image、audio 和 video parts 会转换为 LangChain content blocks。出站的 content blocks 会映射回 `FilePart`，无论是在 task 历史中，还是在最终流式传输的 artifact 中。MIME 类型、URI 和文件名原样透传；内联数据会被重新编码为标准 base64。

### A2UI v0.9

按 assistant 开启：

```json
{ "metadata": { "a2a": { "a2ui": true } } }
```

之后 card 会声明该扩展，并将规范的 MIME 类型追加到两个模式列表中：

```json
"capabilities": {
  "extensions": [
    {
      "uri": "https://a2ui.org/a2a-extension/a2ui/v0.9",
      "description": "Ability to render A2UI v0.9",
      "required": false,
      "params": {
        "v0.9": {
          "supportedCatalogIds": [],
          "acceptsInlineCatalogs": false
        }
      }
    }
  ]
}
```

客户端通过在 `message.extensions` 中列出该 URI 来激活它。payload 会在两个方向上依据 v0.9 schema 校验，A2UI parts 会保留在 `message/send`、`tasks/get` 以及最终的 `message/stream` artifact 中。响应带有 `metadata.mimeType: "application/a2ui+json"`。输入时也接受 `application/json+a2ui` 作为别名。

### 过滤工具结果

默认情况下，每个关联的工具结果都会作为 `DataPart` 发布。如果只想发布其中一部分，请在 deployment 上设置工具名白名单：

```bash
A2A_ALLOWED_TOOL_CALL_RESULTS=generative_ui_tool,another_tool
```

未设置表示发布所有工具结果。该过滤器同时适用于 task 历史和流式传输。

| 功能 | 最低版本 |
|---|---|
| A2A 端点 | `langgraph-api >= 0.4.21` |
| 入站 `FilePart` | `0.12.0` |
| 工具结果 `DataPart` | `0.12.2` |
| `A2A_ALLOWED_TOOL_CALL_RESULTS` | `0.12.4` |
| 出站 `FilePart`、可配置的 card 模式 | `0.13.0` |
| A2UI v0.9 | `0.15.0` |
| `historyScope` | `0.15.0` |

```bash
pip install "langgraph-api>=0.13.0"
```

A2UI v0.9 和 `historyScope` 是在 `0.14.0` release candidates 冻结之后才合入的，因此它们会随 `0.15.0` 到来。该版本尚未作为稳定版本发布——在依赖 `historyScope` 之前，请先检查 agent card 上的 `capabilities.extensions`。

你的 graph 的 state 必须包含 `messages` 键，才能接受 A2A 的 text 和 file parts。输入 schema 中没有 `messages` 字段的 assistant 会被拒绝，并返回说明性错误。

## 创建兼容 A2A 的 agent

下面的示例创建了一个兼容 A2A 的 agent，它使用 OpenAI API 处理传入消息，并维护对话状态。这个 agent 定义了基于消息的状态结构，并处理 A2A 协议中的消息格式。

为了兼容 [A2A 的 "text" parts](https://a2a-protocol.org/dev/specification/#651-textpart-object)，agent 的 state 中必须包含 `messages` 键。

A2A 协议使用两个标识符来维持对话连续性：

* `contextId`：将消息归为同一个会话线程（类似 session ID）
* `taskId`：标识该会话中的每一个独立请求

第一次发送消息时，这两个都不要传入，agent 会生成并在响应中返回它们。之后对话中的所有消息，只需回传前一次响应中的 `contextId` 并省略 `taskId`，这样每一轮都会在同一个对话中开启一个新的 task。只有当要向仍在运行的 task（例如等待输入的 task）追加内容时，才发送 `taskId`。

**LangSmith tracing：** Langsmith Deployment 的 A2A 端点会自动将 A2A 的 `contextId` 转换为 LangSmith tracing 中的 `thread_id`，从而把同一会话中的所有消息归到同一个 thread 下。

例如：

```python
"""LangGraph A2A conversational agent.

Supports the A2A protocol with messages input for conversational interactions.
"""

from __future__ import annotations

import os
from dataclasses import dataclass
from typing import Any, Dict, List, TypedDict

from langgraph.graph import StateGraph
from langgraph.runtime import Runtime
from openai import AsyncOpenAI


class Context(TypedDict):
    """Context parameters for the agent."""
    my_configurable_param: str


@dataclass
class State:
    """Input state for the agent.

    Defines the initial structure for A2A conversational messages.
    """
    messages: List[Dict[str, Any]]


async def call_model(state: State, runtime: Runtime[Context]) -> Dict[str, Any]:
    """Process conversational messages and returns output using OpenAI."""
    # Initialize OpenAI client
    client = AsyncOpenAI(api_key=os.getenv("OPENAI_API_KEY"))

    # Process the incoming messages
    latest_message = state.messages[-1] if state.messages else {}
    user_content = latest_message.get("content", "No message content")

    # Create messages for OpenAI API
    openai_messages = [
        {
            "role": "system",
            "content": "You are a helpful conversational agent. Keep responses brief and engaging."
        },
        {
            "role": "user",
            "content": user_content
        }
    ]

    try:
        # Make OpenAI API call
        response = await client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=openai_messages,
            max_tokens=100,
            temperature=0.7
        )

        ai_response = response.choices[0].message.content

    except Exception as e:
        ai_response = f"I received your message but had trouble processing it. Error: {str(e)[:50]}..."

    # Create a response message
    response_message = {
        "role": "assistant",
        "content": ai_response
    }

    return {
        "messages": state.messages + [response_message]
    }

# Define the graph
graph = (
    StateGraph(State, context_schema=Context)
    .add_node(call_model)
    .add_edge("__start__", "call_model")
    .compile()
)
```

## Agent 之间的通信

当你的 agents 通过 `langgraph dev` 在本地运行，或者已经[部署到生产环境](/langsmith/deployment)后，就可以通过 A2A 协议让它们互相通信。

下面的示例演示了两个 agent 如何通过向彼此的 A2A 端点发送 JSON-RPC 消息来通信。这个脚本模拟了一个多轮对话流程，每个 agent 处理另一个 agent 的响应，并继续推进对话。

```python
#!/usr/bin/env python3
"""Agent-to-Agent conversation simulation using the LangGraph A2A endpoint."""

import asyncio
import aiohttp
import os
from langsmith import uuid7
def extract_text(result: dict) -> str:
    """Best-effort extraction of response text from an A2A result."""
    if "error" in result:
        raise RuntimeError(f"A2A error {result['error']['code']}: {result['error']['message']}")

    for art in result.get("result", {}).get("artifacts", []) or []:
        for part in art.get("parts", []) or []:
            if part.get("kind") == "text" and part.get("text"):
                return part["text"]

    msg = (result.get("result", {}).get("status", {}) or {}).get("message", {}) or {}
    for part in msg.get("parts", []) or []:
        if part.get("kind") == "text" and part.get("text"):
            return part["text"]

    return "(no text found)"


async def send_message(session, port, assistant_id, text, context_id=None):
    """Send an A2A message. Returns (response_text, returned_context_id)."""
    url = f"http://127.0.0.1:{port}/a2a/{assistant_id}"

    message = {
        "role": "user",
        "parts": [{"kind": "text", "text": text}],
        "messageId": str(uuid7()),
    }

    # A2A multi-turn continuity: reuse contextId across turns and agents.
    # Do not reuse taskId — each turn starts a new task within the same context.
    if context_id:
        message["contextId"] = context_id

    payload = {
        "jsonrpc": "2.0",
        "id": str(uuid7()),
        "method": "message/send",
        "params": {"message": message},
    }

    headers = {"Accept": "application/json"}
    async with session.post(url, json=payload, headers=headers) as response:
        result = await response.json()

    text = extract_text(result)
    returned_context_id = result.get("result", {}).get("contextId") or context_id
    return text, returned_context_id


async def simulate_conversation():
    """Simulate a conversation between two agents."""

    #Assistant IDs
    agent_a_id = os.getenv("AGENT_A_ID")
    agent_b_id = os.getenv("AGENT_B_ID")

    if not agent_a_id or not agent_b_id:
        print("Set AGENT_A_ID and AGENT_B_ID environment variables")
        return

    message = "Hello! Let's have a conversation."
    context_id = None

    async with aiohttp.ClientSession() as session:
        for i in range(3):
            print(f"--- Round {i + 1} ---")

            message, context_id = await send_message(
                session, 2024, agent_a_id, message, context_id=context_id
            )
            print(f"🔵 Agent A: {message}")

            message, context_id = await send_message(
                session, 2025, agent_b_id, message, context_id=context_id
            )
            print(f"🔴 Agent B: {message}\n")


if __name__ == "__main__":
    asyncio.run(simulate_conversation())
```

## 分布式追踪

当多个 agent 通过 A2A 通信时，LangSmith 可以将它们的所有 [traces](/langsmith/observability-concepts#traces) 归到同一个 [thread](/langsmith/observability-concepts#threads) 中，这样你就可以统一查看整个多 agent 对话。

### contextId 如何映射到 thread_id

Agent Server 的 A2A 端点会自动将 A2A 的 `contextId` 转换为 LangSmith tracing 中的 `thread_id`。这意味着一次对话中的每条消息，即使跨越多个 agent，也会自动归入 LangSmith 中的同一个 thread，无需额外配置。

整个流程如下：

1. 第一条消息中，客户端省略 `contextId`。服务器会生成一个，并在响应中返回。
1. 客户端在后续所有消息中传入该 `contextId`，以维持对话连续性。
1. Agent Server 会将 `contextId` 映射到 LangSmith [metadata](/langsmith/add-metadata-tags) 中的 `thread_id`，因此所有轮次都会出现在同一个 thread 中。

<Warning>
`contextId` 会直接用作 LangGraph 的 `thread_id`，因此它必须是 UUID。请回传服务器返回的那个值，而不是自己生成标识符。诸如 `session-42` 这样的 `contextId` 会被 `-32602` 拒绝，错误消息为 `Failed to create run: Invalid thread ID`。
</Warning>

### 跨多个 agent 追踪

当来自不同框架的 agents 通过 A2A 通信时，真正把它们 traces 统一起来的正是 `contextId`。在之后的每一个请求中复用第一个 agent 返回的 `contextId`，无论是发给该 agent 还是发给其他 agent。

<Warning>
Agent Server 不会读取 JSON-RPC payload 顶层的 `metadata` 字段。客户端无法直接设置 LangGraph 的 `thread_id`，它始终就是 `contextId`。向 Agent Server deployment 发送 `metadata.thread_id` 不会产生任何效果。
</Warning>

下面的代码片段演示了关键概念。完整的双 agent 可运行实现，请参见 [Google ADK + LangChain 示例](https://github.com/langchain-samples/A2A-google-adk/blob/main/test_agent_conversation.py)。

```python
import asyncio
import aiohttp
from langsmith import uuid7
async def send_message(session, url, text, context_id=None):
    """Send an A2A message and return (response_text, context_id)."""

    # --- 1. Build the message ---
    # On follow-up turns, include contextId inside the message object so the server
    # associates them with the ongoing conversation. Do not resend taskId: each turn
    # opens a new task within that conversation.
    message = {
        "role": "user",
        "parts": [{"kind": "text", "text": text}],
        "messageId": str(uuid7()),
    }
    if context_id:
        message["contextId"] = context_id

    # --- 2. Send it ---
    # contextId travels inside the message. Agent Server turns it into the
    # LangGraph thread_id, so no separate tracing field is needed.
    payload = {
        "jsonrpc": "2.0",
        "id": str(uuid7()),
        "method": "message/send",
        "params": {"message": message},
    }

    async with session.post(url, json=payload, headers={"Accept": "application/json"}) as response:
        if response.status != 200:
            raise RuntimeError(f"HTTP {response.status}: {await response.text()}")
        result = await response.json()

    if "error" in result:
        raise RuntimeError(result["error"].get("message", "Unknown error"))

    result_obj = result.get("result", {})
    returned_context_id = result_obj.get("contextId") or context_id
    text_out = next(
        (
            part.get("text", "")
            for art in result_obj.get("artifacts", []) or []
            for part in art.get("parts", []) or []
            if part.get("kind") == "text"
        ),
        "(no text)",
    )
    return text_out, returned_context_id


async def run_conversation(agent_a_url, agent_b_url):
    # --- 3. Share the context across agents ---
    # The first response carries a contextId. Pass it to every agent from then
    # on, and all their traces land in one LangSmith thread.
    context_id = None
    message = "Hello! Let's collaborate."

    async with aiohttp.ClientSession() as session:
        for _ in range(3):
            message, context_id = await send_message(
                session, agent_a_url, message, context_id=context_id
            )

            message, context_id = await send_message(
                session, agent_b_url, message, context_id=context_id
            )


asyncio.run(run_conversation(
    "http://localhost:2024/a2a/<agent_a_assistant_id>",
    "http://localhost:2025/a2a/<agent_b_assistant_id>",
))
```

**1. 构建消息**：在后续轮次中，把 `contextId` 放到 `message` 对象中，这样服务器才能将其关联到当前对话。第一条消息中不要传入它，因为服务器会生成 `contextId` 并在响应中返回。不要重发已完成轮次的 `taskId`。

**2. 发送消息**：`contextId` 随 `params.message` 传递。Agent Server 会把它用作 LangGraph 的 `thread_id`，因此没有需要单独设置的 tracing 字段。

**3. 在多个 agent 间共享 context**：让第一个 agent 生成 `contextId`，然后在对话的后续过程中把这个值传给每个 agent。正是它把所有 agent 的 traces 归到了同一个 thread 中。

### 在非 LangGraph agent 中接收 thread_id

[前一节](#tracing-across-multiple-agents)讲的是客户端侧，也就是发送消息时如何透传 `contextId`。如果你的某个 agent 不是基于 LangGraph 构建的，那么在接收端它也需要读取该 `contextId` 并将其附加为 thread 标识符，这样它的 traces 才会落到同一个 LangSmith thread 中。使用 `langsmith.integrations.otel.configure()` 设置自动 tracing，并从传入的 A2A 请求中读取 `params.message.contextId`。

```python
from fastapi import FastAPI, Request
from langsmith.integrations.otel import configure as configure_otel
from opentelemetry import trace
import json

# --- 1. Configure OTel ---
# Set up automatic tracing to LangSmith for your non-LangGraph agent.
configure_otel(project_name="my-a2a-project")
tracer = trace.get_tracer(__name__)

app = FastAPI()

@app.middleware("http")
async def set_thread_id_middleware(request: Request, call_next):
    thread_id = None
    if request.method == "POST":
        body_bytes = await request.body()
        if body_bytes:
            # --- 2. Extract contextId from the incoming A2A message ---
            try:
                body = json.loads(body_bytes)
                thread_id = body["params"]["message"].get("contextId")
            except (ValueError, KeyError, TypeError):
                pass
            # Re-inject the body so downstream handlers can still read it
            async def receive():
                return {"type": "http.request", "body": body_bytes}
            request._receive = receive

    # --- 3. Attach thread_id to the trace ---
    # langsmith.metadata.thread_id groups this trace with others in the same thread.
    with tracer.start_as_current_span("agent") as span:
        if thread_id:
            span.set_attribute("langsmith.metadata.thread_id", thread_id)
        return await call_next(request)
```

在这个 middleware 之后，再把你的 agent 路由注册到 `app` 上。

<Note>
在环境中设置 `LANGSMITH_API_KEY`，并根据需要设置 `LANGSMITH_PROJECT`，即可启用 tracing。对话中的所有 agents 都应使用同一个 project，这样它们的 traces 才能一起显示。
</Note>

### 在 LangSmith 中查看 traces

运行多 agent 对话后，打开 [LangSmith UI](https://smith.langchain.com)，然后进入 **Threads**。所有参与 agent 的所有轮次都会显示在同一个 thread 下，并以共享的 `thread_id` 作为标识。

## 测试你的集成

### 针对你自己的 deployment

先获取 card，然后发送一条消息：

```bash
curl "https://your-deployment/a2a/{assistant_id}/.well-known/agent-card.json"
```

```bash
curl -X POST "https://your-deployment/a2a/{assistant_id}" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "SendMessage",
    "params": {
      "message": {
        "role": "ROLE_USER",
        "parts": [{"text": "hello"}],
        "messageId": "test-1"
      }
    }
  }'
```

响应中包含 `result.task.id` 和 `result.task.contextId`。在下一条消息中复用该 `contextId` 即可继续对话。

要使用流式传输，请发送 `Accept: text/event-stream` 并使用 `SendStreamingMessage`。第一个事件是 `Task`，随后是状态和 artifact 更新。

### 针对官方一致性测试套件

A2A 在 [a2aproject/a2a-tck](https://github.com/a2aproject/a2a-tck) 发布了 Technology Compatibility Kit（TCK）。它会按 RFC 2119 等级为实现打分，并且可以针对任何 A2A 端点运行，包括你自己的。

```bash
./run_tck.py --sut-host https://your-deployment/a2a/{assistant_id} --transport jsonrpc
```

<Note>
TCK 通过 `messageId` 前缀（例如 `tck-input-required`）驱动某些场景，这些前缀在其 `docs/SUT_REQUIREMENTS.md` 中有说明。没有实现这些前缀的 graph 会将相应要求报告为 skipped，而不是 failed。
</Note>

### Agent Server 当前未通过的项目

Agent Server 在每次 CI 构建中都会将 TCK 作为必需检查运行，并与一份签入到仓库的已知失败列表进行比对。如果出现新的失败，CI 会失败；如果列表中的某个要求开始通过，CI 同样会失败，因此该列表不会偏离服务器的实际行为。

在基于某项能力构建之前，请先阅读此表：

| 差距 | 你会观察到的现象 |
|---|---|
| 响应的线上格式仍为 v0.3 | Task、message 和 part 携带 `kind` 和 `mimeType`，而不是 v1.0 的成员存在性判别 |
| 流式事件是扁平的 | SSE 发出带 `final` 的 v0.3 对象，而不是 `statusUpdate` / `artifactUpdate` 包装 |
| `tool_results` 是 snake_case | v1.0 期望的是 `toolResults`。保留现状是有意为之，因为线上 A2UI 客户端读取这个键 |
| 时间戳 | 序列化为 `+00:00`，而不是 ISO 8601 的 `Z` 后缀 |
| `SubscribeToTask` | 在规范要求 `-32001` 的地方返回 `-32601` |
| 推送通知配置 | 在规范要求 `-32003` 的地方返回 `-32601` |
| 错误不携带 `data` | 没有附加 `google.rpc.ErrorInfo` 的 reason 或 domain |
| `A2A-Version` 请求头 | 未被读取，因此不支持的版本会被照常处理，而不是返回 `-32009` |
| agent card 缓存 | 没有 `Cache-Control`、`ETag` 或 `Last-Modified` 头 |
| `GetExtendedAgentCard` | 已提供，但从未通过 `capabilities.extendedAgentCard` 声明 |

## 禁用 A2A

如果要禁用 A2A 端点，请在 `langgraph.json` 配置文件中将 `disable_a2a` 设为 `true`：

```json
{
  "$schema": "https://langgra.ph/schema.json",
  "http": {
    "disable_a2a": true
  }
}
```
