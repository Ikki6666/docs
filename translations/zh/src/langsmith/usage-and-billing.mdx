## 数据保留

本节介绍 LangSmith 中数据保留的工作方式以及相关定价。

### 为什么数据保留很重要

* **隐私**：许多数据隐私法规，例如欧洲的 GDPR 或加州的 CCPA，都要求组织在个人数据不再出于收集目的所必需时将其删除。设置保留期限有助于满足此类法规要求。
* **成本**：对于低数据保留级别的 traces，LangSmith 收费更低。更多信息，请参阅如何[强制执行支出限制](/langsmith/billing#enforce-spend-limits)。

<Tip>
在开始发送 traces 之前，先规划好你的保留层级。更改只会应用到新的 traces，现有 traces 会保留原有层级。请参阅[修改项目级默认保留策略](/langsmith/billing#change-project-level-default-retention)。
</Tip>

### 工作方式

按照数据保留策略，LangSmith 的 traces 分为两个层级，具有以下特征：

|                      | Base             | Extended       |
| -------------------- | ---------------- | -------------- |
| **价格**             | [查看定价页面](https://www.langchain.com/pricing-langsmith) | [查看定价页面](https://www.langchain.com/pricing-langsmith) |
| **保留期限**         | 14 天            | 400 天         |

<Note>
企业版客户可以为每个工作区自定义 extended 保留期限。更改只会应用到新的 traces，现有 traces 不受影响。请参阅[自定义 extended 保留策略](/langsmith/data-purging-compliance#customize-extended-retention-policy)。
</Note>

**保留期结束后的数据删除**

在指定保留期结束后，trace 将无法再通过 tracing project UI 或 API 访问。与该 trace 关联的所有用户数据，例如输入和输出，都会在此后一天内从我们的内部系统中删除。与每个 trace 关联的部分元数据可能会因分析和计费目的而被无限期保留。

### 数据保留自动升级

<Warning>
自动升级可能会影响你的账单。请仔细阅读本节，以充分了解估算的 LangSmith tracing 成本。
</Warning>

当你对 `base` 层级 trace 使用某些功能时，其数据保留会自动升级为 `extended` 层级。这会同时增加该 trace 的保留时长和成本。

trace 会在以下场景中发生升级：

* 向 trace 上任意 run 添加了 **反馈**，或向 thread 中任意 trace 添加了反馈，无论是通过[手动标注](/langsmith/annotate-traces-inline)、借助[在线评估器](/langsmith/online-evaluations-llm-as-judge)自动添加，还是通过 SDK[以编程方式添加](/langsmith/attach-user-feedback)。
* 某个 **[标注队列](/langsmith/annotation-queues#assign-runs-to-a-single-run-queue)** 接收到该 trace 中的任意 run。
* 某条 **[自动化规则](/langsmith/rules#create-a-rule)** 命中了 trace 中的任意 run。

<Note>
当你在 tracing project 上创建或编辑在线评估器时，可以选择不升级该评估器打分的 traces，让它们保持在 base 保留层级。该选项仅在项目默认保留层级为 base 时可用。更多信息，请参阅[管理评估器 trace 保留策略](/langsmith/evaluators#manage-evaluator-trace-retention)。
</Note>

**为什么 traces 会自动升级？**

关于 tracing 的自动升级模型，我们有两个原因：

1. 我们认为满足这些条件的 traces 本质上比其他 traces 更值得关注，因此让用户能够更长时间保留它们是有价值的。
2. 从理念上讲，我们希望对那些可能不会被有意义地交互的 traces 收取低一个数量级的费用。我们认为自动升级让定价模型更贴近 LangSmith 带来的价值，也就是只有发生了有意义交互的 traces 才会按更高费率计费。

如果你对我们的定价模型有任何问题或顾虑，请通过 [support.langchain.com](https://support.langchain.com) 联系支持团队，并告诉我们你的想法。

**数据保留如何影响下游功能？**

* **标注队列、Run Rules 和反馈**：使用这些功能的 traces 会被[自动升级](#数据保留自动升级)。
* **监控**：即使 base 层级 trace 的数据保留期结束，监控标签页仍然可以继续工作。它依赖的 trace 元数据会保留超过 30 天，这意味着即便是 `base` 层级 trace，你的监控图表依然会保持准确。
* **数据集**：数据集具有无限期的数据保留期限。换句话说，如果你将某个 trace 的输入和输出加入数据集，它们永远不会被删除。如果你将 LangSmith 用于数据收集，建议充分利用数据集功能。

### 计费模型

**计费指标**

在你的 LangSmith 发票中，会看到两个计费指标：

* LangSmith Traces (Base Charge)
* LangSmith Traces (Extended Data Retention Upgrades)

第一个指标包含所有 traces，不区分层级。第二个指标只统计 extended retention traces 的数量。

**为什么要统计所有 traces 加升级次数，而不是直接统计 base 和 extended traces？**

在考虑我们的定价模型时，一个很自然的问题是，为什么不直接在发票中展示 `base` 层级 traces 和 `extended` 层级 traces 的数量？

我们理解这样看起来更直观，但它无法正确反映 trace 升级的情况。假设某个 `base` 层级 trace 记录于 6 月 30 日，并在 7 月 3 日升级为 `extended` 层级。这个 `base` 层级 trace 发生在 6 月计费周期内，但升级发生在 7 月计费周期内。因此，我们需要能够分别度量这两个事件，才能对客户正确计费。

如果你的 trace 一开始就是以 extended retention trace 的形式记录的，那么 `base` 和 `extended` 两个指标都会以相同时间戳记录。

**成本拆分**

一个 trace 的 Base Charge 是每条 .05 美分。我们将升级定价设置为：一个 `extended` retention trace 的总成本是 base 层级 trace 的 10 倍，即每条 .50 美分，并且该价格已经包含两个指标。因此，每次升级的成本是 .45 美分。

## 速率限制

LangSmith 设有速率限制，用于确保所有用户都能稳定使用服务。

为确保访问性和稳定性，在以下情况下，LangSmith 会返回 HTTP 状态码 429，表示超出了速率或使用量限制：

### 在应用负载均衡器上的 1 分钟临时吞吐限制

此类 429 是由于某个 service key 或 PAT 在 1 分钟窗口内超过了固定 API 调用次数上限。该窗口的起点会略有变化，并不保证从某个整分开始，也可能因应用部署事件而变化。

在达到最大事件数后，我们会持续返回 429，直到距离当前评估窗口开始已满 60 秒，之后新的评估周期重新开始。

此类 429 由应用负载均衡器抛出，对所有 LangSmith 用户都生效，不受 plan tier 影响，其目的是保障所有用户的服务连续性。

| Method            | Endpoints     | Limit | Window   |
| ----------------- | ------------- | ----- | -------- |
| `DELETE`          | `/sessions*`  | 30    | 1 minute |
| `POST` OR `PATCH` | `/runs*`      | 5000  | 1 minute |
| `GET`             | `/runs/:id`   | 30    | 1 minute |
| `POST`            | `/feedbacks*` | 5000  | 1 minute |
| `*`               | `*`           | 2000  | 1 minute |

<Note>
LangSmith SDK 会采取措施，降低在 run 相关端点上触发这些限制的概率，具体做法是将同一个 session ID 下最多 100 个 runs 批量打包为一次 API 调用。
</Note>

### 按套餐区分的每小时 trace event 限制

此类 429 表示你已达到每小时最大可摄取事件数。它按 UTC 整点开始的固定窗口进行计算，并会在每个新小时的开始时重置。

这里的 event 指一次 run 的创建或更新。如果某个 run 在同一小时窗口内先被创建，随后又被更新，则会按 2 个 event 计入该限制。

此类限制由我们的应用抛出，并随 plan tier 不同而不同。Startup/Plus 和 Enterprise 套餐的组织具有更高的每小时限制，而 Free 和 Developer 套餐面向个人使用，因此限制更低。

| Plan                             | Limit          | Window |
| -------------------------------- | -------------- | ------ |
| Developer (no payment on file)   | 50,000 events  | 1 hour |
| Developer (with payment on file) | 250,000 events | 1 hour |
| Startup/Plus                     | 500,000 events | 1 hour |
| Enterprise                       | Custom         | Custom |

### 按套餐区分的每小时 trace 数据摄取限制

此类 429 表示你已达到 trace 输入、输出和元数据总摄取量上限。它按 UTC 整点开始的固定窗口进行计算，并会在每个新小时的开始时重置。

通常，输入、输出和元数据会在 run 创建和更新时都被发送。如果某个 run 在同一小时窗口内创建时大小为 2.0MB，更新后变为 3.0MB，则会按 5.0MB 计入此限制。

此类限制由我们的应用抛出，并随 plan tier 不同而不同。Startup/Plus 和 Enterprise 套餐的组织具有更高的每小时限制，而 Free 和 Developer 套餐面向个人使用，因此限制更低。

| Plan                             | Limit  | Window |
| -------------------------------- | ------ | ------ |
| Developer (no payment on file)   | 500MB  | 1 hour |
| Developer (with payment on file) | 2.5GB  | 1 hour |
| Startup/Plus                     | 5.0GB  | 1 hour |
| Enterprise                       | Custom | Custom |

### 按套餐区分的每月唯一 trace 数量限制

此类 429 表示你已达到每月最大 trace 摄取数量。它按 UTC 的自然月固定窗口进行计算，并会在每个月开始时重置。

此类限制由我们的应用抛出，并且仅适用于未绑定支付方式的 Developer 套餐。

| Plan                           | Limit        | Window  |
| ------------------------------ | ------------ | ------- |
| Developer (no payment on file) | 5,000 traces | 1 month |

### 自定义的每月使用量限制

此类 429 表示你已达到组织管理员配置的使用量限制。它按 UTC 的自然月固定窗口进行计算，并会在每个月开始时重置。

此类限制由我们的应用抛出，并根据各组织的配置而变化。

### 在应用中处理 429 响应

由于某些 429 响应只是临时性的，后续重试可能会成功，因此如果你在应用中直接调用 LangSmith API，我们建议实现带指数退避和抖动的重试逻辑。

为了方便，使用 LangSmith SDK 构建的 LangChain 应用已经内置了这一能力。

<Note>
需要注意的是，如果你在较长时间内持续打满这些端点，重试可能不会有效，因为你的应用最终会积累足够大的回压队列，直到耗尽所有重试机会。

如果确实如此，我们希望更具体地了解你的需求。请通过 [LangSmith Support](https://support.langchain.com) 联系支持团队，并提供你的应用吞吐需求和示例代码，以便我们一起判断最佳方案是修复 bug、调整你的应用代码，还是改用不同的 LangSmith 套餐。
</Note>

## 使用量限制

LangSmith 支持为 tracing 配置使用量限制。请注意，这里是 *usage* limits，而不是 *spend* limits，也就是说，它们限制的是某类事件发生的次数，而不是你最终花费的总金额。

LangSmith 支持设置两种不同的月度限制，对应前文数据保留指南中提到的两项计费指标：

* All traces limit
* Extended data retention traces limit

它们分别用于限制 traces 总数，以及 extended data retention traces 的数量。

### 使用量限制的特性

使用量限制是近似生效的，这意味着我们不保证限制值的绝对精确性。在极少数情况下，可能会在使用量限制开始生效前，短时间内额外处理少量超过阈值的 traces。

### Extended data retention traces limit 的副作用

Extended data retention traces limit 会带来一些副作用。如果该限制已经达到，任何可能触发 tracing 层级自动升级的功能都会变得不可用。这是因为 trace 一旦自动升级，就会新增一个 extended retention trace，而这又不应被该限制允许。因此，你将无法再：

1. 匹配 run rules
2. 向 traces 添加反馈
3. 向标注队列添加 runs

上述每项功能都有可能触发自动升级，因此当达到该限制时，我们会将它们关闭。

### 更新使用量限制

可以在 `Settings` 页面下的 `Usage and Billing` 中更新使用量限制。限制值会被缓存，因此新限制生效可能需要一两分钟。
