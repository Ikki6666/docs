除了基础的 [LangSmith](/langsmith/self-hosted) 平台之外，你还可以在 LangSmith Self-hosted 上启用以下功能：

- **[LangSmith Deployment](/langsmith/deployment)** 增加了一个[控制平面](/langsmith/control-plane)和[数据平面](/langsmith/data-plane)，让你可以直接通过 LangSmith UI 部署、扩缩容并管理 agent 和应用。如果你不需要完整的 UI 式配置，请参见[独立服务器](/langsmith/deploy-standalone-server)，它是一个更轻量的替代方案。
- **[Fleet](/langsmith/fleet/index)** 让你无需编写代码，就能直接在 LangSmith 中创建、部署和管理 AI agent。
- **[Insights](/langsmith/insights)** 在 LangSmith 中提供由 AI 驱动的 trace 和应用数据分析能力。
- **[Chat](/langsmith/chat)** 提供工作区内聊天体验，帮助你分析 trace、线程、提示词和实验结果。
- **[Sandboxes](/langsmith/sandboxes)** 让用户可以从 LangSmith 运行代码、暴露临时服务，并创建 memory snapshots。
- **[Engine](/langsmith/engine-overview)** 在某个 tracing project 中发现重复问题，结合源代码进行诊断，并提出修复方案。Engine 需要 Sandboxes。

<Info>
这些功能需要 [Enterprise](https://langchain.com/pricing) 方案。[预约演示](https://www.langchain.com/contact-sales)了解详情。
</Info>

## 前置条件

<Steps>
  <Step title="安装基础 LangSmith 平台">
    继续之前，请先按照 [Kubernetes 安装指南](/langsmith/kubernetes)安装基础 LangSmith 平台。
  </Step>
  <Step title="安装 KEDA">
    运行以下命令，在你的集群上安装 `KEDA`：

    ```bash
    helm repo add kedacore https://kedacore.github.io/charts
    helm upgrade --install keda kedacore/keda --namespace keda --create-namespace
    ```

    <Info>
    KEDA 会根据队列大小自动伸缩部署系统。
    </Info>
  </Step>
  <Step title="配置 ingress">
    为你的 LangSmith 实例配置 ingress、gateway 或 Istio。所有 agent 都会作为 Kubernetes 服务部署在这个 ingress 后面。参见[设置 ingress](/langsmith/self-host-ingress)。你必须在 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中提供 `hostname`。
  </Step>
  <Step title="验证集群容量">
    确保你的集群有足够的可用容量来运行多个部署。建议启用集群自动扩容器。
  </Step>
  <Step title="验证存储">
    确保你的集群上存在有效的动态 PV provisioner 或可用的 PV。

    ```bash
    kubectl get storageclass
    ```

    至少要有一个 StorageClass 的 `PROVISIONER` 有值（不能是 `kubernetes.io/no-provisioner`），并且被标记为 `(default)`；否则你需要先配置好后再继续。
  </Step>
  <Step title="验证 egress">
    确保可以访问 `https://beacon.langchain.com`。参见 [egress 文档](/langsmith/self-host-egress)。
  </Step>
</Steps>

## 启用 LangSmith Deployment

### 组件

启用 LangSmith Deployment 后，会在你的集群中创建以下资源：

- `listener`：监听[控制平面](/langsmith/control-plane)中的部署变更，并创建或更新下游 CRD。
- `LangGraphPlatform CRD`：管理 LangSmith Deployment 实例。
- `operator`：处理 LangSmith CRD 的变更。
- `host-backend`：[控制平面](/langsmith/control-plane)。

### 启用功能

要启用 LangSmith Deployment，请更新你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts)：

<Steps>
  <Step title="在配置中启用 deployment">
    在 `langsmith_config.yaml` 中启用 `deployment` 选项。同时你还必须已经正确配置了 ingress。

    ```yaml
    config:
      deployment:
        enabled: true
    ```
    <Note>
    从 v0.12.0 起，`langgraphPlatform` 选项已弃用。v0.12.0 之后的版本请使用 `config.deployment`。
    </Note>

  </Step>

  <Step title="（可选）配置镜像镜像同步">
    如果你需要把镜像同步到私有镜像仓库，请在 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中配置 `hostBackendImage` 和 `operatorImage`。请使用 [最新 LangSmith Helm chart release](https://github.com/langchain-ai/helm/releases) 中指定的镜像标签。

    ```yaml
    hostBackendImage:
      repository: "docker.io/langchain/hosted-langserve-backend"
      pullPolicy: IfNotPresent
    operatorImage:
      repository: "docker.io/langchain/langgraph-operator"
      pullPolicy: IfNotPresent
    ```
  </Step>

  <Step title="（可选）配置基础 agent 模板">
    如果你需要自定义 operator 如何创建 agent 的 Kubernetes 资源，请覆盖 [`values.yaml` 中的基础 agent 模板](https://github.com/langchain-ai/helm/blob/main/charts/langsmith/values.yaml#L1428)。最常见的场景是添加 `imagePullSecrets`，以便访问私有容器仓库。详见[为私有仓库配置认证](#configure-authentication-for-private-registries)。
  </Step>

  <Step title="应用变更">
    运行以下命令应用变更。本文中后续凡是提到“应用变更”，都使用这条命令。请把 `<version>` 和 `<namespace>` 替换为你的实际值：

    ```bash
    helm upgrade -i langsmith langchain/langsmith --values langsmith_config.yaml --version <version> -n <namespace> --wait --debug
    ```

    继续之前，请确认新 Pod 已经正常运行：

    ```bash
    kubectl get pods -n <namespace>
    ```

    现在你的实例已经可以创建 deployment 了。
  </Step>
</Steps>

## 启用 Fleet、Insights 和 Chat

<Info>
Fleet 需要 [LangSmith Self-Hosted v0.13](https://changelog.langchain.com/announcements/langsmith-self-hosted-v0-13) 或更高版本。下文描述的独立部署模型需要 v0.15 或更高版本。
</Info>

每个功能都需要一个 Fernet 加密密钥。你可以在一份 Helm 配置中同时启用这三个功能。

### 组件

为每个功能（Fleet、Insights、Chat）启用后，都会在集群中创建以下组件：

- `api-server`：处理该功能请求的主 API 服务器。
- `queue`：后台任务处理队列。
- `postgres`：该功能的独立 PostgreSQL 实例。也可以替换为外部 PostgreSQL。
- `redis`：该功能的独立 Redis 实例，用于缓存和 pub/sub。也可以替换为外部 Redis。

Fleet 还会额外创建：
- `toolServer`：为 agent 提供 MCP 工具执行能力。
- `triggerServer`：处理 webhook 和定时触发器。

<Warning>
从 chart `0.16.0` 开始，Insights 运行在 `langsmith-insights-engine` 上，这是一个同时服务于 `insights` 和 `engine` graphs 的组合 image，chart 默认使用它。之前的仅 Insights image `langsmith-clio` 已退役。

如果你的 values 将 `images.engineInsightsAgentImage.repository` 固定为 `langsmith-clio`，请在升级前移除或更新该设置。chart 会拒绝它。如果你将 images 镜像到私有 registry，请镜像 `langsmith-insights-engine` 并将 repository 指向你的副本。参见[镜像 images](/langsmith/self-host-mirroring-images#additional-images-for-engine)。
</Warning>

### 生成加密密钥

每个功能都使用独立的 Fernet 加密密钥来加密功能相关的敏感信息，例如凭据和 token。分离密钥有助于独立轮换，也能在某个密钥泄露时缩小影响范围。你可以用 Python 为每个功能各生成一个密钥：

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

建议将每个密钥存放在预定义的 Kubernetes secret 中，而不是直接写进配置文件。相关参数见[使用已有 secret](/langsmith/self-host-using-an-existing-secret#parameters)：`agent_builder_encryption_key`、`insights_encryption_key` 和 `polly_encryption_key`。

### 启用功能

<Steps>
  <Step title="将配置添加到 langsmith_config.yaml">
    <Tabs>
      <Tab title="使用 Kubernetes secrets（推荐）">
        通过名称引用已有 secret。chart 会自动从中读取 `agent_builder_encryption_key`、`insights_encryption_key` 和 `polly_encryption_key`。

        ```yaml
        config:
          existingSecretName: "<your-secret-name>"

        fleet:
          enabled: true

        insights:
          enabled: true

        # Chat（原 Polly）
        polly:
          enabled: true

        fleetToolServer:
          enabled: true

        fleetTriggerServer:
          enabled: true
        ```
      </Tab>
      <Tab title="使用内联值">
        直接在配置文件中设置加密密钥。不要把这个文件提交到版本控制中。

        ```yaml
        fleet:
          enabled: true
          encryptionKey: "<fleet-encryption-key>"

        insights:
          enabled: true
          encryptionKey: "<insights-encryption-key>"

        polly:
          enabled: true
          encryptionKey: "<chat-encryption-key>"

        fleetToolServer:
          enabled: true

        fleetTriggerServer:
          enabled: true
        ```
      </Tab>
    </Tabs>

    <Warning>
    如果你正在从旧的 `agentBootstrap` 部署模型迁移，请禁用 `backend.agentBootstrap` 以及旧的 `config.agentBuilder`、`config.insights` 和 `config.polly` 标志。这里指的是 `config` 段下的这些标志，而不是上面示例里的顶层 `fleet`、`insights` 和 `polly`。

    你还必须通过 LangSmith Deployments UI 手动删除现有的 Fleet、Insights 和 Chat 部署。如果你在旧 `agentBootstrap` 模型下没有给 Fleet 使用外部 PostgreSQL，并且还希望保留现有 Fleet agents，请在应用此配置之前通过 [Support Portal](https://support.langchain.com) 联系技术支持。
    </Warning>

    <Note>
    `fleetToolServer` 和 `fleetTriggerServer` 是 Fleet 的必需组件。从 Helm chart v15 开始，它们替代了已弃用的 `agentBuilderToolServer` 和 `agentBuilderTriggerServer`。
    </Note>

    默认情况下，每个功能都会部署自己的独立 PostgreSQL 和 Redis 实例。如果你想改用外部数据库，请在各功能下配置 `postgres.external` 和 `redis.external`。例如：

    ```yaml
    fleet:
      enabled: true
      encryptionKey: "<fleet-encryption-key>"
      postgres:
        external:
          enabled: true
          connectionUrl: "<fleet-postgres-connection-url>"
      redis:
        external:
          enabled: true
          connectionUrl: "<fleet-redis-connection-url>"
    ```
  </Step>
  <Step title="应用变更">
    ```bash
    helm upgrade -i langsmith langchain/langsmith --values langsmith_config.yaml --version <version> -n <namespace> --wait --debug
    ```

    确认 Fleet、Insights 和 Chat 的 Pod 都已正常运行：

    ```bash
    kubectl get pods -n <namespace>
    ```
  </Step>
</Steps>

### （可选）为 Fleet 启用 OAuth 工具和触发器

如果你想在 Fleet 中启用基于 OAuth 的工具，例如 Gmail、Slack 或 Linear，请配置 `providerOrgId`，并为每个要启用的集成添加 provider ID。你可以按需启用任意组合的 provider。

#### 可用 provider

| Provider | Tools enabled | Trigger enabled |
|----------|---------------|-----------------|
| `googleOAuthProvider`<br />[setup guide](#google-oauth-provider) | Gmail、Google Calendar、<br />Google Sheets、BigQuery | Gmail |
| `linearOAuthProvider`<br />[setup guide](#linear-oauth-provider) | Linear | - |
| `linkedinOAuthProvider`<br />[setup guide](#linkedin-oauth-provider) | LinkedIn | - |
| `microsoftOAuthProvider`<br />[setup guide](#microsoft-oauth-provider) | Outlook、Calendar、Teams、SharePoint、<br />Word、Excel、PowerPoint | Outlook |
| `salesforceOAuthProvider`<br />[setup guide](#salesforce-oauth-provider) | Salesforce | - |
| `slackOAuthProvider`<br />[setup guide](#slack-oauth-provider) | Slack | Slack |

#### 通用配置

将以下内容添加到你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中。只保留你需要的 provider。

```yaml
fleet:
  oauth:
    # 配置 OAuth provider 的组织 ID
    providerOrgId: "<your-org-id>"
    # 为你想启用的集成添加 provider ID。
    slackOAuthProvider: "<provider-id>"
    googleOAuthProvider: "<provider-id>"
    linkedinOAuthProvider: "<provider-id>"
    linearOAuthProvider: "<provider-id>"
    microsoftOAuthProvider: "<provider-id>"
    salesforceOAuthProvider: "<provider-id>"
```

<Warning>
provider ID 必须唯一，且不能以 `-agent-builder` 或 `-oauth-provider` 结尾。
</Warning>

  </Step>

<Accordion title="Microsoft OAuth provider" id="microsoft-oauth-provider">

要为 Fleet 启用 Microsoft OAuth，请创建 Azure app registration，添加所需的 Microsoft Graph delegated permissions，并在 LangSmith 中配置 Microsoft OAuth provider。

<Steps>
  <Step title="创建 Azure app registration">
    在 [Microsoft Entra admin center](https://entra.microsoft.com/) 中，进入 **Applications > App registrations** 并创建新的 registration。
  </Step>

  <Step title="选择支持的账号类型">
    根据你的部署方式选择账号类型。如果你需要多个 Microsoft Entra tenant 的用户都能认证，请选择多租户选项。如果部署仅限单一 tenant，则可以使用单租户 app registration。
  </Step>

  <Step title="添加 redirect URI">
    添加以下 web redirect URI，把 `<hostname>` 替换成你的 LangSmith hostname，把 `<provider-id>` 替换成 provider ID：

    ```
    https://<hostname>/host-oauth-callback/<provider-id>
    ```
  </Step>

  <Step title="创建 client secret">
    在 **Certificates & secrets** 中创建新的 client secret。复制 **Application (client) ID** 和生成出的 client secret 值。
  </Step>

  <Step title="添加 Microsoft Graph delegated permissions">
    在 **API permissions** 中添加以下 Microsoft Graph delegated permissions：
    - `Mail.ReadWrite`
    - `Mail.Send`
    - `Calendars.ReadWrite`
    - `Team.ReadBasic.All`
    - `Channel.ReadBasic.All`
    - `Channel.Create`
    - `ChannelMessage.Send`
    - `ChannelMessage.Read.All`
    - `Chat.Create`
    - `Chat.ReadWrite`
    - `User.ReadBasic.All`
    - `Files.ReadWrite.All`
    - `Sites.ReadWrite.All`

    <Note>
    LangSmith 会自动为 Microsoft provider 请求 `offline_access`，以便用户可以获得 refresh token。
    </Note>
  </Step>

  <Step title="授予租户同意">
    如果你的 Microsoft 365 策略要求对这些 delegated permissions 进行管理员同意，请为租户授予 admin consent。
  </Step>

  <Step title="在 LangSmith 中配置 OAuth provider">
    在 LangSmith 中进入 **Settings > OAuth Providers**，添加一个新 provider：
    - **Name**：例如 `Microsoft`
    - **Provider ID**：唯一字符串，例如 `microsoft-oauth-provider`
    - **Client ID**：Azure 中的 Application (client) ID
    - **Client Secret**：Azure 中的 client secret 值
    - **Authorization URL**：`https://login.microsoftonline.com/common/oauth2/v2.0/authorize`
    - **Token URL**：`https://login.microsoftonline.com/common/oauth2/v2.0/token`
    - **Provider Type**：`microsoft`
    - **Token endpoint auth method**：`client_secret_post`

    <Note>
    如果你创建的是单租户 app registration，请把授权和 token URL 中的 `common` 替换成你的 tenant ID。
    </Note>
  </Step>

  <Step title="应用变更">
    将以下内容添加到你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中并部署：

    ```yaml
    fleet:
      oauth:
        providerOrgId: "<your-org-id>"
        microsoftOAuthProvider: "<provider-id>"
    ```

    ```bash
    helm upgrade -i langsmith langchain/langsmith --values langsmith_config.yaml --version <version> -n <namespace> --wait --debug
    ```
  </Step>
</Steps>

</Accordion>

要为 Fleet 启用 Salesforce OAuth，请创建一个 Salesforce External Client App，配置其 OAuth 设置和策略，获取凭据，然后在 LangSmith 中配置 Salesforce OAuth provider。

<Steps>

    - **Distribution State**：**Local**

    <Note>
    External Client App 是 Salesforce 当前用于 OAuth 集成的框架。如果看不到 **New External Client App**，请确认你的组织已在 **Setup > External Client App Settings** 中启用应用创建。
    </Note>
  </Step>

  <Step title="启用 OAuth 并配置 OAuth 设置">
    展开 **API (Enable OAuth Settings)**，勾选 **Enable OAuth**。然后配置：

    - **Callback URL**，把 `<hostname>` 替换成你的 LangSmith hostname，把 `<provider-id>` 替换成 provider ID：

    ```
    https://<hostname>/host-oauth-callback/<provider-id>
    ```

    - **Selected OAuth Scopes**：添加 **Manage user data via APIs (api)** 和 **Perform requests at any time (refresh_token, offline_access)**。
    - 保持勾选 **Require Secret for the Web Server Flow**。
    - 不要勾选 **Enable Authorization Code and Credentials Flow** 和 **Enable Client Credentials Flow**。Fleet 使用标准的 web server（authorization code）流程。

    点击 **Create**。
  </Step>

  <Step title="设置 OAuth 策略">
    打开应用，进入 **Policies** 标签并点击 **Edit**：

    - **Refresh Token Policy**：选择 **Refresh token is valid until revoked**。
    - **Permitted Users**：保持 **All users may self-authorize**。如果你改选 **Admin approved users are pre-authorized**，则必须先把应用分配给某个 permission set 或 profile，否则授权会失败。

    点击 **Save**。

    <Note>
    External Client App 需要在两个地方配置：**Settings**（前一步的 OAuth 定义）和 **Policies**（这一步）。两处都必须保存。
    </Note>
  </Step>

  <Step title="复制凭据">
    在 **Settings** 标签页中，进入 **OAuth Settings** 下的 **Consumer Key and Secret**。其中 **Consumer Key** 就是你的 Client ID，**Consumer Secret** 就是你的 Client Secret。

    <Note>
    创建应用后，首次连接前请预留最多 30 分钟等待其完成传播。
    </Note>
  </Step>

  <Step title="在 LangSmith 中配置 OAuth provider">
    在 LangSmith 中进入 **Settings > OAuth Providers**，点击 **OAuth Provider**，并填写：
    - **Provider ID**：唯一字符串，例如 `salesforce-oauth-provider`。下一步中 `salesforceOAuthProvider` 也要使用同样的值。
    - **Display Name**：例如 `Salesforce`
    - **Client ID**：Salesforce 中的 Consumer Key
    - **Client Secret**：Salesforce 中的 Consumer Secret
    - **Authorization URL**：`https://<MyDomain>.my.salesforce.com/services/oauth2/authorize`
    - **Token URL**：`https://<MyDomain>.my.salesforce.com/services/oauth2/token`

    LangSmith 会根据 Token URL 自动识别 Salesforce，因此不需要额外设置 provider type 或 token auth method。请保持 **Enable PKCE** 关闭，以匹配上面配置的 web server flow。

    <Note>
    请将 `<MyDomain>` 替换为你组织的 My Domain，可在 **Setup > My Domain** 中查看。若为 sandbox，请使用 `https://<MyDomain>--<SandboxName>.sandbox.my.salesforce.com/services/oauth2/authorize` 以及对应的 token URL。
    </Note>
  </Step>

  <Step title="应用变更">
    将以下内容添加到你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中并部署：

    ```yaml
    fleet:
      oauth:
        providerOrgId: "<your-langsmith-org-id>"
        salesforceOAuthProvider: "<provider-id>"
    ```

    ```bash
    helm upgrade -i langsmith langchain/langsmith --values langsmith_config.yaml --version <version> -n <namespace> --wait --debug
    ```
  </Step>
</Steps>

<Warning>
如果登录失败：请确认 Salesforce 中的 **Callback URL** 与 `https://<hostname>/host-oauth-callback/<provider-id>` 完全一致（HTTPS、无尾随斜杠）；如果你选择了 **Admin approved users are pre-authorized**，请通过 permission set 分配该应用；如果你的组织限制登录 IP 范围，请把 Fleet server 的 egress IP 加入用户 profile 白名单，或在应用策略中把 **IP Relaxation** 设为 **Relax IP restrictions**。
</Warning>

### （可选）为 Fleet 启用 GitHub App

Fleet 通过专用的 **GitHub App**（不是 OAuth app）与 GitHub 集成。GitHub App 为 Fleet 的 GitHub 工具提供仓库访问能力，并支持私有仓库访问所需的用户授权流程。

配置过程包括：创建 GitHub App、收集凭据、将其保存为 Kubernetes secrets，并在你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中引用这些值。

<Steps>
  <Step title="创建 GitHub App">
    前往 [GitHub Settings > Developer settings > GitHub Apps](https://github.com/settings/apps)，点击 **New GitHub App**。

    <Note>
    你可以在个人账号或组织下创建该应用。如果有多人共同维护这个集成，建议使用组织拥有的应用。
    </Note>
  </Step>

  <Step title="填写基础信息">
    - **GitHub App name**：任意唯一名称，例如 `acme-langsmith-fleet`。记下 GitHub 自动生成的 slug（名称的小写加连字符形式），它将作为 `FLEET_GITHUB_APP_SLUG` 的值。
    - **Homepage URL**：你的 LangSmith hostname，例如 `https://langsmith.acme.com`。
    - 先取消勾选 **Webhook** 下的 **Active**。后续生成 webhook secret 后再启用。
  </Step>

  <Step title="设置 callback URL">
    在 **Identifying and authorizing users** 下，添加以下 **Callback URL**，把 `<hostname>` 替换成你的 LangSmith hostname：

    ```
    https://<hostname>/v1/platform/fleet/providers/github-app/auth/callback
    ```

    勾选 **Redirect on update**。

    在 **Post installation** 下，添加以下 **Setup URL**：

    ```
    https://<hostname>/v1/platform/fleet/providers/github-app/callback
    ```

    同样勾选 **Redirect on update**。
  </Step>

  <Step title="设置 webhook URL 并生成 webhook secret">
    生成一个随机 webhook secret：

    ```bash
    python3 -c "import secrets; print(secrets.token_urlsafe(48))"
    ```

    在 **Webhook** 下：
    - 勾选 **Active**。
    - 将 **Webhook URL** 设为：

      ```
      https://<hostname>/v1/platform/fleet/providers/github-app/webhooks
      ```

    - 把刚才生成的值填入 **Webhook secret**。保存它，因为后续创建 Kubernetes secret 时还会用到同一个值。
  </Step>

  <Step title="设置仓库权限">
    在 **Permissions > Repository permissions** 下，授予以下权限：

    - **Contents**：Read and write
    - **Issues**：Read and write
    - **Pull requests**：Read and write
    - **Metadata**：Read-only（会自动选中）

    在 **Permissions > Account permissions** 下，授予 **Email addresses: Read-only**。

    <Note>
    这是 Fleet 内置 GitHub 工具（issue 管理、pull request 创建、仓库内容访问）所需的最小权限集合。如果你需要更多工具能力，可以自行调整。
    </Note>
  </Step>

  <Step title="选择安装可见性">
    在 **Where can this GitHub App be installed?** 下，选择与你的分发需求匹配的选项。对于大多数自托管部署，选择 **Only on this account** 即可。
  </Step>

  <Step title="创建应用">
    点击 **Create GitHub App**。在应用设置页面中记下以下值：

    | Value | Where to find it | Environment variable |
    |-------|-----------------|----------------------|
    | **App ID** | 页面顶部的数字值 | `FLEET_GITHUB_APP_ID` |
    | **Public link** | 例如 `https://github.com/apps/acme-langsmith-fleet` | `FLEET_GITHUB_APP_PUBLIC_LINK` |
    | App slug | public link 的最后一段路径 | `FLEET_GITHUB_APP_SLUG` |
    | **Client ID** | **About** 下 | `FLEET_GITHUB_APP_CLIENT_ID` |
  </Step>

  <Step title="生成 client secret">
    在 **Client secrets** 下点击 **Generate a new client secret**，并复制其值。它对应 `FLEET_GITHUB_APP_CLIENT_SECRET`。GitHub 只会显示一次。
  </Step>

  <Step title="生成 private key">
    滚动到 **Private keys**，点击 **Generate a private key**。GitHub 会下载一个 `.pem` 文件。请妥善保管，因为它拥有 GitHub App 的完整访问能力。该 PEM 文件内容对应 `FLEET_GITHUB_APP_PRIVATE_KEY`。
  </Step>

  <Step title="生成 state JWT secret">
    LangSmith 使用 HMAC key 对短时效 OAuth state token 进行签名。生成一个：

    ```bash
    python3 -c "import secrets; print(secrets.token_urlsafe(48))"
    ```

    这就是 `FLEET_GITHUB_APP_STATE_JWT_SECRET`。
  </Step>

  <Step title="创建 Kubernetes secret">
    将这些敏感值保存到 Kubernetes secret 中：

    ```bash
    kubectl create secret generic fleet-github-app \
      --namespace <your-langsmith-namespace> \
      --from-literal=client_secret="<client-secret>" \
      --from-literal=webhook_secret="<webhook-secret>" \
      --from-literal=state_jwt_secret="<state-jwt-secret>" \
      --from-file=private_key=/path/to/fleet-app.private-key.pem
    ```

    对于生产部署，建议通过你现有的 secrets 工作流来管理这个 secret，例如 [Sealed Secrets](https://github.com/bitnami-labs/sealed-secrets) 或 [External Secrets Operator](https://external-secrets.io/)。更多信息见[使用已有 secret](/langsmith/self-host-using-an-existing-secret)。
  </Step>

  <Step title="将配置添加到 langsmith_config.yaml">
    将以下内容加入配置，并把占位符替换成前面收集到的非敏感值：

    ```yaml
    commonEnv:
      - name: FLEET_GITHUB_APP_ID
        value: "<app-id>"
      - name: FLEET_GITHUB_APP_SLUG
        value: "<app-slug>"
      - name: FLEET_GITHUB_APP_PUBLIC_LINK
        value: "https://github.com/apps/<app-slug>"
      - name: FLEET_GITHUB_APP_CLIENT_ID
        value: "<client-id>"
      - name: FLEET_GITHUB_APP_CLIENT_SECRET
        valueFrom:
          secretKeyRef:
            name: fleet-github-app
            key: client_secret
      - name: FLEET_GITHUB_APP_PRIVATE_KEY
        valueFrom:
          secretKeyRef:
            name: fleet-github-app
            key: private_key
      - name: FLEET_GITHUB_APP_WEBHOOK_SECRET
        valueFrom:
          secretKeyRef:
            name: fleet-github-app
            key: webhook_secret
      - name: FLEET_GITHUB_APP_STATE_JWT_SECRET
        valueFrom:
          secretKeyRef:
            name: fleet-github-app
            key: state_jwt_secret

    fleetToolServer:
      deployment:
        extraEnv:
          - name: FLEET_GITHUB_APP_ENABLED
            value: "true"
    ```

    <Note>
    `FLEET_GITHUB_APP_ENABLED` 必须设置在 tool server 上，GitHub 工具才会被注册。其余 `FLEET_GITHUB_APP_*` 变量由 platform backend 消费，因此应放在 `commonEnv` 下。
    </Note>
  </Step>

  <Step title="部署并把应用安装到仓库上">
    运行以下命令应用变更：

    ```bash
    helm upgrade -i langsmith langchain/langsmith --values langsmith_config.yaml --version <version> -n <namespace> --wait --debug
    ```

    Pod 全部健康后：

    1. 在 LangSmith 中打开一个 Fleet agent，并进入 agent 编辑器中的 GitHub 集成。
    2. 点击 **Connect GitHub**，把该应用安装到 Fleet 需要访问的仓库上。
    3. 对于私有仓库，安装时必须显式选择每一个仓库。

    <Note>
    每位用户还必须通过 LangSmith 中的重新授权流程，对自己的 GitHub 账号授权此 GitHub App。这样 Fleet 才能解析出按用户隔离的 token，供那些代表用户执行操作的工具使用。
    </Note>
  </Step>
</Steps>

## 启用 Sandboxes

<Info>
自托管 Sandboxes 需要 LangSmith Helm chart `0.16.0` 或更高版本。
</Info>

Sandboxes 默认禁用。安装后，请参见 [LangSmith Sandboxes](/langsmith/sandboxes) 了解 LangSmith UI 和 API 中的用户工作流。

### 支持的平台

自托管 Sandboxes 支持以下平台：

- Amazon Elastic Kubernetes Service (EKS)
- Google Kubernetes Engine (GKE)

Azure Kubernetes Service (AKS) 受基础 LangSmith chart 支持，但自托管 Sandboxes 不支持 AKS。

### 组件

启用 Sandboxes 会配置以下资源：

- 在支持 KVM 的节点上运行 sandbox 工作负载的 sandbox runtime pods。
- JuiceFS CSI 驱动和基于 JuiceFS 的 volume，用于 sandbox 文件和 snapshots。
- 由 Redis 支持的 JuiceFS metadata store 和由 S3 或 GCS 支持的 object storage。
- 可选的通配符 ingress，用于从 Sandboxes 内部暴露的服务。

### 前置条件

<Steps>
  <Step title="安装基础 LangSmith 平台">
    在启用 Sandboxes 之前，请先在 Kubernetes 上安装 LangSmith。请参见[在 Kubernetes 上自托管 LangSmith](/langsmith/kubernetes)。

    Sandboxes 运行在与 LangSmith release 相同的 Kubernetes 集群和 namespace 中。
  </Step>

  <Step title="添加支持 KVM 的节点">
    你的集群必须包含专用节点，这些节点能够运行在 `/dev/kvm` 处有 Linux KVM 可用的嵌套工作负载。

    这些可以是裸金属机器或启用了嵌套虚拟化的受支持云实例。在 AWS 和 GCP 上，使用暴露 `/dev/kvm` 给 sandbox runtime 的 x86_64 Linux 实例。

    <Warning>
    在 EKS 上，VPC CNI addon 必须为 **v1.21 或更高版本**。`v1.20.0` 在第 8 代
    Intel 实例（例如 `m8i`）上会崩溃：`aws-node` 进入 `CrashLoopBackOff`，节点报告
    `cni plugin not initialized`，托管节点组最终以
    `NodeCreationFailure: Unhealthy nodes in the kubernetes cluster` 失败。
    </Warning>

    默认 Helm 调度 values 期望这些节点具有以下 label 和 taint：

    ```yaml
    label:
      sandbox.langsmith.com/host: "true"
    taint:
      key: sandbox.langsmith.com/host
      value: "true"
      effect: NoSchedule
    ```

    如果你的节点使用不同的 labels 或 taints，请覆盖 `sandboxes.sandboxHost.deployment.nodeSelector` 和 `sandboxes.sandboxHost.deployment.tolerations`。
  </Step>

  <Step title="配置 JuiceFS 存储">
    Sandboxes 需要基于 JuiceFS 的共享存储。你必须提供：

    - 一个兼容 Redis 的 metadata store。
    - 一个 object storage bucket 或 bucket root。
    - 一个 JuiceFS CSI 配置 Secret，或足够的 Helm values 供 chart 创建一个。

    <Warning>
    启用 Sandboxes 会安装 JuiceFS CSI 驱动。CSI 驱动包含集群范围的 Kubernetes 资源。除非你已验证资源所有权，否则一个集群中应只有一个启用 sandbox 的 LangSmith release 管理 JuiceFS CSI 驱动。
    </Warning>

    支持的 object storage 后端：

    | 平台 | `sandboxes.juicefs.storage` | `sandboxes.juicefs.bucket` 格式 |
    | --- | --- | --- |
    | AWS | `s3` | 带区域信息的 HTTPS S3 endpoint，例如 `https://bucket-name.s3.us-west-2.amazonaws.com` |
    | GCP | `gs` | GCS URL，例如 `gs://bucket-name` |

    不要在 `sandboxes.juicefs.name` 中使用 object-store 子路径。使用扁平名称，例如 `sandbox-juicefs`。JuiceFS 会在配置的 bucket 内以该名称存储对象。

    <Tip>
    对于 Redis metadata store，我们建议将 `maxmemory-policy` 设置为 `noeviction`。这可以避免在内存压力下驱逐 JuiceFS metadata。监控 Redis 容量并在其达到内存限制之前进行扩容。

    使用 `noeviction` 时，当实例达到最大内存时 Redis 写入可能会失败，因此请为 sandbox metadata 增长保留足够的内存余量。
    </Tip>
  </Step>

  <Step title="配置 sandbox secrets">
    Sandboxes 需要额外的 secret 材料用于服务间认证和回调签名。

    <Tabs>
      <Tab title="使用 Kubernetes secrets（推荐）">
        如果你使用 `config.existingSecretName`，请将 sandbox keys 添加到同一个 LangSmith app Secret 中。不要在 Helm 中直接设置 secret 值。

        ```yaml
        stringData:
          sandbox_callback_signing_jwk: '<ed25519-private-jwk>'
          # Optional, only during service-auth secret rotation:
        ```
      </Tab>
      <Tab title="使用内联 values">
        如果 Helm chart 管理你的 LangSmith app Secret，请在配置文件中直接设置 sandbox secret 值。避免将此文件提交到版本控制。

        ```yaml
        config:
          sandboxes:
            callbackSigningJwk: '<ed25519-private-jwk>'
        ```
      </Tab>
    </Tabs>

    回调签名值必须是 Ed25519 private JWK。在升级之间保持其稳定。
  </Step>

  <Step title="选择代理 CA 模式">
    Chart 支持两种代理 CA 模式：

    | 模式 | 适用场景 |
    | --- | --- |
    | `generatedSecret` | 你希望 Helm 创建一个自签名 CA Secret。这是默认值。 |
    | `existingSecret` | 你在 LangSmith chart 之外管理 CA Secret。该 Secret 可以手动创建、由 cert-manager 创建，或由其他外部进程创建。 |

    在没有实时集群访问权限的情况下渲染 manifests 的 GitOps 工作流中，优先使用 `existingSecret`。`generatedSecret` 模式使用 Helm 的实时 `lookup` 行为在升级时重用生成的 Secret；纯渲染工作流无法读取实时 Secret，可能在每次渲染时生成新的 cert 材料。
  </Step>
</Steps>

### 使用 Helm 启用

将以下 values 添加到你的 `langsmith_config.yaml` 中，连同[前置条件](#prerequisites-2)中描述的 sandbox secret 值。将占位符替换为你部署特定的值。

```yaml
images:
  sandboxHostImage:
    tag: "<same-release-tag-as-your-langsmith-images>"

sandboxes:
  enabled: true
  juicefs:
    name: "sandbox-juicefs"
    storage: "s3"
    bucket: "https://bucket-name.s3.us-west-2.amazonaws.com"
    redis:
      metaURL: "redis://redis-host:6379/1"
  proxyCa:
    mode: "generatedSecret"
```

如果你自己创建 JuiceFS CSI 配置 Secret，请设置 `sandboxes.juicefs.csi.existingSecretName` 并从 Helm values 中省略 `sandboxes.juicefs.name`、`storage`、`bucket` 和 `redis.metaURL`：

```yaml
sandboxes:
  enabled: true
  juicefs:
    csi:
      existingSecretName: "juicefs-csi-config"
```

现有的 Secret 必须位于 LangSmith release namespace 中，并包含以下 keys：

```yaml
stringData:
  name: "sandbox-juicefs"
  metaurl: "redis://redis-host:6379/1"
  storage: "s3"
  bucket: "https://bucket-name.s3.us-west-2.amazonaws.com"
```

应用更新后的 chart：

```bash
helm upgrade -i langsmith langchain/langsmith \
  --values langsmith_config.yaml \
  --version <version> \
  --namespace <namespace> \
  --wait
```

### 使用 Terraform 启用

LangSmith Terraform modules 可以配置所需的 AWS 和 GCP 基础设施，并生成相应的 Helm values。

#### AWS

在 `modules/aws/infra/terraform.tfvars` 中，启用 Sandboxes 并配置 sandbox 节点容量：

```hcl
enable_sandboxes = true
redis_source     = "external"

sandbox_juicefs_redis_instance_type             = "cache.m6g.large"
sandbox_juicefs_redis_snapshot_retention_limit  = 7

sandbox_host_node_count               = 1
sandbox_host_instance_types           = ["m5d.metal"]
sandbox_host_configure_instance_store = true

sandbox_host_image_tag = "<same-release-tag-as-your-langsmith-images>"
```

AWS Sandboxes 要求 `redis_source = "external"`。Terraform module 会：

- 为 JuiceFS sandbox metadata 创建一个专用的 ElastiCache Redis 实例。
- 为该专用实例配置推荐的 `noeviction` 策略。
- 为 sandbox object storage 复用 LangSmith S3 bucket。
- 创建 JuiceFS CSI 配置 Secret。
- 添加预期的节点 label 和 taint。

AWS 设置脚本通过正常的 SSM 支持的设置流程生成 sandbox service-auth secret、callback signing JWK 和专用 JuiceFS Redis auth token。如果这些值尚不存在，请在应用 Terraform 之前运行 infra 设置脚本。

如果你使用 Terraform app module 部署 Helm release，还需在 `modules/aws/app/terraform.tfvars` 中设置 sandbox app values：

```hcl
enable_sandboxes      = true
chart_version          = "~0.16.0"
sandbox_host_image_tag = "<same-release-tag-as-your-langsmith-images>"
```

当 `enable_sandboxes = true` 时，Terraform app module 要求显式的 LangSmith Helm chart 版本 `0.16.0` 或更高版本，以及一个 sandbox runtime image tag。

运行正常的 AWS 流程：

```bash
make apply
make init-values
CHART_VERSION="~0.16.0" make deploy
```

#### GCP

在 `modules/gcp/infra/terraform.tfvars` 中，启用 Sandboxes 并配置 Standard GKE 节点池：

```hcl
enable_sandboxes = true
redis_source     = "external"

gke_use_autopilot     = false
enable_gcp_iam_module = true

sandbox_juicefs_redis_memory_size       = 5
sandbox_juicefs_redis_high_availability = true

sandbox_host_node_count     = 1
sandbox_host_min_node_count = 1
sandbox_host_max_node_count = 5
sandbox_host_machine_type   = "n2-standard-8"

sandbox_host_image_tag = "<same-release-tag-as-your-langsmith-images>"
```

GCP Sandboxes 要求 `redis_source = "external"`。Terraform module 会：

- 为 JuiceFS sandbox metadata 创建一个专用的 Memorystore Redis 实例。
- 为该专用实例配置推荐的 `noeviction` 策略。
- 为 sandbox object storage 复用 LangSmith GCS bucket。
- 创建 JuiceFS CSI 配置 Secret。
- 添加预期的节点 label 和 taint。

GCP 设置脚本通过正常的 Secret Manager 设置流程生成 sandbox service-auth secret 和 callback signing JWK。如果这些值尚不存在，请在应用 Terraform 之前运行 infra 设置脚本。

如果你使用 Terraform app module 部署 Helm release，还需在 `modules/gcp/app/terraform.tfvars` 中设置 sandbox app values：

```hcl
enable_sandboxes      = true
chart_version          = "~0.16.0"
sandbox_host_image_tag = "<same-release-tag-as-your-langsmith-images>"
```

当 `enable_sandboxes = true` 时，Terraform app module 要求显式的 LangSmith Helm chart 版本 `0.16.0` 或更高版本，以及一个 sandbox runtime image tag。

运行正常的 GCP 流程：

```bash
make apply
make init-values
CHART_VERSION="~0.16.0" make deploy
```

### 可选：启用 service URLs

当用户需要浏览器或编程方式访问 Sandboxes 内部运行的 HTTP 服务时，设置 `sandboxes.serviceUrlBaseUrl`。

```yaml
sandboxes:
  serviceUrlBaseUrl: "https://sandbox-services.example.com"
```

这需要 `*.sandbox-services.example.com` 的通配符 DNS 和 TLS。当 `ingress.enabled` 为 `true` 时，chart 还会添加一个通配符 ingress 规则，将这些 service URLs 路由到 LangSmith platform backend。

### 验证安装

升级完成后，验证 sandbox runtime pods 和 JuiceFS volumes 是否就绪：

```bash
kubectl rollout status deployment/sandbox-host -n <namespace>
kubectl get pods,pvc -n <namespace>
```

然后运行一个 sandbox 冒烟测试：

1. 从公共 image（例如 Python image）创建一个 sandbox。
2. 在 sandbox 内启动一个 Python HTTP server。
3. 对 sandbox 进行带 memory 的 snapshot。
4. 从 snapshot 创建一个新 sandbox。
5. 验证恢复的 sandbox 中 HTTP server 是否仍在运行。

### 升级说明

Sandbox runtime image 变更通过 `sandbox-host` Kubernetes Deployment 推出。Chart 默认使用无 surge 的滚动更新策略，因此 hosts 逐个替换。

在正常 Helm 升级期间，正在终止的 host 会停止接受新 Sandboxes，尝试将每个运行中 Sandbox 的 VM memory 保存到 JuiceFS，然后在该 pod 退出之前停止这些 VMs。此关闭受 `sandbox-host` pod 终止宽限期限制，默认为 300 秒。这不是实时迁移：该 host 上的 Sandboxes 在重启期间会被中断。

Sandboxes 不会被主动重启。当用户或 API 操作启动 Sandbox 时，或者当请求路径唤醒它时，它们会再次启动。LangSmith 随后将 Sandbox 放置在可用 host 上，并在关闭捕获完成时从保存的 memory image 恢复。如果 memory image 缺失或不完整，Sandbox 从保存的 root filesystem 启动。

## 启用 Engine

<Info>
自托管部署需要 LangSmith Helm chart `0.16.0` 或更高版本，并且需要包含 Engine 授权的 license。Engine 单独授权，并以 LCU 计量自己的使用量。[联系你的客户团队](https://www.langchain.com/contact-sales)将其添加到你的订单中。
</Info>

[Engine](/langsmith/engine-overview) 监控生产 traces，将重复故障聚类为 issues，逐个诊断，并提出修复方案。Engine 默认禁用。

Engine 需要 [Sandboxes](#enable-sandboxes)、到 [LangSmith Intelligence](#allow-egress-to-langsmith-intelligence) 的连接、一个外部可达的 [`config.hostname`](#verify-your-hostname-is-externally-reachable)，以及一个 [Engine 加密密钥](#generate-the-engine-encryption-key)。请在启用 Engine 之前完成这些前置条件。

Engine 和 [Insights](#enable-fleet-insights-and-chat) 运行在同一个 image 上，并共享一个 deployment。Insights 不是 Engine 的前提条件。如果你的安装已运行 Insights，启用 Engine 只是添加配置而不是新增 pods。

与本页其他功能不同，Engine 无法完全在集群内运行。Engine 使用 LangSmith Intelligence，一个由 LangChain 管理的零数据保留服务，来执行驱动诊断和修复的模型工作。关于数据流和保留的计费元数据，请参阅[自托管 Engine](/langsmith/engine-self-hosted)。

### 组件

启用 Engine 会配置或复用：

- `standalone-insights-api-server`：同时服务于 `engine` 和 `insights` graphs。
- `standalone-insights-queue`：Engine 和 Insights 的后台 run 处理。
- 一个专用的 PostgreSQL 和 Redis 实例用于共享 deployment，每个都可以用外部实例替换。
- [启用 Sandboxes](#enable-sandboxes) 中描述的 sandbox 组件。

Engine 还向 `platform-backend` 和 `ingest-queue` 添加配置，它们负责调度和排程 Engine 的 runs。

### 前置条件

<Steps>
  <Step title="启用 Sandboxes">
    请先完成[启用 Sandboxes](#enable-sandboxes)，包括支持 KVM 的节点池和 JuiceFS 存储。

    Engine 的 sandboxes 关联到一个 workspace。启用 Engine 的安装必须有一个[共享 organization](/langsmith/administration-overview#organizations)。如果该共享 organization 恰好有一个 workspace，LangSmith 会使用该 workspace。如果该共享 organization 有多个 workspace，LangSmith 不会自动选择其中一个。你必须将 `engine.sandboxTenantId` 设置为该 workspace ID。

    <Warning>
    建议使用一个为 Engine 保留的 workspace：

    - Engine 的 sandboxes 不按 Sandboxes 产品计费，因为 Engine 以 LCU 计量自己的使用量。
    - Engine 的 sandboxes 与该 workspace 中其他 sandboxes 使用相同的并发 sandbox、CPU 和内存配额。如果该 workspace 接近上限，Engine runs 可能会失败，或为交互式 sandboxes 留下更少的容量。
    - Engine 的 sandboxes 会在该 workspace 中列出，任何有权访问该 workspace 的人都可以停止它们。
    - 每个 sandbox 运行 agent 生成的代码。
    - 仓库凭据保留在 sandbox auth proxy 中，对 sandbox 内部运行的代码不可用。
    </Warning>
  </Step>

  <Step title="确认 license 授权">
    Engine 单独授权，方式与 Sandboxes 相同。你的 license 必须携带 Engine 授权。LangSmith 在启动时及此后定期针对 `https://beacon.langchain.com` 校验你的 license key，因此一旦授权添加到你的订单，无需更改任何配置即可生效。
  </Step>

  <Step title="允许到 LangSmith Intelligence 的 egress" id="allow-egress-to-langsmith-intelligence">
    允许从集群到你所用云的 LangSmith Intelligence gateway URL 的出站 HTTPS。将此 URL 作为 `engine.intelligenceBaseUrl` 的值。

    | 云 | `engine.intelligenceBaseUrl` |
    | --- | --- |
    | AWS | `https://beacon.aws.langchain.com/intelligence` |
    | GCP | `https://beacon.langchain.com/intelligence` |

    在 GCP 上，这与 LangSmith 已用于 license 校验和计费遥测的主机相同，因此 Engine 只是新增了一条路径而不是一个新的 egress 目标。

    <Note>
    Engine 在 **AWS US** 和 **GCP US** 的自托管部署中可用。在规划推出之前，请查看[按云和区域的可用性](/langsmith/engine-self-hosted#availability-by-cloud-and-region)并与你的客户团队确认覆盖情况。
    </Note>

    将该 gateway 作为特定的 allowlist 条目添加，而不是开放通用 egress。要将 AWS 流量保持在私有网络上，请[通过 AWS PrivateLink 连接到 LangSmith Intelligence](/langsmith/engine-self-hosted#connect-with-aws-privatelink)。请求使用在 LangSmith license 校验期间获得的短期 license JWT。Engine 的流量与[配置 egress](/langsmith/self-host-egress) 中描述的计费和运营遥测是分开的，即使它们共享一个主机。

    <Note>
    离线（air-gapped）安装无法运行 Engine。没有集群内模型可以回退。
    </Note>
  </Step>

  <Step title="验证你的 hostname 外部可达" id="verify-your-hostname-is-externally-reachable">
    Engine 的 sandboxes 使用 `langsmith` CLI 调用你的 LangSmith 安装，因此 `config.hostname` 必须从 sandbox 网络可达。Helm 校验会拒绝 `localhost` 和集群内 `*.svc` 地址。

    通过你的 ingress 以 TLS 提供该 hostname，如[设置 ingress](/langsmith/self-host-ingress) 中所述。Engine 不要求你暴露用户已访问地址之外的任何内容。Sandbox egress 已 allowlist 到你的 LangSmith hostname、`github.com`、`api.github.com` 和 Python 包注册表。每次运行的凭据由 sandbox 外部的代理注入，而不是在 sandbox 内部可读。
  </Step>

  <Step title="生成 Engine 加密密钥" id="generate-the-engine-encryption-key">
    Engine 使用自己的 Fernet key 来加密 LangSmith 传递给它的 run payloads，这些 payloads 携带短期凭据。生成一个：

    ```bash
    python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
    ```

    将其存储在你预定义的 Kubernetes Secret 中作为 `engine_encryption_key`，而不是配置文件中。参见[使用现有 secret](/langsmith/self-host-using-an-existing-secret#parameters)。

    要稍后轮换该 key，请将当前值复制到 `engine_encryption_key_previous`，并将新 key 设置为 `engine_encryption_key`。之前的 key 仅用于解密，因此在切换前刚加密的 runs 仍能完成。
  </Step>
</Steps>

### 使用 Helm 启用

将以下内容添加到你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中，连同[启用 Sandboxes](#enable-sandboxes) 中的完整 Sandboxes values。这些示例仅展示 Engine 特有的值和 `sandboxes.enabled` 标志。

<Tabs>
  <Tab title="使用 Kubernetes secrets（推荐）">
    按名称引用你现有的 Secret。Chart 会自动从中读取 `engine_encryption_key`。

    ```yaml
    config:
      existingSecretName: "<your-secret-name>"
      # Must be reachable from the sandbox network.
      hostname: "https://langsmith.example.com"

    engine:
      enabled: true
      intelligenceBaseUrl: "https://beacon.aws.langchain.com/intelligence"

    sandboxes:
      enabled: true
    ```
  </Tab>
  <Tab title="使用内联 values">
    在配置文件中直接设置加密密钥。

    <Warning>
    这会将一个活跃凭据放入你的配置文件中。不要将其提交到版本控制；优先使用 Kubernetes Secret。
    </Warning>

    ```yaml
    config:
      hostname: "https://langsmith.example.com"

    engine:
      enabled: true
      intelligenceBaseUrl: "https://beacon.aws.langchain.com/intelligence"
      encryptionKey: "<engine-encryption-key>"

    sandboxes:
      enabled: true
    ```
  </Tab>
</Tabs>

<Note>
如果你的安装有一个包含多个 workspace 的共享 organization，请设置拥有 Engine sandboxes 的 workspace：
</Note>

```yaml
engine:
  sandboxTenantId: "<workspace-id>"
```

<Warning>
从旧的 Insights image 设置升级需要额外检查一次：如果你的 values 将 `images.engineInsightsAgentImage.repository` 固定为已退役的 `langsmith-clio` image，请移除或更新该设置。Engine 和 Insights 现在运行在 `langsmith-insights-engine` 上，chart 会拒绝 `langsmith-clio`。更多信息，请参见[为 LangSmith 安装镜像](/langsmith/self-host-mirroring-images#additional-images-for-engine)。
</Warning>

在应用之前验证更新后的 chart：

```bash
helm template langsmith langchain/langsmith \
  --values langsmith_config.yaml \
  --version <version> \
  --namespace <namespace>
```

Chart 在渲染时验证 Engine 配置，并以消息指出缺失的值而失败，因此此命令可以在配置错误到达集群之前捕获它。

应用更新后的 chart：

```bash
helm upgrade -i langsmith langchain/langsmith \
  --values langsmith_config.yaml \
  --version <version> \
  --namespace <namespace> \
  --wait
```

### 验证安装

确认共享的 Engine 和 Insights deployment 正在运行：

```bash
kubectl get pods -n <namespace> | grep standalone-insights
```

API server 和 queue pods 都应为 `Running`。然后确认 `platform-backend` 健康，因为它负责调度 Engine runs：

```bash
kubectl rollout status deployment/langsmith-platform-backend -n <namespace>
```

如果 Engine 在此之后仍未出现在 LangSmith UI 中，最常见的原因是 license 没有 Engine 授权，以及[在 LangSmith 中开启 Engine](#turn-on-engine-in-langsmith) 中描述的 organization 级别开关。

在 LangSmith UI 中[启用并配置 Engine](#turn-on-engine-in-langsmith) 后，启动一个 Engine 分析并确认 tracing project 是否出现结果。这验证了通过 Engine、Sandboxes 和 LangSmith Intelligence 的完整路径。仅运行 pods 不能验证该路径。

如果分析未能完成，请检查 Engine pods 是否正在运行、sandbox workspace 是否有可用配额，以及集群能否访问在 `engine.intelligenceBaseUrl` 中配置的 LangSmith Intelligence gateway URL。

### 在 LangSmith 中开启 Engine

在 Helm 中启用 Engine 会使该功能可用，但不会启动任何扫描。启用 chart values 后，请在 LangSmith 中完成设置：

1. [Organization Admin](/langsmith/rbac#organization-admin) 在 **Settings > Engine enablement** 下为 organization 开启 Engine。更多信息，请参见[发现并修复 issues](/langsmith/engine#enable-engine-for-your-organization)。
1. 任意用户从项目的 **Engine** 标签页为某个 tracing project 设置 Engine。更多信息，请参见[为 tracing project 设置 Engine](/langsmith/engine#set-up-engine-for-a-tracing-project)。

连接 GitHub 仓库是可选的，但可以改善 Engine 的诊断和修复。没有它，Engine 无法读取你的源代码或提交 pull requests。要创建 GitHub App 并配置 `host-backend`，请参见[将 Engine 连接到 GitHub](/langsmith/engine-github#self-hosted)。

### 禁用 Engine

将 `engine.enabled` 设为 `false` 并重新应用：

```yaml
engine:
  enabled: false
```

Engine 停止调度 runs。Insights 共享同一个 deployment，因此当 `insights.enabled` 为 `true` 时，`standalone-insights` pods 会继续运行。

## 可选配置

### 配置额外的数据平面

<Warning>
**不推荐，且计划弃用。** 通过控制平面配置额外数据平面并不是推荐方案，后续版本会弃用。更建议部署[独立 Agent Servers](/langsmith/deploy-standalone-server)，并将其配置为向你的自托管 LangSmith 实例写入 trace。
</Warning>

除了上面创建的数据平面外，你还可以在其他 Kubernetes 集群中，或在同一集群的不同 namespace 中创建更多数据平面。实现方式不止一种，请按自己的使用场景选择最合适的方案。

#### 前置条件

<Steps>
  <Step title="阅读集群组织方式">
    阅读[hybrid（legacy）文档](/langsmith/hybrid-legacy#listeners)中的集群组织指南，了解如何根据你的场景组织这些资源。
  </Step>

  <Step title="验证 hybrid 前置条件">
    对新集群，验证 [hybrid 部分](/langsmith/hybrid-legacy#prerequisites)中的前置条件。在[前置条件](/langsmith/hybrid-legacy#prerequisites)的第 5 步中，请将 egress 配置为访问你的[自托管 LangSmith 实例](/langsmith/self-host-usage#configuring-the-application-you-want-to-use-with-langsmith)，而不是 `https://api.host.langchain.com` 和 `https://api.smith.langchain.com`。
  </Step>
  <Step title="在 Postgres 中启用功能">
    对你的 LangSmith Postgres 实例运行以下语句以启用该功能。请记下 workspace ID，后续步骤会用到。

    ```sql
    update organizations set config = config || '{"enable_lgp_listeners_page": true}' where id = '<org id here>';
    update tenants set config = config || '{"langgraph_remote_reconciler_enabled": true}' where id = '<workspace id here>';
    ```
  </Step>
</Steps>

#### 部署到不同集群

<Steps>
  <Step title="按照 hybrid 设置指南操作">
    按照 [hybrid setup guide](/langsmith/hybrid-legacy#setup) 的第 2 到第 6 步完成配置。将 `config.langsmithWorkspaceId` 设置为上一步中的 workspace ID。
  </Step>
  <Step title="（可选）在同一集群中添加更多数据平面">
    如果你想在同一集群中添加多个数据平面，请按照[在同一集群中配置额外数据平面](/langsmith/hybrid-legacy#configuring-additional-data-planes-in-the-same-cluster)中的说明操作。
  </Step>
</Steps>

#### 在同一集群的不同 namespace 中部署

<Steps>
  <Step title="更新配置">
    在你的 [`langsmith_config.yaml`](/langsmith/kubernetes#configure-your-helm-charts) 中进行以下修改：
    - 将 `operator.watchNamespaces` 设为当前自托管 LangSmith 实例所在的 namespace。这样可以避免和新数据平面新增的 operator 发生冲突。
    - 使用 [Gateway API](/langsmith/self-host-ingress#option-2%3A-gateway-api) 或 [Istio Gateway](/langsmith/self-host-ingress#option-3%3A-istio-gateway)。同时相应调整你的 `langsmith_config.yaml`。
  </Step>
  <Step title="应用变更">
    ```bash
    helm upgrade -i langsmith langchain/langsmith --values langsmith_config.yaml --version <version> -n <namespace> --wait --debug
    ```
  </Step>
  <Step title="按照 hybrid 设置指南操作">
    按照 [hybrid setup guide](/langsmith/hybrid-legacy#setup) 的第 2 到第 6 步完成配置。将 `config.langsmithWorkspaceId` 设为上一步中的 workspace ID。将 `config.watchNamespaces` 设为与现有数据平面不同的 namespace。
  </Step>
  <Step title="（可选）配置日志访问">
    为控制平面配置权限，以便读取新 namespace 中 Agent Server 部署的日志。参见[从其他 namespace 读取 Agent Server 日志](#read-agent-server-logs-from-other-namespaces)。
  </Step>
</Steps>
