本页记录使用 [GCP Terraform modules](https://github.com/langchain-ai/terraform/tree/main/modules/gcp) 预配的 LangSmith 部署的常见问题、修复方法和诊断命令。

<Tip>
升级之前，先查看 [LangSmith self-hosted changelog](/langsmith/self-hosted-changelog) 了解破坏性变更和需要更新的变量。运行任何 `kubectl` 命令之前，先运行 `gcloud container clusters get-credentials <cluster-name> --region <region> --project <project-id>`。
</Tip>

本页用到的 `kubectl`、`helm` 和 `gcloud` 调用的可复制参考，可直接跳到[诊断命令](#diagnostic-commands)。

在逐条运行命令之前，先试试随附的脚本：

```bash
# Full deployment health check + next-step guidance

```

## 已知问题

### terraform apply 失败：GCP API 未启用

**症状**

```
Error 403: ... has not been used in project <project-id> before or it is disabled.
```

**原因：** 所需的 GCP API 未启用。Terraform 会通过 `google_project_service` 启用它们，但 `cloudresourcemanager.googleapis.com` 必须已经启用，Terraform 才能启用其余 API。

**修复**

```bash
gcloud services enable cloudresourcemanager.googleapis.com --project <project-id>
cd modules/gcp/infra
terraform apply
```

### apply 后 GKE 集群 API server 不可访问

**症状**

```
Error: Get "https://<cluster-endpoint>/api/v1/namespaces": dial tcp: connection refused
```

**原因：** GKE control plane 需要 10 到 15 分钟才能完全就绪。Terraform 等待 `RUNNING` 状态后再加上 90 秒缓冲。较慢项目上的冷启动 API 激活可能超出这个窗口。

**修复：** 等待 `RUNNING` 状态，然后重新运行：

```bash
gcloud container clusters describe <cluster-name> \
  --region <region> --project <project-id> --format="value(status)"

terraform apply
```

### GKE 节点未加入（NotReady）

**症状：** `kubectl get nodes` 显示没有节点，或节点卡在 `NotReady` 状态。

**原因：** node pool 的 service account 缺少 `roles/container.nodeServiceAccount`，或 VPC 防火墙规则阻止了节点到 control plane 的通信。

**修复**

```bash
gcloud container node-pools describe <pool-name> \
  --cluster <cluster-name> --region <region> \
  --format="value(config.serviceAccount)"

gcloud projects add-iam-policy-binding <project-id> \
  --member="serviceAccount:<node-sa-email>" \
  --role="roles/container.nodeServiceAccount"

gcloud compute firewall-rules list --filter="network:<vpc-name>"
```

### GKE pods 连接 Cloud SQL 被拒绝

**症状：** Backend 日志中对 Cloud SQL 私有 IP 显示 `connection refused` 或 `no route to host`。

**原因：** 私有服务连接（VPC peering）未建立，或分配的 IP 范围太小。常见于 networking module 运行前未启用 `servicenetworking.googleapis.com` 的情况。

**修复**

```bash
gcloud services vpc-peerings list --network <vpc-name> --project <project-id>
gcloud sql instances describe <instance-name> --format="value(ipAddresses)"
gcloud compute networks peerings list --network <vpc-name>
```

Terraform 在 `postgres_source = "external"`、`redis_source = "external"`、`enable_sandboxes = true`，或 SmithDB 创建自己的 metastore 时会创建私有服务连接。如果缺少 peering，确认 `terraform.tfvars` 中包含其中一项设置，然后重新 apply：

```bash
terraform apply -target=module.networking
terraform apply
```

### Memorystore Redis 连接超时

**症状：** Pods 无法连接 Redis。日志显示 `dial tcp: connection timed out` 或 `redis: connection refused`。

**原因：** Memorystore 的 `authorized_network` 与 GKE VPC 不匹配，或 Redis 私有 IP 所在的范围无法从 GKE subnet 路由到达。

**修复**

```bash
gcloud redis instances describe <instance-name> --region <region> \
  --format="value(host,authorizedNetwork)"

kubectl run redis-test --rm -it --image=redis:7 -n langsmith -- \
  redis-cli -h <redis-private-ip> ping
# Expected: PONG
```

### cert-manager 无法签发 Let's Encrypt 证书

**症状：** `kubectl get certificate -n langsmith` 显示 `READY=False`。HTTP01 challenge 失败。

**原因：** DNS A record 未指向 Envoy Gateway IP，或 load balancer 上的 80 端口被阻断。

**修复**

```bash
kubectl get gateway -n envoy-gateway-system \
  -o jsonpath='{.items[0].status.addresses[0].value}'

kubectl describe certificate <cert-name> -n langsmith
kubectl get challenges -n langsmith
kubectl describe challenge -n langsmith

dig +short <your-langsmith-domain>
```

在 DNS A record 解析到 Gateway IP 之前，证书无法签发。cert-manager 的 HTTP01 solver 需要能从互联网访问 80 端口。

### LangSmith pods 访问 GCS bucket 被拒绝

**症状：** Backend 日志在写入 GCS 时显示 `AccessDeniedException: 403 Insufficient Permission` 或 `403 Forbidden`。

**原因：** 在原生 GCS 模式（随附的默认值）下，通过 Workload Identity 绑定的 GCP service account 缺少 bucket 上的 `roles/storage.objectAdmin`，或 pod 的 Kubernetes ServiceAccount 缺少 `iam.gke.io/gcp-service-account` annotation。在可选的 S3 兼容模式下，传给 Helm 的 HMAC 凭证不正确，或其 service account 缺少 `roles/storage.objectAdmin`。

**修复**

```bash
# Confirm the bucket and its IAM bindings
helm get values langsmith -n langsmith | grep bucketName
gcloud storage buckets get-iam-policy gs://<bucket-name>

# Native GCS mode: verify the Workload Identity annotation on the pod ServiceAccount
kubectl get serviceaccount langsmith-backend -n langsmith \
  -o jsonpath='{.metadata.annotations.iam\.gke\.io/gcp-service-account}'
```

GCP service account 必须拥有 bucket 上的 `roles/storage.objectAdmin`。如果 annotation 本身缺失，请采用下方 Workload Identity 一节的修复方法。对于 S3 兼容模式，在 **Cloud Storage** > **Settings** > **Interoperability** 下创建 HMAC key；其 service account 也需要 bucket 上的 `roles/storage.objectAdmin`。

### Envoy Gateway webhook 阻塞 GKE 操作

**症状**

```
Error from server (InternalError): failed calling webhook "validate.gateway.envoyproxy.io"
```

**原因：** Envoy Gateway admission webhook 未就绪，或其 `caBundle` 已过期。

**修复**

```bash
kubectl get pods -n envoy-gateway-system

kubectl rollout restart deployment/envoy-gateway -n envoy-gateway-system
kubectl rollout status deployment/envoy-gateway -n envoy-gateway-system
```

### 重新 apply 后 Envoy Gateway external IP 变化

**症状：** Terraform 重新 apply 后 DNS 不再解析到正确的 IP，或现有防火墙白名单失效。

**原因：** Envoy Gateway 的 external IP 绑定在由 Terraform 管理的 `Gateway` Kubernetes 资源上。如果该资源被删除并重建（`terraform taint`、强制替换的 module 变更，或 `terraform destroy` + 重新 apply），GCP 会分配新的 IP。除非预先分配静态 regional 地址，否则无法保留原 IP。

**预防措施**

- 不要 `terraform taint` 或手动删除 `Gateway` 资源。
- 仅在完整拆除和重建时使用 `make destroy` + `make apply`。
- 在任何可能重建 Gateway 的操作之前，记录当前 IP。

**恢复：** 将你的 DNS A record 更新为新 IP：

```bash
kubectl get gateway -n envoy-gateway-system -o jsonpath='{.items[0].status.addresses[0].value}'

gcloud dns record-sets update <your-domain>. \
  --type=A --ttl=300 \
  --rrdatas=<new-ip> \
  --zone=<zone-name> \
  --project=<project-id>
```

### terraform destroy 失败：启用了删除保护

**症状**

```
Error: googleapi: Error 409: The instance is protected from deletion.
```

**原因：** `gke_deletion_protection`、`postgres_deletion_protection` 或 `smithdb_metastore_deletion_protection` 为 `true`。Cloud SQL 同时在 API 层面和 Terraform 中强制删除保护，因此修改 `terraform.tfvars` 在应用该变更之前不会生效。

**修复**

```hcl
# terraform.tfvars
gke_deletion_protection      = false
postgres_deletion_protection = false

# Only when enable_smithdb = true and smithdb_metastore_source = "create"
smithdb_metastore_deletion_protection = false
smithdb_bucket_force_destroy          = true
```

```bash
source infra/scripts/setup-env.sh

terraform -chdir=infra apply \
  -target=module.gke_cluster -target=module.cloudsql \
  -target=module.smithdb -target=module.networking

make destroy
```

如果你从未启用 SmithDB，去掉 `module.smithdb` target。定向 apply 可以避免重新创建完整 `make apply` 会重建的集群内 add-on。

### Workload Identity 不生效（GCS 权限被拒绝）

**症状**

```
AccessDeniedException: 403 <pod-sa>@<project>.iam.gserviceaccount.com
  does not have storage.objects.create access to the Google Cloud Storage bucket.
```

**原因：** LangSmith pods 使用的 Kubernetes ServiceAccount 缺少 Workload Identity annotation，或 GCP SA 缺少 GCS IAM 绑定。

**诊断**

```bash
kubectl get serviceaccount langsmith-backend -n langsmith \
  -o jsonpath='{.metadata.annotations}' | python3 -m json.tool

BUCKET=$(terraform -chdir=infra output -raw storage_bucket_name)
gsutil iam get gs://$BUCKET | grep -A3 "serviceAccount"

GSA=$(terraform -chdir=infra output -raw workload_identity_service_account_email)
gcloud projects get-iam-policy <project-id> \
  --flatten="bindings[].members" --filter="bindings.members:$GSA"
```

**修复**

```bash
terraform -chdir=infra apply -target=module.iam
make init-values
make deploy
```

### `langsmith-ksa` 缺少 Workload Identity annotation

**症状：** operator 拉起的 agent pods 无法启动或卡在 `Pending` 状态。日志显示权限错误。

**原因：** Terraform 在 `k8s-bootstrap` module 中创建 `langsmith-ksa`，并且只在 `enable_gcp_iam_module = true` 时添加 annotation。`deploy.sh` 会在每次部署后重新应用该 annotation。如果 IAM module 关闭、namespace 被带外删除，或上一次部署被中断，annotation 就会缺失。

**诊断**

```bash
kubectl get serviceaccount langsmith-ksa -n langsmith \
  -o jsonpath='{.metadata.annotations.iam\.gke\.io/gcp-service-account}'
```

**修复**

如果 `enable_gcp_iam_module = false`，在 `terraform.tfvars` 中将其设置为 `true` 并运行 `make apply`。对于其他原因，重新运行部署或手动为 ServiceAccount 添加 annotation：

```bash
# Re-run deploy; idempotently creates and annotates langsmith-ksa
make deploy

# Or annotate manually
WI=$(terraform -chdir=infra output -raw workload_identity_annotation)
kubectl create serviceaccount langsmith-ksa -n langsmith --dry-run=client -o yaml \
  | kubectl apply -f -
kubectl annotate serviceaccount langsmith-ksa -n langsmith \
  iam.gke.io/gcp-service-account="$WI" --overwrite
```

### Deploy 拒绝 chart 0.16 的 sandbox values

**症状**

```txt
ERROR: values-overrides.yaml carries sandboxes.juicefs.csi, the chart 0.16 sandbox schema.
```

**原因：** `values-overrides.yaml` 是为 chart 0.16 生成的。Chart 0.17 没有 JuiceFS CSI driver，会忽略 `sandboxes.juicefs.csi` 块。

**修复：** 运行 `make apply`，然后运行 `make init-values` 重新生成该文件，再运行 `make deploy`。

### JuiceFS CSI 卷仍存在时 Deploy 拒绝执行

**症状**

```txt
ERROR: namespace langsmith still mounts sandbox volumes through the chart 0.16 JuiceFS CSI driver.
```

**原因：** Chart 0.17 移除了 JuiceFS CSI driver。在 PersistentVolumeClaims 或挂载 pods 仍在使用它时升级，会让旧的 sandbox-host pods 卡在 `Terminating` 状态。

**修复：** 在 driver 仍在运行时，运行错误信息打印的 `kubectl delete` 命令。等待 `kubectl get pods -n langsmith | grep juicefs` 只列出 `juicefs-csi-*` pods，然后再次运行 `make deploy`。运行中的 sandboxes 会停止。数据仍保留在对象存储和 Redis 中，chart 0.17 会挂载同一个 JuiceFS 卷。

### Deploy 拒绝 chart 0.16 的 SmithDB overlay

**症状**

```txt
ERROR: langsmith-values-smithdb.yaml has chart 0.16 SmithDB values that chart 0.17 rejects:
```

**原因：** `init-values.sh` 只复制一次 SmithDB overlay，因此 chart 0.16 的副本会留在 `helm/values/` 中。它设置了 `local-ssd-storage` 卷或 `smithdb.migration.deployment`，chart 0.17 已替换这些内容。

**修复：** 保存你的副本，并从 0.17 示例重新开始：

```bash
cp helm/values/langsmith-values-smithdb.yaml helm/values/langsmith-values-smithdb-0.16.yaml
cp helm/values/examples/langsmith-values-smithdb.yaml helm/values/langsmith-values-smithdb.yaml
```

只加回那些不设置 `nodeSelector`、`tolerations`、`volumes`、`volumeMounts` 或 `resources` 的修改。生成的 `langsmith-values-smithdb-sizing.yaml` 现在会设置这些内容。

### `init-values.sh` 因缺少 SmithDB 输出而失败

**症状**

```txt
ERROR: enable_smithdb = true but smithdb_helm_values or the resolved metastore TLS
       outputs are missing. The state is older than this module. Run 'make apply'.
```

**原因：** Terraform state 早于添加了 SmithDB 规格和 metastore 输出的 chart 0.17 module。

**修复：** 运行 `make apply`，然后运行 `make init-values`。

### SmithDB 回填 Job 变更导致 Deploy 拒绝执行

**症状**

```txt
ERROR: the existing <job-name> Job does not match what this deploy renders,
       and a Job's pod template cannot be changed in place:
```

**原因：** chart 升级或规格变更会为回填 Job 渲染不同的 pod 模板，而 Kubernetes 不允许就地更改 Job 的 pod 模板。

**修复：** 使用错误信息打印的命令删除该 Job，然后再次运行 `make deploy`。回填进度保存在任务数据库中，新 Job 会从上次进度继续，而不是重新开始。

### JuiceFS format Job 失败

**症状**

```txt
✗ The JuiceFS format Job for release langsmith failed (<reason>).
```

**原因：** `juicefs-format` Job 通过 `langsmith-sandbox-host` Workload Identity 绑定格式化 GCS bucket 中的 sandbox 卷。当原因为 `DeadlineExceeded` 时，Job 未能在 300 秒内完成，通常是因为 pod 无法调度或镜像拉取缓慢。对于其他原因，通常是绑定缺失或已过期。

**修复：**

1. 找出原因。对于 `DeadlineExceeded`，查找 `FailedScheduling` 事件或缓慢的镜像拉取：

    ```bash
    kubectl describe job -n langsmith -l app.kubernetes.io/component=juicefs-format
    ```

    对于其他原因，读取 Job 日志，然后运行 `make apply` 恢复 Workload Identity 绑定：

    ```bash
    kubectl logs -n langsmith -l app.kubernetes.io/component=juicefs-format
    ```

1. 删除失败的 Job 并重新部署。Helm 在清单未更改时不会重新运行失败的 Job，因此必须先删除 Job：

    ```bash
    kubectl delete job -n langsmith -l app.kubernetes.io/component=juicefs-format
    make deploy
    ```

### Helm release 卡在 `pending-upgrade`

**症状**

```
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
```

**原因：** 上一次 `helm upgrade` 被中断（在 `--wait` 期间按 Ctrl+C）。Helm 将 release 留在了锁定状态。

**修复：** `deploy.sh` 会检测并自动恢复该状态。如果手动运行：

```bash
helm rollback langsmith -n langsmith --wait --timeout 5m
make deploy
```

### Secret Manager 访问被拒绝

**症状**

```
ERROR: PERMISSION_DENIED: Permission 'secretmanager.versions.access'
  denied on resource 'projects/.../secrets/...'
```

**原因：** `secretmanager.googleapis.com` 未启用，或操作账号缺少 `roles/secretmanager.admin`。

**修复**

```bash
gcloud services enable secretmanager.googleapis.com --project <project-id>

gcloud projects add-iam-policy-binding <project-id> \
  --member="user:$(gcloud config get account)" \
  --role="roles/secretmanager.admin"
```

升级到 `main` 或 `v0.17.x` tag 之后，你添加的、以 LangSmith service account 身份读取 Secret Manager 的工作负载会失去访问权限，因为项目级 `roles/secretmanager.secretAccessor` 授权现在改为可选加入（opt-in）。请对具体的 secrets 授予访问权限，或设置 `grant_project_secret_accessor = true` 并运行 `make apply`。

### `langsmith-postgres-credentials` 或 `langsmith-redis-credentials` Secret 缺失

**症状：** 部署后 pods 立即因数据库连接错误崩溃，或 `kubectl get secrets -n langsmith` 中未列出 `langsmith-postgres-credentials` / `langsmith-redis-credentials`。

**原因：** 当 `postgres_source` 或 `redis_source` 为 `external` 时，这些 Secrets 由 `k8s-bootstrap` module 创建。如果未运行 `terraform apply`、apply 中途失败，或 namespace 被带外删除，它们就会缺失。

**修复**

```bash
terraform -chdir=infra apply -target=module.k8s_bootstrap

kubectl get secret langsmith-postgres-credentials -n langsmith
kubectl get secret langsmith-redis-credentials -n langsmith
```
