连接 agent 的代码仓库后，[LangSmith Engine](/langsmith/engine) 在调查 trace 时就能读取你的源代码，并在 GitHub 上以 pull request、在 GitLab 上以 merge request 形式提出修复方案。trace 分析不强制要求连接。关于 Engine 从源代码访问中获得什么以及它使用的权限，请参阅 [Why connect a repository](/langsmith/engine#why-connect-a-repository)。

Engine 可以连接 GitHub 上的仓库和 GitLab 上的项目。同一个 agent environment 可以同时使用两者。

GitHub：

- **LangSmith Cloud**：使用 GitHub.com 上由 LangChain 托管的 GitHub App。从[连接 GitHub 仓库](#connect-repositories)开始。
- **自托管 LangSmith**：由运维人员先为你的 GitHub 实例完成[为自托管上的 Engine 配置 GitHub](/langsmith/engine-self-hosted-github)。然后，workspace 用户按照下方相同的仓库连接步骤操作。
- **BYOC**：由 Organization Admin 先注册 GitHub App 并将其保存在 LangSmith UI 中。参见 [Configure the App on BYOC](/langsmith/engine-self-hosted-github#configure-the-app-on-byoc)。然后，workspace 用户按照下方相同的仓库连接步骤操作。

GitLab：由 workspace 管理员在 workspace 设置中连接 GitLab 账户的 access token。GitLab 仅在 LangSmith Cloud 上可用。从[连接 GitLab](#connect-gitlab)开始。

## GitHub

<a id="langsmith-cloud"></a>

### 连接仓库

这些步骤适用于 [LangSmith Cloud](/langsmith/cloud)，以及已配置 GitHub App 的[自托管](/langsmith/self-hosted)和 [BYOC](/langsmith/byoc) 部署。

为你的 tracing project 或 agent environment 启用 [Engine](/langsmith/engine)。你需要在该 project 中配置 Engine 的权限，以及在 LangSmith workspace 中连接 GitHub 集成的权限。如果这些操作不可用，请询问 workspace 管理员。

在 GitHub 上，你需要有在要连接的仓库上安装该 App 的权限，或者能访问已有的安装。你的 GitHub 组织或企业可能要求管理员批准该安装。出现提示时，请完成你组织的 SSO 登录。

<Note>
对于 Enterprise Managed Users，请连接组织拥有的仓库。GitHub 不允许将该 App 安装到 managed user 的个人账户。关于 GitHub.com 和 `ghe.com` 上的要求，请参阅 [Enterprise Managed Users](/langsmith/engine-self-hosted-github#enterprise-managed-users)。
</Note>

对于修复方案，仓库必须允许 Engine 的分支和 PR。在测试修复方案之前，请先查看[仓库政策](#repository-policies)。

要连接 GitHub 仓库：

1. 打开 tracing project 或 agent environment。在其 **Engine** 页面中，选择 **Configure Engine**。
2. 在 **Code repository** 下，选择 **Connect GitHub**。如果你的 workspace 已有连接，则会改为出现仓库选择器。
3. 在 GitHub 中，为你的 LangSmith 部署授权所配置的 App。将其安装到拥有你的代码的组织或账户，并选择它可以访问的仓库。如果该 App 已安装，LangSmith 可能会要求你选择一个已有的安装。
4. 完成所有 GitHub 审批提示并返回 LangSmith。授权 App 和安装 App 是两个独立的步骤：授权用于识别你的 GitHub 账户；安装则授予该 App 对仓库的访问权限。
5. 在仓库选择器中，按账户或仓库名称搜索，选择一个仓库，然后点击 **Connect repository**。
6. 对其他仓库重复上述操作。每个仓库都可以有自己的分支和子文件夹。

你也可以在首次设置 Engine 时，在 **Connect your agent's code repository** 下连接仓库。

#### 选择分支和子文件夹

对于每个已连接的仓库：

- **Branch**：选择 Engine 应读取并作为修复方案基础的分支。留空则使用仓库的默认分支。
- **Subfolder**：可选地让 Engine 只关注仓库中包含你的 agent 的部分。此设置不会限制 GitHub App 的仓库访问权限。

Engine 会在已连接的仓库中创建 fix 分支，并针对所选的基础分支打开 pull request。在 LangSmith v0.17 中，pull request 会以 draft 形式打开。请通过你常用的 GitHub 流程审查并合并这些 pull request。Engine 不会替你合并它们。

#### 连接另一个组织或账户

一个 GitHub App 可以在多个组织或账户中各有一个安装。来自这些安装的仓库可以在同一个 agent environment 中连接。

在仓库选择器中，选择 **Install on another GitHub organization or repository...**。完成 GitHub 流程，返回 LangSmith，然后连接其他仓库。在自托管 LangSmith 上，该 App 的[所有权和可见性](/langsmith/engine-self-hosted-github#choose-who-owns-the-app)决定了 GitHub 会提供哪些账户作为安装目标。

在自托管 LangSmith 上，所有已连接的仓库必须属于同一个 GitHub 实例。连接到不同的 LangSmith workspace 也需要在该 workspace 中连接相应的安装。

#### 管理仓库访问权限

将 App 安装到 **Only select repositories** 并不会自动包含之后创建的仓库。在选择器中，选择 **Missing a repo? Manage repo access for ...** 或 **Manage app access →**。在 GitHub 中添加该仓库，保存安装设置，然后重新加载选择器。

移除仓库会让 Engine 停止在该 agent environment 中使用它。这不会卸载 GitHub App，也不会移除它在其他 agent environment 中的访问权限。请在 GitHub 中管理该 App 的安装以撤销仓库访问权限。

#### 验证连接

使用一个测试仓库和一个带有代表性 traces 的 agent environment。在自托管 LangSmith 上，在此测试期间请让运维人员[验证 webhook 投递](/langsmith/engine-self-hosted-github#verify-webhook-delivery)。

验证连接：

1. 运行一次 Engine 分析，确认它可以使用仓库的源代码。
2. 为某个 issue 生成修复方案，检查其 diff，然后点击 **Open PR**。确认 **View PR** 会在预期的 GitHub 实例、仓库和基础分支上打开一个 PR。
3. 审查并合并测试 PR。确认对应的 Engine issue 变为 complete。

要自动创建 PR，请在 **Code repository** 设置中启用 **Open a pull request for every fix**。在 LangSmith v0.17 中，该设置名为 **Open a draft pull request for every fix**。

#### 仓库政策

仓库必须允许 Engine 推送 fix 分支。在 LangSmith v0.17 中，还必须支持 draft PR。Engine 不使用基于 fork 的贡献工作流。

Engine 的 Git commit 是未签名的。要求 fix 分支上有签名 commit 的规则可能会拒绝推送。分支名称规则、push 限制和 GHES pre-receive hook 也可能拒绝修复方案。在 LangSmith v0.17 中，fix 分支使用 `issues-agent/` 前缀。

请审查适用于这些分支和该 App 身份的政策。在目标分支上保留你正常的审查和合并要求。目标分支上的要求在人工合并时可能仍需满足；配置该 App 不会绕过仓库政策。

Engine 不会获取 Git LFS 文件内容，也不会初始化 Git 子模块。

#### 排查仓库选择问题

| 症状 | 检查什么 |
| --- | --- |
| GitHub 未配置，或在 GitHub 页面打开之前连接失败 | 在自托管 LangSmith 上，请让运维人员检查[部署配置](/langsmith/engine-self-hosted-github#configure-langsmith)。 |
| 你的组织不是安装目标 | 确认你的 GitHub 角色、组织审批政策和该 App 的可见性。私有 App 只能安装到其拥有的账户。 |
| 你的 managed user 账户不是安装目标 | 使用组织拥有的仓库。个人 managed user 仓库无法使用此集成。 |
| App 已安装，但 LangSmith 没有连接 | 在 LangSmith 中开始 **Connect GitHub**，包括在管理员批准安装之后，或你直接从 GitHub 安装之后。在自托管 LangSmith 上，如果授权未完成，请让运维人员[检查设置](/langsmith/engine-self-hosted-github#troubleshoot-setup)。 |
| 缺少安装或仓库 | 检查你授权的是哪个 GitHub 账户、该 App 选定的仓库，以及该安装是否已连接到此 LangSmith workspace。出现提示时，请完成你组织的 SSO 授权。 |
| 授权成功，但无法读取仓库 | 检查该 App 的仓库访问权限。在自托管 LangSmith 上，还请让运维人员检查 [GitHub API 和 sandbox 网络访问](/langsmith/engine-self-hosted-github#allow-network-access)。浏览器登录不会测试这些连接。 |
| 无法推送修复方案 | 检查适用于新 fix 分支的规则，包括签名 commit 要求、分支限制和 pre-receive hook。请参阅[仓库政策](#repository-policies)。 |

## GitLab

Engine 通过每个 workspace 一个 access token 连接到 GitLab。该 token 属于一个 GitLab 账户（通常是 service account），该账户的组和项目成员关系决定了 Engine 可以读取哪些项目、向哪些项目推送 fix 分支以及在其中打开 merge request。与 GitHub 不同，GitLab 不需要安装 app：你需要在 GitLab 中准备好账户，然后将其 token 保存到 LangSmith。

<Note>
GitLab 仅在 [LangSmith Cloud](/langsmith/cloud) 上可用。它尚不支持[自托管 LangSmith](/langsmith/self-hosted) 或 [BYOC](/langsmith/byoc)。
</Note>

### 连接 GitLab

连接 GitLab 需要 [Workspace Admin](/langsmith/rbac#workspace-admin) 角色，或具有 `workspaces:manage` 权限的自定义角色。其他 workspace 成员可以查看该连接，并将其可以访问的项目添加到 Engine。

你的 GitLab 实例必须满足以下要求：

- **Version**：GitLab.com，或运行 GitLab 16.10 或更高版本的自管理实例。LangSmith 使用 GitLab 的 token 自轮换 API 来续期 token，更早的版本没有该 API。
- **URL**：端口 443 上的 HTTPS，且没有路径。不支持安装在相对 URL 根路径下的 GitLab，例如 `https://example.com/gitlab`。
- **Network access**：LangSmith 通过互联网访问 GitLab，并拒绝解析为私有 IP 地址的 GitLab URL。该实例还必须能够向 LangSmith 投递 webhook。

#### 准备 service account

准备 Engine 所使用的账户：

1. 为 LangSmith 创建一个 [GitLab service account](https://docs.gitlab.com/user/profile/service_accounts/)。在 GitLab.com 上，由顶级组 Owner 在该组的 **Settings** > **Service accounts** 下创建。在 GitLab Self-Managed 上，默认由管理员创建。在 GitLab 18.11 或更高版本中，所有 GitLab 层级都提供 service account。在更早的 Free 层级实例上，请改用专用用户账户。
2. 将该账户以 **Maintainer** 角色添加到 Engine 应工作的组或项目中。**Developer** 是最低角色，但使用该角色时 LangSmith 无法注册 [merge request webhook](#complete-issues-on-merge)，因此合并修复方案不会完成对应的 issue。在选择角色之前，请查看[项目政策](#project-policies)。
3. 为该账户创建一个具有 `api` scope 的 personal access token。对于 service account，由组 Owner 或管理员从 **Service accounts** 页面创建 token。

该 token 只用于 LangSmith。保存时 LangSmith 会轮换它，因此你粘贴的值将停止工作，LangSmith 持有唯一可用的副本。

#### 保存连接

连接 GitLab：

1. 在 LangSmith 中，前往 **Settings** > **Integrations** > **GitLab**。
2. 在 **GitLab URL** 中，输入 `https://gitlab.com` 或你的实例的 HTTPS URL。
3. 在 **Access token** 中，粘贴 token。
4. 点击 **Connect GitLab**。

LangSmith 会与 GitLab 校验 token 并轮换它。页面会显示实例信息以及 token 的续期时间。在 **Connection health** 下，会显示以下详细信息：

- **Instance**：GitLab URL 和版本。
- **Token status**：GitLab 是否接受该 token，例如 **Accepted by GitLab**。
- **Scopes**：token 的 scope。
- **Expires**：当前 token 的过期时间。
- **Webhook URL**：GitLab 向其投递 merge request webhook 的 URL。
- **Last webhook delivery**：LangSmith 最近一次收到 GitLab webhook 的时间。

每个 workspace 只有一个 GitLab 连接，连接到一个 GitLab 实例。

#### 管理 access token

LangSmith 会加密存储 token 并管理其生命周期：

- **Renewal**：LangSmith 会在 token 生命周期过半时轮换它。每次轮换都会请求一个有效期为一年的 token。如果实例设置了更短的最长有效期，LangSmith 会使用实例可接受的最长时长（180、90、60、30、14、7 或 2 天）。将 token 限制为一天有效期的实例无法连接。
- **Edit connection**：要更换 token 或切换实例，请点击 **Edit connection**，输入新的值，然后点击 **Save connection**。LangSmith 会撤销被替换的 token。切换后，Engine 跟踪的 GitLab 项目路径将指向新实例上的项目，之前在旧实例上打开的修复方案会被隐藏，直到你切换回去。
- **Disconnect**：点击 **Disconnect** 撤销 token。Engine 会立即失去对 GitLab 项目的访问权限，包括正在进行的 run。LangSmith 的 webhook 会保留在你的项目上，并在你重新连接后恢复工作，但在此期间合并的 merge request 不会完成其 issue。

删除 workspace 会删除其 GitLab 连接，但不会撤销 token。token 会自行过期，你也可以在 GitLab 中撤销它。

### 添加 GitLab 项目

workspace 管理员连接 GitLab 后，任何能在某个 agent environment 中配置 Engine 的用户都可以添加该 GitLab 账户可以访问的项目。

添加 GitLab 项目：

1. 打开 agent environment。在其 **Engine** 页面中，选择 **Configure Engine**。
2. 在 **Code repository** 下，按项目名称或路径搜索仓库选择器。结果按 host 分组，GitHub 仓库在前，GitLab 项目位于 **GitLab** 标题下。选择器只显示前 20 个匹配的 GitLab 项目，因此请细化搜索以找到其他项目。
3. 选择项目以添加。
4. （可选）设置项目的 **Branch** 和 **Subfolder**。参见[选择分支和子文件夹](#choose-the-branch-and-subfolder)。
5. 对其他项目重复上述操作。

你也可以在首次设置 Engine 时，在 **Connect your agent's code repository** 下添加项目。

如果选择器中缺少某个项目，请将该 GitLab 账户以至少 **Developer** 角色添加到该项目。在 workspace 管理员连接 GitLab 之前，选择器会向 workspace 管理员显示 **Connect GitLab**，向其他用户显示 **Ask a workspace admin to connect GitLab.**

Engine 可以在同一个 agent environment 中同时跟踪 GitHub 仓库和 GitLab 项目。每个路径在每个 agent environment 中只能来自一个 host。要跟踪与已跟踪 GitHub 仓库路径相同的 GitLab 项目，请先移除该 GitHub 仓库。

#### 打开 merge request

在 GitLab 上，Engine 处理修复方案的方式与 GitHub 相同，只是用 merge request 代替 pull request。修复相关控件保留原有名称，例如 **Open PR** 和 **View PR**。

- **Fix branches**：Engine 会将每个修复方案推送到项目中一个新的 `langsmith-engine/<id>` 分支。
- **Author**：已连接的 GitLab 账户使用其 GitLab noreply 电子邮件地址作为 commit 和 merge request 的作者。
- **Merge requests**：在 issue 上点击 **Open PR**，即可针对项目所选的分支或其默认分支打开 merge request。merge request 打开后即可审查，因此跳过 draft merge request 的 pipeline 仍会运行。
- **Automatic merge requests**：**Code repository** 设置中的 **Open a pull request for every fix** 同样适用于 GitLab 项目。

请通过你常用的 GitLab 流程审查并合并 Engine 的 merge request。Engine 不会替你合并它们。

#### 合并时完成 issue

LangSmith 会在 Engine 跟踪的每个 GitLab 项目上注册一个 merge request webhook。当带有 Engine 修复方案的 merge request 被合并时，该 webhook 会完成修复方案对应的 issue。当 merge request 关闭但未合并时，Engine 会记录该关闭状态。注册该 webhook 需要对项目具有 **Maintainer** 角色。

LangSmith 会在你连接 GitLab 之后、添加项目时，以及 Engine 每次打开 merge request 时创建或修复该 webhook。

如果 webhook 无法工作，该项目在 **Code repository** 下的行会显示警告图标和 **GitLab settings** 链接。将鼠标悬停在图标上可查看原因。在你解决了阻止注册的问题后，无需其他步骤。Engine 仍会读取该项目的代码并在其中打开 merge request。

GitLab 会将 webhook 投递到 **Connection health** 下显示的 **Webhook URL**，因此你的实例必须能够访问该 URL。

#### 验证 GitLab 连接

使用一个测试 GitLab 项目和一个带有代表性 traces 的 agent environment。

验证连接：

1. 在 **Settings** > **Integrations** > **GitLab** 下，确认 **Token status** 显示 **Accepted by GitLab**。
2. 添加测试项目，并确认其在 **Code repository** 下的行没有警告。
3. 运行一次 Engine 分析，确认它可以使用该项目的源代码。
4. 为某个 issue 生成修复方案，检查其 diff，然后点击 **Open PR**。确认 **View PR** 会在预期的 GitLab 实例、项目和目标分支上打开一个 merge request。
5. 审查并合并测试 merge request。确认 Engine issue 变为 complete，且 **Last webhook delivery** 得到更新。

#### 项目政策

Engine 只推送自己的 fix 分支，但 GitLab 不会将 token 限制在这些分支上。账户的角色和你的分支保护决定了该 token 可以更改的内容：

- **Developer**：GitLab 的默认分支保护会阻止 Developer 推送到默认分支或合并到默认分支。LangSmith 无法注册 merge request webhook。
- **Maintainer**：LangSmith 可以注册 merge request webhook。Maintainer 可以推送到允许 Maintainer 的受保护分支并合并到其中，在 GitLab 的默认保护设置下这包括默认分支。

只将该账户添加到 Engine 需要的项目，并保护 Engine 不应更改的分支。在目标分支上保留你正常的审查和合并要求。

推送规则可能会拒绝 Engine 的推送，例如要求签名 commit、限制分支名称或检查 commit 作者电子邮件地址的规则。与在 GitHub 上一样，Engine 的 commit 是未签名的，并且 Engine 不使用 fork、不获取 Git LFS 文件内容、也不初始化 Git 子模块。

#### GitLab 限制

以下 Engine 功能不适用于 GitLab 项目：

- **Fix validation**：[使用预览部署验证修复方案](/langsmith/engine-fix-validation)需要 GitHub 仓库。
- **Red Teaming**：[Red Teaming](/langsmith/engine-red-teaming) 运行只使用 GitHub 仓库，并采用只读凭证。GitLab access token 无法限制为只读访问，因此 Red Teaming 永远不会拿到这种 token。
- **由其他工具打开的 merge request**：Engine 不会关联在 Engine 之外打开的 merge request，包括由 [Slack 中提及的编码 agent](/langsmith/engine-notifications#mention-a-coding-agent) 打开的 merge request。
- **Linear**：Engine 不会跟踪与 [Linear issue](/langsmith/engine-issues#create-a-linear-issue) 关联的 merge request。

#### 排查 GitLab 问题

| 症状 | 检查什么 |
| --- | --- |
| **GitLab** 未出现在 **Settings** > **Integrations** 下 | 个人组织无法使用 Engine，因此 GitLab 不会显示在其中。GitLab 仅在 LangSmith Cloud 上可用。 |
| 连接失败并提示 "GitLab rejected the access token" | token 错误、已过期或已撤销。请创建一个新 token。 |
| 连接失败并提示 "the access token needs the api scope" | 创建一个具有 `api` scope 的 token。 |
| 连接失败并提示 "LangSmith needs GitLab 16.10 or later" | 升级 GitLab 实例。 |
| 连接失败并提示 "Could not reach GitLab" | 检查 URL。该实例必须能在公网 IP 地址上通过端口 443 的 HTTPS 从互联网访问。 |
| 连接失败并提示 "the GitLab connection could not be saved" | GitLab 轮换了 token，但 LangSmith 无法存储新的 token，因此你粘贴的 token 已失效。请创建一个新 token 并重新连接。 |
| GitLab 设置页面显示 **GitLab rejected the access token** | token 已被撤销或过期，或者续期未完成。请创建一个新 token，点击 **Edit connection** 并保存。 |
| GitLab 设置页面显示 **Token renewal failed** | GitLab 拒绝了计划中的续期。横幅会显示 GitLab 给出的原因。当前 token 在过期前仍可继续使用，LangSmith 会重试续期。 |
| 选择器中缺少某个项目 | 检查 GitLab 账户是否对项目具有至少 **Developer** 角色；如果选择器只显示前 20 个匹配项，请细化搜索。 |
| 项目行显示警告图标，其 tooltip 要求 **Developer** 角色 | 为该 GitLab 账户授予项目上至少 **Developer** 角色。在此之前，Engine 运行会跳过该项目。 |
| 项目行显示警告图标，其 tooltip 说明已合并的修复方案不会解决其 issue | tooltip 会给出原因，例如缺少 **Maintainer** 角色、merge request 事件已关闭，或 GitLab 无法访问 **Webhook URL**。如果 GitLab 在多次投递失败后禁用了 webhook，请在项目的 webhook 设置中重新启用。参见[合并时完成 issue](#complete-issues-on-merge)。 |
| Engine 设置显示 **Engine can't access GitLab** | workspace 的 GitLab 连接存在问题。点击 **Open GitLab settings** 查看。 |
| 无法推送修复方案 | 检查新 fix 分支的分支保护和推送规则。参见[项目政策](#project-policies)。 |

在自托管 LangSmith 上，运维人员需要先注册 GitHub App 并配置 LangSmith，然后任何人才可以连接仓库。请参阅[为自托管上的 Engine 配置 GitHub](/langsmith/engine-self-hosted-github)。

## BYOC
