LangSmith 是用于测试、部署、监控和改进 agents 的平台。保护 agents 的安全涉及谁可以访问你的组织、其 traces 会如何处理，以及他们可以使用哪些模型和工具。LangChain 以 SOC 2 Type II 鉴证以及 ISO/IEC 27001 和 42001 认证为该平台提供保障。

LangChain 与你的组织共同负责 LangSmith 的安全。[共享责任模型](/langsmith/shared-responsibility-model)说明了各项职责的归属，[BYOC 共享责任模型](/langsmith/byoc-shared-responsibility)对 Bring Your Own Cloud 也做了同样说明。如果审查人员需要了解 LangSmith 数据存放在哪里以及谁可以访问这些数据，请先阅读 [LangChain Trust Center](https://trust.langchain.com/resources) 中的 LangSmith 安全概览。

## 合规与认证

LangChain 持有每年接受审计的 SOC 2 Type II 鉴证，并拥有 ISO/IEC 27001:2022 和 ISO/IEC 42001:2023 认证。LangChain 遵守 GDPR、CCPA 和 HIPAA。

[LangChain Trust Center](https://trust.langchain.com) 发布 LangChain 的安全报告和政策，并列出 LangChain 的子处理者及其处理地点。你可以在那里申请访问以下文档：

- SOC 2 Type II 审计报告和 bridge letter
- ISO/IEC 27001:2022 证书和适用性声明
- ISO/IEC 42001:2023 证书和适用性声明
- 渗透测试执行摘要
- 共识评估倡议问卷（CAIQ）
- 安全政策

如有安全问题或报告请求，请联系 [trust@langchain.dev](mailto:trust@langchain.dev)。要报告安全事件，请联系 [security@langchain.dev](mailto:security@langchain.dev)。要报告 LangSmith 漏洞，请使用 Intigriti 上的 [LangChain VDP](https://app.intigriti.com/researcher/programs/langchain/langchain-vdp)。如涉及其他安全问题，请参见[安全政策](/oss/security-policy)。

## 部署模型

部署模型决定了由谁运维 LangSmith 的各个层，因而也决定了由谁配置和保护本页中的各项控制。

| 部署模型 | Control plane | Data plane | 数据位置 |
|-------|---------------|------------|------------------|
| [Cloud](/langsmith/cloud) | LangChain | LangChain | 注册时选择的[区域](/langsmith/cloud#regions)：GCP US、EU 或 APAC，AWS US 或 Azure US。 |
| [BYOC](/langsmith/byoc) | LangChain | LangChain，在你的云账户中 | 你的云账户，位于你选择的区域。 |
| [Self-hosted](/langsmith/self-hosted) | 你 | 你 | 你的环境，位于你运行的任意区域。 |

[Hybrid](/langsmith/hybrid) 只改变 Agent Servers 的运行位置。你托管 Agent Servers，它们将 traces 发送到 LangSmith Cloud 或自托管实例，因此 trace 数据存放在该实例运行的任何位置。

BYOC 在 AWS 上已正式发布（GA），在 GCP 和 Azure 上处于 beta。自托管 LangSmith 和 BYOC 需要 [Enterprise 方案](/langsmith/pricing-plans)。

Cloud 将组织数据存储在注册时选择的区域。你不能将组织迁移到其他区域。对于存储在区域之外的数据（例如身份验证和计费数据），请参见[区域存储](/langsmith/cloud#regional-storage)和[区域 FAQ](/langsmith/regions-faq)。

## 身份与访问

### 身份验证

单点登录（SSO）让用户通过你自己的身份提供商（IdP）进行身份验证，并且你可以要求每次登录都使用 SSO。

- **Cloud 和 BYOC**：使用 [SAML SSO](/langsmith/user-management) 搭配任意 SAML 2.0 IdP（例如 Okta 或 Microsoft Entra ID），或使用 OIDC。SAML SSO 需要 Enterprise 方案。
- **自托管**：使用[采用 OAuth 2.0 和 OIDC 的 SSO](/langsmith/self-host-sso)。

所有登录选项，请参见[身份验证方法](/langsmith/authentication-methods)。

### 授权

一个[组织](/langsmith/administration-overview#organizations)包含一个或多个[工作区](/langsmith/administration-overview#workspaces)。Tracing project、dataset 和 prompt 等资源属于某个工作区，用户在每个加入的工作区中都会获得一个角色。使用独立的工作区隔离业务单元、团队或用例。相关模式请参见[工作负载隔离](/langsmith/workload-isolation)。

工作区 RBAC、自定义角色、角色限制、ABAC 和用户组均需要 Enterprise 方案。其他方案为每个用户分配 Admin 工作区角色。

- **[基于角色的访问控制（RBAC）](/langsmith/rbac)**：分配内置的 Admin、Editor 或 Viewer 工作区角色，或使用细粒度权限构建自定义角色。将敏感角色[标记为受限](/langsmith/rbac#restrict-roles)，使只有被允许分配受限角色的成员（例如 Workspace Admins）才能分配这些角色。
- **[基于属性的访问控制（ABAC）](/langsmith/abac)**：使用基于资源标签或 root run metadata 的访问策略，缩小工作区内的访问范围。
- **[用户组](/langsmith/user-groups)**：为一组用户分配工作区成员身份和角色，而不是逐个用户分配。

### 用户预配

预配会将 LangSmith 连接到你的 IdP，使访问权限随员工生命周期变化。

- **[SCIM](/langsmith/user-management#set-up-scim-for-your-organization)**：从 IdP 添加、更新和移除用户及其角色。在 Cloud 上，SCIM 需要 SAML SSO。
- **[SSO Groups Sync](/langsmith/user-management#sso-groups-sync-alternative)**：每次登录时从 SSO token 读取组成员关系，作为 SCIM 的替代方案。
- **[JIT 预配](/langsmith/jit-invite-sso)**：当用户首次使用 SSO 登录时，将其添加到组织及其默认工作区。

## API 密钥

API 密钥用于向 LangSmith 验证你的应用和脚本。共有三种类型：

- **[个人访问令牌（PAT）](/langsmith/administration-overview#personal-access-tokens-pats)**：继承创建该密钥的用户的权限。个人脚本和工具请使用 PAT。
- **[服务密钥](/langsmith/administration-overview#service-keys)**：作用域为特定工作区或整个组织，独立于任何用户。Agents、CI 和生产服务请使用服务密钥。
- **[Tracing 密钥](/langsmith/create-account-api-key#tracing-keys)**：仅通过 tracing 摄取 API 提交 traces。使用 tracing 密钥为仅需发送 traces 的 agents 添加 instrumentation。

你可以控制密钥的有效期及其可访问范围：

- **过期**：每个密钥都可以设置过期日期。在 Enterprise 方案中，管理员还可以在 **Settings** > **Max expiry settings** 下限制 service keys 和 tracing keys 的最长有效期。已过期的密钥无法重新激活。
- **撤销**：你可以随时删除任何密钥。Organization Admins 和 Organization Operators 可以停用、重新启用或删除任何成员的 PAT。
- **作用域**：为服务密钥分配[组织角色](/langsmith/rbac#organization-roles)，并在 Enterprise 方案中分配[工作区角色](/langsmith/administration-overview#workspace-roles)（包括自定义角色），使其仅拥有集成所需的权限。

要创建和管理密钥，请参见[创建账户和 API 密钥](/langsmith/create-account-api-key)。

## 审计日志

[审计日志](/langsmith/audit-logs)记录组织中的管理和配置操作，例如成员关系和角色变更、API 密钥变更以及 SSO 配置。每条事件记录时间、操作人、操作、受影响的资源和结果。LangSmith 最多保留审计日志 400 天。

审计日志需要 Enterprise 方案。自托管 LangSmith 需要 Helm chart 0.12.33 或更高版本。

审计日志 API 以 [OCSF](https://schema.ocsf.io/) v1.7.0 API Activity 格式返回事件。要将事件拉取到 Splunk 或其他安全信息和事件管理（SIEM）工具中，请参见[将审计日志发送到 SIEM](/langsmith/audit-logs-siem)。

## 数据保护

### 传输中和静态数据

你的应用通过 SDK、REST API 或 [OpenTelemetry](/langsmith/trace-with-opentelemetry) 将 traces 发送到 LangSmith。Tracing 需要主动启用，每条 trace 包含什么由你决定。在 BYOC 和自托管部署中，trace 摄取最终落在你自己的 data plane 中。

LangSmith Cloud 使用 AES-256 加密静态数据，并使用 TLS 1.2 或更高版本加密传输中的数据。在由你运行 data plane 的部署中，你还可以使用自己的密钥：

- **AWS 上的 BYOC**：使用你自己的 AWS KMS 密钥加密 data plane。请参见[自带密钥（CMK）](/langsmith/byoc-byok-aws)。
- **Agent Server**：使用内置 AES 加密或你自己的 encryption handler 加密 checkpoint 等 agent 数据。请参见[静态加密](/langsmith/encryption)。

### 数据保留与删除

默认 trace 保留期取决于部署模型，而不是方案。你可以为 traces 选择基础或扩展保留层级。在 Cloud 上，基础保留期为 14 天，扩展保留期为 180 天。BYOC 和自托管的默认值，请参见[保留期](/langsmith/usage-and-billing#retention-periods)。

Enterprise 方案允许你为每个工作区[设置扩展保留期](/langsmith/data-purging-compliance#customize-extended-retention-policy)，在 Cloud 上为 30 到 180 天。管理员还可以关闭工作区的扩展保留。你可以随时通过 API 删除 traces 和 dataset examples。请参见[用于合规的数据清除](/langsmith/data-purging-compliance)。

Datasets 会一直保留，直到你将其删除，即使其源 traces 已过期。

### traces 中的敏感数据

LangSmith 在 trace 生命周期的每个阶段提供控制，使敏感数据不被看到。

- **在数据离开你的环境之前**：在 SDK 中[遮蔽或隐藏 trace 输入和输出](/langsmith/mask-inputs-outputs)，[脱敏 API 密钥和 token 等密钥](/langsmith/redact-secrets)，或使用你运行的 [OpenTelemetry collector 进行脱敏](/langsmith/otel-gateway-trace-redaction)。
- **在 LangSmith 内部**：使用 `runs:read-inputs` 和 `runs:read-outputs` [权限](/langsmith/rbac)限制谁可以读取 trace 输入和输出，并使用[访问策略](/langsmith/abac#control-access-to-run-inputs-and-outputs)在特定项目中隐藏它们。没有这些权限的用户仍可看到 run tree、延迟、成本和 metadata。要限制用户在项目内可读取的 traces，请使用 [root run metadata 策略](/langsmith/abac#control-trace-access-with-root-run-metadata)。
- **共享时**：在有人创建公开链接之前，traces 仅对你的工作区可见。请在 **Settings** > **Shared URLs** 下审查每个公开链接，并取消共享不再需要的链接。请参见[共享 trace](/langsmith/manage-trace#share-a-trace)。

有关输入、输出和 trace 级访问控制的完整演练，请阅读 LangChain 博客上的 [Protect sensitive data in your traces](https://www.langchain.com/blog/protect-sensitive-data-in-your-traces-new-controls-in-langsmith) 一文。

### 评估与审查功能中的数据

评估和审查功能基于 trace 数据的副本工作，其中一些会将数据发送到你选择的系统：

- **[Datasets](/langsmith/manage-datasets)**：存储你添加为 examples 的 trace 输入和输出副本。即使源 traces 已过期，datasets 仍会保留。
- **[LLM-as-judge 评估器](/langsmith/llm-as-judge)**：将评估器评分的 run 数据发送到你为该评估器选择的模型 provider。这也适用于针对生产 traces 的[在线评估器](/langsmith/online-evaluations-llm-as-judge)。
- **[自动化规则](/langsmith/rules)**：将匹配的 traces 添加到 dataset 或 annotation queue、延长其保留期，或将其发送到你选择的 [webhook](/langsmith/webhooks) endpoint。
- **[Annotation queues](/langsmith/annotation-queues)**：向工作区中的审查人员显示队列中的 runs。工作区角色和[访问策略](/langsmith/abac)决定谁可以读取队列以及审查人员使用的 datasets。

在 BYOC 和自托管部署中，datasets、experiments 和 annotation queues 会保留在你的 data plane 中。

## Agent 与模型治理

这些控制决定 agents 使用哪些模型和工具，并使 provider 凭据不暴露给最终用户。

- **[模型配置](/langsmith/model-configurations)**：选择 Playground 和评估器等 LangSmith 功能可用的模型 provider 和模型。LangSmith 在服务器端存储 provider 密钥。
- **[LLM Gateway](/langsmith/llm-gateway)**（beta）：通过 LangSmith 路由模型调用，以应用[支出策略](/langsmith/llm-gateway-spend-policies)和可对敏感数据进行脱敏的[数据策略](/langsmith/llm-gateway-data-policy)。
- **[Tool Gateway](/langsmith/tool-gateway)**（beta）：在 LangSmith 中存储 MCP server 凭据，并设置可阻止工具调用或要求审批的[策略](/langsmith/tool-gateway-policies)。
- **[Agent Auth](/langsmith/agent-auth)**（beta）：让 agents 使用 OAuth 2.0 代表用户向外部服务进行身份验证。
- **[Sandboxes](/langsmith/sandboxes)**：在隔离环境中运行 agent 生成的代码。
- **[LLM 身份验证代理](/langsmith/llm-auth-proxy-self-hosted)**：在你的环境中运行基于 Envoy 的代理，对每次模型调用进行身份验证，使 provider 凭据永远不会暴露给最终用户。LLM 身份验证代理需要 Enterprise 方案。

要在生产中标记敏感或不安全内容，请对实时 traces 运行[在线评估器](/langsmith/online-evaluations-llm-as-judge)，并使用[自动化规则](/langsmith/rules)将匹配的 traces 发送到 annotation queue 或 webhook。

[Fleet](/langsmith/fleet/access-and-oversight) 和 [Engine](/langsmith/engine-security) 建立在相同的工作区权限、保留和 masking 控制之上。二者都有各自的安全页面。

## 数据处理与模型训练

对于由 LangChain 管理模型的 AI 功能，推理通过配置为零数据保留（ZDR）的模型 provider 运行。它们与 LangChain 的协议禁止使用客户数据训练。当你使用自己的模型 provider 时，适用该 provider 的数据条款。

LangChain 为需要就 LangSmith 如何处理其数据获得合同承诺的客户提供 Enterprise 协议，即 [Enterprise 服务条款](https://www.langchain.com/terms-of-service)和 [Enterprise DPA](https://www.langchain.com/enterprise-data-processing-addendum)。根据这些条款，LangChain 不会使用客户数据训练、开发或改进其产品（包括其模型）。要了解更多信息，请[联系销售](https://www.langchain.com/contact-sales)。

## 安全最佳实践

在组织内推广 LangSmith 时，请使用以下检查清单。SSO、自定义角色、最大密钥过期时间、审计日志和保留设置需要 Enterprise 方案。

- **要求使用 SSO**：强制仅通过 SSO 登录，并使用 SCIM 或 SSO Groups Sync 预配用户，使人员离开 IdP 后访问权限随即终止。
- **授予最小权限**：为用户分配其所需的最低角色。为范围较窄的职责使用自定义角色，并将管理员级角色标记为受限。
- **谨慎选择工作区边界**：遵循[工作负载隔离](/langsmith/workload-isolation)模式，该模式建议每个业务单元使用一个工作区。将环境和客户保留在同一个工作区中，而不是为每个环境或客户创建独立工作区，否则工作区数量可能增长到数百个。
- **隐藏敏感输入和输出**：从仅需调试性能的角色中移除 `runs:read-inputs` 和 `runs:read-outputs`，再通过访问策略按项目逐一授予这些权限。
- **每个服务使用一个服务密钥**：不要在服务之间共享密钥，也不要为生产服务使用 PAT。只给每个服务密钥分配其所需的角色。
- **设置密钥过期时间并轮换密钥**：为每个密钥设置过期日期。在 Enterprise 方案中，还要为 service keys 和 tracing keys 设置最长过期时间。将密钥存储在环境变量或密钥管理器中，绝不要存储在源代码中。如果你怀疑密钥已泄露，请删除它并创建新密钥。
- **在源头脱敏**：在 traces 离开你的环境之前，在 SDK 或 OpenTelemetry collector 中遮蔽 PII 和密钥。不要发送禁止发送的数据，例如支付卡数据。
- **禁用或审查公开共享**：在 **Settings** > **Security Policies** > **Public Sharing** 下为整个组织关闭公开共享，或使用[组织 API](/langsmith/manage-organization-by-api#security-settings) 中的 `disable_public_sharing` 字段关闭。如果保留共享功能，请定期审计 **Settings** > **Shared URLs**。无论采用哪种方式，在向任何人（包括 LangChain 支持团队）共享 trace 前，请先对敏感内容进行脱敏。
- **监控审计日志**：将审计日志转发到你的 SIEM，并对角色变更、密钥创建和 SSO 配置变更设置告警。
- **使保留期符合你的策略**：在 Enterprise 方案中，将扩展保留期设置为你的用例允许的最短时间。在所有方案中，请删除不再需要的 dataset examples。
