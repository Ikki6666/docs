LangSmith 将 run 的输入、输出、错误、manifests、extras、events 和附件存储在 blob storage 中。自 LangSmith v0.18 起，blob storage 是必需的。缺少 blob storage 时，自托管 API 和队列 worker 无法启动。

如果你没有配置自己的存储，LangSmith Helm chart 会在你的集群中部署并使用兼容 S3 的对象存储 [RustFS](https://rustfs.com)。RustFS 运行在单个 pod 中，使用一个持久卷，容量取决于该卷的大小，且不提供复制。生产环境请使用你自己的 blob storage，例如 Amazon S3、Google Cloud Storage 或 Azure Blob Storage。如果你使用 [LangSmith Managed ClickHouse](/langsmith/langsmith-managed-clickhouse)，这样也能将敏感 run 数据保存在你控制的存储中。

<Tip>
**如需按云平台分别配置**，请选择你的平台：
- [Amazon S3 (AWS)](#amazon-s3)
- [Google Cloud Storage (GCP)](#google-cloud-storage)
- [Azure Blob Storage](#azure-blob-storage)
- [Neon Object Storage](#neon-object-storage)

完整的云平台专属配置与架构指南，请参见 [AWS](/langsmith/aws-self-hosted)、[GCP](/langsmith/gcp-self-hosted) 或 [Azure](/langsmith/azure-self-hosted)。
</Tip>

<a id="upgrade-to-v0-18"></a>

## 升级到 v0.18

升级到 LangSmith v0.18 时，当前 blob storage 配置决定升级行为。

- **已配置 bucket 或容器**。如果设置了 `config.blobStorage.bucketName`（S3 或 GCS）或 `config.blobStorage.azureStorageContainerName`（Azure），LangSmith 会继续使用该存储，无需更改 Helm values。
- **未配置 blob storage**。Helm chart 会部署 RustFS，LangSmith 将 blob 存储在那里。如果要使用自己的存储，请在升级前完成配置。参见[配置](#configuration)。
- **设置了 `config.blobStorage.enabled`**。Helm chart 已移除此设置，请从 Helm values 中删除它。设置 `enabled: false` 会导致 Helm chart 部署失败。
- **`engine` 为 `GCS` 或 `Azure`，且未配置 bucket 或容器**。Helm chart 部署会失败，RustFS 不会部署。请设置 bucket 或容器。

如果部署 LangSmith 时没有使用 Helm chart，请在升级前配置 blob storage。服务读取与 Helm chart 相同的 `BLOB_STORAGE_ENGINE`、`S3_BUCKET_NAME` 和 `AZURE_STORAGE_CONTAINER_NAME` 设置。

<a id="use-the-bundled-rustfs"></a>

## 使用内置 RustFS

当 `config.blobStorage.external.enabled` 为 `false`，且未设置 `bucketName` 和 `azureStorageContainerName` 时，Helm chart 会部署 RustFS。它会创建一个名为 `langsmith` 的 bucket，并配置 LangSmith 服务使用该 bucket。内置 RustFS 适用于开发和评估环境。

在 Helm values 的 `rustfs` 下进行配置。

- **卷大小**。`rustfs.statefulSet.persistence.size` 设置持久卷大小，默认为 `50Gi`。使用 `storageClassName` 选择存储类。如果未启用持久化，RustFS pod 重启后，已存储的 trace 将丢失。
- **凭据**。访问密钥为 `langsmith`。如果 `rustfs.secretKey` 为空，Helm chart 会保留之前安装时的 secret key，或从 `config.apiKeySalt` 派生一个密钥，确保每次渲染都使用同一密钥。要指定密钥，请设置 `rustfs.secretKey`，或将 `rustfs.existingSecretName` 设置为包含 `access_key` 和 `secret_key` 的 Kubernetes secret。
- **安全上下文**。RustFS 以用户和组 `10001` 运行，并通过 `fsGroup: 10001` 获得卷的写入权限。对于会分配用户 ID 的平台，例如使用 `restricted-v2` 安全上下文约束的 OpenShift，请将 `rustfs.statefulSet.podSecurityContext` 下的 `runAsUser`、`runAsGroup` 和 `fsGroup` 设为 `null`。

```yaml Helm
rustfs:
  statefulSet:
    persistence:
      size: 100Gi
      storageClassName: "your-storage-class"
```

<Note>
如果使用 `config.existingSecretName`，并像 Argo CD 一样在没有集群访问权限的情况下渲染 Helm chart，Helm values 中就没有 `config.apiKeySalt`。此时请设置 `rustfs.secretKey` 或 `rustfs.existingSecretName`，否则每次渲染都会生成新的随机 secret key。
</Note>

RustFS 支持只读根文件系统。在 `rustfs.statefulSet.securityContext` 和 `rustfs.bucketJob.securityContext` 中设置 `readOnlyRootFilesystem: true`。

## 要求

使用自己的 blob storage 时，需要满足以下要求。

<Note>
Azure blob storage 从 Helm chart `0.8.9` 及以上版本可用。[删除 trace 项目](/langsmith/observability-concepts#data-retention) 从 Helm chart `0.10.43` 开始在 Azure 中受支持。

原生 GCS blob storage engine 支持（使用 `engine: "GCS"`）从 Helm chart `0.13.29` 及以上版本可用。对于更早版本，可以通过设置 `engine: "S3"` 并使用 HMAC 凭据，借助兼容 S3 的 API 来支持 GCS。
</Note>

* 可用的 blob storage 服务访问权限

  * [Amazon S3](https://aws.amazon.com/s3/)
  * [Google Cloud Storage (GCS)](https://cloud.google.com/storage?hl=en)
  * [Azure Blob Storage](https://azure.microsoft.com/en-us/products/storage/blobs)
  * [Neon Object Storage](https://neon.com/docs/storage/get-started)（兼容 S3）

* 一个用于存储数据的 bucket 或目录。强烈建议为 LangSmith 数据单独创建 bucket 或目录。
  * **如果你启用了 TTL**，则需要设置生命周期策略来删除旧数据。更多信息请参见 [配置 TTL](/langsmith/self-host-ttl)。这些策略应与你在 LangSmith 配置中设置的 TTL 保持一致，否则可能会发生数据丢失。关于如何设置生命周期规则，请参见 [blob storage 的 TTL 配置](#ttl-configuration)。
  * 如果你使用自动化规则，请单独配置[自动化结果保留](#automation-outcome-retention)，即使 trace TTL 已禁用。

* 允许 LangSmith Services 访问该 bucket 或目录的凭据
  * 你需要为 LangSmith 实例提供访问该 bucket 或目录所需的凭据。更多信息请阅读下方的认证[章节](#authentication)。

* 如果使用 S3 或 GCS，还需要提供 blob storage 服务的 API URL

  * 这是 LangSmith 访问你的 blob storage 系统时使用的 URL
  * 对于 Amazon S3，它应为 S3 endpoint 的 URL，例如：`https://s3.amazonaws.com`，如果使用区域 endpoint，也可以是 `https://s3.us-west-1.amazonaws.com`
  * 对于 Google Cloud Storage，它应为 GCS endpoint 的 URL，例如：`https://storage.googleapis.com`
  * 对于 Neon Object Storage，它是你的 Neon branch 的 storage endpoint，例如：`https://br-cool-darkness-a1b2c3d4.storage.c-1.us-east-2.aws.neon.tech`

## 认证

### Amazon S3

要认证到 [Amazon S3](https://aws.amazon.com/s3/)，你需要创建一个 IAM policy，为你的 bucket 授予以下权限。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::your-bucket-name",
        "arn:aws:s3:::your-bucket-name/*"
      ]
    }
  ]
}
```

有了正确的 policy 之后，可以通过以下三种方式认证到 Amazon S3：

1. [IAM Roles for Service Accounts (IRSA)](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html)（推荐）：你可以为 LangSmith 实例创建一个 IAM role，并将该 policy 附加到这个 role 上。这是在生产环境中认证到 Amazon S3 的推荐方式。
    1. 你需要创建一个附带该 policy 的 IAM role。
    1. 你需要允许 LangSmith service accounts 来 assume 这个 role。`langsmith-queue`、`langsmith-backend`、`langsmith-platform-backend` 和 `langsmith-ingest-queue` 这些 service accounts 都需要能够 assume 该 role。
        <Warning>
        如果你使用了自定义 release name，service account 名称会有所不同。你可以在集群中运行 `kubectl get serviceaccounts` 来查看 service account 名称。
        </Warning>
    1. 你需要将 role ARN 提供给 LangSmith。可以在 Helm Chart 安装中，为 `queue`、`backend`、`platform-backend` 和 `ingest-queue` 服务添加 `eks.amazonaws.com/role-arn: "<role_arn>"` annotation 来完成。

2. [Access Key and Secret Key](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html)：你可以向 LangSmith 提供 access key 和 secret key。这是最简单的认证方式，但由于安全性较低，不建议在生产环境中使用。
    1. 你需要创建一个附加该 policy 的用户，然后为其生成 access key 和 secret key。

3. [VPC Endpoint Access](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-s3.html)：你可以通过 VPC endpoint 启用对 S3 bucket 的访问，让流量能够从你的 VPC 安全地进入 S3 bucket。
    1. 你需要创建一个 VPC endpoint，并配置它允许访问你的 S3 bucket。
    1. 你可以参考我们的[公开 Terraform modules](https://github.com/langchain-ai/terraform/tree/main/modules/aws) 获取指导和配置示例。

### KMS encryption header 支持

从 LangSmith Helm chart **0.11.24** 开始，你可以通过传递 KMS encryption key header 并提供其 ARN，强制写入时使用特定的 KMS key。要启用它，请在 Helm chart 中设置以下值：

```yaml
config:
  blobStorage:
    kmsEncryptionEnabled: true
    kmsKeyArn: <your_kms_key_arn>
```

### Google Cloud Storage

要认证到 [Google Cloud Storage](https://cloud.google.com/storage?hl=en)，你需要创建一个具有访问 bucket 所需权限的 [`service account`](https://cloud.google.com/iam/docs/service-account-overview)。

这个 service account 需要拥有 `Storage Admin` 角色，或者拥有等效权限的自定义角色。权限范围可以仅限于 LangSmith 使用的那个 bucket。

准备好 service account 后，你需要为它生成一个 [`HMAC key`](https://cloud.google.com/storage/docs/authentication/hmackeys)。这个 key 和 secret 会用于认证到 Google Cloud Storage。

<Note>
从 Helm chart **0.13.29** 开始，你可以直接将 blob storage engine 设置为 `"GCS"`。这支持两种认证方式：

1. **GCP Workload Identity（推荐）**：将 `accessKey` 和 `accessKeySecret` 留空。LangSmith 会使用 [Application Default Credentials](https://cloud.google.com/docs/authentication/application-default-credentials)。你需要为 `backend`、`platform-backend`、`queue` 和 `ingest-queue` service accounts 添加 workload identity annotation。
2. **HMAC keys**：将 `accessKey` 和 `accessKeySecret` 设置为你的 GCS [HMAC 凭据](https://cloud.google.com/storage/docs/authentication/hmackeys)。

这两种方式都需要将 `apiURL` 设置为 `https://storage.googleapis.com`，并将 `bucketName` 设置为你的 GCS bucket 名称。

对于 Helm chart `0.13.29` 之前的版本，GCS 通过兼容 S3 的 API 来支持，配置方式是设置 `engine: "S3"` 并使用 HMAC 凭据。
</Note>

  </Tab>

### Azure Blob Storage

要认证到 [Azure Blob Storage](https://azure.microsoft.com/en-us/products/storage/blobs)，你需要使用以下任一方式授予 LangSmith workloads 访问 [container](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blobs-introduction#containers) 的权限（按优先级排序）：

1. [Storage account and access key](https://learn.microsoft.com/en-us/azure/storage/common/storage-account-keys-manage)
2. [Connection string](https://learn.microsoft.com/en-us/azure/storage/common/storage-configure-connection-string)
3. [Workload identity](https://azure.github.io/azure-workload-identity/docs/introduction.html)（推荐）、managed identity，或 [`DefaultAzureCredential`](https://learn.microsoft.com/en-us/azure/developer/go/azure-sdk-authentication?tabs=bash#2-authenticate-with-azure) 支持的环境变量。如果前两种配置都没有提供，这会成为默认认证方式。
   1. 如果要使用 workload identity，请为 `queue`、`backend`、`platform-backend` 和 `ingest-queue` deployments 添加 `azure.workload.identity/use: true` label。另外，还需要为对应的 service accounts 添加 `azure.workload.identity/client-id` annotation，其值应为现有 Azure AD Application 的 client ID 或 user-assigned managed identity 的 client ID。更多细节请参见 [Azure 文档](https://azure.github.io/azure-workload-identity/docs/topics/service-account-labels-and-annotations.html)。

<Note>
某些部署可能需要进一步自定义连接配置，即使用 Service URL Override，而不是默认的服务 URL（`https://<storage_account_name>.blob.core.windows.net/`）。例如，如果你要使用不同的 blob storage 域名（如政府云或中国区域），就需要这个 override。
</Note>

### Neon Object Storage

[Neon Object Storage](https://neon.com/docs/storage/get-started) 是挂载到 Neon branch 的兼容 S3 的对象存储。LangSmith 使用 `S3` engine 以及 access key 和 secret key 连接到它。

要为 LangSmith 设置 Neon Object Storage：

1. 在你的 Neon branch 上创建一个私有 bucket，例如 `langsmith`。更多信息请参见 [Neon buckets](https://neon.com/docs/storage/buckets)。
2. 创建一个同时具有 `storage:read` 和 `storage:write` scope 的凭据。LangSmith 会读取、写入和删除对象，因此需要这两个 scope：

    ```bash
    neon credentials create --scope storage:read --scope storage:write --name langsmith-blob-storage
    ```

3. 将该凭据的 `token_id`（以 `nak_live_` 开头）用作 `accessKey`，将其 `s3_secret_access_key`（以 `nsk_live_` 开头）用作 `accessKeySecret`。更多信息请参见 [Neon Object Storage authentication](https://neon.com/docs/storage/authentication)。
4. 将该 branch 的 storage endpoint 用作 `apiURL`。在 Neon Console 中点击 **Connect** 并打开 **Storage** 选项卡，即可找到它，字段名为 `AWS_ENDPOINT_URL_S3`。
5. 在你的[配置](#configuration)中设置 `s3UsePathStyle: true`：

    ```yaml
    config:
      blobStorage:
        external:
          enabled: true
        engine: "S3"
        bucketName: "langsmith"
        apiURL: "https://br-cool-darkness-a1b2c3d4.storage.c-1.us-east-2.aws.neon.tech"
        accessKey: "nak_live_..."
        accessKeySecret: "nsk_live_..."
        s3UsePathStyle: true
    ```

<Warning>
Neon Object Storage 仅通过 path-style URL（`<apiURL>/<bucket>/<key>`）提供 bucket 访问。如果不设置 `s3UsePathStyle: true`，LangSmith 会将请求发送到 `<bucket>.<endpoint>`，由于 Neon 证书不覆盖该主机名，TLS 校验会失败。`s3UsePathStyle` 需要 Helm chart 0.12.4 或更高版本。
</Warning>

Neon 不会执行 lifecycle rule，因此在启用 [TTL](#ttl-configuration) 之前，请先规划好数据过期方式。更多信息请参见 [Neon Object Storage lifecycle rules](#neon-object-storage-lifecycle-rules)。

  </Tab>

## CH search

默认情况下，LangSmith 仍然会把用于搜索的 tokens 存储在 ClickHouse 中。如果你使用的是 LangSmith Managed Clickhouse，你可能希望禁用这个功能，以避免将潜在敏感信息发送到 ClickHouse。你可以在 blob storage 配置中关闭它。

## 配置

创建 bucket 并获取所需凭据后，配置 LangSmith 使用你的 blob storage 系统。设置 `external.enabled: true`，使 Helm chart 跳过 RustFS 部署。

```yaml Helm
config:
  blobStorage:
    external:
      enabled: true # Use your own storage instead of the bundled RustFS
    engine: "S3" # Or "GCS" or "Azure". This is case-sensitive.
    chSearchEnabled: true # Set to false if you want to disable CH search (Recommended for LangSmith Managed Clickhouse)
    bucketName: "your-bucket-name"
    apiURL: "Your connection url"
    accessKey: "Your access key" # Optional. Only required if using S3 access key and secret key
    accessKeySecret: "Your access key secret" # Optional. Only required if using access key and secret key
    s3UsePathStyle: false # Optional. Set to true for S3-compatible services that require path-style URLs, such as Neon Object Storage or MinIO
    # The following blob storage configuration values are for Azure and require blobStorage.engine = "Azure". Omit otherwise.
    azureStorageAccountName: "Your storage account name" # Optional. Only required if using storage account and access key.
    azureStorageAccountKey: "Your storage account access key" # Optional. Only required if using storage account and access key.
    azureStorageContainerName: "your-container-name" # Required
    azureStorageConnectionString: "" # Optional.
    azureStorageServiceUrlOverride: "" # Optional
  backend: # Optional, only required if using IAM role for service account on AWS, workload identity on GKE, or workload identity on AKS
    deployment: # Azure only
      labels:
        azure.workload.identity/use: true
    serviceAccount:
      annotations:
        azure.workload.identity/client-id: "<client_id>" # Azure only
        eks.amazonaws.com/role-arn: "<role_arn>" # AWS only
        iam.gke.io/gcp-service-account: "<gsa_name>@<project_id>.iam.gserviceaccount.com" # GCP only
  platformBackend: # Optional, only required if using IAM role for service account on AWS, workload identity on GKE, or workload identity on AKS
    deployment: # Azure only
      labels:
        azure.workload.identity/use: true
    serviceAccount:
      annotations:
        azure.workload.identity/client-id: "<client_id>" # Azure only
        eks.amazonaws.com/role-arn: "<role_arn>" # AWS only
        iam.gke.io/gcp-service-account: "<gsa_name>@<project_id>.iam.gserviceaccount.com" # GCP only
  queue: # Optional, only required if using IAM role for service account on AWS, workload identity on GKE, or workload identity on AKS
    deployment: # Azure only
      labels:
        azure.workload.identity/use: true
    serviceAccount:
      annotations:
        azure.workload.identity/client-id: "<client_id>" # Azure only
        eks.amazonaws.com/role-arn: "<role_arn>" # AWS only
        iam.gke.io/gcp-service-account: "<gsa_name>@<project_id>.iam.gserviceaccount.com" # GCP only
  ingestQueue: # Optional, only required if using IAM role for service account on AWS, workload identity on GKE, or workload identity on AKS
    deployment: # Azure only
      labels:
        azure.workload.identity/use: true
    serviceAccount:
      annotations:
        azure.workload.identity/client-id: "<client_id>" # Azure only
        eks.amazonaws.com/role-arn: "<role_arn>" # AWS only
        iam.gke.io/gcp-service-account: "<gsa_name>@<project_id>.iam.gserviceaccount.com" # GCP only
```

<Note>
如果使用 access key 和 secret，也可以提供一个已经存在的 Kubernetes secret，让它来保存认证信息。相比直接在配置中填写 access key 和 secret key，这种方式更推荐。所需 secret keys 的格式可参考[生成的 secret template](https://github.com/langchain-ai/helm/blob/main/charts/langsmith/templates/secrets.yaml)。
</Note>

## TTL 配置

如果在 LangSmith 中使用了 [TTL](/langsmith/self-host-ttl) 功能，你还需要为 blob storage 配置 TTL 规则。存储在 blob storage 中的 trace 信息会放在特定的 prefix 路径下，该路径决定了数据的 TTL。当某条 trace 的保留期被延长时，对应的 blob storage 路径也会变化，以确保它匹配新的延长保留期。

系统使用以下 TTL prefixes：

* `ttl_s/`：短期（基础）TTL，配置为 14 天。
* `ttl_l/`：长期（扩展）TTL，默认配置为 400 天。

<a id="custom-workspace-level-retention-prefixes"></a>
<a id="custom-retention-prefixes"></a>

### 自定义保留前缀

如果你使用[工作区级扩展保留期](/langsmith/data-purging-compliance#customize-extended-retention-policy)或[项目级扩展保留期](/langsmith/data-purging-compliance#project-level-extended-retention-for-self-hosted)，LangSmith 会将 blob 数据写入形如 `ttl_XXd/` 的前缀，其中 `XX` 是为该工作区或项目配置的天数。例如，如果某个工作区配置了 90 天扩展保留期，则该工作区的 blob 数据会写入 `ttl_90d/` 前缀。

你必须为工作区和项目中使用的**每一种**自定义保留期分别创建生命周期规则。如果你设置了[用户可选的保留期](/langsmith/self-host-ttl#choose-the-extended-retention-periods-users-can-pick)，请在用户选择前，为列表中的每个值创建对应的规则。常见示例包括：

* `ttl_90d/` — 90 天保留
* `ttl_180d/` — 180 天保留
* `ttl_365d/` — 365 天保留

<Warning>
如果某个已配置保留周期缺少对应的 lifecycle rule，则该前缀下的 blob 数据永远不会被自动删除。每当配置新的 workspace 保留周期时，都要确保增加匹配的 lifecycle rule。
</Warning>

例如，如果你的 workspaces 中配置了 90 天和 180 天的扩展保留期，那么除了默认的 [`ttl_s` 和 `ttl_l` 规则](#ttl-configuration)之外，还需要增加以下 lifecycle rules：

<Tabs>
  <Tab title="AWS">

```hcl
rule {
  id      = "ttl-90d"
  prefix  = "ttl_90d/"
  enabled = true
  expiration {
    days = 90
  }
}
rule {
  id      = "ttl-180d"
  prefix  = "ttl_180d/"
  enabled = true
  expiration {
    days = 180
  }
}
```

  </Tab>
  <Tab title="GCP">

```hcl
lifecycle_rule {
  condition {
    age            = 90
    matches_prefix = ["ttl_90d"]
  }
  action {
    type = "Delete"
  }
}
lifecycle_rule {
  condition {
    age            = 180
    matches_prefix = ["ttl_180d"]
  }
  action {
    type = "Delete"
  }
}
```

  </Tab>
  <Tab title="Azure">

```hcl
rule {
  name    = "ttl-90d"
  enabled = true
  type    = "Lifecycle"
  filters {
    prefix_match = ["my-container/ttl_90d"]
    blob_types   = ["blockBlob"]
  }
  actions {
    base_blob {
      delete_after_days_since_creation_greater_than = 90
    }
    snapshot {
      delete_after_days_since_creation_greater_than = 90
    }
    version {
      delete_after_days_since_creation_greater_than = 90
    }
  }
}
rule {
  name    = "ttl-180d"
  enabled = true
  type    = "Lifecycle"
  filters {
    prefix_match = ["my-container/ttl_180d"]
    blob_types   = ["blockBlob"]
  }
  actions {
    base_blob {
      delete_after_days_since_creation_greater_than = 180
    }
    snapshot {
      delete_after_days_since_creation_greater_than = 180
    }
    version {
      delete_after_days_since_creation_greater_than = 180
    }
  }
}
```

  </Tab>
  <Tab title="Neon">

Neon Object Storage 不会执行 lifecycle rule。请确保你的[清理任务](#neon-object-storage-lifecycle-rules)会在对象超过对应前缀的 TTL 后，删除 `ttl_90d/`、`ttl_180d/` 等每个自定义前缀下的对象。

  </Tab>
</Tabs>

如果你自定义了 LangSmith 配置中的 TTL，那么也需要同步调整 blob storage 配置中的 TTL。

<Tabs>
  <Tab title="AWS">

### Amazon S3 lifecycle rules

如果使用 S3 作为 blob storage，则需要配置与上述 prefixes 匹配的 filter lifecycle configuration。你可以在[Amazon 文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html#intro-lifecycle-rules-filter)中找到相关说明。

例如，如果你使用 Terraform 管理 S3 bucket，可以配置如下：

```hcl
rule {
  id      = "short-term-ttl"
  prefix  = "ttl_s/"
  enabled = true
  expiration {
    days = 14
  }
}
rule {
  id      = "long-term-ttl"
  prefix  = "ttl_l/"
  enabled = true
  expiration {
    days = 400
  }
}
```

  </Tab>
  <Tab title="GCP">

### Google Cloud Storage lifecycle rules

你需要为使用中的 GCS buckets 配置 lifecycle conditions。你可以在[Google 文档](https://cloud.google.com/storage/docs/lifecycle#conditions)中找到相关说明，这里尤其需要使用 `matchesPrefix`。

例如，如果你使用 Terraform 管理 GCS bucket，可以配置如下：

```hcl
lifecycle_rule {
  condition {
    age            = 14
    matches_prefix = ["ttl_s"]
  }
  action {
    type = "Delete"
  }
}
lifecycle_rule {
  condition {
    age            = 400
    matches_prefix = ["ttl_l"]
  }
  action {
    type = "Delete"
  }
}
```

  </Tab>
  <Tab title="Azure">

### Azure blob storage lifecycle management

你需要在 container 上配置一个 [lifecycle management policy](https://learn.microsoft.com/en-us/azure/storage/blobs/lifecycle-management-policy-configure)，以便让匹配上述 prefixes 的对象过期删除。

例如，如果你[使用 Terraform 管理 blob storage container](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/storage_management_policy)，可以配置如下：

```hcl
resource "azurerm_storage_management_policy" "example" {
  storage_account_id = "my-storage-account-id"
  rule {
    name = "base"
    enabled = true
    type = "Lifecycle"
    filters {
      prefix_match = ["my-container/ttl_s"]
      blob_types = ["blockBlob"]
    }
    actions {
      base_blob {
        delete_after_days_since_creation_greater_than = 14
      }
      snapshot {
        delete_after_days_since_creation_greater_than = 14
      }
      version {
        delete_after_days_since_creation_greater_than = 14
      }
    }
  }
  rule {
    name = "extended"
    enabled = true
    type = "Lifecycle"
    filters {
      prefix_match = ["my-container/ttl_l"]
      blob_types = ["blockBlob"]
    }
    actions {
      base_blob {
        delete_after_days_since_creation_greater_than = 400
      }
      snapshot {
        delete_after_days_since_creation_greater_than = 400
      }
      version {
        delete_after_days_since_creation_greater_than = 400
      }
    }
  }
}
```

  </Tab>
  <Tab title="Neon">

### Neon Object Storage lifecycle rules

<Warning>
Neon Object Storage 会接受并存储 lifecycle 配置，但不会执行过期规则。`ttl_s/`、`ttl_l/` 和 `ttl_XXd/` 前缀下的对象不会被自动删除，因此 blob 数据的存续时间会超过在 LangSmith 中配置的 TTL。更多信息请参见 [Neon Object Storage troubleshooting](https://neon.com/docs/storage/troubleshooting)。
</Warning>

要强制执行 TTL，请运行一个定时任务（例如 Kubernetes CronJob），删除超过各前缀 TTL 的对象。
  </Tab>
</Tabs>

## 自动化结果保留

[自动化规则](/langsmith/rules)可以将结果详情存储在 LangSmith blob storage bucket 或 container 中的 `run_rules/outcomes/` 下。请配置一条生命周期规则，使这些对象在 30 天后过期。此策略独立于 trace 保留，且不适用于其他 `run_rules/` 对象或 SmithDB 数据。

<Warning>
请将此规则添加到现有的生命周期配置中。不要替换针对 `ttl_s/`、`ttl_l/` 或自定义保留前缀的现有规则。在任何灾难恢复 bucket 上也要保持相同的规则。

该规则同时覆盖现有对象和未来对象。策略生效后，超过 30 天的现有对象将符合删除条件。对象年龄基于存储时间戳，而不是对象名称中的时间戳。生命周期处理是异步的，因此 30 天并非精确的删除截止期限。
</Warning>

<Tabs>
  <Tab title="AWS">

将此规则添加到现有的 `aws_s3_bucket_lifecycle_configuration` 资源中：

```hcl
rule {
  id     = "automation-outcomes"
  status = "Enabled"
  filter {
    prefix = "run_rules/outcomes/"
  }
  expiration {
    days = 30
  }
  noncurrent_version_expiration {
    noncurrent_days = 30
  }
}
```

在启用版本控制的 bucket 中，过期会添加删除标记，而不是永久删除当前版本。该示例还会在非当前版本变为非当前状态 30 天后将其删除。这可能会使数据在实际上传 30 天后仍被保留。请审查这一额外保留期以及你针对已过期删除标记的清理规则。请参见 [S3 生命周期操作](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html#intro-lifecycle-rules-actions)。

  </Tab>
  <Tab title="GCP">

将此代码块添加到现有的 `google_storage_bucket` 资源中：

```hcl
lifecycle_rule {
  condition {
    age            = 30
    matches_prefix = ["run_rules/outcomes/"]
  }
  action {
    type = "Delete"
  }
}
```

不要将该规则限制为仅作用于活动对象。在没有 `is_live` 条件的情况下，它也会覆盖非当前版本。软删除的对象在该 bucket 的软删除保留期内仍可恢复。请参见 [Cloud Storage 生命周期管理](https://cloud.google.com/storage/docs/lifecycle)。

  </Tab>
  <Tab title="Azure">

将此规则添加到现有的 `azurerm_storage_management_policy` 资源中。请将 `my-container` 替换为你的 LangSmith container 名称：

```hcl
rule {
  name    = "automation-outcomes"
  enabled = true
  filters {
    prefix_match = ["my-container/run_rules/outcomes/"]
    blob_types   = ["blockBlob"]
  }
  actions {
    base_blob {
      delete_after_days_since_modification_greater_than = 30
    }
    snapshot {
      delete_after_days_since_creation_greater_than = 30
    }
    version {
      delete_after_days_since_creation = 30
    }
  }
}
```

base blob 根据其最后修改时间过期。快照和先前版本根据其创建时间过期。软删除可能会使已删除的 blob 在这些期限之后仍被保留。请参见 [Azure 生命周期删除策略](https://learn.microsoft.com/en-us/azure/storage/blobs/lifecycle-management-policy-delete)。

  </Tab>
  <Tab title="MinIO">

使用 MinIO 客户端添加一条限定前缀的过期规则。请将 `myminio/my-bucket` 替换为你配置的 alias 和 LangSmith bucket：

```bash
mc ilm rule add --prefix "run_rules/outcomes/" --expire-days 30 --noncurrent-expire-days 30 myminio/my-bucket
```

与 S3 一样，非当前版本的保留期从版本变为非当前状态时开始计算，而不是从上传时开始。MinIO 的 scanner 会异步处理过期规则。请参见 [MinIO 生命周期规则配置](https://docs.min.io/aistor/reference/cli/mc-ilm-rule/mc-ilm-rule-add/)。

  </Tab>
  <Tab title="Neon">

Neon 不会运行生命周期过期规则。请扩展你的[定时清理任务](#neon-object-storage-lifecycle-rules)，删除 `run_rules/outcomes/` 下超过 30 天的对象。

  </Tab>
</Tabs>

对象锁定、法律保留和存储保留策略可能会阻止删除。在依赖生命周期规则进行永久删除之前，请结合版本控制、快照和软删除一起审查这些设置。
