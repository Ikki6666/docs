每个 LLM Gateway 请求（包括被阻止或失败的请求）都会生成一条 LangSmith trace。该 trace 会把 provider 尝试、策略检查和 LLM runs 组织在一个 `gateway.request` root run 之下。策略违规会出现在 [LangSmith Engine](/langsmith/engine) 中，供分类处理。

## 查找 gateway traces

每个 gateway 请求都会追踪到调用方 API key 所关联[工作区](/langsmith/administration-overview#workspaces)中名为 `gateway` 的 project。要查看 gateway 请求，请前往 **LLM Gateway** 并选择 **Traces** 标签页。Simulator 的 **View trace** 按钮会在该标签页中打开其请求。要查看某个用户或 API key 支出背后的请求，请在 [**Usage** 标签页](/langsmith/llm-gateway-monitoring#analyze-the-chart-and-table)中选择该用户或 key，然后单击 **View traces**。在 Developer 方案中，请改为打开工作区中的 `gateway` tracing project。

对所有组织而言，trace 内容（请求和响应 body）默认关闭，因此 gateway traces 只记录 metadata，例如 token 数量、策略结果和调用方身份。这些 traces 的 `ls_metadata_only` 为 `true`。不含内容的 traces 不计入你的 LangSmith trace 配额。要存储内容，请在 [data policy](/langsmith/llm-gateway-data-policy#data-retention) 中开启 **Trace content**。无论进行了多少次 provider 尝试，一条记录了内容的请求都只会按一次计入你方案的 trace 用量。

<Note>
任何可以查看工作区中 runs 的用户都可以查看该工作区的 gateway traces。要限制访问，请参阅[限制 trace 可见性](#restrict-trace-visibility)。
</Note>

## 解读 trace 树

展开 `gateway.request` 可以查看每次尝试。每次尝试都有自己的策略检查和 provider 调用，因此一次发生回退（fallback）的请求会按每次尝试重复下面的结构：

```text
gateway.request
├─ gateway.attempt #1
│  ├─ gateway.policy_check
│  │  └─ policy: <name>
│  ├─ gateway.data_policy
│  │  └─ policy: <name>
│  │     └─ rule: <rule_id>
│  └─ <provider LLM run>
└─ gateway.attempt #2
   └─ …
```

gateway 专属的 key 以 `gateway.` 为前缀出现在每个 run 的 metadata 中，并记录为 `langsmith.metadata.gateway.*` span attributes。gateway 会自行设置这些 key，因此客户端无法通过请求 headers 覆盖它们。下面按 run 列出最值得检查的 key：

- **`gateway.request`**：root run，展示该请求的最终结果。
  - `gateway.request.outcome` 取值为 `success`、`upstream_error`、`blocked`、`rejected` 或 `fallback_exhausted`。
  - `gateway.request.error_reason` 说明请求被阻止或被拒绝的原因。被限流的请求 outcome 为 `blocked`、error reason 为 `rate_limit`，并没有单独的 `throttled` outcome。
  - `gateway.request.served_model` 指明实际应答的模型。
  - `gateway.request.id` 用于关联该请求的 root、attempt、策略和 provider runs，批量导出中同样适用。
- **`gateway.attempt #N`**：一个模型候选项，即主模型、[fallback](/langsmith/llm-gateway-fallbacks) 或 `/routes` 候选项。尝试不一定都会发起 provider 调用。
  - `gateway.attempt.outcome` 记录该次尝试的结果。因冷却期被跳过的候选项 outcome 为 `skipped`，且没有 provider LLM run。`skipped` 只是尝试级 outcome，不会作为请求级 outcome。
  - `gateway.attempt.upstream_status_code` 在调用失败时记录 provider 返回的状态码。
- **`gateway.policy_check`**：针对[支出](/langsmith/llm-gateway-spend-policies)、[速率限制](/langsmith/llm-gateway-rate-limit-policies)、[模型访问](/langsmith/llm-gateway-model-access-policies)和路由策略的检查。该 run 表明 gateway 已针对本次尝试评估过策略。为保持 trace 简洁，只有拒绝或限流该请求的策略才会以 `policy: <name>` 子 run 的形式出现。
  - 每个 `policy: <name>` run 上的 `gateway.policy.action` 记录该策略是拒绝了请求还是对其限流。
  - `gateway.policy.matched_names` 列出所有匹配的策略名称，包括未拒绝或未限流该请求的策略。
- **`gateway.data_policy`**：[data policy](/langsmith/llm-gateway-data-policy) 对 PII 和 secrets 的扫描，与策略检查分开执行。对内容做了脱敏或阻止的 data policy 会以 `policy: <name>` 子 run 出现，命中的每条规则各对应一个 `rule: <rule_id>` run。
  - 每个 `rule: <rule_id>` run 上的 `gateway.rule.matches` 统计该规则的命中次数。
- **Provider LLM run**：实际发起时对 provider 的调用。选中它可以查看 token 用量、成本，以及在开启 trace 内容时查看请求和响应。
  - `ls_model_name` 和 `ls_provider` 标识模型和 provider。这些 key 位于 provider LLM run 上，而不是 root run 上。
  - `gateway.credential_source` 记录为这次调用付费的凭证，例如工作区 provider key 对应的 `byok`，或 [Gateway Credits](/langsmith/llm-gateway-credits) 对应的 `credits`。

<Note>
被阻止的尝试可能有策略 runs，但没有 provider LLM run。在任何尝试之前就被拒绝的请求只有 root run。
</Note>

## 按调用方过滤 traces

root run 和 provider LLM runs 记录了请求的发起者。下面的 key 最适合用来查找某个调用方的 traces：

- **`gateway.api_key_id`**：发起请求的 API key。
- **`gateway.user_id`**：发起请求的用户。仅为 personal access tokens 设置，因此使用 service key 的请求没有用户。
- **`gateway.<name>`**：每个 `X-Gateway-*` 请求 header。关于名称的规范化方式，请参见 [Matchable headers](/langsmith/llm-gateway-header-policies#matchable-headers)。

## 限制 trace 可见性

<a id="restrict-trace-visibility"></a>

gateway traces 是工作区 project 中的 runs，因此它们与其他工作区 runs 受相同的权限管控。在工作区中拥有 `runs:read`（以及查看 project 本身所需的 `projects:read`）的任何用户都可以查看该工作区 gateway project 中的 traces。内置的 Workspace Admin、Workspace Editor 和 Workspace Viewer [角色](/langsmith/rbac#workspace-roles)默认都包含这两项权限。

要限制对 gateway traces 的访问，有两种选择：

- **独立的工作区**（适用于任何[方案](/langsmith/pricing-plans)）：创建一个成员受限的工作区，再为开发者 coding agents 创建一个成员范围更广的工作区。每个工作区都有自己的 provider secrets 和 trace projects。
- **Project 级访问策略**（需要 [Enterprise 方案](/langsmith/pricing-plans)）：编写一个 [ABAC](/langsmith/abac) 策略，把 gateway project 上的 `projects:read` 和 `runs:read` 限制给特定用户或角色。

## 分类处理策略违规

当治理策略触发时（例如达到支出限制、PII 被脱敏，或捕获到 secret），该事件会作为 metadata 记录在 trace 上。这些策略违规会作为 [LangSmith Engine 中的问题](/langsmith/engine-issues)出现。

在 Engine 问题中，你可以：

1. **查看违规内容：** 找出哪条策略触发，以及它阻止或脱敏了什么。
1. **点击进入 trace：** 准确查看策略触发时 agent 正在做什么。
1. **诊断根本原因：** 例如重试循环消耗了预算、用户把凭证粘贴到了 prompt 中，或合法工作负载超出了上限。
1. **采取行动：** 更新 agent 的配置、调整策略，或上报处理。
