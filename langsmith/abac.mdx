基于属性的访问控制（ABAC）允许组织管理员根据资源的属性授予或限制对 LangSmith 资源的访问。

它构建在[基于角色的访问控制（RBAC）](/langsmith/rbac)之上。角色会在整个工作区范围内授予某项权限，例如读取所有 project。访问策略则会将这项权限收窄或扩展到属性匹配的资源，例如带有 `Environment=Development` 标签的 projects。

访问策略可以匹配两类属性：

- **资源标签**（`resource_tag_key`）：projects、datasets、prompts 以及其他工作区资源上的[资源标签](/langsmith/set-up-resource-tags)。
- **Root run metadata**（`root_run_metadata`）：每条 trace 的 root run 上的 metadata。用它来控制用户在某个 project 内可以读取哪些 traces。详见[使用 root run metadata 控制 trace 访问](#control-trace-access-with-root-run-metadata)。

<Note>
ABAC 在 Enterprise 计划中提供。如果你对该功能感兴趣，请[联系销售团队](https://www.langchain.com/contact-sales)。其他计划默认所有用户都使用 Admin 角色。
</Note>

## 开始前准备

你需要具备：

- **为你的组织启用 ABAC**：在 LangSmith Cloud 上，ABAC 是 Enterprise 计划的一部分。在自托管部署上，请先[启用 ABAC](#enable-abac-on-a-self-hosted-deployment)。
- **管理策略的权限**：创建、编辑或删除策略需要 `organization:access-control:manage` 权限，[Organization Admins](/langsmith/rbac#organization-admin) 和 [Organization Operators](/langsmith/rbac#organization-operator) 拥有该权限。
- **资源标签**：对于基于标签的条件，请在工作区中[设置资源标签](/langsmith/set-up-resource-tags)。仅使用 root run metadata 的策略不需要资源标签。
- **API 凭证**：若要通过 API 管理策略，请使用拥有 `organization:access-control:manage` 权限的用户的 personal access token（PAT），或拥有 Organization Admin 权限的组织范围 service key。请将请求发送到你的 API URL。对于 LangSmith Cloud，请在 [Regional storage](/langsmith/cloud#regional-storage) 中查找你所在区域的 API URL。对于自托管部署，请使用 `https://<your-langsmith-domain>/api`。

## 为自托管部署启用 ABAC

在[自托管](/langsmith/self-hosted)部署上使用 ABAC 需要 Helm chart 0.11.28 或更高版本（应用版本 0.12.1）。升级后，可使用以下任一方式启用 ABAC：

- **为单个组织启用**：对你的 LangSmith PostgreSQL 数据库执行如下语句，并把 `<organization_id>` 替换成从 UI 中组织设置页面复制的 ID：

    ```sql
    UPDATE organizations SET config = config || '{"can_use_abac": true}' WHERE id = '<organization_id>' AND NOT is_personal;
    ```

- **为所有组织启用**：在 `values.yaml` 的 `commonEnv` 中加入如下环境变量：

    ```yaml
    DEFAULT_ORG_FEATURE_CAN_USE_ABAC: "true"
    ```

    <Note>
    该环境变量对 personal organizations 不生效，因为 personal organizations 不启用 [RBAC](/langsmith/rbac)。
    </Note>

## 访问策略结构

访问策略是一个 JSON 对象，用于设置 effect、一个或多个条件组，以及该策略适用的角色：

```json
{
  "name": "Policy Name",
  "description": "Optional description",
  "effect": "allow | deny",
  "condition_groups": [
    {
      "permission": "projects:read",
      "resource_type": "project",
      "conditions": [
        {
          "attribute_name": "resource_tag_key",
          "attribute_key": "Environment",
          "operator": "equals",
          "attribute_value": "Production"
        }
      ]
    }
  ],
  "role_ids": ["<role-uuid>"]
}
```

### Effect

`effect` 决定在条件匹配时会发生什么：

- **`allow`**：条件匹配时授予访问。
- **`deny`**：条件匹配时拒绝访问。

<Note>
Deny 策略始终优先。如果 allow 和 deny 策略同时匹配，最终结果一定是拒绝访问。
</Note>

### Condition groups

`condition_groups` 数组中包含一个或多个条件组。LangSmith 使用 **OR 逻辑** 评估多个条件组。只要任意一个组匹配，策略就会生效。

每个条件组包含以下字段：

- **`permission`**：该组适用的权限。
- **`resource_type`**：要匹配的资源类型。
- **`conditions`**：条件数组，组内采用 **AND 逻辑** 评估。

#### 资源类型与权限

| 资源类型 | 支持的权限 |
| --- | --- |
| `project` | `projects:read`, `projects:update`, `projects:delete`, `runs:read`, `runs:read-inputs`, `runs:read-outputs`, `runs:share`, `runs:delete`, `projects:increase-trace-tier`, `projects:decrease-trace-tier` |
| `prompt` | `prompts:read`, `prompts:update`, `prompts:delete`, `prompts:share`, `prompts:tag` |
| `dataset` | `datasets:read`, `datasets:update`, `datasets:delete`, `datasets:share`, `datasets:download`, `datasets:clone` |
| `deployment` | `deployments:read`, `deployments:update`, `deployments:delete` |
| `queues` | `annotation-queues:create`, `annotation-queues:delete`, `annotation-queues:read`, `annotation-queues:update` |
| `mcp_server` | `mcp-servers:read`, `mcp-servers:invoke`, `mcp-servers:update`, `mcp-servers:delete`。详见 [Fleet 工具访问控制](/langsmith/fleet/access-and-oversight#tool-access-control)。 |
| `fleet_integration` | `mcp-servers:read`, `mcp-servers:invoke`。详见 [Fleet 工具访问控制](/langsmith/fleet/access-and-oversight#tool-access-control)。 |

某些资源类型的评估方式有所不同：

- **Runs**：Runs 本身没有独立标签。Run 权限（`runs:read`、`runs:read-inputs`、`runs:read-outputs`、`runs:create`、`runs:share`、`runs:delete`）是基于其父 project 的标签来评估的。关于输入与输出权限如何影响响应，请参阅[控制对 run 输入与输出的访问](#control-access-to-run-inputs-and-outputs)。
- **Agent environments**：在[基于 agent 的工作区](/langsmith/agent-registry)中，一个 tracing project 是某个 agent 的一个 [environment](/langsmith/agent-environments)。`project` 条件组会分别应用于每个 environment，而不是应用于整个 agent。
- **Dataset clones**：克隆（clone）会将示例从源数据集复制到目标数据集。LangSmith 会校验两次 `datasets:clone`，每次针对一个数据集的标签。策略必须对这两个数据集都授予 `datasets:clone`。

#### Conditions

`conditions` 数组中的每个条件包含以下字段：

- **`attribute_name`**：`resource_tag_key` 用于匹配资源标签，`root_run_metadata` 用于匹配 root run metadata。
- **`attribute_key`**：要匹配的标签 key 或 metadata key，例如 `Environment` 或 `Application`。
- **`operator`**：比较运算符。
- **`attribute_value`**：要比较的值。

下面的运算符适用于 `resource_tag_key` 条件。`root_run_metadata` 条件仅支持 `equals`。相关规则请参阅[使用 root run metadata 控制 trace 访问](#control-trace-access-with-root-run-metadata)。

#### 运算符

| 运算符 | 说明 |
| --- | --- |
| `equals` | 精确匹配（区分大小写） |
| `not_equals` | 值不同（区分大小写） |
| `equals_ignore_case` | 精确匹配（不区分大小写） |
| `not_equals_ignore_case` | 值不同（不区分大小写） |
| `matches` | 使用 `*` 和 `?` 通配符的 glob 模式匹配 |
| `not_matches` | 当值不匹配 glob 模式时匹配 |

#### `_if_exists` 变体

每个运算符都提供一个 `_if_exists` 变体：如果标签 key 不存在，则默认视为匹配；如果标签存在，则按正常条件计算：

| 运算符 | 说明 |
| --- | --- |
| `equals_if_exists` | 精确匹配（区分大小写），或标签 key 不存在 |
| `not_equals_if_exists` | 值不同（区分大小写），或标签 key 不存在 |
| `equals_ignore_case_if_exists` | 精确匹配（不区分大小写），或标签 key 不存在 |
| `not_equals_ignore_case_if_exists` | 值不同（不区分大小写），或标签 key 不存在 |
| `matches_if_exists` | glob 模式匹配，或标签 key 不存在 |
| `not_matches_if_exists` | 值不匹配 glob 模式时匹配，或标签 key 不存在 |

<Tip>
在 **allow** 策略中，`_if_exists` 变体会允许访问那些要么满足条件、要么根本没有该标签 key 的资源。在 **deny** 策略中，它们会阻止那些要么满足条件、要么缺少该标签 key 的资源。
</Tip>

### Roles

`role_ids` 数组指定策略适用于哪些工作区角色。当某个拥有该角色的用户访问资源时，就会对其执行策略条件评估。

策略可以在创建时直接绑定到[工作区角色](/langsmith/rbac#workspace-roles)（内置或[自定义](/langsmith/rbac#custom-roles)），也可以稍后在 UI 中或通过 API 附加。

策略还可以绑定到 [teams](/langsmith/teams#access-policies)。Team 的策略会应用于其成员在 team 可访问的工作区中。

如需从你的身份提供商自动将用户 provision 到角色中，请参阅 [SCIM](/langsmith/user-management#set-up-scim-for-your-organization)。

## 管理访问策略

你可以在组织设置中使用可视化编辑器，或通过 [LangSmith API](https://api.smith.langchain.com/docs#/access_policies) 管理访问策略。两者都需要 `organization:access-control:manage` 权限。

### 在 UI 中创建访问策略

在可视化编辑器中，每个 **rule** 对应一个[条件组](#condition-groups)。

要创建访问策略：

1. 进入 **Settings**，选择 **Organization**。然后进入 **Permissions** > **Access Policies**。在某些版本的设置页面中，该页面列在 **Access and Security** 下的 **ABAC** 中。
2. 在 **ABAC** 下，选择 **Policies** 标签页，然后点击 **Create Policy**。
3. 输入 **Name**，并可选填写 **Description**。
4. 将 **Effect** 设为 **Allow** 或 **Deny**。
5. 点击 **Add rule**，然后选择 **Resource Type** 和 **Permission**。
6. 点击 **Add condition**，并选择条件来源：
   - **Resource tag**：输入 **Tag Key**、运算符和 **Tag Value**。在策略中使用资源标签之前，请先[创建资源标签](/langsmith/set-up-resource-tags)。
   - **Root-run metadata**：首先为 **Resource Type** 选择 **Project**，为 **Permission** 选择 `runs:read`。输入 **Metadata Key** 和 **Metadata Value**。运算符固定为 `equals`，**Metadata Value** 会预填 `${user.ls_user_id}`，用于匹配当前用户。若要匹配固定值，请将其替换为字面值。相关要求和示例请参阅[在 UI 中创建 root run metadata 策略](#create-a-root-run-metadata-policy-in-the-ui)。
7. 点击 **Save condition**，按需添加更多条件，然后点击 **Add rule** 返回策略编辑器。一个 rule 内的所有条件都必须匹配，多个 rule 之间使用 OR 逻辑。
8. （可选）将策略附加到角色。策略只有在你将其附加到角色或 [team](/langsmith/teams#access-policies) 后才会生效。在 **Roles** 下的对话框中，点击 **Add role**。选择该策略适用的工作区角色，然后点击 **Add roles**。添加之前，你可以查看每个角色的权限。你也可以稍后再将策略附加到角色。
9. 完成时，点击 **Create policy**。

<Tip>
如需改用 JSON 编写策略，请点击策略编辑器中 **UI** 旁的 **JSON editor** 图标（<Icon icon="code" />）。JSON 编辑器会以[访问策略结构](#access-policy-structure)展示目前已构建的策略。
</Tip>

### 编辑或删除访问策略

在 **Policies** 标签页中，使用策略 **Actions** 列中的图标。要编辑策略（包括附加或移除角色），点击其编辑图标，进行修改，然后点击 **Save changes**。要删除策略，点击其删除图标，输入策略名称以确认，然后点击 **Delete**。

<Warning>
删除策略会移除其角色和 team 附加关系。删除 deny 策略可能会授予访问。删除 allow 策略可能会移除访问。
</Warning>

### 将策略附加到 teams

[Teams](/langsmith/teams) 不创建策略，只附加已有策略：

- 将策略附加到 team 需要 `organization:teams:manage-policies`。
- Workspace Admin 可在其工作区中把已有策略作为[仅工作区策略](/langsmith/teams#add-workspace-only-members-and-policies)附加到 team，所需权限为 `workspaces:teams:manage-policies`。

## ABAC 与 RBAC 如何协同工作

<a id="how-abac-works-with-rbac"></a>

在决定是否允许访问资源时，系统会同时考虑 [RBAC](/langsmith/rbac) 权限和 ABAC 策略：

- ABAC **deny** 策略会覆盖 RBAC 权限。
- ABAC **allow** 策略即使在没有 RBAC 权限的情况下，也可以授予访问。
- 如果没有任何 ABAC 策略匹配，系统就会回退到 RBAC。

当用户属于多个 [teams](/langsmith/teams) 时，LangSmith 会同时评估用户角色和每个 team 带来的权限与策略。只要其中任一来源存在匹配的 deny 策略，访问仍会被拒绝。

访问模型取决于组织启用了哪些功能：

| RBAC enabled | ABAC enabled | 行为 |
| --- | --- | --- |
| ✗ | ✗ | 所有工作区成员都拥有 Admin 级访问 |
| ✓ | ✗ | 标准 RBAC（根据角色权限决定访问） |
| ✓ | ✓ | RBAC + ABAC（细粒度、基于属性的访问控制） |

当 RBAC 和 ABAC 同时启用时，每个请求按如下方式解析：

| RBAC permits | Allow policy matches | Deny policy matches | 结果 |
| --- | --- | --- | --- |
| ✓ | ✓ | ✗ | **允许** |
| ✓ | ✗ | ✗ | **允许**（RBAC 回退） |
| ✓ | ✓ | ✓ | **拒绝**（deny 优先） |
| ✓ | ✗ | ✓ | **拒绝**（deny 优先） |
| ✗ | ✓ | ✗ | **允许**（ABAC 授权） |
| ✗ | ✗ | ✗ | **拒绝** |
| ✗ | ✓ | ✓ | **拒绝**（deny 优先） |

## 控制对 run 输入与输出的访问

<a id="control-access-to-run-inputs-and-outputs"></a>

`runs:read` 控制用户能否看到某个 run。`runs:read-inputs` 和 `runs:read-outputs` 控制用户能否看到该 run 的输入与输出。消息与轨迹视图需要同时具备这两个权限。

这些权限的策略使用 `resource_type: "project"`，并评估每个 run 的父 project 的标签。你可以用它们在敏感 project 中隐藏输入、输出或两者，同时保持工作区中其他 project 不受影响。这些权限的 RBAC 与 ABAC 组合方式与其他任何权限相同，详见 [ABAC 与 RBAC 如何协同工作](#how-abac-works-with-rbac)。示例请参阅[在敏感 project 中隐藏 run 输入与输出](#6-hide-run-inputs-and-outputs-in-sensitive-projects)。

## 使用 root run metadata 控制 trace 访问

<a id="control-trace-access-with-root-run-metadata"></a>

`root_run_metadata` 条件根据每条 trace 的 root run metadata 中的某个 key，限制用户在 project 中可以读取哪些 traces。借助它，你可以在不把 traces 拆分到不同 project 的前提下，隐藏 project 中的部分 traces，或只向用户显示标记给他们的 traces。

`root_run_metadata` 条件只能用在 `permission: "runs:read"` 且 `resource_type: "project"` 的条件组中。它接受以下字段：

- **`attribute_key`**：root run metadata 中的顶层 key。不支持嵌套 key，因此该 key 不能包含 `.`。
- **`operator`**：仅支持 `equals`。匹配区分大小写。
- **`attribute_value`**：要匹配的值，或占位符 `${user.ls_user_id}`。该占位符会匹配发起请求用户的 `ls_user_id`。可从 [`GET /auth/public`](/langsmith/smith-api/auth/get-public-auth-info) 获取该值。请使用响应中的 `ls_user_id` 字段，它不同于 `user_id` 或用户对象的 `id`。

`attribute_key` 和 `attribute_value` 都不能包含双引号或反斜杠，并且各自限制为 255 字节。以 `${` 开头的值必须正好是 `${user.ls_user_id}`。

条件组可以把 `root_run_metadata` 条件与 `resource_tag_key` 条件组合使用。标签条件用于选择该组适用的 projects，metadata 条件用于选择这些 project 中的 traces。组内所有条件都必须匹配。

条件只评估 root run，因此一条 trace 中的所有 runs 要么全部可见，要么全部隐藏。请在摄取之前为 root run 设置好 metadata key 和 value。root run metadata 在摄取后不可变，因此你无法事后再添加或修改它来让某条 trace 匹配策略。关于如何添加 metadata，请参阅[为 traces 添加 metadata 与标签](/langsmith/add-metadata-tags)。

### 在 UI 中创建 root run metadata 策略

<Note>
**Root-run metadata** 选项需要 **Project** 资源类型和 `runs:read` 权限。你的组织还必须启用 root run metadata 条件。该选项在自托管 UI 中不可用；在自托管安装中，请改用 [API](#7-hide-traces-by-root-run-metadata) 创建 root run metadata 策略。在 cloud 上，如果你在选择该资源类型和权限后该选项被禁用，请联系你的 LangChain 代表。
</Note>

以下示例创建一条 deny 策略，隐藏 root run 的 `source` 为 `customer` 的 traces。

要创建该策略：

1. 打开策略编辑器，步骤与[在 UI 中创建访问策略](#create-an-access-policy-in-the-ui)的第 1、2 步相同。在 **Name** 中输入 `Hide Customer Traces`，并将 **Effect** 设为 **Deny**。
2. 点击 **Add rule**。为 **Resource Type** 选择 **Project**，为 **Permission** 选择 `runs:read`。
3. 点击 **Add condition**，将来源从 **Resource tag** 改为 **Root-run metadata**。
4. 在 **Metadata Key** 中输入 `source`。运算符固定为 `equals`。将 **Metadata Value** 中预填的 `${user.ls_user_id}` 替换为 `customer`。
5. 点击 **Save condition**，然后点击 **Add rule**。
6. 在 **Roles** 下，添加不应看到这些 traces 的工作区角色。点击 **Create policy**。

这会生成[按 root run metadata 隐藏 traces](#7-hide-traces-by-root-run-metadata)示例策略。向同一个 rule 添加资源标签条件，可将其限制到特定 projects。

如需[只向用户显示标记给他们的 traces](#8-show-users-only-the-traces-labeled-for-them)，请改用 **Allow**。将 **Metadata Key** 设为 `allowed_ls_user_id`，并保留 **Metadata Value** 中预填的 `${user.ls_user_id}`。将该策略附加到没有 `runs:read` 的角色上。如果角色拥有 `runs:read`，其 RBAC 权限仍会授予对其他 traces 的访问。

### metadata 条件如何与 RBAC 结合

metadata 条件遵循与其他策略相同的优先级：先应用 deny 策略，再应用 RBAC，最后应用 allow 策略。

- **Deny 策略**：带 metadata 条件的 deny 策略会隐藏匹配的 traces，而不会封锁整个 project。用户仍可访问该 project 中的其他 traces。当多条 deny 策略生效时，只要某条 trace 匹配其中任意一条，就会被隐藏。
- **Allow 策略**：带 metadata 条件的 allow 策略只对匹配的 traces 授予 `runs:read`。当多条 allow 策略生效时，用户只要匹配其中任意一条，就能读取对应的 trace。
- **RBAC**：如果用户角色授予了 `runs:read`，那么除 deny 策略隐藏的 traces 之外，用户可以读取所有 traces，此时 allow 策略不起作用。若要把某个角色限制为 allow 策略匹配的 traces，请从该角色中移除 `runs:read`。

使用 service key 认证的请求没有关联的 `ls_user_id`，因此使用 `${user.ls_user_id}` 的条件不会匹配。使用 Personal Access Token（PAT）或已登录浏览器会话认证的请求会带有用户的 `ls_user_id`。关于 PAT 与 service key 的详情，请参阅 [API keys](/langsmith/create-account-api-key#api-keys)。

### metadata 条件下的响应

<a id="responses-under-metadata-conditions"></a>

当 metadata 条件对某个 project 中的用户生效时，LangSmith 会将该用户在该 project 中的读取范围过滤为其可见的 traces：

- run 列表、trace 列表和 run 分析会省略隐藏的 traces。
- 按 ID 请求隐藏的 trace 或其任意 run 会返回 `404 Not Found`，包括下载该 trace 以及打开其 messages 或 trajectory。
- project 列表会省略该 project 的 run 与 feedback 统计信息。

## 示例场景

### 1. 将 annotators 限制在其数据集内

只允许 annotators 访问标记给其标注组的数据集：

```json
{
  "name": "Annotator Group A Access",
  "effect": "allow",
  "condition_groups": [{
    "permission": "datasets:read",
    "resource_type": "dataset",
    "conditions": [{
      "attribute_name": "resource_tag_key",
      "attribute_key": "Annotation-Group",
      "operator": "equals",
      "attribute_value": "Group-A"
    }]
  }]
}
```

### 2. 阻止敏感数据

拒绝访问包含 PII 的 datasets。由于 deny 策略会覆盖 allow 策略，因此即便用户已经拥有 RBAC 权限，也仍然会被挡住：

```json
{
  "name": "Block PII Datasets",
  "effect": "deny",
  "condition_groups": [{
    "permission": "datasets:read",
    "resource_type": "dataset",
    "conditions": [{
      "attribute_name": "resource_tag_key",
      "attribute_key": "Contains-PII",
      "operator": "equals",
      "attribute_value": "true"
    }]
  }]
}
```

### 3. 基于应用家族的访问（通配符）

允许工程师访问属于 “chatbot” 家族的任意应用项目，使用 glob 模式匹配：

```json
{
  "name": "Chatbot Apps Access",
  "effect": "allow",
  "condition_groups": [{
    "permission": "projects:read",
    "resource_type": "project",
    "conditions": [{
      "attribute_name": "resource_tag_key",
      "attribute_key": "Application",
      "operator": "matches",
      "attribute_value": "chatbot-*"
    }]
  }]
}
```

### 4. 客户与用途双重隔离（AND 逻辑）

只有在同时满足两个条件时才允许访问，也就是该 dataset 既用于训练，又属于某个特定客户：

```json
{
  "name": "Client Training Data Access",
  "effect": "allow",
  "condition_groups": [{
    "permission": "datasets:read",
    "resource_type": "dataset",
    "conditions": [
      {
        "attribute_name": "resource_tag_key",
        "attribute_key": "Purpose",
        "operator": "equals",
        "attribute_value": "Training"
      },
      {
        "attribute_name": "resource_tag_key",
        "attribute_key": "Client",
        "operator": "equals",
        "attribute_value": "Acme-Corp"
      }
    ]
  }]
}
```

### 5. 客户数据 + 没有 `Client` 标签的资源（使用 `_if_exists`）

假设 consultants 没有 RBAC 的 `datasets:read` 权限，但这条策略可以授予他们访问 `Client=Acme-Corp` 的 datasets，以及根本没有 `Client` 标签的 datasets。那些标记为其他客户的 datasets，例如 `Client=Other-Corp`，仍然会被阻止：

```json
{
  "name": "Acme Consultant Access",
  "effect": "allow",
  "condition_groups": [{
    "permission": "datasets:read",
    "resource_type": "dataset",
    "conditions": [{
      "attribute_name": "resource_tag_key",
      "attribute_key": "Client",
      "operator": "equals_if_exists",
      "attribute_value": "Acme-Corp"
    }]
  }]
}
```

### 6. 在敏感 project 中隐藏 run 输入与输出

允许用户继续浏览包含 PII 的 project 中的 runs，但隐藏这些 runs 的输入与输出。每个权限各有一个独立的条件组，各组之间按 OR 逻辑评估。用户仍然需要 `runs:read` 才能看到 runs：

```json
{
  "name": "Hide PII Run Payloads",
  "effect": "deny",
  "condition_groups": [
    {
      "permission": "runs:read-inputs",
      "resource_type": "project",
      "conditions": [{
        "attribute_name": "resource_tag_key",
        "attribute_key": "Contains-PII",
        "operator": "equals",
        "attribute_value": "true"
      }]
    },
    {
      "permission": "runs:read-outputs",
      "resource_type": "project",
      "conditions": [{
        "attribute_name": "resource_tag_key",
        "attribute_key": "Contains-PII",
        "operator": "equals",
        "attribute_value": "true"
      }]
    }
  ]
}
```

### 7. 按 root run metadata 隐藏 traces

在任意 project 中，隐藏 root run 的 `source` 为 `customer` 的 traces。角色授予 `runs:read` 的用户仍可看到其他所有 traces：

```json
{
  "name": "Hide Customer Traces",
  "effect": "deny",
  "condition_groups": [{
    "permission": "runs:read",
    "resource_type": "project",
    "conditions": [{
      "attribute_name": "root_run_metadata",
      "attribute_key": "source",
      "operator": "equals",
      "attribute_value": "customer"
    }]
  }]
}
```

### 8. 只向用户显示标记给他们的 traces

只向每个用户显示 root run 的 `allowed_ls_user_id` 等于该用户 LangSmith 用户 ID 的 traces。请把这条策略附加到不授予 `runs:read` 的角色上，因为 RBAC 权限优先于 allow 策略：

```json
{
  "name": "Traces Labeled for the Caller",
  "effect": "allow",
  "condition_groups": [{
    "permission": "runs:read",
    "resource_type": "project",
    "conditions": [{
      "attribute_name": "root_run_metadata",
      "attribute_key": "allowed_ls_user_id",
      "operator": "equals",
      "attribute_value": "${user.ls_user_id}"
    }]
  }]
}
```

### 9. 生产 project 中的团队 traces

授予对 root run 的 `team` 为 `payments` 的 traces 的访问权限，但仅限于标记了 `Environment=prod` 的 projects。标签条件用于选择 projects，metadata 条件用于选择其中的 traces：

```json
{
  "name": "Payments Traces in Prod",
  "effect": "allow",
  "condition_groups": [{
    "permission": "runs:read",
    "resource_type": "project",
    "conditions": [
      {
        "attribute_name": "resource_tag_key",
        "attribute_key": "Environment",
        "operator": "equals",
        "attribute_value": "prod"
      },
      {
        "attribute_name": "root_run_metadata",
        "attribute_key": "team",
        "operator": "equals",
        "attribute_value": "payments"
      }
    ]
  }]
}
```

## 创建时标记资源

启用 ABAC 策略后，资源会按其标签受到访问控制。为确保资源在创建后立即受到保护，你可以在创建请求中通过 `tag_value_ids` 参数直接提供标签。

project、dataset 和 prompt 的创建端点都支持这一做法，包括 fork 和 clone 操作。标签会与资源创建在同一个数据库事务中原子地应用。

完整细节和示例，请参见资源标签指南中的[在创建时为资源打标签](/langsmith/set-up-resource-tags#tag-a-resource-at-creation-time)。

<Note>
如果你依赖 LangSmith SDK 在 trace 摄取期间自动创建 tracing project，该自动创建路径不支持 `tag_value_ids` 参数。为确保 ABAC 策略从一开始就生效，请在开始 trace 会话之前，通过 `POST /api/v1/sessions` 并带上所需的 `tag_value_ids` 预先创建 project。
</Note>

## 故障排查

**访问被意外拒绝？**
- 检查是否命中了 deny 策略（deny 永远优先）
- 检查用户是否拥有 RBAC 权限，或命中了某条 allow 策略
- 验证资源是否真的带有预期标签和值
- 带 `_if_exists` 的 deny 策略会阻止缺失该标签 key 的资源
- 对于区分大小写的运算符（`equals`、`not_equals`），检查是否存在大小写不一致
- 如果一个条件组内有多个条件，则它们必须全部匹配（AND 逻辑）

**访问被意外放行？**
- 检查 RBAC 权限（用户可能是通过角色本身获得访问）
- 检查 allow 策略是否过于宽泛，例如使用了通配符
- `_if_exists` 运算符会匹配缺失该标签 key 的资源

**看不到 run 输入或输出？**
- 检查用户角色是否授予了 `runs:read-inputs` 和 `runs:read-outputs`，或者是否有 allow 策略为该 run 所属的 project 授予了这两个权限
- 检查是否存在匹配该 project 标签的 `runs:read-inputs` 或 `runs:read-outputs` deny 策略
- 只有同时授予这两个权限，消息与轨迹视图才能正常显示，否则会返回 `403 Forbidden`

**找不到 traces 或返回 `404 Not Found`？**
- 检查是否存在带 `root_run_metadata` 条件、且匹配该 trace root run metadata 的 deny 策略
- 如果用户的访问权限来自带 `root_run_metadata` 条件的 allow 策略，请检查 root run 是否带有该 metadata key，且值完全一致（包括大小写）
- 条件只匹配 root run 上的顶层 key，不会匹配子 run 上的 metadata

**Threads、共享或实验对比返回 `403 Forbidden`？**
- 在 `root_run_metadata` 条件对用户生效的任何 project 中，这些界面都不可用。完整列表请参阅 [metadata 条件下的响应](#responses-under-metadata-conditions)

**策略没有生效？**
- 确认策略附加到了正确的角色上
- 验证用户在该工作区中确实拥有这个角色
- 检查 `resource_type` 和 `permission` 是否与实际访问的资源一致
