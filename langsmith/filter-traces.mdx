过滤可以将 tracing project 中的 [runs](/langsmith/observability-concepts#runs) 缩小到需要注意的那些，例如出错的对话、缓慢的 tool 调用，或 feedback 分数低的 runs。在搜索栏中编写一个查询，然后选择查询要在 [trace](/langsmith/observability-concepts#traces) 或 [thread](/langsmith/observability-concepts#threads) 层级结构中的哪些 runs 上进行匹配。

在 [agent-based workspace](/langsmith/agents) 中，一个 tracing project 是一个 agent 的一个 [environment](/langsmith/agent-environments)，因此过滤适用于你当前打开的 environment，而不是整个 agent。要跨 agent 的 environments 过滤，请逐一过滤每个 environment。

## 构建查询

一个查询由多个 clause 组成，每个 clause 将一个 field 与一个 operator 和一个 value 配对：

```text

```

要构建查询，点击搜索栏并开始输入：

<Steps>
  <Step title="Choose a field">
    输入一个字段名或从建议列表中选择一个。建议按类别分组，**Recents** 列出之前运行过的查询。使用方向键在列表中移动，按 `Enter` 选择。
  </Step>
  <Step title="Choose an operator">
    输入 `:` 可以看到该字段支持的 operators，每个都附有一个示例。
  </Step>
  <Step title="Enter a value">
    对于 LangSmith 索引其值的字段，例如 run 名称和 tags，建议列表会提供该 project 中最常见的值。
  </Step>
</Steps>

每个完成的 clause 会成为搜索栏中的一个 chip。点击 chip 可以编辑它，或点击其移除图标删除它。在 chip 后继续输入可以添加另一个 clause。

搜索栏之外的两个控件也会影响结果：

- **时间范围控件**与查询同时生效。结果必须落在时间范围内并且匹配查询。
- **Threads、Traces 和 Runs 选择**设置表格中每行代表什么，它还决定查询可以使用哪些 [scopes](#choose-what-a-filter-matches)。

<Note>
搜索栏使用本页描述的语法，它不是 SDK 和 REST API 接受的结构化查询语言。该语言请参阅 [Trace query syntax](/langsmith/trace-query-syntax)。
</Note>

## 选择过滤器匹配什么

一个 trace 是一棵 runs 树，一个 thread 是一系列 traces。像 `status:error` 这样的 clause 在你说明它适用于该层级结构中的哪些 runs 之前是有歧义的：是启动 trace 的 run、其中任意位置的任何 run，还是整个 thread。搜索栏左侧的 scope 选择器就是你说明这一点的地方。

有四种 scope 可用：

- **Thread**：匹配整个 thread。
- **Root run**：只匹配入口 runs。
- **Single run**：匹配 run 本身。
- **Any run**：匹配树中任意位置。

scope 下拉框会针对一个示例 trace 预览每个选项，因此你可以在选择之前看到它覆盖哪些 runs：

提供的 scopes 以及默认选中的 scope，取决于表格选择：

| 表格选择 | 默认 scope | 可用 scopes |
| --------------- | ------------- | ---------------- |
| **Threads** | Any run | Thread, Root run, Any run |
| **Traces** | Root run | Root run, Any run |
| **Runs** | Single run | Single run, Root run, Any run |

### 组合 scopes

要同时按多个 scope 过滤，点击 **Filter**。这会添加一个带有自己的 scope 选择器和搜索栏的行。各行之间以 `AND` 组合，因此一个 thread、trace 或 run 必须满足每一行才会出现在表格中。

每个 scope 最多持有一行，因此 **Threads** 和 **Runs** 选择接受三行，**Traces** 接受两行。所有可用 scope 都被占用后，**Filter** 会禁用。要移除一行，点击它旁边的 **Remove filter**。

例如，在 **Threads** 视图中，查找超过 20 轮且包含失败 tool 调用的 threads：

| Scope | 查询 |
| ----- | ----- |
| Thread | `turn_count:>20` |
| Any run | `run_type:tool AND status:error` |

### 表格选择无法使用的 scopes

更改表格选择可能让某一行停留在新选择不支持的 scope 上，例如从 **Runs** 切换到 **Threads** 后的 **Single run** 行。该行保持可见并带有 **Not applied** badge，其查询被保留但不应用。更改该行的 scope 或返回兼容的表格选择即可重新应用。

## 查询语法

### Operators

一个字段接受的 operators 取决于其类型。

| Operator | 语法 | 匹配 |
| -------- | ------ | ------- |
| is | `field:value` | 对值的精确匹配。 |
| is not | `-field:value` | 精确匹配之外的一切。 |
| matches | `field:~value` | 对该字段的全文搜索。用引号包住值可以搜索短语。 |
| does not match | `-field:~value` | 全文搜索未匹配到的一切。 |
| wildcard | `field:value*` | 一个模式，其中 `*` 代表任意字符序列。 |
| exists | `field:*` | 字段已设置的记录。 |
| does not exist | `-field:*` | 字段未设置的记录。 |
| comparison | `field:>value` | 高于给定值的值。也接受 `>=`、`<` 和 `<=`。 |
| inclusive range | `field:[10 TO 20]` | 从 10 到 20 的值，包含两个边界。 |
| exclusive range | `field:{10 TO 20}` | 介于 10 和 20 之间的值，不包含两个边界。 |
| mixed range | `field:[10 TO 20}` | 从 10 到（但不包含）20 的值。交换分隔符可以反转哪个边界是包含的。 |

一些字段只接受这些 operators 的子集：

- **全文搜索字段**：`input`、`output`、`metadata` 和 `error` 只接受 `~`。
- **比较和范围 operators**：这些适用于数值字段（如 `latency` 和 `total_tokens`）、时间戳字段（如 `first_token_time`），以及数值型的 [`metadata` 路径](#match-a-json-key)。

要匹配多个值中的任意一个，请用 `OR` 组合 clause，例如 `status:error OR status:interrupted`。不支持在一个 clause 中列出多个值。

### 组合 clause

使用 `AND`、`OR`、`NOT` 和括号组合 clause：

- **`AND`**：两个 clause 都必须匹配。两个 clause 之间的空白相当于 `AND`，因此 `status:error run_type:llm` 与 `status:error AND run_type:llm` 等价。
- **`OR`**：任意一个 clause 匹配即可。
- **`NOT`**：否定其后的 clause。`-` 前缀的作用相同，因此 `NOT status:error` 与 `-status:error` 等价。
- **括号**：对 clause 分组以控制优先级。

`AND` 比 `OR` 绑定得更紧密，因此 `a OR b AND c` 匹配 `a OR (b AND c)`。使用括号分组可以改变这一点：`(a OR b) AND c`。

关键字不区分大小写。

### 为值加引号

对包含空格、包含冒号或含有需要按字面匹配的字符的值，使用双引号：

```text
name:"docs agent"
tags:"env:prod"
```

加引号也会关闭 wildcard 匹配，因此 `name:"docs*"` 匹配字面字符串 `docs*`。作为加引号的替代方案，可以用反斜杠转义该字符，如 `name:docs\ agent`。

在 run scopes 中，包含空格的未加引号的值会拆分为两个 clause，因此 `name:docs agent` 匹配名称为 `docs` 且其索引内容包含 `agent` 的 runs。

### 不指定字段进行搜索

在 **Single run**、**Root run** 和 **Any run** scopes 中，一个裸词会搜索所有[已索引字段](#full-text-search-indexing)：

```text
"capital of France"
```

**Thread** scope 不支持裸词搜索。

## 字段

建议列表将字段按类别分组。可用字段取决于过滤行的 [scope](#choose-what-a-filter-matches)。

### Run 字段

这些字段在 **Single run**、**Root run** 和 **Any run** scopes 中可用。

**Run 属性**

| 字段 | 描述 |
| ----- | ----------- |
| `name` | Run 名称。支持 wildcard。 |
| `status` | Run 状态：`pending`、`success`、`error` 或 `interrupted`。 |
| `run_type` | [run 的类型](/langsmith/run-data-format#run-types)，例如 `llm`、`chain`、`tool` 或 `retriever`。 |
| `tags` | Run tags。只要 run 上的任意一个 tag 匹配，该 clause 就匹配。 |

**内容**

| 字段 | 描述 |
| ----- | ----------- |
| `input` | Run 输入。使用 `~` 搜索文本，或使用 `input.<key>` 匹配 JSON key。 |
| `output` | Run 输出。使用 `~` 搜索文本，或使用 `output.<key>` 匹配 JSON key。 |
| `metadata` | Run metadata。使用 `metadata.<key>` 匹配 JSON key，或用 `~` 搜索 metadata 值。 |
| `error` | 错误文本。使用 `~` 搜索文本。 |
| `attachments` | 附件名称。 |

**Identity**

| 字段 | 描述 |
| ----- | ----------- |
| `id`, `trace_id`, `thread_id`, `parent_run_id` | 按 ID 匹配特定的 run、trace、thread 或父 run。 |
| `ls_user_id` | run 归属的 LangSmith 用户。 |

**性能**

| 字段 | 描述 |
| ----- | ----------- |
| `latency` | Run 时长（秒）。 |
| `first_token_time` | 产生第一个 token 的时间。 |
| `prompt_tokens`, `completion_tokens`, `total_tokens` | Run 的 token 数量。 |
| `prompt_cost`, `completion_cost`, `total_cost` | Run 的成本。 |
| `prompt_token_details`, `completion_token_details` | Token 细分。使用点号表示法定位组件，例如 `prompt_token_details.cache_read` 或 `completion_token_details.reasoning`。 |
| `prompt_cost_details`, `completion_cost_details` | 成本细分，组件与 token 细分相同。 |

**Feedback**

| 字段 | 描述 |
| ----- | ----------- |
| `feedback` | Run 上的 feedback。请参阅 [Filter on feedback](#filter-on-feedback)。 |

Metadata 和 tags 通常是最高效的过滤字段，因为你可以控制放入其中的内容。请参阅 [Add metadata and tags to traces](/langsmith/add-metadata-tags)。

### Thread 字段

**Thread** scope 对 thread 整体的属性进行过滤，因此它支持一组不同的字段。建议列表将这一组标记为 **Thread attributes**。

| 字段 | 描述 |
| ----- | ----------- |
| `thread_id` | Thread ID。 |
| `turn_count` | Thread 中的轮数。 |
| `num_errored_turns` | 以错误结束的轮数。 |
| `thread_duration` | 从第一轮开始到最后一轮结束。 |
| `trace_latency_p50` | 轮次延迟的中位数。 |
| `trace_latency_p99` | 轮次延迟的 P99。 |
| `total_tokens` | 整个 thread 的 token 数量。 |
| `total_cost` | 整个 thread 的成本。 |
| `prompt_token_details`, `completion_token_details`, `prompt_cost_details`, `completion_cost_details` | 整个 thread 的 token 和成本细分。 |

<Note>
诸如 `name`、`status` 和 `input` 的 run 字段在 **Thread** scope 中不可用。要按 thread 所含 runs 的属性过滤 threads，请在 **Any run** scope 中添加第二个过滤行。请参阅 [Combine scopes](#combine-scopes)。
</Note>

### 匹配 JSON key

`input`、`output` 和 `metadata` 保存 JSON。使用点号表示法定位其中的 key：

```text
metadata.env:production
input.user_id:abc123
output.status:success
```

嵌套路径的工作方式相同，例如 `metadata.config.temperature:0.7`。对包含点的 key 加引号，如 `metadata."my.key":production`。

只有 `metadata` 路径支持比较和范围 operators，且仅在值为数值时支持：

```text
metadata.retries:>=3
```

### 按 feedback 过滤

使用点号表示法定位一个 feedback key 及其子字段之一：

```text
feedback.correctness.score:>=0.5
feedback.relevance.value:pass
feedback.quality.comment:~helpful
```

可用的子字段是 `key`、`score`、`value`、`comment`、`source` 和 `error`。在 **Thread** scope 中，只有 `key`、`score` 和 `value` 可用。

要匹配带有任何 feedback 的记录，使用 `feedback:*`。要匹配带有特定 feedback key 而不论其值的记录，使用 `feedback.<key>:*`。比较值需要指定子字段，因此 `feedback.correctness:0.5` 是无效的。

使用 `feedback:{...}` 对一个 feedback 条件分组：

```text
feedback:{correctness.score:>0.5}
```

## 示例

可复制并调整的查询。除非另有说明，每个示例都假设其表格选择的默认 scope。

**同样缓慢的出错 LLM 调用。** 使用 **Runs** 选择：

```text
run_type:llm AND status:error AND latency:>10
```

**你的 evaluator 打分很差的 runs。** 使用 **Runs** 选择：

```text
run_type:llm AND feedback.correctness.score:<0.5
```

**未成功的 production 流量。** 使用 **Traces** 选择：

```text
metadata.env:production AND -status:success
```

**提到某个主题且出现问题的对话。** 使用 **Threads** 选择：

```text
input:~"refund" AND status:error
```

<a id="example-filtering-for-tool-calls"></a>

**调用了特定 tool 的 traces。** 使用 **Traces** 选择和 **Any run** scope，这样 clause 会与 trace 中的每个 run 匹配，而不是入口 run：

```text
run_type:tool AND name:search_documents
```

**昂贵的 traces。** 使用 **Traces** 选择：

```text
total_cost:>0.5
```

## 保存过滤器

Saved views 存储一个过滤器以供复用。视图属于 tracing project，而不是创建它的人，因此任何有权访问该 project 的人都可以选择它。在 agent-based workspace 中，这意味着视图属于一个 [environment](/langsmith/agent-environments)：保存在 **Production** 中的视图不会在 **Staging** 中提供，你想要在每个 environment 中使用的过滤器必须在每个 environment 中分别保存。

要保存当前过滤器：

1. [构建查询](#build-a-query)。
1. 点击 **Save View**。
1. 输入名称和描述，然后保存。

视图之后会出现在 **Views** 下拉框中，与 **Default view** 并列。每个条目都会列出其过滤器使用的 scopes，一目了然地表明它是否适用于当前表格选择。

要更新一个已保存的视图，选中它、更改查询，然后点击 **Save View**。要重命名或删除视图，点击 **Views** 下拉框中它旁边的 <Icon icon="dots-vertical"/> 图标。

要放弃未保存的更改并返回所选视图，点击 **Reset**。

### 使用旧语法保存的视图

在此过滤体验发布之前保存的视图继续有效。选中一个会将其过滤器转换为本页的语法，并且 LangSmith 会提示你保存转换后的视图。

## 过滤 trace 内部的 runs

在打开的 trace 内部过滤会高亮匹配的 runs，这就是你在一个大型 trace 中找到关键之处的办法。打开一个 thread 或 trace 进入 [Details view](/langsmith/view-traces#details-view)，然后使用 run 列表上方的 **Filter runs**。

匹配的 runs 会在原位高亮，trace 的其余部分保持在它们周围可见，因此一个匹配保留了能解释它的上下文。在 **Any run** scope 中应用的过滤器会自动带过来，因此从表格打开一个 thread 或 trace 会高亮匹配它的 runs。

## 全文搜索索引

`~` operator 和[裸词搜索](#search-without-naming-a-field)匹配的是一个派生的搜索索引，而不是存储的 run 数据。LangSmith 通过递归地从 run 输入、输出和错误中的字符串值提取搜索 token 来构建该索引。Object keys 不被索引，值也不会因长度而被拒绝或截断。

以下限制适用于该索引：

- **每个字段的 token 数**：LangSmith 为每个已索引字段最多保留 2,000 个不同的搜索 token，从最多 200,000 个不同候选中选出。
- **嵌套深度**：LangSmith 处理嵌套数据的最大深度为 30。
- **Token 长度**：一个搜索 token 在 2 到 44 个 ASCII 文本字符之间。超出该范围的字符串不被索引，非 ASCII 文本按其占用的空间度量，而不是按字符数。
- **排除的内容**：URLs、图像 data URLs、纯数字 token，以及诸如 "the" 和 "of" 的常见停用词不被索引。

这些限制只约束搜索索引。Run 数据完整存储，因此索引未包含的值仍然可以在 trace 本身中看到。

Metadata 和 key 路径是分开索引的。Key-path 过滤不受全文 token 限制的约束，LangSmith 目前也未公布其单独限制。像 `input.<key>` 或 `metadata.<key>` 这样的过滤器会在特定路径上查找值，因此它仍然可以匹配全文索引忽略的值。请参阅 [Match a JSON key](#match-a-json-key)。

## 排查查询问题

**搜索栏标记查询无效。** 搜索栏在你输入时进行验证，并内联指出问题，包括未知字段名、引号或括号不配对，以及 operator 与其冒号之间被空格分隔。修复它指向的 clause。

**查询有效但匹配不到任何内容。** 按顺序检查以下各项：

1. **检查时间范围。** 它与查询同时生效，因此即使过滤器正确，匹配的 runs 落在窗口之外时仍然返回空。
1. **检查 scope。** 在层级结构的错误层级上测试 clause 是最常见的原因。在 **Root run** scope 中用 `run_type:llm` 过滤 traces 只匹配入口 run 是 LLM 调用的 traces，这很少是你想要的。将该行切换为 **Any run**。
1. **检查是否有 Not applied badge。** 停留在当前表格选择不支持的 scope 上的行会被保留但不应用。
1. **检查值是否被索引。** 全文搜索会跳过 URLs、停用词、纯数字 token，以及非常短或非常长的 token。改为按 [JSON key](#match-a-json-key) 过滤，它不受这些限制约束。
