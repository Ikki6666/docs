## 数据区域

Deployments 可以创建在两个数据区域中：US 和 EU。

某个 deployment 的数据区域由其创建所在 LangSmith organization 的数据区域决定。Deployments 及其底层数据库都不能在不同数据区域之间迁移。

## 静态 IP 地址

所有在 2025 年 1 月 6 日之后创建的 deployments，其流量都会经过 NAT gateway。该 NAT gateway 会根据数据区域拥有若干静态 IP 地址。

## Payload 大小

发送到 Cloud deployments 的所有请求，其最大 payload 大小为 25MB。超过 25MB 的请求会返回 `413 Payload Too Large` 错误。

## Deployment 类型

Control plane 提供两种 deployment 类型：Serverless 和 Dedicated。每种类型都提供三种[规格](#sizes)：Small、Medium 和 Large。

<Note>
`langgraph deploy` 默认创建 Serverless deployment。旧版 CLI 使用 `dev` 表示不支持缩容到零的旧版 Development deployment，使用 `prod` 表示 Dedicated deployment。旧版 `dev` 不等同于 Serverless；请参阅 [`langgraph deploy`](/langsmith/cli#deploy)。
</Note>

| **Deployment type** | **Scaling** | **Database** | **Best for** |
|---|---|---|---|
| Serverless | 不活跃后缩容到零，下一个请求时唤醒 | 共享、多租户 | 后台和其他对延迟容忍的生产工作负载，以及开发与测试 |
| Dedicated | 始终在线，跨 replicas 自动扩缩容 | 独享，带自动备份和高可用 | 需要始终在线容量的对延迟敏感工作负载 |

<Warning>
**不可变 deployment 类型**
一旦 deployment 创建完成，就无法更改 deployment 类型。但你仍可以更改它的[规格](#sizes)。
</Warning>

两种 deployment 类型上的 Agent Server 都具备容错能力：它会自动从临时的 Redis 或 Postgres 中断中恢复，并重试失败的后台 runs。

### Serverless

Serverless deployment 运行单个 replica，空闲时缩容到零，并在下一个请求时唤醒。它适合后台 agents、开发和测试，以及能够容忍冷启动延迟的生产工作负载。

在创建时或在 **Scaling** 对话框中，将 **Scale down after** 设置为 `1 hour`、`1 day` 或 `1 week`（默认值）。较短的窗口可减少空闲计算费用；较长的窗口可减少冷启动。

平台会检查未来 10 分钟内到期的计划 runs 和已启用的 [cron jobs](/langsmith/cron-jobs)，提前启动已缩容的 deployment。这可以减少冷启动延迟，但并不保证就绪。启动期间的请求默认最多等待 60 秒，然后超时。

该 replica 不会横向扩容。其 queue worker 默认最多处理 10 个并发 runs，可通过 [`N_JOBS_PER_WORKER`](/langsmith/env-var-cloud#n_jobs_per_worker) 配置；更多的 runs 会排队。

<Note>
缩容到零目前处于 [beta](/langsmith/release-stages) 阶段，初期仅适用于采用基于用量计费的 deployments。关于定价和过渡时间表，请参阅[计费管理](/langsmith/billing#langsmith-deployment-billing)。
</Note>

### Dedicated

Dedicated deployment 保持在线，并对独立的 API server 和 queue worker replicas [自动扩缩容](#scaling)。每个 deployment 都拥有自己的数据库，带有自动备份、时间点恢复和高可用。它适合需要始终在线容量的对延迟敏感工作负载。

如需申请更多资源，请[联系支持团队](https://support.langchain.com)。资源增加取决于你的用例和可用容量。

## Sizes

以下表格展示了 LangSmith Cloud（GCP）上计费计算所请求的 vCPU 和内存。Redis 未列入，因为任何 deployment 类型或规格都不对它计费；请参阅[计算计费](/langsmith/billing#langsmith-deployment-billing)。

Serverless deployment 运行一个 replica，其中包含一个 API server 和一个 queue worker，外加一个独立的 Redis 容器：

| Container | Serverless S | Serverless M | Serverless L |
|---|---|---|---|
| API server | 0.4 vCPU / 1 GiB | 2 vCPU / 2 GiB | 4 vCPU / 4 GiB |
| Queue worker | 0.4 vCPU / 1 GiB | 2 vCPU / 2 GiB | 4 vCPU / 4 GiB |
| **计费 runtime 总计** | **0.8 vCPU / 2 GiB** | **4 vCPU / 4 GiB** | **8 vCPU / 8 GiB** |
| Database | 共享、多租户 | 共享、多租户 | 共享、多租户 |

Dedicated deployment 运行独立的 API server 和 queue worker replica 池、一个 Redis 容器，以及自己的数据库实例：

| Container | Dedicated S | Dedicated M | Dedicated L |
|---|---|---|---|
| API server，每 replica | 1 vCPU / 2 GiB | 2 vCPU / 4 GiB | 4 vCPU / 8 GiB |
| API server replicas | 2 到 10 | 2 到 20 | 2 到 40 |
| Queue worker，每 replica | 1 vCPU / 2 GiB | 2 vCPU / 4 GiB | 4 vCPU / 8 GiB |
| Queue worker replicas | 1 到 10 | 1 到 20 | 1 到 40 |
| **最低计费 runtime 总计** | **3 vCPU / 6 GiB** | **6 vCPU / 12 GiB** | **12 vCPU / 24 GiB** |
| Database 实例 | 1 vCPU / 4 GiB | 2 vCPU / 8 GiB | 4 vCPU / 16 GiB |
| Database 存储 | 自动扩容磁盘 | 自动扩容磁盘 | 自动扩容磁盘 |

最低计费 runtime 总计包含 2 个 API server replicas 和 1 个 queue worker。[自动扩缩容](#scaling)会按表中列出的每 replica 规格增加 replicas。

在 Dedicated deployment 上，计算规格和数据库规格可以在 **Scaling** 对话框中独立设置。规格变更会以新 revision 的方式推出，并保留 deployment 的 threads、checkpoints 和 API URL。

关于每种规格的价格，请参阅[定价页面](https://www.langchain.com/pricing)，其中包含 deployment 成本计算器。关于 Serverless 和 Dedicated deployments 的计费方式，请参阅[计费管理](/langsmith/billing#langsmith-deployment-billing)。

### 在一个 deployment 上运行多个 agents

Deployment 的计费[基于其消耗的资源](/langsmith/billing#langsmith-deployment-billing)，而不是其服务的 agent 数量。要在单个 deployment 的资源上运行多个 agents，可以在一个 `langgraph.json` 中[定义多个 graphs](/langsmith/application-structure#define-multiple-graphs-in-one-deployment)。这种方式很适合 Dedicated：一个始终在线、拥有专属数据库的实例可以承载多个生产环境 agents。

一个 deployment 中的所有 graphs 共享它的计算资源、数据库、自动扩缩容和 deployment 类型。它们还会作为一个 revision 一起发布。如果某个 agent 需要不同的规格、延迟特征，或需要与其他 agents 隔离，就为它单独创建一个 deployment。

## 数据库配置

Control plane 与 [data plane](/langsmith/data-plane) listener application 会协同工作，为每个 Cloud deployment 自动创建一个 Postgres 数据库。该数据库充当 deployment 的[持久化层](/oss/python/langgraph/persistence#memory-store)。

在实现 LangGraph 应用时，无需手动配置 [checkpointer](/oss/python/langgraph/persistence#checkpointer-libraries)。系统会自动为 graph 配置一个 checkpointer。任何为 graph 显式配置的 checkpointer，都会被自动配置的那个替换。

无法直接访问数据库。所有数据库访问都必须通过 [Agent Server](/langsmith/agent-server)。

只有当 deployment 自身被删除时，数据库才会被删除。

关于自托管部署，请参阅[自定义 PostgreSQL 配置](/langsmith/self-hosted-platform-features#custom-postgresql)。

## 扩缩容

Cloud deployments 会自动扩缩容。你不需要直接配置 queue workers、replicas 或 pool sizes。

[Serverless](#serverless) 在零到一个 replica 之间扩缩容。

Dedicated deployment 会在[其规格允许的最大值](#sizes)内增减 replicas。[API servers](/langsmith/agent-server#runtime-architecture) 和 [queue workers](/langsmith/agent-server#runtime-architecture) 是相互独立的池，各自独立扩缩容，因此读取流量不会拖慢 run 提交，反之亦然：

- **API servers** 按 CPU 扩缩容。目标是 CPU limit 的 50%，即[规格表](#sizes)中所请求 vCPU 的两倍。最少为 2 个 replicas。
- **Queue workers** 按 CPU 或按 run 积压量扩缩容，以需要更多 replicas 的指标为准。CPU 目标与前者相同。积压目标按 [`N_JOBS_PER_WORKER`](/langsmith/env-var-cloud#n_jobs_per_worker) 的 75% 向下取整统计 pending 和 running 的 runs。默认值为 10 时，目标是每个 replica 7 个 runs；30 个 runs 需要 5 个 workers。最少为 1 个 replica。

内存不会触发扩缩容。Redis 和数据库计算不会自动扩缩容。为避免频繁的扩缩容变化，缩容会先等待 15 分钟，然后每 2 分钟最多移除 10% 的 replicas（至少一个）。在 revision 发布期间缩容会暂停。Replicas 在缩容完成之前仍然[计费](/langsmith/billing#langsmith-deployment-billing)。

自动扩缩容只改变 replicas 的数量，每个 replica 可用的 CPU 和内存由 deployment 的[规格](#sizes)固定。如果某个 deployment 持续承受 CPU 压力，或其容器内存不足，请将其升级到更大的规格。规格变更会以无停机的新 revision 方式推出；但 deployment 类型无法更改。

应用层的扩缩容手段（durability modes、异步模式、避免同步阻塞、使用 `/join` 而非轮询）对 Cloud 和自托管同样适用。底层概念请参阅[自托管环境下的扩缩容](/langsmith/agent-server-scale)；但其中涉及的 Helm 和资源配置不适用于 Cloud。
