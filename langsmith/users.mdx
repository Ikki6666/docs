LangSmith 中的用户是你的应用在某条 trace 中服务的人。LangSmith 从 trace 根 run 的 [metadata](/langsmith/observability-concepts#metadata) 中的 `user_id` 键读取用户，与它使用 `thread_id` 将 traces 归组到 [threads](/langsmith/threads) 的方式相同。记录用户后，你可以找到报告问题的某位用户的所有 traces，并查看每位用户的活动、成本和错误。

<Note>
本页介绍的用户功能处于 [beta](/langsmith/release-stages) 阶段，可在 [LangSmith Cloud](/langsmith/cloud) 上使用。这些功能在 [self-hosted](/langsmith/self-hosted) LangSmith 或 [BYOC](/langsmith/byoc) 部署中不可用；在这些部署中，`user_id` 会作为普通 metadata 存储。
</Note>

<Note>
`user_id` 标识你的应用的一位最终用户。它不同于 `ls_user_id`，后者标识 run 归属的 LangSmith 用户。
</Note>

## 在 trace 上记录用户

要记录用户，请为每条 trace 的根 run 的 metadata 添加一个 `user_id` 键。值可以是任何能在你的应用中标识该用户的字符串。请在不同 traces 中为同一位用户使用相同的值，这样按用户筛选时会返回其所有 traces。

[LangSmith SDK](/langsmith/reference) 会将 run 的 metadata 复制到它创建的 child runs。当你在根 run 上设置 `user_id` 时，SDK 会将其记录到该 trace 中的每个 run 上。在 child run 上设置的 `user_id` 会覆盖该 run 所复制的值。如果只在 child run 上设置 `user_id`，trace 顶栏不会显示用户，搜索栏也不会建议该用户 ID。

<AgentTracingPrerequisite />

<CodeGroup>

```python Python
from langsmith import traceable


@traceable
def retrieve_docs(question: str) -> list[str]:
    return ["Traces record each step of a request."]


@traceable
def answer_question(question: str) -> str:
    docs = retrieve_docs(question)
    return " ".join(docs)


# Pass the user at invocation time so each request records its own user.
answer_question(
    "What is a trace?",
    langsmith_extra={"metadata": {"user_id": "user_123"}},
)
```

```typescript TypeScript
import { traceable } from "langsmith/traceable";

const retrieveDocs = traceable(
  async (question: string) => {
    return ["Traces record each step of a request."];
  },
  { name: "retrieve_docs" }
);

async function handleRequest(question: string, userId: string) {
  // Create the root run with this request's user in its metadata.
  const answerQuestion = traceable(
    async (question: string) => {
      const docs = await retrieveDocs(question);
      return docs.join(" ");
    },
    { name: "answer_question", metadata: { user_id: userId } }
  );
  return answerQuestion(question);
}

await handleRequest("What is a trace?", "user_123");
```

</CodeGroup>

有关设置 metadata 的其他方式，例如 `tracing_context` 或包装后的 client，请参阅[为 traces 添加 metadata 和 tags](/langsmith/add-metadata-tags)。使用 LangChain 或 LangGraph 时，请在调用 agent 时于 run config 的 `metadata` 字段中传入 `user_id`。请参阅[追踪 LangChain agents](/langsmith/trace-with-langchain#add-metadata-and-tags-to-traces)。

## 在 trace 上查看用户

LangSmith 会在四个位置显示用户 ID：

- **Tracing 表格**：在 **Columns** 中开启 **User** 列，以显示每个 run 的用户 ID。**LangSmith User** 列则不同：它显示该 run 归属的 LangSmith 用户。
- **Trace 顶栏**：打开不属于某个 thread 的 trace 时，顶栏会显示带有用户 ID 的 **User** 标签。
- **Run 头部**：当 trace 属于某个 thread 时，所选 run 的头部会显示记录在该 run 上的用户 ID。这适用于 thread 的 **Details** 视图，也适用于从 tracing 表打开 trace 的情况。
- **Trajectory 视图**：将鼠标悬停在 thread 的 **Trajectory** 视图中的某条用户消息上，会在其下方显示用户 ID。AI 消息和工具响应不会显示用户。

点击用户 ID 可复制完整值。有关这些视图的更多信息，请参阅[查看 traces](/langsmith/view-traces)。

## 按用户筛选 traces

<FilteringExperienceNote />

`user_id` 简写适用于搜索栏体验。在 **Add filter** 体验中，请按 `user_id` metadata 键进行筛选。

要查找某位用户的 runs、traces 或 threads，请在 tracing 搜索栏中输入 `user_id` 子句：

```text
user_id:user_123
```

**Traces** 表默认使用 **Root run** scope，它会按每条 trace 的根 run 上的用户来匹配该 trace。请参阅[选择过滤器匹配什么](/langsmith/filter-traces#choose-what-a-filter-matches)。

输入时，搜索栏会建议所选时间范围内最常见的用户 ID。你也可以输入不在列表中的用户 ID。

`user_id` 是 `metadata.user_id` 的简写，并支持相同的运算符：

- `-user_id:user_123` 匹配来自其他所有用户的 runs，包括没有 `user_id` 的 runs。
- `user_id:*` 匹配带有 `user_id` 键的 runs。
- `-user_id:*` 匹配没有 `user_id` 键的 runs，例如尚未接入 instrumentation 的 traces。
- `metadata.user_id:user_123` 匹配与 `user_id:user_123` 相同的 runs。

完整查询语法请参阅[过滤 traces](/langsmith/filter-traces)。

## 查看用户活动

agent 的 **Monitoring** 页面中的 **Users** 标签页会列出一个 environment 的用户，并按最近活动排序。使用它可以查看谁在使用你的 agent，以及哪些用户的成本或错误率较高。

要查看用户活动：

1. 选择你的 agent，然后在侧边栏中选择 **Monitoring**。
2. 选择 **Users** 标签页。
3. 选择 environment 和时间范围。

每一行显示所选时间范围内的用户 ID、最近活动、traces、tokens、总成本、错误率和 P50 延迟。该标签页最多覆盖 31 天，因此对于更长的时间范围，LangSmith 会将其缩短为最近 31 天。

该标签页只列出记录在根 run 上的用户。如果该标签页为空，请检查你的 traces 是否在根 run 上设置了 `user_id`。请参阅[在 trace 上记录用户](#record-the-user-on-a-trace)。

要查找某位用户，请在搜索框中输入其精确的用户 ID。点击某一行，会打开 **Tracing** 页面，并筛选出该用户的 traces。

## 按用户分组图表

按用户分组会将每张 dashboard 图表拆分为每位用户一条 series。LangSmith 会按 runs 的 `user_id` metadata 值对 runs 分组，因此你无需输入 metadata 路径。

- **Prebuilt dashboards**：在 dashboard 的 [group by](/langsmith/dashboards#group-by) 设置中选择 **User**。
- **Custom charts**：当你[配置图表](/langsmith/dashboards#filter-and-group)时，请选择 **User** 作为 group-by 属性。若要从已按用户分组的图表开始，请使用 **Traces by user** 或 **Cost by user** 模板。

与其他 group-by 属性一样，图表会显示出现频率最高的用户。没有 `user_id` 的 runs，以及不在出现频率最高之列的用户，会在图表显示 **Other** 分组时计入该分组。**Metadata** 键列表不提供 `user_id`，因为 **User** 已取代它。

## 为用户添加 traits

traits 是键值属性，例如姓名或电子邮件地址，你通过 [LangSmith REST API](/langsmith/smith-api-ref) 为用户存储这些属性。使用 traits 可以将团队需要了解的用户详细信息，例如用户的身份和联系方式，保存在 traces 记录的同一个 `user_id` 下。LangSmith 会将 traits 与 traces 分开存储，因此 [trace retention](/langsmith/observability-concepts#data-retention) 不适用于 traits。traits 会一直保留，直到你通过更新将其移除，或者直到 [agent environment](/langsmith/agent-environments) 或 workspace 被删除。

traits 属于一个 agent environment。相同的 `user_id` 在两个 environments 中会对应两套相互独立的 traits。`{session_id}` 路径参数是 agent environment 的 ID。要获取该 ID，请[解析 agent 环境](/langsmith/resolve-an-agent)，该操作会将 ID 作为 `session_id` 返回。

### 设置权限

每项操作都需要一项权限。关于包含各项权限的角色，请参阅[组织与工作区操作](/langsmith/organization-workspace-operations#runs)：

- **创建用户**：`runs:create`，与发送 traces 所需的权限相同。
- **更新 traits**：`runs:create` 和 `runs:read`。
- **获取或列出用户**：`runs:read`。

如果某个 environment 中的[访问策略](/langsmith/abac#control-trace-access-with-root-run-metadata)通过 root run metadata 限制你可以读取哪些 traces，则 traits API 在该 environment 中不可用。LangSmith 会针对这些请求返回 `403`。

### 创建和更新用户

API 提供以下操作：

- **[创建用户](/langsmith/smith-api/users/create-a-user)**：使用 `user_id` 和可选的 `traits` 调用 `POST /api/v1/platform/sessions/{session_id}/users`。成功时返回 `201` 和新用户；如果用户已存在，则返回 `409`。要创建用户或更新已有用户，请先发送创建请求；当创建请求返回 `409` 时，再发送更新请求。
- **[更新 traits](/langsmith/smith-api/users/update-a-users-traits)**：使用 `traits` 对象调用 `PATCH /api/v1/platform/sessions/{session_id}/users/{user_id}`。LangSmith 会将 `traits` 对象合并到已存储的 traits 中：你发送的键会覆盖现有值，省略的键会保留，`null` 值会移除某个键。成功时返回 `200` 和已存储的用户；如果用户不存在，则返回 `404`。
- **[获取用户](/langsmith/smith-api/users/get-a-user)**：`GET /api/v1/platform/sessions/{session_id}/users/{user_id}`。如果用户不存在，则返回 `404`。
- **[列出用户](/langsmith/smith-api/users/list-users)**：`GET /api/v1/platform/sessions/{session_id}/users`，按最近更新时间排序。可选的 `page_size` 参数默认值为 20，最大值为 100。将响应中的 `next_cursor` 值作为 `cursor` 传入，以获取下一页。在最后一页，`next_cursor` 为 `null`。使用 `user_id_prefix` 对用户 ID 执行区分大小写的前缀匹配。

例如，以下请求体会创建一个包含姓名和电子邮件地址的用户：

```json
{"user_id": "user_123", "traits": {"name": "Alex Rivera", "email": "alex@example.com"}}
```

响应包含 `user_id`、`traits`、`created_at` 和 `updated_at`。

以下更新请求体会更改姓名并移除电子邮件地址，同时保留其他所有 traits：

```json
{"traits": {"name": "Alex R.", "email": null}}
```

### 保持在请求限制内

每个请求都必须遵守以下限制：

- **用户 ID**：用户 ID 的长度为 1 到 512 个字符。在路径中，请对用户 ID 进行 URL 编码，但保持每个 `/` 不变，因为 LangSmith 会拒绝路径中的 `%2F`。如果用户 ID 包含 `.` 或 `..` 段、`//` 或前导 `/`，则无法获取或更新该用户，因为该 ID 无法用于路径。
- **traits 值**：`traits` 必须是最多包含 50 个键的 JSON 对象。`name` 和 `email` 键必须是字符串，或在更新中为 `null`。创建请求不能包含 `null` 值。
- **大小**：用户的已存储 traits 限制为 16,384 字节，请求体限制为 65,536 字节。超出已存储限制的更新会失败，已存储的 traits 保持不变。
- **速率限制**：LangSmith 会限制一个 workspace 每分钟可以创建的用户数量。超出限制的请求会返回 `429`，并带有 `Retry-After` 响应头。

LangSmith 还会返回以下错误：

- **`400`**：LangSmith 无法读取请求，例如 JSON 无效、字段未知或请求体超出大小限制。
- **`422`**：用户 ID 或 trait 值违反了请求限制。响应会指出相应字段。
- **`501`**：你的 workspace 尚未启用用户功能。
