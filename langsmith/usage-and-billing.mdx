本页介绍 LangSmith 如何保留 traces、对 traces 实施速率限制以及计费。内容涵盖各托管选项的保留层级与保留期、会返回 HTTP 429 响应的速率限制，以及你可以设置的使用量限制。

<Note>
如需设置计费、更新发票信息或设置支出上限，请参阅[管理计费](/langsmith/billing)。
</Note>

## Data retention

LangSmith 只会按每条 trace 所属层级的保留期保存该 trace。保留期结束后，LangSmith 会删除该 trace。

### 为什么数据保留很重要

* **隐私**：许多数据隐私法规（例如欧洲的 GDPR 或加利福尼亚州的 CCPA）要求组织在个人数据对于最初收集目的不再必要时删除这些数据。设置保留期有助于遵守此类法规。
* **成本**：base traces 的费用低于 extended traces。如需控制 tracing 支出，请参阅[实施支出限制](/langsmith/billing#enforce-spend-limits)。

### Retention periods

每条 trace 都属于两种保留层级之一：base 或 extended。每个层级的保留期取决于你的[托管选项](/langsmith/platform-setup)：

| 托管选项 | Base | Extended（默认） | Enterprise 客户可选择的 extended 时长 |
| -------------- | ---- | ------------------ | -------------------------------------------------- |
| Cloud          | 14 天 | 180 天 | 30、60、90、120、150 或 180 天 |
| BYOC           | 14 天<br />（data plane 默认值） | 400 天<br />（data plane 默认值） | 30、60、90、120、150、180、240、300、365 或 400 天 |
| Self-hosted    | 14 天<br />（Helm chart 默认值） | 400 天<br />（Helm chart 默认值） | 可配置。请参阅[启用 TTL 和数据保留](/langsmith/self-host-ttl)。 |

在 AWS 或 Azure 的 BYOC data plane 上，你可以更改这两个 data plane 默认值。关于如何更改 data plane 设置，请参阅 [AWS](/langsmith/byoc-operations-aws#ttl-retention) 和 [Azure](/langsmith/byoc-operations-azure#data-plane-settings)。GCP data plane 会保留 14 天和 400 天的默认值。工作区选择的 extended 保留时长会覆盖 data plane 默认值。

要为工作区选择 extended 时长，请参阅[自定义扩展保留策略](/langsmith/data-purging-compliance#customize-extended-retention-policy)。2026 年 9 月 14 日之前摄入的 Cloud traces 会保留其摄入时的保留期。

### 保留期结束后会发生什么

保留期结束后，traces 将无法再通过 UI 或 API 访问。与该 trace 关联的所有用户数据（例如输入和输出）会在此后不久从 LangSmith 系统中删除。与每条 trace 关联的部分 metadata 可能会出于分析和计费目的被无限期保留。

### 保留层级在哪里设置

默认保留层级属于某个 agent 的[环境](/langsmith/agent-environments)，而不是整个 agent。新环境会继承工作区的默认层级，你可以在[配置 trace 层级分布](/langsmith/billing#configure-trace-tier-distribution)中设置该默认层级。更改工作区默认层级不会影响现有环境，除非你选择将其应用到所有环境。[自动升级](#data-retention-auto-upgrades)可以将单条 trace 移动到 extended 保留层级，而不受其环境层级的影响。

由于层级是按环境设置的，一个 agent 可以让生产 traces 使用 extended 保留，让开发 traces 使用 base 保留。要更改整个 agent 的层级，请在每个环境上分别设置。

<Tip>
在开始发送 traces 之前，请先规划好保留层级。更改环境层级只会应用于新的 traces。已摄入的 traces 会保留其原有层级。请参阅[更改环境的默认保留设置](/langsmith/billing#change-default-retention-for-an-environment)。
</Tip>

### Data retention auto-upgrades

<Warning>
自动升级会增加你的账单。请阅读本节，以了解预估的 tracing 成本。
</Warning>

某些操作会把 base 层级 trace 升级到 extended 层级，这同时会增加其保留期和成本。哪些操作可以延长保留期由你控制。

要阻止整个工作区的新升级，请[禁用 extended trace retention](/langsmith/data-purging-compliance#disable-extended-trace-retention)。Feedback 和评估仍会继续，但不会延长 retention。

当工作区允许 extended retention 时，各操作对保留行为的影响取决于具体操作：

* **通过 API 或 SDK 提交 feedback**：通过显式传入 `extend_trace_retention=true`（TypeScript 中为 `extendTraceRetention: true`）的 API 或 SDK 调用，可以把 feedback 添加到该 trace 上的任意 run（或该 thread 中的任意 trace）。更多信息请参阅[附加用户 feedback](/langsmith/attach-user-feedback)。LangSmith UI 提交 feedback 和 note 时不会延长保留期。
* **在线 evaluator**：在线 evaluator 对 trace 打分，并且其保留设置已启用。trace 级和 thread 级的 evaluator 都可以选择不触发此升级。
* **Automation rules**：启用了保留延长的 [automation rule](/langsmith/rules#create-a-rule) 会匹配该 trace 中的任意 run。匹配单个 run 会升级整个 trace，而不仅仅是该 run。当规则的[条目类型](/langsmith/rules#set-the-item-type-to-runs-or-threads)为 **Threads** 时，会升级匹配 thread 中的每条 trace，而不只是最近的那条。
* **手动添加到 annotation queue**（不升级）：手动把 runs 或 threads 添加到 [annotation queue](/langsmith/annotation-queues#assign-runs-and-threads-to-a-single-run-queue) 默认不会升级保留层级。

对于新的在线 evaluator 和 automation rule，保留延长默认处于启用状态。你可以在创建或编辑每个 evaluator 或 rule 时将其关闭。只有当环境的默认保留层级为 base 时，在线 evaluator 才能选择不延长保留。请参阅[管理 evaluator trace 保留](/langsmith/evaluators#manage-evaluator-trace-retention)。

关闭保留延长不会降级 traces。先前操作已经升级过的 traces 会保留其 extended 保留层级。

#### 为什么 LangSmith 会自动升级 traces

自动升级模型遵循两条原则：

1. 通过 API 收到 feedback、被在线 evaluator 打分或匹配 automation rule 的 traces，通常比其他 traces 更有价值，因此更长时间地保留它们是有意义的。
1. 无人交互的 traces 的费用应低一个数量级。只有发生有意义交互的 traces 才会按更高的 extended 费率计费。

如有关于 LangSmith 定价的问题，请通过 [support.langchain.com](https://support.langchain.com) 联系支持团队。

### Billing model

你的 LangSmith 发票会显示两个 tracing 指标：

* **LangSmith Traces (Base Charge)**：每条 trace，无论所属层级。
* **LangSmith Traces (Extended Data Retention Upgrades)**：每条 extended retention trace。

#### 为什么发票会单独统计升级次数

直接统计 base 和 extended traces 会更简单，但无法正确处理升级场景。例如，某条 base 层级 trace 记录于 6 月 30 日，并于 7 月 3 日升级为 extended 层级；该 trace 属于 6 月计费周期，而升级行为属于 7 月计费周期。分别计量这两个事件，才能把各自计入正确的计费周期。

以 extended 保留层级创建的 trace 会以相同时间戳记录这两个指标。

## Rate limits

LangSmith 设有速率限制，旨在确保所有用户都能稳定使用服务。

当超出速率限制或使用量限制时，LangSmith 会返回 HTTP 状态码 429，具体包括以下情况：

### 负载均衡器上的每分钟吞吐限制

此类 429 是由于按 service key 或 PAT 计算的 1 分钟窗口内 API 调用次数超过固定上限。该窗口不一定从某个整分开始，其起点也可能随应用部署事件而变化。

达到最大调用次数后，LangSmith 会持续返回 429，直到距离该窗口开始已满 60 秒。之后窗口会重新开始。

此 429 由 LangSmith 应用负载均衡器返回。它对所有 LangSmith 用户生效，与方案无关。

| Method            | Endpoints     | Limit | Window   |
| ----------------- | ------------- | ----- | -------- |
| `DELETE`          | `/sessions*`  | 30    | 1 分钟 |
| `POST` OR `PATCH` | `/runs*`      | 5000  | 1 分钟 |
| `GET`             | `/runs/:id`   | 30    | 1 分钟 |
| `POST`            | `/feedbacks*` | 5000  | 1 分钟 |
| `*`               | `*`           | 2000  | 1 分钟 |

<Note>
LangSmith SDK 会尽量减少你触达这些 run 相关端点限制的概率，例如它会把同一个 session ID 下最多 100 个 runs 批量合并为一次 API 调用。
</Note>

### 方案级每小时 trace event 限制

此类 429 表示你已达到每小时可摄入的 events 数量上限。它以从 UTC 每个整点开始的固定窗口计算，并在下一个整点重置。

这里的 event 指的是创建或更新一个 run。如果某个 run 在同一小时窗口内先被创建、随后又被更新，那么它会计作 2 个 events。

此 429 由 LangSmith 应用返回。该限制因方案而异：Startup/Plus 和 Enterprise 方案的小时限制高于面向个人使用的 Developer 方案。

| Plan                             | Limit          | Window |
| -------------------------------- | -------------- | ------ |
| Developer（未绑定支付方式）   | 50,000 events  | 1 小时 |
| Developer（已绑定支付方式） | 250,000 events | 1 小时 |
| Startup/Plus                     | 500,000 events | 1 小时 |
| Enterprise                       | Custom         | Custom |

### 方案级每小时 trace 数据摄入限制

此类 429 表示你已达到每小时 trace 输入、输出和 metadata 的总摄入量上限。它同样以 UTC 每个整点开始的固定窗口计算，并在下一个整点重置。

通常情况下，输入、输出和 metadata 会在 run 创建和更新时一并发送。如果某个 run 在同一小时窗口内创建时为 2.0MB，更新后为 3.0MB，那么它会计入 5.0MB 的存储量。

此 429 由 LangSmith 应用返回。该限制因方案而异：Startup/Plus 和 Enterprise 方案的小时限制高于面向个人使用的 Developer 方案。

| Plan                             | Limit  | Window |
| -------------------------------- | ------ | ------ |
| Developer（未绑定支付方式）   | 500MB  | 1 小时 |
| Developer（已绑定支付方式） | 2.5GB  | 1 小时 |
| Startup/Plus                     | 5.0GB  | 1 小时 |
| Enterprise                       | Custom | Custom |

### 方案级每月唯一 traces 限制

此类 429 表示你已达到每月可摄入的唯一 traces 数量上限。它以从 UTC 每个自然月开始的固定窗口计算，并在下个月开始时重置。

此 429 由 LangSmith 应用返回。它仅适用于未绑定支付方式的 Developer 方案。

| Plan                           | Limit        | Window  |
| ------------------------------ | ------------ | ------- |
| Developer（未绑定支付方式） | 5,000 traces | 1 个月 |

### 自行配置的每月使用量限制

此类 429 表示你已达到组织管理员配置的使用量限制。它以从 UTC 每个自然月开始的固定窗口计算，并在下个月开始时重置。

此 429 由 LangSmith 应用返回。该限制取决于你的组织所配置的使用量限制。请参阅[使用量限制](#usage-limits)。

### Run query endpoint

LangSmith 提供两个版本的 run 查询端点，它们具有不同的速率限制配置。

**v2（推荐）**：`POST /v2/runs/query`（Python 中的 [`list_runs`](https://reference.langchain.com/python/langsmith/client/Client/list_runs)，JavaScript 中的 [`listRuns`](https://reference.langchain.com/javascript/langsmith/client/Client/listRuns)）由 SmithDB 提供支持，具有按 API key 计算的统一限制，没有按时间窗口划分的层级：

| **限制** | **时间窗口** |
|---|---|
| 300 个请求 | 10 秒 |

设置了 `sem_filter`（语义搜索）的 API key 请求还受限于每个工作区每分钟 10 个请求。

**v1**：`POST /runs/query` 具有租户级速率限制，具体因查询参数而异：

| **查询类型** | **限制** | **时间窗口** |
|---|---|---|
| 短时间窗口（≤ 7 天） | 10 个请求 | 10 秒 |
| 大时间窗口（> 7 天） | 3 个请求 | 10 秒 |
| 全文搜索，短时间窗口（≤ 7 天） | 3 个请求 | 10 秒 |
| 全文搜索，大时间窗口（> 7 天） | 1 个请求 | 10 秒 |
| 选择 `child_run_ids`，短时间窗口（≤ 7 天） | 3 个请求 | 10 秒 |
| 选择 `child_run_ids`，大时间窗口（> 7 天） | 1 个请求 | 10 秒 |

时间窗口由 `end_time - start_time` 决定。如果未提供 `end_time`，LangSmith 会使用当前时间。未带 `start_time` 的查询会被视为大时间窗口查询。

为避免触发 v1 速率限制并缩短查询时间：

- **设置 `start_time`**：省略它会进入大时间窗口层级（每 10 秒 3 个请求，而不是 10 个）。尽可能使用 7 天或更短的时间窗口。
- **使用 `select`**：默认会返回所有字段。仅指定你需要的字段（例如 `select=["inputs", "outputs"]`）可以大幅减少响应大小和查询时间。
- **设置 `limit`**：如果不需要遍历所有结果，请限制返回的结果数量。
- **避免全文搜索**：`filter='search("...")'` 的速率限制最严格；请尽可能使用结构化过滤器（例如 `eq()`、`has()`）。
- **避免选择 `child_run_ids`**：这同样会触发更严格的速率限制层级。

### Run stats endpoint

[`POST /runs/stats`](/langsmith/smith-api/run/stats-runs) 端点具有租户级速率限制，具体因查询时间窗口而异：

| **查询类型** | **限制** | **时间窗口** |
|---|---|---|
| 短时间窗口（≤ 14 天） | 10 个请求 | 10 秒 |
| 大时间窗口（> 14 天且 < 90 天） | 3 个请求 | 10 秒 |
| 超大时间窗口（≥ 90 天）或未指定 `start_time` | 1 个请求 | 10 秒 |

时间窗口由 `end_time - start_time` 决定。如果未提供 `end_time`，LangSmith 会使用当前时间。未带 `start_time` 的查询会受到最严格的限制。

在 GCP 托管的美国区域，此端点的 API key 请求还受限于每个 API key 每 10 秒 1 个请求。

为避免触发速率限制：

- **设置 `start_time`**：尽可能使用 14 天或更短的时间窗口。
- **避免开放式查询**：始终提供 `start_time`，以保持在限制较宽松的层级。

### Workspace invite batch endpoint

工作区邀请批量请求按工作区进行速率限制，以减少批量邀请滥用。

`POST /workspaces/current/members/batch` 端点允许每个工作区每秒 2 个请求。此限制仅适用于 LangSmith Cloud。

### 在应用中处理 429 响应

某些 429 响应是暂时性的，因此稍后重试可能会成功。如果你的应用直接调用 LangSmith API，请实现带指数退避和抖动的重试逻辑。LangSmith SDK 已内置此重试逻辑。

<Note>
如果你的应用在较长时间内持续打满这些端点，重试可能也无济于事，因为积压的请求最终会耗尽所有重试次数。

在这种情况下，请通过 [LangSmith 支持](https://support.langchain.com) 联系支持团队，并提供你的应用吞吐需求和示例代码。支持团队可以帮助你判断应当修复 bug、调整应用代码，还是改用其他 LangSmith 方案。
</Note>

## Usage limits

使用量限制用于限制 LangSmith 每个自然月摄入的 traces 数量。它们限制的是 trace 数量，而不是支出。如需设置每月支出目标并让 LangSmith 据此推导限制，请参阅[设置工作区支出上限](/langsmith/billing#set-a-workspace-spend-limit)。关于 evaluator runs 的支出限制，请参阅[跟踪并限制 evaluator 支出](/langsmith/evaluator-spend)。

你可以在三个作用域设置使用量限制：

- **工作区**：两个限制，分别对应两个[计费指标](#billing-model)：all traces 限制和 extended data retention traces 限制。
- **Agent environment**：针对单个 agent 环境的每月 trace 限制。UI 将此作用域标记为 **Project**。
- **用户**：针对单个工作区成员的每月 trace 限制。

某条 trace 只有处于所有适用于它的使用量限制之内，才会被摄入。

### 设置工作区使用量限制

要更新工作区的使用量限制，请前往 **Settings** > **Billing and Usage** > **Usage limits**。

### Side effects of extended data retention traces limit

Extended data retention traces limit 会带来一些副作用。如果已达到该限制，LangSmith 会阻止那些会再创建一条 extended retention trace 的操作。例如，你将无法再：

1. 运行会延长 trace 保留期的 automation rules。
1. 运行会延长 trace 保留期的 evaluators。

不会改变 trace 保留期的操作不计入该限制。达到该限制后，你仍然可以在 LangSmith UI 中提交 feedback、把 runs 或 threads 添加到 annotation queues，以及运行已关闭保留延长的 automation rules 或 evaluators。

### 设置环境和用户使用量限制

环境和用户使用量限制可以防止某个 agent 环境或工作区成员消耗掉工作区 traces 中不成比例的一大部分。设置这些限制需要与工作区使用量限制相同的权限（`Update usage limits`）。

要添加环境或用户使用量限制：

1. 前往 **Settings** > **Usage configuration**。
1. 在 **Project & user limits** 部分中，点击 **Add limit**。
1. 设置以下字段：
    - **Scope**：选择 **Project** 以限制单个 agent 环境，或选择 **User** 以限制单个工作区成员。此处 UI 将环境标记为项目。
    - **Workspace**：包含该环境或成员的工作区。
    - **Project** 或 **User**：要施加上限的环境或成员。**Project** 列表会按每个环境的 `tracer_session_name` 显示环境。要查找环境的 `tracer_session_name`，请参阅[配置需要 project name 的集成](/langsmith/create-an-agent#use-an-environment-project)。
    - **Monthly trace limit**：每个自然月允许的最大 trace 数量。

**Project** 限制针对的是某个 agent 的单个[环境](/langsmith/agent-environments)，而不是整个 agent。系统没有 agent 作用域，因此若要限制某个 agent 的 traces 总量，就需要为每个环境分别添加一条限制。

用户使用量限制只统计归属于该工作区成员的 traces。通过未绑定到成员的 API key 或 service key 发送的 traces，不会计入任何用户使用量限制。

### 使用量限制如何执行

- **每月重置**：使用量限制按 UTC 自然月计算，并在每个月开始时重置。
- **达到限制后停止摄入**：一旦工作区、环境或用户达到使用量限制，LangSmith 会丢弃其新摄入的 traces，直到该限制重置。
- **近似执行**：在限制生效之前，可能会有少量 traces 超过限制仍被处理。
- **缓存**：限制值会被缓存，因此新建或修改后的限制可能需要一两分钟才会生效。
